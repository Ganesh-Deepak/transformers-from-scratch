7 · Position: Sinusoidal → Learned → RoPE → ALiBi

Attention has a strange property: it does not know what order the tokens are in. "Dog bites man" and "man bites dog" produce identical outputs unless you do something about it. This chapter is about what that something is — ending with RoPE, which essentially every model shipped since 2023 uses.

Builds onCh 05 — position enters through the q-k dot product
Leads toCh 16 — MLA has to split RoPE off to work
Ch 21 — context extension is RoPE scaling
Why this chapterAttention cannot see order. Everything here is about telling it.

7.1 · Proving attention is position-blind

This isn't a hand-wave. Let P be a permutation matrix that shuffles the token order. Then:

Attention(PQ, PK, PV) = softmax(PQ (PK)T√d) PV = softmax(P QKT√d PT) PV = P · Attention(Q, K, V) shuffle the input → the output is shuffled the same way, but otherwise unchanged

This is called permutation equivariance. The set of tokens is all attention sees; their order is invisible. And the MLP that follows works on each position independently, so it can't fix this either.

Why this is actually a feature

An RNN gets order for free but pays with sequential computation. A transformer gets full parallelism but must be told about order. Because position is injected explicitly rather than baked into the architecture, we can choose the encoding — and that freedom is why context windows grew from 512 to 1M tokens. You cannot retrofit an RNN's notion of position; you can swap a transformer's.

7.2 · Approach 1 — Sinusoidal (the original, 2017)

Add a fixed, hand-designed vector to each token's embedding before layer 1:

PE(pos, 2i) = sin(pos / 100002i/d)      PE(pos, 2i+1) = cos(pos / 100002i/d) 
def sinusoidal(T, d):
    pos = torch.arange(T)[:, None]                            # (T, 1)
    i   = torch.arange(0, d, 2)[None, :]                      # (1, d/2)
    ang = pos / (10000 ** (i / d))                            # (T, d/2)
    pe  = torch.zeros(T, d)
    pe[:, 0::2] = torch.sin(ang)
    pe[:, 1::2] = torch.cos(ang)
    return pe                                                  # (T, d)

x = embed(ids) + sinusoidal(T, C)[None]        # (B,T,C) + (1,T,C)

Each dimension is a sine wave of a different frequency — fast on the left, slow on the right — so the vector encodes position the way a binary counter encodes a number, but continuously. The clever property is that PEpos+k is a linear function of PEpos (rotation by a fixed angle), so relative offsets are in principle learnable.

Why it fell out of favour: it's added once at the input, so by layer 20 the positional signal has been mangled by 20 rounds of attention and MLPs. Extrapolation beyond the trained length is poor in practice despite the theory.

7.3 · Approach 2 — Learned absolute (GPT-2, BERT, ViT)

self.wpe = nn.Embedding(max_T, C)              # (1024, 768) for GPT-2
x = self.wte(ids) + self.wpe(torch.arange(T))  # (B,T,C)

Simplest possible thing: a second lookup table indexed by position. Works well, and for a while was the default.

The hard ceiling

The table has max_T rows. Position 1025 in a GPT-2 model does not exist — it's an index error, not a quality degradation. You cannot extend the context of a learned-absolute model without training new rows from scratch. This limitation, more than anything, is what pushed the field to relative schemes.

7.4 · Approach 3 — RoPE (Rotary Position Embedding)

Su et al. (2021). The idea that won. Every one of Llama, Mistral, Qwen, Gemma, DeepSeek, Phi and GPT-NeoX uses it.

The idea in one sentence

Don't add anything to the embedding. Instead, rotate the query and key vectors by an angle proportional to their position — so that when you take their dot product, the angles subtract and what survives depends only on the relative distance.

The 2D case

Take a pair of adjacent features and treat them as a point in a plane. For a token at position m, rotate that point by mθ:

Rm = [ cos mθ   −sin mθ
sin mθ     cos mθ ]

Now the crucial algebra. Rotation matrices satisfy RmTRn = Rn−m, so:

⟨Rmq, Rnk⟩ = (Rmq)T(Rnk) = qTRmTRnk = qTRn−mk the absolute positions m and n vanish — only (n − m) survives

That equation is the whole paper. Absolute rotations applied separately to q and k produce an attention score that is a function of relative distance only, with zero parameters and no change to the attention formula itself.

Drag the sliders. Notice how the rotation speed depends on which feature pair you're looking at:

Scaling to dhead dimensions

Split the head dimension into d/2 pairs, and give pair i its own frequency:

θi = base−2i/d,    i = 0, 1, …, d/2 − 1     (base = 10000 originally)

Pair 0 rotates fast (full turn every ~6.3 tokens) and encodes fine local ordering; the last pair rotates extremely slowly and encodes coarse long-range position. One mechanism, all scales — the same logic as the sinusoidal frequencies, but applied multiplicatively inside attention instead of additively at the input.

Worked example — rotate one pair, then watch the positions cancel

d_head = 8, so 4 pairs. Take pair i = 0, where θ₀ = 100000 = 1 — one radian per token.

Now the point of the whole scheme. Take q = [0.6, 0.8] at position m and k = [1, 0] at position n, and compute the dot product: 
m= 0  n= 2   offset 2   dot = +0.477750
m= 1  n= 3   offset 2   dot = +0.477750
m= 5  n= 7   offset 2   dot = +0.477750
m=10  n=12   offset 2   dot = +0.477750   <- identical every time

m= 1  n= 4   offset 3   dot = -0.481099   <- different offset, different value

That is the theorem, measured. The absolute positions were 0, 1, 5 and 10 — wildly different — yet the attention score is bit-identical because the gap was always 2. Absolute position went in; only relative position came out. No parameters, no lookup table, no maximum length.

import torch, math
def rot(v, m, theta=1.0):
    a = m * theta
    return torch.tensor([v[0]*math.cos(a) - v[1]*math.sin(a),
                         v[0]*math.sin(a) + v[1]*math.cos(a)])

q, k = torch.tensor([0.6, 0.8]), torch.tensor([1.0, 0.0])
for m, n in [(0, 2), (1, 3), (5, 7), (10, 12)]:
    print(m, n, round(torch.dot(rot(q, m), rot(k, n)).item(), 6))   # all +0.47775
assert abs(torch.dot(rot(q,0),rot(k,2)) - torch.dot(rot(q,10),rot(k,12))) < 1e-6
Why no max length A learned position table has max_T rows and position 1025 simply does not exist. RoPE computes cos(m·θ) for any m — which is why context extension (Ch 21) is possible at all.

Implementation

def build_rope_cache(T, d_head, base=10000.0, device=None):
    """Precompute cos/sin tables once; reuse every layer, every step."""
    inv_freq = 1.0 / (base ** (torch.arange(0, d_head, 2, device=device).float() / d_head))
    t = torch.arange(T, device=device).float()          # (T,)
    freqs = torch.outer(t, inv_freq)                    # (T, d_head/2)
    emb = torch.cat((freqs, freqs), dim=-1)             # (T, d_head)
    return emb.cos(), emb.sin()                         # 2 × (T, d_head)

def rotate_half(x):
    x1, x2 = x.chunk(2, dim=-1)                         # split the head dim in half
    return torch.cat((-x2, x1), dim=-1)

def apply_rope(q, k, cos, sin):
    # q, k: (B, n_head, T, d_head);  cos, sin: (T, d_head)
    cos, sin = cos[None, None], sin[None, None]         # (1, 1, T, d_head)
    q = q * cos + rotate_half(q) * sin
    k = k * cos + rotate_half(k) * sin
    return q, k
Two conventions, both correct

The original paper pairs adjacent dimensions (x0,x1), (x2,x3), …. The HuggingFace/Llama implementation above pairs (x0, x_{d/2}), (x1, x_{1+d/2}), … — it splits the head in half instead. These are related by a fixed permutation of the feature axis, so they are mathematically equivalent (the model just learns its weights in the corresponding permuted basis). But they are not interchangeable at inference: loading Llama weights into an adjacent-pair implementation produces garbage. If you ever port RoPE between codebases, check this first.

Where RoPE is applied — and where it isn't

q = W_q(x).view(B, T, nh, hd).transpose(1, 2)     # (B, nh, T, hd)
k = W_k(x).view(B, T, nh, hd).transpose(1, 2)
v = W_v(x).view(B, T, nh, hd).transpose(1, 2)

q, k = apply_rope(q, k, cos, sin)                  # ← q and k ONLY. Never v.

out = F.scaled_dot_product_attention(q, k, v, is_causal=True)

V is never rotated. Position matters for deciding who to attend to (which is the dot product, i.e. q and k). It should not distort the content being retrieved. Rotating v would make the same information mean different things at different positions.

Also note: RoPE is applied inside every layer, freshly, on every forward pass. Unlike sinusoidal encoding, the positional signal cannot be washed out by depth.

What is the key mathematical property that makes RoPE encode relative position?
Rotations preserve vector norms
sin and cos are periodic
RmTRn = Rn−m, so absolute positions cancel in the dot product
The frequencies form a geometric series
The composition property of rotations. Options A and D are true statements about RoPE (norm preservation is why it doesn't change vector magnitudes; the geometric frequency series gives multi-scale coverage) but neither produces relative encoding. Only the group property RmTRn = Rn−m makes the absolute positions cancel.
Why is RoPE applied to q and k but not v?
It would be too slow
Position should influence which tokens are selected, not what those tokens contain
v has a different shape than q and k
It is applied to v in most implementations
Separation of concerns. q·k determines the attention weights — that's where position belongs. v is the payload. Rotating v would mean the same retrieved fact gets a different vector depending on where it sat, forcing the model to undo the rotation. (Note in GQA/MHA v often does have the same shape as k — that's not the reason.)
A model is trained with RoPE at base=10000 and 4k context. You run it at 32k tokens with no other change. What happens?
It runs without error but quality degrades badly — the rotation angles are far outside the trained range
It raises an index error
It works perfectly — RoPE extrapolates by design
Only the first 4k tokens are used
Runs, degrades. Unlike a learned table there's no hard limit — you can compute cos(m·θ) for any m. But the model never saw those angle regimes and generalises poorly. The fixes (position interpolation, NTK-aware scaling, YaRN) are Chapter 21. This "silently gets worse rather than crashing" behaviour is why long-context claims need to be benchmarked, not trusted.

7.5 · Approach 4 — ALiBi (and the "no positional encoding" result)

ALiBi (Press et al. 2021) is almost aggressively simple: add a linear penalty to attention scores based on distance. No embeddings at all.

# head h gets slope m_h; slopes form a geometric sequence, e.g. 1/2, 1/4, 1/8, ...
scores = q @ k.transpose(-2,-1) / sqrt(d)
scores = scores + m_h * (j - i)      # (j - i) <= 0 for causal, so this is a penalty

Distant tokens get systematically down-weighted, with different heads decaying at different rates — some near-sighted, some far-sighted. ALiBi extrapolates to longer sequences remarkably well and was used by BLOOM and MPT. It has largely lost to RoPE in new models, but the idea survives inside sliding-window attention.

NoPE: it turns out causally-masked decoders can learn position implicitly — the mask itself breaks the permutation symmetry, since token i sees exactly i+1 tokens. Kazemnejad et al. (2023) showed NoPE models can match or beat explicit schemes on some length-generalisation tasks. It's not mainstream, but it's a good reminder that the "attention has no position" story is subtler for decoders than for encoders.

Where this stands in 2026

RoPE is the default, and the interesting action has moved to how you scale its base frequency for long context. Llama 3 raised the base from 10,000 to 500,000 specifically to make 128k context viable — a one-line change with a large effect. Many current long-context models also interleave local (sliding-window) RoPE layers with a few global layers, so most layers only pay attention cost over a small window. Gemma 2/3 popularised that pattern. Chapter 21 covers the scaling methods properly.

Note

With a causal mask the equivariance already breaks, even without positional encoding — that's the NoPE observation from §7.5. To see clean equivariance you must remove the mask. This is a good exercise precisely because it forces you to notice that the mask is itself a source of positional information.

7.2Verify the relative-position property numericallyessential

The claim is ⟨Rmq, Rnk⟩ depends only on n − m. Test it:

d = 64
cos, sin = build_rope_cache(200, d)
q, k = torch.randn(1,1,1,d), torch.randn(1,1,1,d)

def score(m, n):
    qm = q * cos[m] + rotate_half(q) * sin[m]
    kn = k * cos[n] + rotate_half(k) * sin[n]
    return (qm * kn).sum().item()

print(score(5, 8), score(50, 53), score(100, 103))   # all offset +3
print(score(5, 9))                                    # offset +4 → different
Expected

The first three agree to ~6 decimal places. The fourth differs. If yours don't match, your rotate_half convention is inconsistent with your cos/sin table construction — the exact issue described in §7.4's convention box.
