7 · Position: Sinusoidal → Learned → RoPE → ALiBi

Attention has a strange property: it does not know what order the tokens are in. "Dog bites man" and "man bites dog" give identical outputs unless you do something about it. This chapter is about what that something is, ending with RoPE, which almost every model released since 2023 uses.

Builds onCh 05 — position enters through the q-k dot product
Leads toCh 16 — MLA has to split RoPE off to work
Ch 21 — context extension is RoPE scaling
Why this chapterAttention cannot see order. Everything here is about telling it.
The whole chapter in five sentences

Attention is permutation-equivariant, so order has to be supplied from outside. The 2017 answers add a position vector to the input, either sinusoidal or learned. That fixes a maximum length, and the signal can fade with depth. RoPE rotates each pair of q and k channels by an angle proportional to the position, so their dot product depends only on the distance between them, in every layer. Variants rotate only some channels (partial and decoupled RoPE) or divide the channels between several coordinates (M-RoPE for images and video). None of them extends to longer sequences for free: a model trained at 64 tokens and run at 128 fails, and the repo's own measurement shows why.

7.1 · Proving attention is position-blind

This can be proved. Let P be a permutation matrix that shuffles the token order. Then:

Attention(PQ, PK, PV) = softmax(PQ (PK)T√d) PV = softmax(P QKT√d PT) PV = P · Attention(Q, K, V) shuffle the input → the output is shuffled the same way, but otherwise unchanged

This property is called permutation equivariance. Attention sees the set of tokens, and their order is invisible to it. The MLP that follows works on each position separately, so it cannot fix this either.

Why this is actually a feature

An RNN gets order for free but pays for it with sequential computation. A transformer gets full parallelism but has to be told the order. Because position is supplied explicitly instead of being built into the architecture, we can choose the encoding, and that freedom is why context windows grew from 512 to 1M tokens. You cannot swap out an RNN's sense of position, but you can swap a transformer's.

7.2 · Approach 1 — Sinusoidal (the original, 2017)

Add a fixed, hand-designed vector to each token's embedding before layer 1:

PE(pos, 2i) = sin(pos / 100002i/d)      PE(pos, 2i+1) = cos(pos / 100002i/d) 
def sinusoidal(T, d):
    pos = torch.arange(T)[:, None]                            # (T, 1)
    i   = torch.arange(0, d, 2)[None, :]                      # (1, d/2)
    ang = pos / (10000 ** (i / d))                            # (T, d/2)
    pe  = torch.zeros(T, d)
    pe[:, 0::2] = torch.sin(ang)
    pe[:, 1::2] = torch.cos(ang)
    return pe                                                  # (T, d)

x = embed(ids) + sinusoidal(T, C)[None]        # (B,T,C) + (1,T,C)

Each dimension is a sine wave of a different frequency, fast on the left and slow on the right, so the vector encodes position the way a binary counter encodes a number, but smoothly. Its useful property is that PEpos+k is a linear function of PEpos (a rotation by a fixed angle), so in principle the model can learn relative offsets.

Why it was dropped: it is added only once, at the input, so by layer 20 the position signal has been mixed up by 20 rounds of attention and MLPs. In practice it handles lengths beyond the trained length poorly, whatever the theory says.

7.3 · Approach 2 — Learned absolute (GPT-2, BERT, ViT)

self.wpe = nn.Embedding(max_T, C)              # (1024, 768) for GPT-2
x = self.wte(ids) + self.wpe(torch.arange(T))  # (B,T,C)

The simplest option: a second lookup table, indexed by position. It works well, and for a while it was the default.

The hard ceiling

The table has max_T rows, so position 1025 in a GPT-2 model does not exist: you get an index error, not just worse quality. You cannot extend the context of a model with learned absolute positions without training new rows from scratch. More than anything, this limit pushed the field toward relative schemes.

7.4 · Approach 3 — RoPE (Rotary Position Embedding)

Su et al. (2021) proposed the scheme that won. Llama, Mistral, Qwen, Gemma, DeepSeek, Phi and GPT-NeoX all use it.

The idea in one sentence

Do not add anything to the embedding. Instead, rotate the query and key vectors by an angle proportional to their position. When you take their dot product, the angles subtract, and what remains depends only on the relative distance.

The 2D case

Take a pair of neighbouring features and treat them as a point in a plane. For a token at position m, rotate that point by mθ:

Rm = [ cos mθ   −sin mθ
sin mθ     cos mθ ]

Now the important algebra. Rotation matrices satisfy RmTRn = Rn−m, so:

⟨Rmq, Rnk⟩ = (Rmq)T(Rnk) = qTRmTRnk = qTRn−mk the absolute positions m and n vanish — only (n − m) survives

That equation is the core of the paper. Absolute rotations applied separately to q and k produce an attention score that depends only on the relative distance, with no parameters and no change to the attention formula.

Drag the sliders. Notice how the rotation speed depends on which pair of features you look at:

Scaling to dhead dimensions

Split the head dimension into d/2 pairs, and give pair i its own frequency:

θi = base−2i/d,    i = 0, 1, …, d/2 − 1     (base = 10000 originally)

Pair 0 rotates fast (a full turn every ~6.3 tokens) and encodes fine local order; the last pair rotates very slowly and encodes rough long-range position. One mechanism covers every scale. The logic is the same as the sinusoidal frequencies, but it is applied by multiplication inside attention instead of by addition at the input.

Worked example — rotate one pair, then watch the positions cancel

d_head = 8, so there are 4 pairs. Take pair i = 0, where θ₀ = 100000 = 1, one radian per token.

This is the theorem, measured. The absolute positions were 0, 1, 5 and 10, all very different, yet the attention score is identical (to float32 rounding, about 10−8) because the gap was always 2. Absolute positions went in, and only the relative position came out. There are no parameters, no lookup table and no maximum length.

import torch, math
def rot(v, m, theta=1.0):
    a = m * theta
    return torch.tensor([v[0]*math.cos(a) - v[1]*math.sin(a),
                         v[0]*math.sin(a) + v[1]*math.cos(a)])

q, k = torch.tensor([0.6, 0.8]), torch.tensor([1.0, 0.0])
for m, n in [(0, 2), (1, 3), (5, 7), (10, 12)]:
    print(m, n, round(torch.dot(rot(q, m), rot(k, n)).item(), 6))   # all +0.47775
assert abs(torch.dot(rot(q,0),rot(k,2)) - torch.dot(rot(q,10),rot(k,12))) < 1e-6
Why no max length A learned position table has max_T rows, and position 1025 simply does not exist. RoPE computes cos(m·θ) for any m, which is what makes context extension (Ch 21) possible at all.

Implementation

def build_rope_cache(T, d_head, base=10000.0, device=None):
    """Precompute cos/sin tables once; reuse every layer, every step."""
    inv_freq = 1.0 / (base ** (torch.arange(0, d_head, 2, device=device).float() / d_head))
    t = torch.arange(T, device=device).float()          # (T,)
    freqs = torch.outer(t, inv_freq)                    # (T, d_head/2)
    emb = torch.cat((freqs, freqs), dim=-1)             # (T, d_head)
    return emb.cos(), emb.sin()                         # 2 × (T, d_head)

def rotate_half(x):
    x1, x2 = x.chunk(2, dim=-1)                         # split the head dim in half
    return torch.cat((-x2, x1), dim=-1)

def apply_rope(q, k, cos, sin):
    # q, k: (B, n_head, T, d_head);  cos, sin: (T, d_head)
    cos, sin = cos[None, None], sin[None, None]         # (1, 1, T, d_head)
    q = q * cos + rotate_half(q) * sin
    k = k * cos + rotate_half(k) * sin
    return q, k
Two conventions, both correct

The original paper pairs neighbouring dimensions, (x0,x1), (x2,x3), …. The Hugging Face/Llama implementation above pairs (x0, xd/2), (x1, x1+d/2), …: it splits the head in half instead. The two differ by a fixed permutation of the feature axis, so they are mathematically equivalent (the model just learns its weights in the permuted basis). But they are not interchangeable at inference: loading Llama weights into an implementation that pairs neighbours produces nonsense. If you ever port RoPE between codebases, check this first.

Where RoPE is applied — and where it isn't

q = W_q(x).view(B, T, nh, hd).transpose(1, 2)     # (B, nh, T, hd)
k = W_k(x).view(B, T, nh, hd).transpose(1, 2)
v = W_v(x).view(B, T, nh, hd).transpose(1, 2)

q, k = apply_rope(q, k, cos, sin)                  # ← q and k ONLY. Never v.

out = F.scaled_dot_product_attention(q, k, v, is_causal=True)

V is never rotated. Position matters for deciding which tokens to attend to, which is the dot product of q and k. It should not distort the content being retrieved. Rotating v would make the same information mean different things at different positions.

Note also that RoPE is applied inside every layer, afresh, on every forward pass. Unlike the sinusoidal encoding, its position signal cannot fade with depth.

It would be too slow
Position should influence which tokens are selected, not what those tokens contain

Each part has its own job. q·k decides the attention weights, so that is where position belongs. v is the content being carried. Rotating v would give the same retrieved fact a different vector depending on where it sat, and the model would have to undo the rotation. (In GQA and MHA, v often does have the same shape as k, so shape is not the reason.)

Only the first 4k tokens are used
It runs, and gets worse. Unlike a learned table there is no hard limit: you can compute cos(m·θ) for any m. But the model never saw those angles and generalises poorly to them. The fixes (position interpolation, NTK-aware scaling, YaRN) are in Chapter 21. Because it quietly gets worse instead of crashing, long-context claims need to be measured, not trusted.

7.5 · Approach 4 — ALiBi (and the "no positional encoding" result)

ALiBi (Press et al. 2021) is about as simple as it gets: add a linear penalty to the attention scores based on distance, with no position embeddings at all.

# head h gets slope m_h; slopes form a geometric sequence, e.g. 1/2, 1/4, 1/8, ...
scores = q @ k.transpose(-2,-1) / sqrt(d)
scores = scores + m_h * (j - i)      # (j - i) <= 0 for causal, so this is a penalty

Distant tokens are steadily down-weighted, and different heads decay at different rates, so some heads look near and some look far. ALiBi handles longer sequences remarkably well and was used by BLOOM and MPT. New models mostly use RoPE instead, but the idea lives on in sliding-window attention.

NoPE: decoders with a causal mask can learn position implicitly, because the mask itself breaks the permutation symmetry: token i sees exactly i+1 tokens. Kazemnejad et al. (2023) showed that NoPE models can match or beat explicit schemes on some length-generalisation tasks. Few models use it, but it is a good reminder that "attention has no sense of position" is less simple for decoders than for encoders.

7.6 · Partial and decoupled RoPE: rotate only some channels

Nothing requires RoPE to rotate every channel of a head. Partial RoPE rotates the first r of the d_head channels and passes the rest through unchanged:

def apply_partial_rope(x, pos, rot_dim):           # x: (T, d_head)
    cos, sin = build_rope_cache(max(pos) + 1, rot_dim)
    cos, sin = cos[pos], sin[pos]                  # (T, rot_dim)
    xr, xp = x[..., :rot_dim], x[..., rot_dim:]    # rotated part, pass-through part
    xr = xr * cos + rotate_half(xr) * sin
    return torch.cat([xr, xp], dim=-1)             # (T, d_head)

The dot product splits into two sums. The rotated channels contribute a term that depends only on the distance n − m, exactly as in §7.4; the other channels contribute a term that does not depend on position at all. test_ch07_partial_rope checks both halves: the unrotated channels are bit-identical to the input, and a score at positions (3, 5) equals the score at (100, 102). So a head has some channels for asking "how far away?" and some for asking "what is it?", without position getting in the way. Real configurations:

DeepSeek has a hard reason for it, which Chapter 16 develops. MLA caches a compressed latent and wants to fold the key up-projection into the query ("absorption"). A rotation that depends on the key's position sits between the two matrices and blocks the fold. So MLA decouples position: 128 channels per head carry content without rotation and can be absorbed, and a separate 64-channel RoPE part, shared across heads for the key, carries position. It is partial RoPE, chosen for a systems reason instead of a modelling one.

7.7 · Multimodal RoPE: more than one coordinate

Text has one position. An image patch has two (row and column) and a video patch has three (frame, row and column). Flattening an image into a sequence and using 1-D RoPE throws that structure away: the patch directly below another would look 32 positions away. M-RoPE (Qwen2-VL, Wang et al. 2024) splits the d_head/2 rotation frequencies into three sections and rotates each one by a different coordinate. Qwen2-VL's config uses mrope_section = [16, 24, 24] for a head 128 wide: 16 frequencies follow the time index, 24 the height and 24 the width.

θi = ps(i) · base−2i/d     s(i) = t for i < 16, h for 16 ≤ i < 40, w for 40 ≤ i < 64 each frequency index i is assigned one coordinate of the token's (t, h, w) position (tfs.foundations.mrope_angles)

For a video patch at (t, h, w) = (3, 5, 9), the angles at the start of each section are 3 × 1 = 3.0 (i = 0), 5 × 10000−32/128 = 0.5 (i = 16) and 9 × 10000−80/128 = 0.0285 (i = 40). Text tokens get the same index in all three coordinates, (p, p, p), so every frequency is rotated by p, and M-RoPE becomes exactly ordinary 1-D RoPE for text (test_ch07_mrope_reduces_to_rope_for_text checks the cosines against build_rope_cache). That design constraint let Qwen2-VL start from a text model's weights. Later versions refine how the time index tracks real time and how the sections are interleaved, but the idea, one rotation per coordinate, is the same.

7.8 · Measured: how far does RoPE extrapolate?

The table below says RoPE extends to longer sequences "with scaling", and that hides a measurement. Here it is on the repo's own model. The 2-layer tfs.model.Model from Chapter 4's logit-lens run (train_toy_copy_model: RoPE, trained only on 64-token sequences whose second half copies the first) is evaluated at longer lengths. Two tests separate two possible causes of failure:

  • Copy at half the length (copy_loss): the second half repeats the first, so at length T the model must copy from T/2 positions back. At T > 64 that distance never appeared in training.
  • Copy at the trained distance (periodic_loss): a 32-token block repeated to fill T tokens, so the copy distance is always 32, exactly as in training, and only the absolute positions are new. RoPE depends only on relative position, so a naive argument says this should still work.

The first column is expected: a copy distance the model never saw fails, worse than guessing (the model is confidently wrong). The last column is the lesson. Even when the distance the model needs was in training, every position past 64 fails. The cause is the other keys. At position 100 the query also scores keys at distances of 65 to 100, rotation angles the model never saw in training. Nothing constrained those scores, and some of them come out large enough to take the softmax away from the key at distance 32. RoPE makes the score depend only on relative position, but it does not make unseen relative positions harmless. Positions below 64 in the same sequences, where every distance is within range, stay perfect.

Chapter 21's methods solve this problem. Position interpolation squeezes long positions back into the trained range, so no angle is new. NTK-aware scaling and YaRN raise the base so the low-frequency channels rotate more slowly, and leave the high-frequency channels alone (they have already turned many times and have been seen at every angle). Sliding windows avoid the problem by never showing a layer a distance beyond its window. Exercise 7.4 has you try the first of these on this model.

Where this stands in 2026

RoPE is the default, and most of the current work is on how to scale its base frequency for long context. Llama 3 raised the base from 10,000 to 500,000 to make 128k context workable, a one-line change with a large effect. Many current long-context models also mix local (sliding-window) RoPE layers with a few global layers, so most layers only pay the attention cost of a small window. Gemma 2 and 3 made that pattern popular. Llama 4 goes one step further and drops positional encoding entirely in every fourth (global) attention layer, alternating RoPE layers with NoPE layers so that the long-range layers are not tied to trained rotation angles. Chapter 21 covers the scaling methods in full.

7.1Demonstrate permutation equivariancewarm-up

Build a 1-layer attention module with no positional encoding and no causal mask. Feed it x and x[:, perm] for a random permutation, and show that out[:, perm] == out_permuted. Then add RoPE and show that the property breaks.

Note

With a causal mask the equivariance breaks already, even without a positional encoding; that is the NoPE observation from §7.5. To see clean equivariance you have to remove the mask. The exercise is useful because it makes you notice that the mask itself carries position information.

7.2Verify the relative-position property numericallyessential

The claim is ⟨Rmq, Rnk⟩ depends only on n − m. Test it:

d = 64
cos, sin = build_rope_cache(200, d)
q, k = torch.randn(1,1,1,d), torch.randn(1,1,1,d)

def score(m, n):
    qm = q * cos[m] + rotate_half(q) * sin[m]
    kn = k * cos[n] + rotate_half(k) * sin[n]
    return (qm * kn).sum().item()

print(score(5, 8), score(50, 53), score(100, 103))   # all offset +3
print(score(5, 9))                                    # offset +4 → different
Expected

The first three agree to ~6 decimal places, and the fourth differs. If yours do not match, your rotate_half convention does not match the way you built the cos/sin table, which is exactly the issue described in the convention box in §7.4.

7.3Plot the frequency spectrumcode

For d_head=128, plot the wavelength (2π/θ_i, in tokens) of each RoPE pair i = 0..63 on a log y-axis, for base=10000 and base=500000.

  1. What is the shortest wavelength? The longest?
  2. How many pairs have wavelength longer than 4096 at each base?
  3. Explain in one sentence why raising the base helps long context.
Answers
  1. Shortest is always 2π ≈ 6.28 tokens (i=0, θ=1). Longest at base=10000 is 2π·10000126/128 ≈ 5.4×10⁴ tokens; at base=500000 it's ≈ 2.6×10⁶ tokens.
  2. 18 of 64 pairs exceed 4096 tokens at base 10000; 32 at base 500000. (A pair i has wavelength 2π · base2i/d, so it exceeds L when i > (d/2) · ln(L/2π) / ln(base).)
  3. Raising the base stretches every wavelength, so more dimensions complete less than one full rotation over the whole context. Those dimensions encode position without ambiguity instead of wrapping around. A dimension that wraps many times within the context cannot tell distance 100 from distance 100 + its wavelength.
7.4Predict, then measure: fix the extrapolationcode

Take the toy model from §7.8. Without retraining, implement position interpolation: at evaluation length T, multiply every position by 64 / T before building the RoPE cache, so the angles never exceed the trained range. Predict the result first, then measure periodic_loss beyond position 64 at T = 128 and 256.

  1. Does it fix the failure? Fully?
  2. Why does interpolation also change what the model sees at distance 32?
  3. What does that suggest about why real models fine-tune briefly after interpolating?
What you should find

It does not fix it; it makes it worse. Measured with periodic_loss_interpolated: beyond position 64 the loss is 5.45 at T = 128 (3.62 without interpolation) and 6.89 at T = 256 (5.94 without). Interpolation removes the unseen angles, but it also moves the key the model needs: distance 32 now produces the rotation that distance 16 produced in training, and this model, trained on a single copy distance, has learned to look for one exact angle. Every distance the model relies on is now at the wrong angle. That answers question 2. It is an extreme version of what happens in real models, which use many distances and degrade less. It also answers question 3: position interpolation, NTK and YaRN are always followed by a short fine-tune at the new length (Chen et al. used about 1,000 steps), during which the model relearns what the compressed angles mean (Chapter 21). If you predicted that interpolation would fix it, the exercise taught you something.

7.5Partial RoPE costs nothing, and buys what?thinking

(1) How many FLOPs per token does applying RoPE cost for a head of width 128, and what does rotating only 32 channels save, relative to the head's attention cost at T = 4096? (2) DeepSeek-V3's MLA shares one 64-wide RoPE key across all 128 heads. How many bytes per token does that part of the KV cache take in bf16, compared with a 64-wide RoPE key for every head?

Answers
1. RoPE: ~3 FLOPs per channel (two multiplies, one add) for q and for k: 3 × 128 × 2 ≈ 768 per head per token
   attention at T = 4096: 2·4096·128 (scores) + 2·4096·128 (mix) = 2.1 M per head per token
   → rotating 32 channels instead of 128 saves ~576 FLOPs of 2.1 M: nothing. Partial RoPE is a modelling choice.
2. shared:   64 × 2 bytes           =    128 bytes per token per layer
   per head: 128 × 64 × 2 bytes     = 16,384 bytes per token per layer (128× more)

The second answer is why MLA shares the RoPE key: a rotated key for every head would undo most of the compression the latent achieves.
