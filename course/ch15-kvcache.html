15 · The KV Cache and the Memory Wall

This chapter explains why serving an LLM is a different engineering problem from training one. It also explains why almost every architecture change since 2023 (GQA, MLA, MoE, speculative decoding) targets the same bottleneck. That bottleneck is memory bandwidth, not FLOPs.

Ch 02 — arithmetic intensity
Leads toCh 16 — shrinking the cache
Ch 17 — a different bottleneck
Ch 18 — serving is built on this arithmetic
Why this chapterNot FLOPs. Memory bandwidth. This chapter reframes everything after it.
The whole chapter in five sentences

In a causal model a token's keys and values never change, so compute them once and keep them. Generation then drops from O(T³) to O(T²) work. Decode then reads every weight and every cached byte to make one token, so bandwidth limits it, and its speed is bytes ÷ bandwidth. The cache grows as 2 · layers · KV heads · head dim · tokens · bytes, and at long context it gets bigger than the model. Chunked prefill and every other cache trick must give exactly what one-shot attention computes. The mask alignment is where they fail without any error. You can store the cache more cheaply (Chapter 16, fp8) or keep fewer tokens (eviction), and only the first loses nothing.

15.1 · The waste in the naive loop

Look again at generation. To produce token 101, we feed tokens 1 to 100 through the model. To produce token 102, we feed tokens 1 to 101. So we compute K and V for tokens 1 to 100 a second time, and they come out identical. The causal mask means token 50's representation cannot depend on anything after it.

The insight

In a causal model, the K and V vectors for a token never change once computed. So compute them once and keep them. Generating token t+1 then only needs a single new query vector attending against the stored keys and values.

15.2 · Implementation

class CachedAttention(nn.Module):
    def forward(self, x, cache=None):
        """
        Training / prefill:  x is (B, T, C), cache is None
        Decoding:            x is (B, 1, C), cache holds (k_prev, v_prev)
        """
        B, T, C = x.shape
        q, k, v = self.qkv(x).split(C, dim=-1)
        q = q.view(B, T, self.nh, self.hd).transpose(1, 2)     # (B, nh, T, hd)
        k = k.view(B, T, self.nh, self.hd).transpose(1, 2)
        v = v.view(B, T, self.nh, self.hd).transpose(1, 2)

        q, k = apply_rope(q, k, self.cos[pos:pos+T], self.sin[pos:pos+T])

        if cache is not None:
            k_prev, v_prev = cache                             # (B, nh, T_past, hd)
            k = torch.cat([k_prev, k], dim=2)                  # (B, nh, T_past+T, hd)
            v = torch.cat([v_prev, v], dim=2)
        new_cache = (k, v)

        # During decode T=1, so this is (B, nh, 1, T_total) — a single row.
        # No causal mask needed: the one query is the newest token, it may see everything.
        y = F.scaled_dot_product_attention(q, k, v, is_causal=(T > 1))

        return self.proj(y.transpose(1, 2).reshape(B, T, C)), new_cache
Three cache bugs that produce subtly wrong output
  1. RoPE position offset. During decode the new token is at absolute position T_past, not 0. If you use cos[0] every step, every token thinks it comes first. Symptom: the output makes sense for a few tokens, then falls apart.
  2. is_causal=True during decode. With a single query row, PyTorch lines the causal mask up with the top-left corner, so the one query is treated as position 0 and can see only key 0. Symptom: the output ignores the whole prompt.
  3. Not clearing the cache between sequences. The next request inherits the keys of the previous conversation. Symptom: strange mixing of conversations that only shows up under batching.

15.3 · Prefill vs decode — two different machines

This difference is the core of LLM serving, and it is easy to miss until someone points it out.

Prefill — process the prompt
  • All T prompt tokens, one pass
  • Big matmuls: (T, C) @ (C, C)
  • Compute-bound: keeps the GPU fully busy
  • Cost ∝ prompt length
  • Determines time to first token
Decode — generate, one token at a time
  • Exactly 1 token per pass
  • Skinny matmuls: (1, C) @ (C, C)
  • Memory-bandwidth-bound: the GPU is mostly idle
  • Cost ∝ number of output tokens
  • Determines tokens per second

Why decode is memory-bound — the arithmetic

Consider a single (4096, 4096) weight matrix in bf16, generating one token.

Bytes moved:   4096 × 4096 × 2 bytes            = 33.5 MB   (read the weights)
FLOPs done:    2 × 1 × 4096 × 4096              = 33.6 MFLOP

Arithmetic intensity = 33.6e6 / 33.5e6 ≈ 1.0 FLOP per byte

An H100 delivers roughly 990 TFLOP/s (bf16, with sparsity off) against 3.35 TB/s of HBM bandwidth. Its ridge point, the intensity above which you are compute-bound, is about 295 FLOP/byte.

1 FLOP/byte  ≪  295 FLOP/byte decode sits ~300× below the ridge: the GPU is a memory-transfer device that occasionally multiplies
The consequence, stated plainly

During decode, you read every weight in the model and every byte of the KV cache from HBM to produce one token. So your token rate is approximately:

tokens/sec ≈ memory bandwidthmodel bytes + KV cache bytes

Sanity check: a 7B model in bf16 is 14 GB. On an H100 at 3.35 TB/s, the ceiling for batch size 1 is 3350/14 ≈ 240 tokens/sec. Real systems reach 100 to 150. The gap is overhead plus the KV cache. For a one-line model, predicting real inference speed to within a factor of ~2 is very good.

The fix: batching

The weights are read once however many sequences you process, so batching is nearly free:

BatchWeight bytes readFLOPsIntensityRegime
114 GB14 GFLOP~1hopeless
3214 GB448 GFLOP~32better
25614 GB3.6 TFLOP~256approaching the ridge

Batch 256 gives you roughly 256× the throughput for the same weight traffic. This is why inference providers batch heavily, and why your API latency is better when the service is busy than when it is idle. It is also why the KV cache matters so much: the cache is what limits batch size.

15.4 · The cache size calculation

bytes = 2 × n_layer × n_kv_head × d_head × seq_len × batch × dtype_bytes the leading 2 is for K and V

Worked example — build the number from scratch, one factor at a time

Every factor in that formula counts something physical. Take Llama-3-8B, one token, bf16.

1
One head stores one key vector. d_head = 128 numbers, 2 bytes each in bf16: 
128 × 2 = 256 bytes
2
You need the value vector too. Same size — hence the leading 2: 
256 × 2 = 512 bytes   (one K + one V, for one head, for one token)
3
How many heads must you store? Not 32 — Llama-3 uses GQA with n_kv_head = 8. This is the factor Chapter 16 attacks: 
512 × 8 = 4,096 bytes   (per token, per LAYER)
4
Every layer keeps its own cache. Layer 7's keys are useless to layer 8 — they live in different representation spaces: 
4,096 × 32 layers = 131,072 bytes = 128 KiB per token
5
Now multiply by context. This is where it stops being small: 
   2,048 tokens ->  128 KiB ×   2,048 =   0.25 GiB
   8,192 tokens ->  128 KiB ×   8,192 =   1.00 GiB
  32,768 tokens ->  128 KiB ×  32,768 =   4.00 GiB
 131,072 tokens ->  128 KiB × 131,072 =  16.00 GiB   <- ONE user
6
Compare it with the model itself. Llama-3-8B in bf16 is 8.03 B × 2 bytes = 16.06 GB = 14.96 GiB of weights. So at 128k context one user's cache is larger than the whole model: 16.0 GiB against 14.96 GiB. Ten such users need 160 GiB of cache alone, which does not fit on an 80 GB H100 at any batch size.

The factor to attack. Look back at step 3: n_kv_head is a free parameter. Full MHA would use 32 there instead of 8. That is 4× everything above, so 64 GiB for that one 128k user. This one choice decides whether the model can be served at all.

def kv_bytes(n_layer, n_kv_head, d_head, seq, batch=1, dtype_bytes=2):
    """2 (K and V) × layers × kv_heads × head_dim × seq × batch × bytes"""
    return 2 * n_layer * n_kv_head * d_head * seq * batch * dtype_bytes

# Llama-3-8B, one token
assert kv_bytes(32, 8, 128, 1) == 131_072              # 128 KiB  ✓
# ...at 128k context
assert kv_bytes(32, 8, 128, 131072) / 1024**3 == 16.0   # 16 GiB   ✓
# ...and what full MHA would have cost
assert kv_bytes(32, 32, 128, 131072) / 1024**3 == 64.0  # 4× worse

Read it with Chapter 14 in mind. Uncached cost per token grows with position, roughly linearly at first and then faster once the activations no longer fit in the CPU's caches. Your numbers will differ, but the shapes will not. test_cache_timing_shape checks the shapes (the uncached slope and the gap between cached and uncached), not the milliseconds.

15.7 · Chunked prefill, and a bug that does not crash

A 32k-token prompt prefilled in one forward pass holds the GPU for hundreds of milliseconds, and every user who is partway through decoding waits that long for their next token. Chunked prefill (Agrawal et al., Sarathi, 2023; Sarathi-Serve, 2024) splits the prompt into chunks of a few hundred to a few thousand tokens. It runs one chunk per step alongside the ongoing decodes. Chapter 18 works out the scheduling trade-off. Here we cover the correctness requirement, which is stricter than it looks.

Chunk c starts at absolute position P (the tokens already cached). Its query i sits at position P + i and must see all P cached keys plus the chunk's keys up to itself. That is a causal mask aligned to the bottom-right of the (chunk × (P + chunk)) score matrix:

P = k.size(2) - T                                   # tokens already in the cache
qpos = torch.arange(P, P + T)[:, None]              # (T, 1)      absolute query positions
kpos = torch.arange(P + T)[None, :]                 # (1, P+T)    absolute key positions
mask = kpos <= qpos                                 # (T, P+T)    True = may attend
y = F.scaled_dot_product_attention(q, k, v, attn_mask=mask)
The repo's own model gets this wrong, silently

tfs.model.Model passes is_causal=(T > 1). That is right for training, for one-shot prefill and for one-token decode. But feed it a multi-token chunk on top of a cache, and PyTorch lines the causal mask up with the top-left. The chunk's first query is treated as position 0 and sees only key 0, which is the cache's first token, not its own. It runs and returns logits of the right shape, and they are wrong. Prefilling 40 tokens as 32 + 8 gives last-position logits that differ from one-shot prefill by up to 0.34. tfs.kvcache.prefill_chunked runs the same weights with the bottom-right mask above and matches one-shot prefill to 10−5 for chunk sizes 1, 7, 16 and 40. Both facts are asserted in test_chunked_prefill_exact. This is the second bug of §15.2, extended from one query row to many.

Chunking does not change the result (it is exact) or the total FLOPs. It changes when the work happens, and that is the point: a scheduler can cap how much prefill work any one step contains.

15.8 · Keeping less: eviction and compression

Every technique in §15.5 keeps every token and stores it more cheaply. The other family keeps fewer tokens: decide which cached positions the model will not need, and drop them. Unlike everything else in this chapter, this loses information. It relies on a measured fact: attention is sparse. Most queries put most of their weight on a small set of positions.

StreamingLLM: the window, plus the sinks

The obvious policy is a sliding window: keep the last w tokens. Xiao et al. (2023) found that it breaks suddenly the moment the first tokens are evicted, even though they carry little meaning. The cause is the softmax (Chapter 5). Every query's weights must sum to 1, so a head with nothing useful to attend to parks its weight on the first few positions, which every later token can see. They called these attention sinks. Evict them and that parked weight is forced onto real tokens, and perplexity explodes. StreamingLLM keeps 4 sink tokens plus a recent window and generates stably over millions of tokens with a fixed-size cache. It does not remember what fell out of the window. It lets the model keep generating; it does not help it recall.

H2O and SnapKV: keep the tokens attention actually uses

  • H2O ("Heavy-Hitter Oracle", Zhang et al., 2023) keeps the recent tokens plus the older tokens that have received the most attention in total so far, and it updates the choice as decoding goes on.
  • SnapKV (Li et al., 2024) decides once, after prefill. The last few prompt tokens (an "observation window", which in a chat prompt usually contains the question) vote on which earlier positions they attend to, per head. The votes are smoothed with a max-pool so whole phrases survive, and only the top positions are kept for decoding.
Worked example — how much attention mass each policy keeps

Here is a synthetic head with the structure these papers measured: a sink on token 0, 24 "heavy hitter" tokens scattered through a 1,024-token context, and a bias toward recent tokens. We keep a budget of B tokens and ask what fraction of the newest query's attention lands on the tokens we kept. H2O keeps B/2 recent tokens and B/2 heavy hitters chosen from a noisy history of the same pattern.

budget B           64     128     256       (of 1,024 tokens)
recent only       0.14    0.26    0.46
sinks + window    0.14    0.27    0.46      (StreamingLLM: 4 sinks + B−4 recent)
H2O               0.44    0.54    0.69

With a quarter of the cache, H2O keeps 69% of the attention weight and a window keeps 46%. The sinks add almost nothing to the weight here, and that is the subtle point. What matters is that evicting them moves weight the model learned to park there; the newest query barely uses them. synthetic_attention, streaming_keep, h2o_keep and snapkv_keep are in tfs/kvcache.py, asserted in test_eviction_policies. Real heads differ. Some are almost entirely local and some retrieve from far back, so the papers choose budgets per head or per layer.

What eviction costs

A dropped token is gone. A question that needs a detail the policy threw away (a needle in the haystack, the third clause of a contract) cannot be answered. Average benchmark scores hide this, because most questions do not need the dropped tokens. Use eviction to fit more users only for workloads whose recall needs you have measured. Where they are enough, prefer the levers that lose nothing (GQA/MLA, Chapter 16; fp8 KV; offload to CPU memory, Chapter 18). Production engines ship those by default.

15.1Add a KV cache and measure itessential

Add caching to your Chapter 9 model. Then:

  1. Correctness: assert that cached generation produces token-identical output to uncached generation with the same seed and greedy decoding. This is required. If they differ, you have one of the three bugs from §15.2.
  2. Speed: time generating 200 tokens with and without the cache. Plot time-per-token against position for both.
What the plot shows

Uncached: time per token grows linearly with position, because each step reprocesses the whole prefix, so total time is quadratic. Cached: time per token is nearly flat, rising only slightly as the attention row gets longer. At 200 tokens the speedup is typically 10 to 30×; at 2000 tokens it is over 100×. No other single change speeds up LLM inference as much.

15.2Build a serving calculatorcode

Write plan(model_cfg, gpu_gb, gpu_bandwidth_tbs, context, dtype_bytes). It should return the weight memory, the KV bytes per token, the maximum number of sequences at once, and the estimated batch-1 tokens/sec. Check it against the Llama-3-70B numbers in §15.4, then use it to answer:

  1. How many H100s does it take to serve Llama-3-70B at 128k context to 20 users at once?
  2. What happens to that answer with fp8 KV cache?
Answers
  1. Cache: 20 users × 40 GiB = 800 GiB = 859.0 GB. Plus 141.2 GB of weights = 1,000.2 GB → 13 H100s (80 GB each; 12 would hold only 960 GB), and realistically more for activations and fragmentation.
  2. fp8 halves the cache: 141.2 + 429.5 = 570.7 GB → 8 H100s. Saving 5 GPUs is why KV quantization is standard in production despite the small accuracy cost. (Computing the cache in GB instead of GiB gives 12 and 7. That is the unit slip from the box above, and it costs one GPU each time.)
15.3Find the roofline crossoverthinking

For a 7B model on an H100 (990 TFLOP/s bf16, 3.35 TB/s), at what batch size does decode stop being memory-bound? Compare that with prefill of a 2000-token prompt at batch 1. Which regime is it in, and why?

Answer

Ridge point = 990e12 / 3.35e12 ≈ 295 FLOP/byte. Decode intensity ≈ batch size. In bf16 each weight is 2 bytes and each sequence does 2 FLOPs per weight. The two cancel, giving ~1 FLOP/byte for each sequence in the batch. So you need batch ≈ 300 to reach the ridge. That is why production serving runs batches in the hundreds.

Prefill with T=2000 at batch 1 has intensity ≈ 2000, well into compute-bound territory. This difference is behind splitting prefill and decode apart: the two phases want different hardware and different batching, so several serving stacks from 2025 and 2026 now run them on separate GPU pools. See Chapter 18.

15.4Find the chunked-prefill bug yourselfcode

Prefill a 40-token prompt into tfs.model.Model in one call, then again as 32 + 8 tokens using caches and pos_offset. Compare the last-position logits. Then write the bottom-right mask yourself and show the two agree.

What you should see, and why

Expect a maximum difference of about 0.3 with the stock forward pass, and ~10−7 with your mask. Print the mask PyTorch builds for is_causal=True with an (8, 40) score matrix. It is the lower triangle of the top-left 8 × 8 corner, so query 0 of the chunk sees only key 0 of the whole sequence.

15.5Implement StreamingLLM and break itexploration

Add a fixed-size cache to your Chapter 11 model that keeps n_sink first tokens and a window of recent ones (re-index positions inside the cache, as the paper does, so RoPE never sees positions beyond the cache size). Generate 2,000 tokens with n_sink = 0 and with n_sink = 4, and plot per-token loss on held-out text.

What to look for

With no sinks, the loss jumps as soon as the first tokens leave the window. With 4 sinks it stays near the full-cache loss. Then ask the model to repeat a fact stated in token 50 after 1,500 tokens: both fail. Sinks keep generation stable. They do not make the model remember.

15.6Size an eviction budgetthinking

Llama-3-8B at 128k context needs 16 GiB of cache per user, on a GPU with 50 GiB free for cache. With an eviction budget of 4,096 tokens per sequence (sinks + heavy hitters + window), how many users fit? What fraction of the cache did each user give up, and what kind of request should never be sent to this setup?

Answer

4,096 × 128 KiB = 0.5 GiB per user, so 100 users instead of 3. Each keeps 3.1% of its tokens. Never send requests whose answer depends on exact recall from deep in the context: retrieval over long documents, contract review, or needle-in-a-haystack lookups.
