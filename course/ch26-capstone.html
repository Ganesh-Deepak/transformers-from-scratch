Why this matters more than reading another paper

Milestone 1 — Tokenizer

M1Train a byte-level BPE tokenizer~1 hr

Train on your chosen corpus. Provide encode, decode, and special tokens <|bos|>, <|eos|>, <|user|>, <|assistant|>.

Tests that must pass:

assert tok.decode(tok.encode(s)) == s          # for 1000 random corpus slices
assert tok.decode(tok.encode("🤖 émoji ñ 中文")) == "🤖 émoji ñ 中文"   # byte-level
assert len(tok.encode(text)) < len(text.encode()) * 0.4   # compression ≥ 2.5×
assert all(i < cfg.vocab_size for i in tok.encode(text))

Milestone 2 — The model

M2Implement the architecture~2 hrs

Build RMSNorm, build_rope_cache/apply_rope, GroupedQueryAttention, SwiGLU, Block, Model.

Tests that must pass — do not skip any of these:

# 1. Shapes
logits, loss = model(ids)                 # ids: (2, 16)
assert logits.shape == (2, 16, cfg.vocab_size)

# 2. Loss at init ≈ ln(V)                                        [Ch 9]
assert abs(loss.item() - math.log(cfg.vocab_size)) < 0.3

# 3. CAUSALITY — perturb one token, earlier outputs must not move [Ch 9]
ids2 = ids.clone(); ids2[0, 8] = (ids2[0, 8] + 1) % cfg.vocab_size
assert torch.allclose(model(ids)[0][0, :8], model(ids2)[0][0, :8], atol=1e-5)
assert not torch.allclose(model(ids)[0][0, 8], model(ids2)[0][0, 8])

# 4. RoPE encodes RELATIVE position                               [Ch 7]
assert abs(score(5, 8) - score(50, 53)) < 1e-5

# 5. GQA grouping is correct (loop vs vectorised)                 [Ch 16]
assert torch.allclose(gqa_loop(x), gqa_vectorised(x), atol=1e-5)

# 6. Every parameter receives a gradient
loss.backward()
for n, p in model.named_parameters():
    assert p.grad is not None and p.grad.abs().sum() > 0, n

# 7. Parameter count matches your hand calculation                [Ch 9]
assert abs(count_params(cfg) - sum(p.numel() for p in model.parameters())) < 10

Test 3 is the one people skip and regret. Test 6 catches a disconnected sub-module, which otherwise looks like "the model just learns slowly."

Milestone 3 — Training

M3Train it~1-2 hrs

Corpus options, in increasing order of interest: TinyStories (best results at this scale), Tiny Shakespeare (fastest), or ~20 MB of any text you like.

Before the real run: the overfit-one-batch test from Chapter 11. Loss must reach < 0.1 on a single fixed batch within 500 steps. If it can't, stop and debug — nothing downstream will work.

Suggested: batch 32 × seq 256, lr 3e-4, warmup 200, ~5000 steps,
grad clip 1.0, eval every 250 steps.

Deliverables: train/val loss curves, final val perplexity, 500 tokens of generated text, and the loss-vs-ln(V) check at step 0.

Target numbers

On TinyStories with 15M parameters, expect val loss around 1.6–2.2 (perplexity 5–9) and genuinely coherent short stories with consistent characters — TinyStories is designed so small models can actually succeed. On Shakespeare expect loss ~1.4–1.8 with convincing form and no meaning. Either is a pass; TinyStories is much more satisfying.

Milestone 4 — Efficient inference

M4KV cache + samplers~1 hr

Add KV caching and the full sampler suite (temperature, top-k, top-p, min-p).

# The test that catches all three cache bugs from Ch 15:
torch.manual_seed(0); a = generate(model, prompt, 100, use_cache=False, temperature=0)
torch.manual_seed(0); b = generate(model, prompt, 100, use_cache=True,  temperature=0)
assert torch.equal(a, b), "cache changes the output — check RoPE offset & is_causal"

Deliverables: a plot of time-per-token vs position, cached and uncached; the measured speedup at 100, 200 and 400 tokens; and generated samples at three temperatures.

Milestone 5 — Alignment

M5SFT then DPO~2 hrs

Build a small preference dataset — 200–500 triples is enough. The easiest way to make the effect visible at this scale is to choose a stylistic axis you can generate synthetically:

  • short answers (chosen) vs rambling ones (rejected)
  • stories that end happily (chosen) vs abruptly (rejected)
  • always-in-character vs breaking character

Then: (a) SFT with prompt masking, (b) DPO with β=0.1, logging loss, implicit rewards, margin, ranking accuracy, and absolute chosen/rejected log-probs.

Deliverables:

  1. Reward-margin and ranking-accuracy curves. Accuracy should reach > 0.8.
  2. Side-by-side generations from base, SFT, and DPO models on 10 held-out prompts.
  3. A β sweep {0.01, 0.1, 0.5} with samples from each — and a paragraph on what β=0.01 did.
  4. The implicit-reward evaluation from Exercise 24.3: does β·log(π/π_ref) rank held-out pairs above chance?
What success looks like

The DPO model should visibly follow your preference axis while remaining coherent. At β=0.01 you'll likely see it collapse — very short outputs, repetition, or degraded grammar — which is the KL constraint being too weak, exactly as Chapter 24 predicts. Seeing that failure yourself is the most valuable part of this milestone.

Self-assessment

You have understood this course if you can answer these without looking anything up:

Why is √dk the right scaling factor?
It normalises the vector lengths
It makes attention weights sum to 1
Var(q·k) = d_k for unit-variance inputs, so std = √d_k — dividing by it keeps softmax out of saturation
It compensates for the number of heads
Ch 5. Variances add over the d_k summed terms; the standard deviation is the square root.
Why is LLM decoding memory-bound?
The KV cache is larger than the model
One token's forward pass reads every weight but does only ~1 FLOP per byte read — hundreds of times below the GPU's ridge point
GPUs have slow memory
Attention is quadratic
Ch 15. Arithmetic intensity ≈ 1 vs a ridge point around 295 FLOP/byte on an H100.
Why does GQA reduce memory but not FLOPs?
All query heads still attend over the full sequence; only the number of stored/read K,V heads shrinks
It skips some attention computations
It uses lower precision for K and V
It reduces the sequence length
Ch 16. K and V are expanded back up (or re-read) before the matmul.
Why is FlashAttention faster despite doing the same or more arithmetic?
It approximates the softmax
It uses fewer attention heads
It runs in lower precision
It never writes the N×N matrix to HBM — tiling plus the online softmax keep everything in SRAM
Ch 17. It is exact; the win is entirely in data movement.
Why does DPO not need a reward model?
It uses a fixed heuristic reward
The KL-constrained optimum lets you express reward as β·log(π/π_ref) + β·log Z(x), and Z(x) cancels in the Bradley-Terry difference
It trains the reward model implicitly through a second head
It uses verifiable rewards instead
Ch 24. The policy is the reward model; the intractable term cancels exactly.
Why does GRPO not need a value model?
It uses the reference model's values
It doesn't compute advantages
Sampling G completions per prompt makes the group mean an empirical baseline for the advantage
The reward model provides per-token values
Ch 25. Trade a learned critic for G× generation.
