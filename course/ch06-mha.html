6 · Multi-Head Attention: The Reshape Dance

Single-head attention computes one weighted average per token. That's one relationship at a time — but a word relates to its subject, its object, its adjective and its clause simultaneously. Multi-head attention runs several attention operations in parallel, and the only genuinely tricky part is the tensor gymnastics. This chapter draws every step.

6.1 · Why more than one head

A softmax row sums to 1. That is a budget: if a head spends 0.8 of its attention on the subject, it has 0.2 left for everything else. One head cannot simultaneously do "find my grammatical subject" and "find the previous mention of this entity" — those want different weight distributions.

The core trade

Instead of one attention over d_model=512 features, do 8 attentions over d_head=64 features each. Same parameter count, same FLOPs — you've spent representational width to buy relational diversity. Each head is dumber, but you get eight of them, and empirically that is a very good trade.

Interpretability work has found heads that specialise cleanly: previous-token heads, duplicate-token heads, induction heads (which implement "I saw A B earlier, I just saw A, so predict B" — the mechanism behind in-context learning), and syntactic heads that track subject–verb agreement.

6.2 · The reshape dance, drawn

Here is the operation everyone gets wrong. Change n_head and watch what happens to the same numbers:

Nothing is computed here

view and transpose move zero data (Chapter 1). The "dance" is purely about which numbers are adjacent so that a batched matmul treats each head as an independent problem. That's all multi-head attention is: a reshape that turns one big matmul into n_head small parallel ones.

Skip the transpose and reshape reads memory in (head, token) order instead, so with 2 tokens you get token 0's vector built partly from token 1's head outputs. Shapes stay valid; the model just quietly learns something worse. 
# Prove the partition, and prove the bug is real
import torch
B, T, nh, hd = 1, 2, 3, 4
q = torch.arange(B * T * nh * hd).float().view(B, T, nh * hd)
#   token 0 = [0..11], token 1 = [12..23]

heads = q.view(B, T, nh, hd).transpose(1, 2)     # (B, nh, T, hd)
print(heads[0, 0, 0])      # head 0, token 0 -> [0., 1., 2., 3.]
print(heads[0, 2, 0])      # head 2, token 0 -> [8., 9., 10., 11.]

right = heads.transpose(1, 2).reshape(B, T, nh * hd)   # transpose FIRST
wrong = heads.reshape(B, T, nh * hd)                   # forgot the transpose

assert torch.equal(right, q), "correct merge is a perfect round-trip"
assert not torch.equal(wrong, q)
print("wrong[0,0] =", wrong[0, 0].tolist())
#   [0,1,2,3, 12,13,14,15, 4,5,6,7]  <- token 1's numbers leaked into token 0
Why it hides Both merges give shape (B, T, C). Nothing raises. The model still trains — just to a worse loss, with no error message pointing at the cause.

Step by step, with shapes

B, T, C = 2, 100, 512
nh = 8
hd = C // nh                                   # 64 — MUST divide evenly

x = torch.randn(B, T, C)                       # (2, 100, 512)

# ── 1. Project ────────────────────────────────────────────────
q = W_q(x)                                     # (2, 100, 512)
k = W_k(x)                                     # (2, 100, 512)
v = W_v(x)                                     # (2, 100, 512)

# ── 2. Split the feature axis into (heads, head_dim) ──────────
q = q.view(B, T, nh, hd)                       # (2, 100, 8, 64)
#         ^^^^^^^^^^^^^ 512 = 8 × 64, re-labelled. No data moved.

# ── 3. Move heads next to batch ──────────────────────────────
q = q.transpose(1, 2)                          # (2, 8, 100, 64)
#   now axes are (B, n_head, T, d_head)
#   → the LAST TWO axes are a (T, d_head) matrix, one per (batch, head)

k = k.view(B, T, nh, hd).transpose(1, 2)       # (2, 8, 100, 64)
v = v.view(B, T, nh, hd).transpose(1, 2)       # (2, 8, 100, 64)

# ── 4. Attention — batched over (B, n_head) ──────────────────
scores = q @ k.transpose(-2, -1) / hd**0.5     # (2, 8, 100, 100)
scores = scores.masked_fill(~causal, MIN)
attn   = scores.softmax(dim=-1)                # (2, 8, 100, 100)
out    = attn @ v                              # (2, 8, 100, 64)

# ── 5. Put the heads back together ───────────────────────────
out = out.transpose(1, 2)                      # (2, 100, 8, 64)
out = out.contiguous().view(B, T, C)           # (2, 100, 512)
#     ^^^^^^^^^^^^ REQUIRED — see below

# ── 6. Mix the heads ─────────────────────────────────────────
out = W_o(out)                                 # (2, 100, 512)
Step 5 is where everyone's implementation breaks

After transpose(1,2) the tensor is not contiguous — its strides are out of order. .view() then raises:

RuntimeError: view size is not compatible with input tensor's size and stride

Two valid fixes: .contiguous().view(B,T,C) or just .reshape(B,T,C) (which calls contiguous internally when needed). What you must not do is "fix" it by reordering the transpose — that silently interleaves head outputs and produces a model that trains to a mediocre loss and never tells you why.

Why step 6 exists

After concatenation, the 512 features are 8 independent blocks of 64 that have never interacted. W_o — the output projection — is what lets information from head 3 combine with information from head 7. Without it, the heads would write to disjoint slices of the residual stream forever.

MultiHead(Q,K,V) = Concat(head1, …, headh) WO   where   headi = Attention(QWiQ, KWiK, VWiV) Vaswani et al. 2017, §3.2.2
The paper's notation vs the code

The paper writes h separate projection matrices WiQ of shape (dmodel, dk). The code uses one matrix of shape (dmodel, dmodel) and slices the output. These are mathematically identical — the big matrix is just the small ones stacked side by side — but the single matmul is far faster on a GPU. Most implementations go further and fuse Q, K, V into one (C, 3C) projection, then split.

6.3 · A complete, correct implementation

import math, torch, torch.nn as nn, torch.nn.functional as F

class MultiHeadAttention(nn.Module):
    def __init__(self, d_model, n_head, max_T=2048, dropout=0.0, causal=True):
        super().__init__()
        assert d_model % n_head == 0, "d_model must be divisible by n_head"
        self.nh, self.hd, self.causal = n_head, d_model // n_head, causal
        self.qkv  = nn.Linear(d_model, 3 * d_model, bias=False)   # fused projection
        self.proj = nn.Linear(d_model, d_model,     bias=False)   # W_o
        self.drop = nn.Dropout(dropout)
        self.register_buffer(
            "mask", torch.tril(torch.ones(max_T, max_T, dtype=torch.bool))[None, None],
            persistent=False)                                     # (1,1,max_T,max_T)

    def forward(self, x):
        B, T, C = x.shape

        qkv = self.qkv(x)                              # (B, T, 3C)
        q, k, v = qkv.split(C, dim=-1)                 # 3 × (B, T, C)

        # (B, T, C) → (B, nh, T, hd)
        q = q.view(B, T, self.nh, self.hd).transpose(1, 2)
        k = k.view(B, T, self.nh, self.hd).transpose(1, 2)
        v = v.view(B, T, self.nh, self.hd).transpose(1, 2)

        att = (q @ k.transpose(-2, -1)) / math.sqrt(self.hd)      # (B, nh, T, T)
        if self.causal:
            att = att.masked_fill(~self.mask[:, :, :T, :T],
                                  torch.finfo(att.dtype).min)
        att = self.drop(att.softmax(dim=-1))
        y = att @ v                                    # (B, nh, T, hd)

        y = y.transpose(1, 2).reshape(B, T, C)         # (B, T, C)
        return self.proj(y)

And the version you should actually ship:

    def forward(self, x):

                q, k, v, is_causal=self.causal,
                dropout_p=self.drop.p if self.training else 0.0)

        return self.proj(y.transpose(1, 2).reshape(B, T, C))

Catastrophic silent scrambling. y is (B, nh, T, hd); reshaping directly to (B, T, C) reinterprets nh×T×hd numbers in memory order — so "token 0's feature vector" is actually built from head 0's outputs for tokens 0 and 1, etc. The shapes are all valid, nothing errors, and the model learns something mediocre. This is the single most common bug in hand-written attention. Test it: run one token through and check the output equals the concatenation of per-head outputs.

Patterns worth noticing:

  • d_head is almost always 64 or 128. It's held roughly fixed while d_model grows, so n_head is what scales. 64 and 128 are also what tensor cores like.
  • n_kv_head diverged from n_head starting around 2023. That's GQA — Chapter 16.
  • Too many tiny heads hurts: below d_head ≈ 32 each head has too little room to express a useful query.

6.5 · Exercises

6.1Prove your heads are independentessential

The definitive test that your reshape is correct. Implement MHA, then implement a naive loop version that runs single-head attention n_head times on explicit slices and concatenates. Assert they match.

def mha_loop(x, W_q, W_k, W_v, W_o, nh):
    B, T, C = x.shape
    hd = C // nh
    q, k, v = W_q(x), W_k(x), W_v(x)          # (B,T,C) each
    outs = []
    for h in range(nh):
        sl = slice(h * hd, (h + 1) * hd)      # this head's feature slice
        qh, kh, vh = q[..., sl], k[..., sl], v[..., sl]     # (B,T,hd)
        att = (qh @ kh.transpose(-2,-1) / hd**0.5).softmax(-1)
        outs.append(att @ vh)                 # (B,T,hd)
    return W_o(torch.cat(outs, dim=-1))       # (B,T,C)

assert torch.allclose(mha_loop(...), mha_vectorised(...), atol=1e-5)

If this assert fails, your view/transpose order is wrong. Fix it before moving on — every later chapter builds on this.

6.2einops rewritewarm-up

Rewrite the forward pass using only einops.rearrange — no view, no transpose. Confirm identical output.

Solution
from einops import rearrange

q, k, v = self.qkv(x).chunk(3, dim=-1)
q, k, v = (rearrange(t, 'b t (h d) -> b h t d', h=self.nh) for t in (q, k, v))

att = torch.einsum('bhqd,bhkd->bhqk', q, k) / self.hd**0.5
att = att.masked_fill(~mask, MIN).softmax(-1)
y   = torch.einsum('bhqk,bhkd->bhqd', att, v)

y = rearrange(y, 'b h t d -> b t (h d)')
return self.proj(y)

Notice that the bug from Checkpoint 1 Q3 is now impossible to write by accident — 'b h t d -> b t (h d)' states the intent explicitly, and 'b h t d -> b t (d h)' would be visibly different. This is the strongest argument for einops.

6.3Head ablationexploration

Load GPT-2. For each of the 144 (layer, head) pairs, zero out that head's output (set its slice of y to 0 before W_o) and measure the increase in perplexity on a held-out paragraph. Rank the heads.

What you'll find

The distribution is extremely skewed: most heads can be removed with almost no effect, while a handful cause large jumps. This replicates Michel et al. 2019, "Are Sixteen Heads Really Better than One?", which found many heads are prunable at inference. Two caveats worth internalising: (a) heads that are individually redundant may not be jointly redundant, and (b) heads that look useless on one distribution can be critical on another. Ablation tells you about this input, not about the head in general.

6.4Parameter accountingthinking

For one MHA layer with d_model=4096, n_head=32, no biases:

  1. How many parameters in total? Break it down by matrix.
  2. How does that change if n_head=64 with d_head=64?
  3. How does it change with GQA at n_kv_head=8?
Answers
  1. W_q, W_k, W_v, W_o are each 4096×4096 = 16,777,216 → 4 × 16.78M = 67.1M per layer.
  2. Identical. 64 heads × 64 dims = 4096 = 32 × 128. The head split doesn't touch parameter count at all — this is the point of §6.1.
  3. W_q and W_o stay 4096×4096. W_k and W_v shrink to 4096 × (8×128) = 4096×1024 = 4.19M each. Total = 16.78 + 16.78 + 4.19 + 4.19 = 41.9M, a 37% reduction in attention parameters — and, far more importantly, a 4× reduction in KV cache. Chapter 16.
