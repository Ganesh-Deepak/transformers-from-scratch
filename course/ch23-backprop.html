23 · The Backward Pass, Derived

Everything so far said "autograd handles it". That is a hole. This chapter derives every gradient in a transformer by hand — softmax, cross-entropy, RMSNorm, attention — and checks each one against autograd. After this you can implement a backward pass, debug a wrong one, and read a CUDA kernel.

Builds onCh 05 — the forward attention you are about to differentiate
Ch 08 — RMSNorm and the residual
Ch 10 — where these gradients get used
Leads toCh 14 — why the backward pass can recompute tiles
Why this chapterThe layer under "autograd handles it". Nothing here is optional if you want to work below the framework.
The one idea in this chapter

Backprop is one rule applied repeatedly: given ∂L/∂output, produce ∂L/∂input and ∂L/∂weights. Every layer is a small, local function that answers that question. The chain rule stitches them together. There is no global magic.

23.1 · The only rule

Write the network as a chain of functions. The loss is a scalar at the end:

x → f1 → h1 → f2 → h2 → … → L

Each layer receives the upstream gradient ∂L/∂hi — a tensor the same shape as its own output — and must return ∂L/∂hi−1, the same shape as its input.

Shapes make backprop almost mechanical

A gradient always has the same shape as the thing it is a gradient of. x.grad.shape == x.shape, always. So if the forward was 4, 3 @ 3, 5 → 4, 5, then backward takes a 4, 5 and must produce a 4, 3 and a 3, 5. There is usually only one way to contract the indices that gives those shapes — which is often enough to derive the formula.

Matmul, the base case

For C = A B with A of shape (m,k) and B of shape (k,n):

∂L∂A = ∂L∂C BT      ∂L∂B = AT ∂L∂C shapes: (m,n)(n,k) = (m,k) ✓  ·  (k,m)(m,n) = (k,n) ✓

Read those shapes. dL/dC is (m,n); to get something (m,k) you must multiply by something (n,k), and the only candidate is BT. The formula is forced.

23.2 · Softmax: the dense Jacobian

Softmax is the first genuinely interesting one, because every output depends on every input. So its derivative is not a vector but a full (n, n) Jacobian.

Let si = exi / Σj exj. Differentiate with the quotient rule, splitting on whether the index matches:

Derivation — two cases
1
Case i = j. Let Z = Σkexk. 
ds_i/dx_i = (e^x_i · Z − e^x_i · e^x_i) / Z²
          = (e^x_i/Z) · (1 − e^x_i/Z)
          = s_i(1 − s_i)
2
Case i ≠ j. The numerator exi does not depend on xj, only Z does: 
ds_i/dx_j = (0 · Z − e^x_i · e^x_j) / Z²
          = −s_i s_j
3
Combine with the Kronecker delta (δij is 1 when i=j, else 0):
∂si∂xj = si(δij − sj)   i.e.   J = diag(s) − s sT
=
Checked numerically at x = [1.0, 2.0, 0.5], so s = [0.2312, 0.6285, 0.1402]: 
autograd Jacobian        diag(s) − s sᵀ
[ 0.1778 −0.1453 −0.0324]   [ 0.1778 −0.1453 −0.0324]
[−0.1453  0.2335 −0.0881] = [−0.1453  0.2335 −0.0881]
[−0.0324 −0.0881  0.1206]   [−0.0324 −0.0881  0.1206]
Note it is symmetric, and every row sums to zero — because the outputs must keep summing to 1, so any increase somewhere is exactly paid for elsewhere.

The vector-Jacobian product, which is what actually runs

Frameworks never build that (n,n) matrix. They compute JTg directly for upstream gradient g:

∂L∂x = s ⊙ (g − (g·s)) one elementwise multiply and one dot product — O(n), not O(n²) 
def softmax_backward(s, g):
    """s: forward output. g: upstream gradient. Both (..., n)."""
    return s * (g - (g * s).sum(-1, keepdim=True))

# equals the full Jacobian product, without ever forming it
x = torch.tensor([1.0, 2.0, 0.5], requires_grad=True)
s = x.softmax(0); g = torch.tensor([0.3, -1.2, 0.7])
s.backward(g)
assert torch.allclose(x.grad, softmax_backward(s.detach(), g), atol=1e-6)

23.3 · Cross-entropy + softmax: why it collapses to p − y

Here is the most satisfying result in the chapter. Softmax alone has that dense Jacobian. Compose it with cross-entropy and almost everything cancels.

With L = −log pc for correct class c, and p = softmax(z):

Derivation — three lines
1
Gradient of the loss w.r.t. the probabilities. Only the correct class appears in the loss: 
dL/dp_i = −1/p_c   if i = c,   else 0
2
Chain through the softmax Jacobian. Only the i=c term survives step 1: 
dL/dz_j = Σ_i (dL/dp_i)(dp_i/dz_j)
        = (−1/p_c) · p_c(δ_cj − p_j)
        = −(δ_cj − p_j)
        = p_j − δ_cj
3
In vector form, with y the one-hot target:
∂L∂z = p − y
=
Checked at logits = [2.0, 1.0, 0.1], target class 0: 
p        = [ 0.6590,  0.2424,  0.0986]
p − y    = [−0.3410,  0.2424,  0.0986]
autograd = [−0.3410,  0.2424,  0.0986]   ✓
Read what p − y says

The gradient on each logit is simply "how much probability you assigned minus how much you should have". The correct token gets a negative gradient proportional to how much mass it was missing; every wrong token gets a positive one proportional to the mass it stole. It is the prediction error, nothing more.

And this is why you must never softmax before cross_entropy. PyTorch's F.cross_entropy takes logits precisely so it can use this fused, stable form. Feed it probabilities and you apply softmax twice — the loss still decreases, so it looks like it works, while the gradients are wrong.

23.4 · RMSNorm: where the gradient gets a correction term

Forward (dropping γ for clarity): y = x / r where r = √(mean(x²)).

The subtlety: r depends on every element of x, so changing x1 changes all the outputs. That produces a second term:

∂L∂x = 1r [ g ⊙ γ − x (g ⊙ γ) · xd · r² ] first term: the obvious rescale. second: the correction because r moved too.
Verified, and what the correction term does

x = [3, 1, 4, 8], rms = 4.7434, upstream g = [1, 0, 0, 0]:

autograd:  [ 0.189737, −0.007027, −0.028109, −0.056218]
formula :  [ 0.189737, −0.007027, −0.028109, −0.056218]   ✓

Look at what happened: we pushed only on element 0, yet elements 1–3 received negative gradient. Raising x0 would raise the RMS, which would shrink everything else — so the gradient pre-emptively pushes them the other way.

The geometric fact: dot(grad, x) = 0.0, exactly. The gradient is orthogonal to x. Normalisation makes the layer invariant to the scale of its input, so the gradient carries no component that would merely rescale x — that direction cannot change the loss, so it gets zero gradient. This is the mechanism behind "normalisation stabilises training", stated precisely.

def rmsnorm_backward(x, g, gamma, eps=0.0):
    d = x.shape[-1]
    r = x.pow(2).mean(-1, keepdim=True).add(eps).sqrt()
    gg = g * gamma
    return (gg - x * (gg * x).sum(-1, keepdim=True) / (d * r**2)) / r

x = torch.tensor([3., 1., 4., 8.], requires_grad=True)
gamma = torch.ones(4); g = torch.tensor([1., 0., 0., 0.])
(x / x.pow(2).mean().sqrt() * gamma).backward(g)
assert torch.allclose(x.grad, rmsnorm_backward(x.detach(), g, gamma), atol=1e-6)
assert abs(torch.dot(x.grad, x.detach())) < 1e-5          # orthogonal

23.5 · Attention backward, all three gradients

Now assemble. Forward: S = QKT/√d, P = softmax(S), O = PV. Given dO, we need dQ, dK, dV.

Derivation — walk the chain backwards
1
O = PV, so by the matmul rule: 
dV = Pᵀ @ dO           (T,T)ᵀ(T,d) -> (T,d) ✓
dP = dO @ Vᵀ           (T,d)(d,T)  -> (T,T) ✓
2
Through the softmax, row by row, using §23.2's VJP: 
dS = P ⊙ (dP − rowsum(dP ⊙ P))
3
S = QKT/√d, matmul rule again: 
dQ = dS  @ K / √d
dK = dSᵀ @ Q / √d
=
All three verified against autograd for random (T=4, d=3) inputs — match to 1e-5. 
def attention_backward(q, k, v, P, dO):
    dk_ = q.shape[-1]
    dV = P.transpose(-2, -1) @ dO
    dP = dO @ v.transpose(-2, -1)
    dS = P * (dP - (dP * P).sum(-1, keepdim=True))       # softmax VJP
    dQ = dS @ k / dk_**0.5
    dK = dS.transpose(-2, -1) @ q / dk_**0.5
    return dQ, dK, dV
Now Chapter 14 makes sense at the kernel level

Look at what step 2 needs: P and a row sum. No (T,T) Jacobian is ever constructed — the softmax backward is elementwise plus one reduction. That is exactly why FlashAttention can throw P away in the forward pass and recompute it tile by tile in the backward: each tile of dS needs only the corresponding tile of P and a running row statistic. Without this structure, the recomputation trick would be impossible.

23.6 · The residual connection, quantified

Chapter 4 asserted that y = x + f(x) gives ∂y/∂x = 1 + f′(x). Here is what that does over depth.

Why 100 layers train at all
1
Plain stack. The gradient reaching layer 1 is a product of every Jacobian above it. If each has magnitude 0.9: 
20 layers:  0.9²⁰ = 0.1216      <- 8× weaker
50 layers:  0.9⁵⁰ = 0.0052      <- 190× weaker
100 layers: 0.9¹⁰⁰ = 0.0000266  <- 37,600× weaker, effectively dead
2
Residual stack. Each term is (1 + f′). Even when f′ is small, the 1 survives, so the product stays near 1 and the gradient reaches layer 1 essentially undamped.
=
Verified: f(x)=0.3x² at x=2 gives f′=1.2, and autograd returns 2.2000 for d(x+f)/dx — exactly 1 + 1.2.
Why does F.cross_entropy take logits rather than probabilities?
Probabilities would be slower to compute
Fusing softmax with the loss lets the gradient collapse to the stable, exact p − y
Logits use less memory
It doesn't matter; both work
The fused gradient. Separately, softmax has a dense Jacobian and log of a tiny probability is numerically nasty. Fused, everything cancels to p − y — one subtraction, no cancellation error. If you softmax first and then call cross_entropy, you apply softmax twice; loss still falls, so it looks like it works, while gradients are wrong.
You push upstream gradient on one element of an RMSNorm output. Why do the other elements receive nonzero gradient?
A bug — they should be zero
Because γ mixes the channels
Because the RMS depends on every element, so changing one changes all the outputs
Because of the epsilon term
The normaliser couples them. Raising one element raises the RMS, which shrinks every other output — so the gradient includes a correction pushing them the other way. The result is a gradient exactly orthogonal to x: the direction that merely rescales the input cannot change the loss, so it receives no gradient. (γ is elementwise and does not mix channels.)
What does the softmax backward need, and why does that matter for FlashAttention?
Only P and a row sum — elementwise plus one reduction, so P can be recomputed tile by tile
The full (T,T) Jacobian, which must be stored
The original logits S, which must be stored
Nothing — softmax has no gradient
P and a row sum. dS = P ⊙ (dP − rowsum(dP ⊙ P)) is elementwise plus one reduction. No Jacobian is materialised, and each tile is independent given its row statistic — which is precisely what lets FlashAttention discard P in the forward pass and rebuild it in SRAM during backward.

23.1Write backward for every layer, check against autogradessential

Implement softmax_backward, rmsnorm_backward, attention_backward and a linear layer's backward. Verify each against autograd on random inputs:

def check(fn_forward, manual_backward, *inputs):
    ins = [t.clone().requires_grad_(True) for t in inputs]
    out = fn_forward(*ins)
    g = torch.randn_like(out)
    out.backward(g)
    mine = manual_backward(*[t.detach() for t in inputs], g)
    for auto, man in zip([t.grad for t in ins], mine):
        assert torch.allclose(auto, man, atol=1e-5), (auto, man)
    return "ok"

Use float64 while debugging — float32 noise can hide a genuinely wrong formula behind a loose tolerance.

23.2Gradient checking from first principlesessential

Before autograd existed, this is how everyone verified a backward pass. Central differences:

∂L∂xi ≈ L(x + εei) − L(x − εei)2ε 
def grad_check(f, x, eps=1e-6):
    x = x.double()
    num = torch.zeros_like(x)
    for i in range(x.numel()):
        xp, xm = x.clone(), x.clone()
        xp.view(-1)[i] += eps; xm.view(-1)[i] -= eps
        num.view(-1)[i] = (f(xp) - f(xm)) / (2 * eps)
    xa = x.clone().requires_grad_(True); f(xa).backward()
    rel = (num - xa.grad).norm() / (num.norm() + xa.grad.norm())
    return rel.item()          # want < 1e-7 in float64
Why central and not forward differences

Forward differences (L(x+ε) − L(x))/ε have error O(ε); central differences have O(ε²). With ε=1e-6 that is the difference between ~1e-6 and ~1e-12 error — enough to distinguish a correct formula from a subtly wrong one. Also: do this in float64. In float32 the subtraction of two nearly-equal numbers loses most of your significant digits, and everything looks wrong.

23.3Measure the residual's effect on gradient flowcode

Build a 40-layer stack of x -> tanh(Wx) with and without a residual connection. Do one backward pass and plot grad.norm() per layer on a log axis.

What you should see

Without residuals the gradient norm decays roughly geometrically with depth — a straight line on a log axis, often 4–6 orders of magnitude between layer 40 and layer 1. With residuals it is nearly flat. That plot is the vanishing-gradient problem, and it is far more convincing than any prose about it.

23.4Break cross-entropy on purposethinking

Compute the loss two ways and compare both the value and the gradient:

logits = torch.randn(4, 10, requires_grad=True)
target = torch.randint(0, 10, (4,))

a = F.cross_entropy(logits, target)                    # correct
b = F.cross_entropy(logits.softmax(-1), target)        # softmax applied TWICE
c = F.nll_loss(logits.softmax(-1).log(), target)       # also correct, less stable
  1. Which two agree? By how much do the gradients differ?
  2. Now set logits = logits * 50 and compare a against c. What happens to c, and why?
Answers
  1. a and c agree. b is wrong — it softmaxes an already-normalised vector, which flattens it drastically, so the loss is far too uniform and the gradient direction is wrong. Critically b still decreases during training, which is why this bug survives code review.
  2. At ×50 the largest logits dominate completely; softmax underflows the small entries to exactly 0, and log(0) = −inf. Version a is fine because the fused kernel uses the log-sum-exp trick internally and never materialises a zero probability. This is what "numerically stable" buys you — not accuracy in the last decimal, but the difference between a number and inf.
