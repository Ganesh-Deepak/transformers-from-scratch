10 · Training a Transformer

You have a model that maps tokens to logits. Now make it good. This chapter covers the loss, the optimizer, the schedule, and the dozen practical details that separate a run that works from one that spikes at step 4000 and never recovers.

10.1 · The objective: predict the next token

That's the whole thing. There is no clever auxiliary loss in standard pretraining.

ℒ = − 1T Σt=1T log Pθ(xt | x<t) average negative log-likelihood of the true next token 
loss = F.cross_entropy(logits[:, :-1].reshape(-1, V),   # (B*(T-1), V)
                       ids[:, 1:].reshape(-1))          # (B*(T-1),)

F.cross_entropy fuses log-softmax and negative-log-likelihood into one numerically stable op. Never write log(softmax(x)) yourself — it overflows.

Reading the number

Loss (nats)PerplexityInterpretation

Perplexity = exp(loss), and it means "the model is as uncertain as if it were choosing uniformly among this many options." Perplexity 20 ≈ "it has narrowed the next token down to about 20 candidates."

A loss on its own means very little. Convert it every time.

Check your step 0 against ln(V). An untrained model is uniform, so its loss is exactly ln V: 
ln(65)     =  4.174      character-level

Start much below this and you have a label bug (Ch 9). Start above it and your initialisation is broken.

The habit: never quote a loss without saying which tokenizer produced it, and compare runs on bpb. Row 2 of step 2 is the trap in one line — the model with nearly triple the loss is the better one.

Loss is NOT comparable across tokenizers

The table above assumes a ~32k BPE vocabulary. Change the tokenizer and every number moves, because loss is measured per token and tokens carry different amounts of text. A character-level model on Shakespeare reaching loss 1.5 and a BPE-2048 model reaching 5.8 can be the same quality — the BPE token is worth ~3.3 characters.

The comparable metric is bits per byte:

bpb = lossnats/tokenln(2) · bytes_per_token 
char-level Shakespeare, good small model   ~2.1 bits/byte
GPT-2 on web text                          ~1.0 bits/byte
strong modern LLMs                         ~0.6-0.8 bits/byte

Always report bits-per-byte when comparing runs with different vocabularies. tfs/train.py prints it as bpb on every eval line for exactly this reason.

Teacher forcing, and its consequence

During training we always condition on the true prefix, never on the model's own predictions. That's what makes the causal mask trick work — all T predictions computed in one pass. But it creates exposure bias: at generation time the model conditions on its own (possibly flawed) output, a distribution it never trained on. This is one reason long generations drift, and part of why RL-based post-training (Part VI) helps — it trains on the model's own rollouts.

10.2 · The optimizer: AdamW

Plain SGD does not train transformers well. Adam does, and AdamW is the correction that made it right.

# Adam: per-parameter adaptive step sizes from first and second gradient moments
m = β₁·m + (1-β₁)·g                 # momentum      (β₁ = 0.9)
v = β₂·v + (1-β₂)·g²                # second moment (β₂ = 0.95 for LLMs, 0.999 default)
m̂ = m / (1 - β₁ᵗ);  v̂ = v / (1 - β₂ᵗ)          # bias correction
θ = θ - lr · m̂ / (√v̂ + ε)

The key behaviour: dividing by √v̂ means parameters with consistently small gradients get large steps and vice versa. Transformers have wildly different gradient scales across embeddings, norms and attention, so this per-parameter normalisation matters a lot.

What the W in AdamW fixes

L2 regularisation adds λ‖θ‖² to the loss, so the gradient gains a λθ term — which then gets divided by √v̂ along with everything else. Parameters with large gradients get less regularisation. That is not what anyone wanted.

AdamW decouples it: apply weight decay directly to the parameters, outside the adaptive machinery.

θ = θ - lr · m̂/(√v̂ + ε) - lr · λ · θ      # ← decoupled decay term
# The standard LLM setup, with the parameter grouping people usually forget
decay, no_decay = [], []
for n, p in model.named_parameters():
    if not p.requires_grad: continue
    # Don't decay biases, norm gains, or (usually) embeddings —
    # they're not "weights" in the sense weight decay assumes.
    (no_decay if p.ndim < 2 else decay).append(p)

opt = torch.optim.AdamW(
    [{"params": decay,    "weight_decay": 0.1},
     {"params": no_decay, "weight_decay": 0.0}],
    lr=3e-4, betas=(0.9, 0.95), eps=1e-8, fused=True)
HyperparameterTypical LLM valueNote
lr1e-4 … 6e-4scales down as models get bigger; ~6e-4 at 125M, ~1.5e-4 at 175B
β₁0.9rarely changed
β₂0.95lower than PyTorch's 0.999 default — LLM gradients are noisy and 0.999 adapts too slowly
weight_decay0.1on 2-D weights only
grad_clip1.0global norm clipping — near-universal
The memory cost of Adam

Adam stores m and v per parameter, in fp32. That is 8 bytes per parameter on top of the weights — for a 7B model, 56 GB of optimizer state alone. Add fp32 master weights (28 GB) and gradients (28 GB) and you understand why training needs ZeRO / FSDP sharding while inference fits on one GPU.

2026 note: Muon

Adam's ~9-year reign is finally seeing real competition. Muon (Jordan et al., 2024) orthogonalises the momentum matrix via a Newton–Schulz iteration before stepping, which empirically improves the loss-per-FLOP for the 2-D weight matrices. It's used for hidden layers with AdamW retained for embeddings and the LM head. Kimi K2 (1T params) was trained with a Muon variant at scale, which is the strongest evidence so far that it isn't just a small-model effect. Still not the default, but worth knowing about.

10.3 · The learning-rate schedule

A constant learning rate is leaving a lot on the table. The standard is linear warmup → cosine decay:

def lr_at(step, base_lr, warmup=2000, total=100_000, min_ratio=0.1):
    if step < warmup:                                   # 1. linear warmup
        return base_lr * (step + 1) / warmup
    if step > total:
        return base_lr * min_ratio
    p = (step - warmup) / (total - warmup)              # 2. cosine decay
    return base_lr * (min_ratio + (1 - min_ratio) * 0.5 * (1 + math.cos(math.pi * p)))
Why warmup is not optional

At step 0, Adam's second-moment estimate v is near zero, so m̂/√v̂ can be enormous — the very first updates are effectively unbounded. Combine that with a randomly-initialised model whose gradients are large and uninformative, and a full-size first step can push the weights somewhere unrecoverable. Warmup ramps in gently while v stabilises. Post-LN models need it desperately; pre-LN models need it less, but everyone still uses it.

The WSD alternative

Cosine has an annoying property: you must fix total_steps in advance, and the intermediate checkpoints are all mid-decay and therefore not usable as final models. WSD (Warmup–Stable–Decay, popularised by MiniCPM and now used by several labs) holds the LR constant for most of training and only decays over the last ~10%. You can stop at any point, decay briefly, and get a good model — which makes continued pretraining and mid-run data changes far more practical.

10.4 · The training loop, complete

model = GPT(cfg).to(device)
model = torch.compile(model)                    # 1.3-2× speedup, one line

opt = torch.optim.AdamW([...], lr=6e-4, betas=(0.9, 0.95), fused=True)
ACC_STEPS = 8                                    # gradient accumulation

for step in range(total_steps):
    # ── learning rate ──────────────────────────────────
    lr = lr_at(step, base_lr=6e-4)
    for g in opt.param_groups:
        g["lr"] = lr

    # ── forward / backward with accumulation ──────────
    opt.zero_grad(set_to_none=True)
    total_loss = 0.0
    for micro in range(ACC_STEPS):
        ids, targets = next(train_iter)          # (B, T) each
        with torch.autocast(device_type="cuda", dtype=torch.bfloat16):
            _, loss = model(ids, targets)
            loss = loss / ACC_STEPS              # ← average, don't sum
        loss.backward()
        total_loss += loss.item()

    # ── clip, step ─────────────────────────────────────
    norm = torch.nn.utils.clip_grad_norm_(model.parameters(), 1.0)
    opt.step()

    if step % 100 == 0:
        print(f"step {step:6d}  loss {total_loss:.4f}  lr {lr:.2e}  gnorm {norm:.2f}")

The four practical techniques in that loop

TechniqueWhat it buysWhat it costs
Mixed precision (bf16)~2× speed, ~half activation memorynothing — bf16's fp32-range exponent means no loss scaling needed
Gradient accumulationlarge effective batch on small memoryproportionally more wall-clock per optimizer step
Gradient clippingsurvives loss spikes from bad batchesone extra pass over gradients
torch.compile1.3–2× via kernel fusion30–90 s compile time; recompiles on shape changes
Gradient checkpointing~√L activation memory instead of L~30% more compute (recomputes activations in backward)
Two accumulation bugs
  1. Forgetting to divide by ACC_STEPS. Your effective learning rate becomes 8× larger than you think, and it diverges.
  2. Calling opt.zero_grad() inside the micro-batch loop. Then you're not accumulating at all — you just did 8× the work for one micro-batch's gradient.

10.5 · Data: packing

Documents have different lengths. Padding each to T wastes compute on <pad> tokens — sometimes 50% of it. The standard fix is to concatenate everything and slice:

# Tokenize the whole corpus once, write to a flat uint16/uint32 memmap.
data = np.memmap("train.bin", dtype=np.uint16, mode="r")     # (N_total,)

def get_batch(B, T):
    ix = torch.randint(len(data) - T - 1, (B,))
    x = torch.stack([torch.from_numpy(data[i     : i+T  ].astype(np.int64)) for i in ix])
    y = torch.stack([torch.from_numpy(data[i + 1 : i+1+T].astype(np.int64)) for i in ix])
    return x, y                                              # (B,T), (B,T)

Zero padding, 100% of the compute does useful work. The trade-off is that sequences can span document boundaries — the model sometimes attends across an unrelated document break. Most pretraining just accepts this; if you care, you can pass a document-id mask to block cross-document attention (supported by FlashAttention's varlen API and PyTorch FlexAttention).

Your loss starts at 10.4 (V=32000), drops to 6.2 in 200 steps, then plateaus for 2000 steps. Most likely cause?
The model is broken
Nothing is wrong — it learned unigram frequencies fast, and syntax takes much longer
Learning rate is too low
You have the label-shift bug
Normal. The fastest available win is matching the marginal token distribution ("the" is common, "aardvark" isn't), which gets you to roughly the unigram entropy — around 6 for English. Everything after that requires actual modelling and comes much more slowly. Loss curves are characteristically step-like for this reason.
Why β₂ = 0.95 for LLMs instead of PyTorch's default 0.999?
0.999 averages over ~1000 steps, adapting too slowly to LLM gradient statistics and reacting badly to outlier batches
0.95 uses less memory
0.999 causes NaN in bf16
It's arbitrary
Adaptation speed. The effective averaging window is ~1/(1−β₂): 20 steps at 0.95 vs 1000 at 0.999. LLM gradients are noisy and non-stationary, and a long window means a single bad batch's huge gradient inflates v for a thousand steps afterwards, suppressing learning. GPT-3, Llama, Chinchilla and most others use 0.95.
You want an effective batch of 512 sequences but only 8 fit in memory. What do you do, and what must you not forget?
Reduce sequence length instead
Use gradient checkpointing; nothing else changes
Accumulate over 64 micro-batches; call opt.step() each time
Accumulate over 64 micro-batches; divide each loss by 64 and step once
Divide by the accumulation count, step once. loss.backward() adds into .grad, so without the division you get the sum of 64 losses — a 64× larger effective learning rate. Option C defeats the purpose entirely (that's just 64 small steps).

10.6 · Debugging a training run

Case study: a real bug this course shipped, and what caught it

While building the training script for this course, get_batch returned a pre-shifted y = data[i+1 : i+1+T], and it was passed to a forward() that also shifts internally (logits[:, :-1] vs targets[:, 1:]). The labels were shifted twice: the model was trained to predict two tokens ahead.

Here is what that looked like, on a model trained to memorise a short text:

train losschars correctgreedy output
correct0.0482100%'e we proceed any further, hear me speak.'
double-shifted0.045711%' ew rr rcedayfr e,haieode,ha er e,ha er'

The buggy version had the LOWER training loss. Predicting two tokens ahead is a perfectly learnable task — it just isn't language modelling. No exception, no NaN, no suspicious curve. Every unit test on forward() still passed, because forward() was never wrong; the caller was.

What caught it: closing the loop. Train a model to memorise a short text, then check that greedy generation reproduces it. A memorised model that cannot echo its own training data has a train/inference mismatch. The tell for this particular bug is that teacher-forced output is off by exactly one token. That check is test_generation_reproduces_memorised_text in tests/test_tfs.py.

The overfit-one-batch test — do this first, always 
ids, targets = next(train_iter)
for step in range(500):
    opt.zero_grad()
    _, loss = model(ids, targets)      # SAME batch every time
    loss.backward(); opt.step()
    if step % 50 == 0: print(step, loss.item())

Loss must go to near zero. If it can't memorise 8 sequences, no amount of data will help — you have a bug, not a capacity problem. This test takes 30 seconds and catches label-shift errors, broken masks, frozen parameters, and detached graphs.

SymptomLikely cause
Loss starts far below ln(V)label-shift bug (predicting the input), or leaked future via a broken mask

Read it carefully, because both halves are informative:

10.2Ablate the schedulecode

Train the same model 4 ways for the same number of steps: (a) constant LR, (b) cosine without warmup, (c) warmup + cosine, (d) warmup + cosine at 10× the LR. Plot all four loss curves on one chart.

What you'll see

(c) wins, usually by a clear margin. (b) often shows a spike in the first ~100 steps. (d) either diverges to NaN or plateaus high. The gap between (a) and (c) is typically 0.05–0.15 nats — small-looking, but that's the difference between a model and a better model at zero extra compute, which is why nobody skips it.

10.3Plant a bug, then find itessential

Introduce each bug below one at a time, run 200 steps, and record the loss-curve signature. Build yourself a lookup table so you can diagnose these by sight later.

  1. Remove the label shift (predict input instead of next token)
  2. Remove the causal mask
  3. Forget opt.zero_grad()
  4. Use lr=1.0
  5. Forget to divide by ACC_STEPS
Signatures
  1. Loss crashes to ~0 within a few dozen steps. Generation is gibberish. Diagnostic: loss below the data's entropy is impossible.
  2. Loss drops much faster than normal and reaches an implausibly low value; generation is incoherent. Same tell as (1) — the model is cheating.
  3. Gradients accumulate forever, so effective LR grows without bound. Loss falls then explodes to NaN.
  4. NaN within ~10 steps.
  5. Behaves like an 8× LR: either divergence or a noisy plateau well above where it should be.

The meta-lesson: (1) and (2) both produce a beautiful loss curve. Never trust a loss curve alone — always generate samples and always check loss against ln(V) at step 0.
