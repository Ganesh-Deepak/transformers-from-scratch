2 · Matrix Multiplication as a Machine

Every learnable operation in a transformer is a matmul. If you can predict the output shape of a matmul without thinking, and know what broadcasting will do before you run it, the rest of this course is bookkeeping. This chapter makes both automatic.

Leads toCh 05 — attention is two matmuls and a softmax
Ch 15 — the FLOP counting returns as the memory wall
Why this chapterA matmul consumes one dimension. Find the vanishing axis and you can read any equation in any paper.
The one idea in this chapter

A matmul consumes one dimension. In (m, k) @ (k, n) → (m, n), the two ks meet, are multiplied and summed, and vanish. Everything else is carried along unchanged. To read any matmul in any paper, find the dimension that vanishes.

2.1 · The machine, one cell at a time

Drag both sliders. Watch which row and which column light up, and read the arithmetic underneath.

That widget should leave you with three facts:

  1. Output cell (i, j) depends only on row i of A and column j of B.
  2. The inner dimension k must match, and then it disappears. It is the axis being summed over.
  3. The output shape is the two outer dimensions, (m, n). You can read it off the outside of the expression without doing any arithmetic.
Cij = Σk Aik Bkj the repeated index k is the one being summed away

This is the summation from Chapter 1: Cij = Σk AikBkj is step 3 written as a formula. Loop k over the shared dimension, multiply each pair, and keep a running total. The repeated index k is the one that vanishes.

# check every number above
import torch
A = torch.tensor([[1, 2, 3], [4, 5, 6]])
B = torch.tensor([[1, 0, 2, 1], [0, 1, 1, 0], [2, 1, 0, 3]])
C = A @ B
print(C)                      # [[ 7,  5,  4, 10], [16, 11, 13, 22]]
assert C.shape == (2, 4)
assert C[0, 0] == (A[0, :] * B[:, 0]).sum() == 7
assert C[1, 2] == (A[1, :] * B[:, 2]).sum() == 13
Try it Change one number in row 1 of A, and exactly one row of C changes. Change one number in column 2 of B, and exactly one column of C changes. Because the outputs are independent like this, matmuls split across parallel hardware with no extra work.

What a matmul means in a neural network

There are two ways to read a matmul, and you need both.

Reading A — dot products

Each output number is a similarity score between a row of A and a column of B. This is the right reading for attention, where Q @ K.T asks how well each query matches each key.

Reading B — a learned projection

Each row of A (one token's feature vector) is re-expressed in a new basis by the weight matrix. This is the right reading for nn.Linear: take this 4096-dimensional description and produce an 11008-dimensional description of the same thing.

2.2 · Batched matmul: the leading axes come along for the ride

Real tensors are rank 3 or 4, not rank 2. PyTorch's rule for them is simple:

The batched matmul rule

@ works on the last two axes only. Every axis before those is treated as a batch index: broadcast if needed, and passed through unchanged.

A = torch.randn(8, 4, 3)        # 8 independent (4,3) matrices
B = torch.randn(8, 3, 5)        # 8 independent (3,5) matrices
(A @ B).shape                   # (8, 4, 5)   ← 8 independent matmuls

A = torch.randn(2, 8, 4, 3)     # (B=2, H=8) grid of (4,3) matrices
B = torch.randn(2, 8, 3, 5)
(A @ B).shape                   # (2, 8, 4, 5)  ← 16 independent matmuls

That second example is multi-head attention: (B, n_head, T, d_head) @ (B, n_head, d_head, T) → (B, n_head, T, T). Batch and head ride along, d_head is consumed, and you get a T×T score matrix for each head.

The four shapes of @

nn.Linear does not do what its shape suggests

nn.Linear(in_features, out_features) stores its weight with shape (out_features, in_features), the transpose of what you might expect, and computes x @ W.T + b.

lin = nn.Linear(512, 2048)
lin.weight.shape          # (2048, 512)   ← out first!
x = torch.randn(8, 128, 512)
lin(x).shape              # (8, 128, 2048)  ← only the LAST axis changes

The practical rule: nn.Linear rewrites the last axis and leaves every other axis alone. That is why you can feed it (B, T, C) without reshaping: it treats B×T as one big pile of vectors.

2.3 · Broadcasting — the rule that causes silent bugs

Broadcasting lets you combine tensors of different shapes without writing loops. It is very useful, and it is also the main source of bugs that do not crash.

The complete rule

Line the two shapes up from the right, and pad the shorter one with 1s on the left. Then, at each position, the two dimensions are compatible if:

  • they are equal, or
  • one of them is 1, in which case it is stretched to match the other.

The bug that will bite you

scores = torch.randn(4, 8, 16, 16)   # (B, H, T, T)
mask   = torch.randn(16)             # (T,)   ← you meant a per-key mask

scores + mask     # (4, 8, 16, 16)   ← NO ERROR. Broadcast along the last axis.
                  #                     If you meant per-QUERY, you are now silently wrong.

Both readings produce a valid tensor of the right shape, but only one is what you wanted. The fix is to say explicitly which axis you mean:

mask[None, None, :, None]    # (1,1,T,1) → broadcasts across KEYS   (per-query mask)
mask[None, None, None, :]    # (1,1,1,T) → broadcasts across QUERIES (per-key mask)
The classic un-crashing catastrophe 
pred   = torch.randn(32, 1)     # (32, 1)
target = torch.randn(32)        # (32,)
loss = ((pred - target) ** 2).mean()

You expected 32 squared errors. Broadcasting gave you a (32, 32) matrix of the differences between every pair, and a mean over 1024 numbers. The loss is wrong and training is useless, but nothing crashes. Always assert pred.shape == target.shape before computing a loss.

2.4 · einsum: say what you mean

einsum lets you write the index equation directly instead of arranging transposes by hand. Once it makes sense to you, you will prefer it for anything complicated.

How to read an einsum string

Give every axis of every input a letter, and write the output's letters after ->. Then any letter that appears in the inputs but not in the output is summed over. A letter repeated across inputs is multiplied elementwise before that sum.

import torch

A = torch.randn(4, 3)
B = torch.randn(3, 5)

torch.einsum('ik,kj->ij', A, B)     # matmul: k appears twice, not in output → summed
torch.einsum('ij->ji', A)           # transpose: no sum, just relabel
torch.einsum('ij->', A)             # sum everything: no output labels at all
torch.einsum('ij->i', A)            # row sums: j is dropped → summed over
torch.einsum('i,i->', v, w)         # dot product
torch.einsum('i,j->ij', v, w)       # outer product: nothing is summed

Attention in one line

q = torch.randn(2, 8, 100, 64)     # (B, H, T, D)
k = torch.randn(2, 8, 100, 64)
v = torch.randn(2, 8, 100, 64)

# scores: for each (batch, head), every query against every key
scores = torch.einsum('bhqd,bhkd->bhqk', q, k) / 64**0.5    # (2, 8, 100, 100)
#                          ^^^^ d is summed away — it's the dot product

attn = scores.softmax(dim=-1)                                # (2, 8, 100, 100)

out = torch.einsum('bhqk,bhkd->bhqd', attn, v)               # (2, 8, 100, 64)
#                        ^^^^ now k is summed away — the weighted average

Compare it with the transpose version, which does the same computation:

scores = (q @ k.transpose(-2, -1)) / 64**0.5
out    = attn @ v

The @ version is quicker to type and usually runs on a slightly better-optimised path; the einsum version documents itself and cannot be written backwards. Real codebases use @ in the hot path and einsum everywhere else, so learn to read both.

einops: the same idea for reshaping

from einops import rearrange, repeat, reduce

x = torch.randn(2, 100, 512)                          # (B, T, C)

# The multi-head reshape — one readable line instead of view+transpose:
q = rearrange(x, 'b t (h d) -> b h t d', h=8)         # (2, 8, 100, 64)

# ...and back again after attention:
out = rearrange(q, 'b h t d -> b t (h d)')            # (2, 100, 512)

# Mean-pool over time:
pooled = reduce(x, 'b t c -> b c', 'mean')            # (2, 512)
Why (h d) and not (d h) matters

'b t (h d) -> b h t d' says the 512 features are laid out as 8 blocks of 64: head 0 owns features 0 to 63, head 1 owns 64 to 127, and so on. Writing (d h) would mean the features are interleaved across heads. Both are valid reshapes with the same output shape, but they scramble the weights differently. This is the most common bug in from-scratch attention, and einops makes it visible instead of hiding it inside a .view().

2.5 · Counting FLOPs — the skill that makes you sound senior

A matmul (m, k) @ (k, n) costs 2·m·k·n floating-point operations: one multiply and one add for each term. Everyone uses that factor of 2.

For a transformer, the well-known approximation is:

FLOPs per token ≈ 2 N   (forward)   ·   ≈ 6 N   (forward + backward) N = number of parameters. Backward costs roughly 2× forward.

So training on D tokens costs about 6ND FLOPs. Every scaling-law calculation in Chapter 21 rests on this formula, and you should be able to derive it:

  • Forward: each weight is used in exactly one multiply-add per token, so 2N.
  • Backward: you compute gradients with respect to both the inputs and the weights, which costs about 2× the forward pass, so 4N.
  • Total: 6N per token.
What 6ND leaves out

Attention's T×T score matrix costs FLOPs that do not scale with parameter count: roughly 12 · n_layer · d_model · T² per sequence for a training step (4 for the two attention matmuls of the forward pass, × 3 for forward plus backward; a causal mask can skip about half). For short contexts this is a few percent and everyone ignores it. At T = 128k it can dominate. That crossover is why sparse attention (Chapter 22) exists.

Where 2N comes from: one layer, matmul by matmul

"2N per token" is a summary. Derive it once from the matmuls of a single standard transformer layer (multi-head attention and a 4× MLP; Chapters 5 to 8 build each piece) and you will not need to take it on trust again. A token's vector has d features. Applying a weight matrix (d_in, d_out) to one token is a (1, d_in) @ (d_in, d_out) matmul: 2 · d_in · d_out FLOPs, which is 2 FLOPs per weight.

Training multiplies that by 3, because the backward pass computes two matmuls for every forward one: a gradient for the input and one for the weight. Raise T and the attention row grows while the others stay fixed. In one layer it overtakes the weights at 4Td = 24d², that is at T = 6d, which is Chapter 5's crossover point.

2.6 · Shapes affect speed: intensity and tile alignment

FLOPs tell you how much arithmetic a matmul needs. They do not tell you how long it takes, because a GPU can only do arithmetic on numbers it has already fetched from memory. Two facts about shapes decide which of those limits you hit. Chapter 14 covers both in full; you need a first version now, because this is the first place where shapes affect speed as well as correctness.

Arithmetic intensity: FLOPs per byte moved

For (M, K) @ (K, N) in bf16, the matmul does 2MKN FLOPs and must at least read both inputs and write the output once: 2(MK + KN + MN) bytes. The ratio of the two is the arithmetic intensity. An H100 does about 295 bf16 FLOPs in the time it takes to move one byte from HBM (Chapter 14's ridge point). Below 295 FLOPs per byte it waits on memory; above it, it waits on arithmetic. Keep the weight fixed at (4096, 4096) and vary M, the number of tokens processed at once (tfs.foundations.matmul_intensity):

M (tokens)FLOPsbytes movedFLOPs / byteon an H100 (ridge 295)

16537 M33.8 MB15.9memory-bound

4096137 G101 MB1365compute-bound

Look at the bytes column. At small M it is almost all the weight matrix (33.5 MB), which is read once no matter how few tokens use it. That row explains the economics of LLM inference. Decoding one token means M = 1: a matrix-vector product with intensity 1, so a decode step is limited by how fast the weights stream from memory, not by FLOPs. Batching many users' tokens together (raising M) costs nothing extra until the intensity reaches the ridge. Training and prefill process thousands of tokens at once and stay on the compute side. Chapters 14, 15 and 18 all follow from this table.

Tile alignment: why vocab sizes are padded

Tensor cores do not multiply single numbers. They multiply small tiles of fixed size: for bf16 the instructions need dimensions in multiples of 8 or 16, and the kernels that use them cut every matrix into blocks of 64 or 128. If a dimension is not a multiple of the block size, the last block is partly empty, and the kernel pays for the whole block anyway. NVIDIA's performance guide gives the practical rule: for fp16 and bf16, keep matmul dimensions multiples of 8, and larger powers of two are better still. The share of useful work with a partial block is n / (⌈n / tile⌉ · tile):

n = 4097,  tile 128:   4097 / (33 × 128)   = 97.0% useful     one extra element costs a whole block
n = 65,    tile 64:      65 / (2 × 64)     = 50.8% useful     a small dimension can halve throughput
n = 50257, tile 128:  50257 / (393 × 128)  = 99.9% useful     but the irregular size can also miss the fast kernel

The third row is GPT-2's vocabulary, 50,257, which is an odd number. The output projection (d, V) is the largest matmul in a small model, and an odd V rules out the fast aligned code paths entirely, whatever the tile arithmetic says. So implementations pad the vocabulary with unused rows: nanoGPT pads 50,257 to 50,304, the next multiple of 64 (and also of 128), at the cost of 47 rows that are never predicted. Modern models pick aligned sizes from the start: Llama 3's 128,256 is 1,002 × 128, and the vocabulary of 152,064 in Qwen2.5's config.json is 1,188 × 128, larger than the tokenizer's real token count for the same reason. The same rule is why d_ff values such as 11,008 and 14,336 are multiples of 256 (Chapter 8), and why head dimensions are 64 or 128 (Chapter 14).

2.2Implement matmul three wayscode

Write matmul_loops, matmul_broadcast (no explicit loop over k: use broadcasting and a sum) and matmul_einsum. Check with torch.allclose that all three agree with A @ B. Then time them on 256×256 matrices.

Solution
def matmul_loops(A, B):
    m, k = A.shape; k2, n = B.shape
    assert k == k2
    C = torch.zeros(m, n)
    for i in range(m):
        for j in range(n):
            C[i, j] = (A[i, :] * B[:, j]).sum()
    return C

def matmul_broadcast(A, B):
    # A: (m,k) -> (m,k,1);  B: (k,n) -> (1,k,n)
    return (A[:, :, None] * B[None, :, :]).sum(dim=1)      # sum over k

def matmul_einsum(A, B):
    return torch.einsum('ik,kj->ij', A, B)

A, B = torch.randn(256, 256), torch.randn(256, 256)
ref = A @ B
for f in (matmul_loops, matmul_broadcast, matmul_einsum):
    assert torch.allclose(f(A, B), ref, atol=1e-4), f.__name__

Expect roughly: loops ≈ 4 s, broadcast ≈ 20 ms, einsum ≈ 1 ms, @ ≈ 0.5 ms. The broadcast version teaches something, but it materialises an (m,k,n) intermediate: 256³ = 16.7M floats = 67 MB. FlashAttention (Chapter 17) solves exactly this problem of materialising a big intermediate, at a much larger scale.

2.3Find the broadcasting bugessential

This causal-mask code runs without error but trains badly. Find the bug.

T = 8
scores = torch.randn(2, 4, T, T)              # (B, H, T, T)
mask = torch.tril(torch.ones(T, T))           # (T, T) lower triangular
scores = scores.masked_fill(mask == 0, -1e9)  # looks fine?

# ...later, with a padding mask:
pad = torch.tensor([1,1,1,1,1,0,0,0])         # (T,) 1 = real token
scores = scores.masked_fill(pad == 0, -1e9)
Answer

The causal mask is fine: (T,T) broadcasts correctly against (B,H,T,T).

The padding mask is the bug. pad has shape (T,), which lines up with the last axis, the key axis. That happens to be what you usually want for padding, so this case is right by accident. But it is hard to read and one refactor away from breaking. If someone later gives pad the shape (B, T), it will broadcast against (B,H,T,T) as (1,1,B,T) and silently mask the wrong thing whenever B == T, or crash otherwise.

Always write the mask at full rank:

pad = pad.view(1, 1, 1, T)      # (1,1,1,T) — explicitly "per key"
scores = scores.masked_fill(pad == 0, float('-inf'))

  3. Why does the answer barely depend on the weight's shape, as long as it is large?
Answers
1. FLOPs = 2·M·4096·14336        bytes = 2·(4096M + 4096·14336 + 14336M)
   intensity = 4096·14336·M / (4096·14336 + 18432·M)
2. solve intensity = 295:  M = 295 / (1 − 295·18432/(4096·14336)) ≈ 325

3. When K·N is much larger than (K + N)·M, the weight dominates the bytes and the intensity is ≈ M: each token in the batch reuses every weight once. So the rule "decode becomes compute-bound at a batch size of roughly the ridge point" holds for every large layer. (Check part 2 with matmul_intensity(326, 4096, 14336), which gives 295.7.) In practice the KV cache, which is not shared between sequences, keeps decode memory-bound well past this batch size; see Chapter 15.

2.6Predict, then measure: one extra elementcode

Predict the ratio of run times for a @ b with square bf16 matrices of size 4096 and 4097. Then measure it on a GPU (or fp32 on CPU), timing 20 runs after 5 warm-ups and calling torch.cuda.synchronize() before reading the clock.

What to expect

The FLOP count grows by 0.07%, so a FLOP model predicts no change. Tile arithmetic predicts at least the 97%-useful figure from the text, about 3% slower. On GPUs the measured penalty is often much larger, because a dimension that is not a multiple of 8 can push cuBLAS onto a slower, unaligned kernel. On a CPU the difference is usually small. The shape that is cheapest to think about is not always the cheapest to run, so profile before believing either.
