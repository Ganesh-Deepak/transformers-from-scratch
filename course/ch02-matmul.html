2 · Matrix Multiplication as a Machine

Every learnable operation in a transformer is a matmul. If you can predict the output shape of a matmul without thinking, and you know what broadcasting will do before you run it, the rest of this course is bookkeeping. This chapter makes that automatic.

Why this chapterA matmul consumes one dimension. Find the vanishing axis and you can read any equation in any paper.
The one idea in this chapter

A matmul consumes one dimension. (m, k) @ (k, n) → (m, n): the two ks meet, get multiplied-and-summed, and vanish. Everything else is carried along untouched. Finding the vanishing dimension is how you read any matmul in any paper.

2.1 · The machine, one cell at a time

Drag both sliders. Watch which row and which column light up, and read the arithmetic underneath.

Three facts that widget should make permanent:

  1. Output cell (i, j) depends on row i of A and column j of B. Nothing else.
  2. The inner dimension k must match, and then disappears. It is the axis being summed over.
  3. The output shape is "the outer two": (m, n). You can read it off the outside of the expression without any arithmetic.
Cij = Σk Aik Bkj the repeated index k is the one being summed away
Worked example — (2,3) @ (3,4), every number

Do this one with a pencil. It is the only way the rule stops being abstract.

      │   they VANISH  │

The inner 3 is consumed. The output is "the outer two". You knew the answer before doing any arithmetic.

One output cell = one dot product. C[0,0] uses row 0 of A and column 0 of B — nothing else in either matrix matters. 
row 0 of A  = [1, 2, 3]
col 0 of B  = [1, 0, 2]
C[0,0] = 1×1 + 2×0 + 3×2 = 1 + 0 + 6 = 7
4

row 1 of A  = [4, 5, 6]
col 2 of B  = [2, 1, 0]
C[1,2] = 4×2 + 5×1 + 6×0 = 8 + 5 + 0 = 13
5
All eight cells. 
C = [[ 7,  5,  4, 10],
     [16, 11, 13, 22]]        shape (2, 4)  ✓

Notice the summation you met in Chapter 1: Cij = Σk AikBkj is literally step 3 — loop k over the shared dimension, multiply the pair, keep a running total. The repeated index k is the one that vanishes.

# check every number above
import torch
A = torch.tensor([[1, 2, 3], [4, 5, 6]])
B = torch.tensor([[1, 0, 2, 1], [0, 1, 1, 0], [2, 1, 0, 3]])
C = A @ B
print(C)                      # [[ 7,  5,  4, 10], [16, 11, 13, 22]]
assert C.shape == (2, 4)
assert C[0, 0] == (A[0, :] * B[:, 0]).sum() == 7
assert C[1, 2] == (A[1, :] * B[:, 2]).sum() == 13
Try it Change one number in row 1 of A. Exactly one row of C changes. Change one number in column 2 of B and exactly one column of C changes. That independence is why matmuls parallelise perfectly.

What a matmul means in a neural network

There are two readings, and you need both.

Reading A — dot products

Each output number is a similarity score between a row of A and a column of B. This is the right reading for attention, where Q @ K.T literally asks "how well does each query match each key?"

Reading B — a learned projection

Each row of A (a token's feature vector) gets re-expressed in a new basis by the weight matrix. This is the right reading for nn.Linear: "take this 4096-dim description and produce an 11008-dim description of the same thing."

2.2 · Batched matmul: the leading axes come along for the ride

Real tensors are rank 3 or 4, not rank 2. PyTorch's rule is beautifully simple:

The batched matmul rule

@ operates on the last two axes only. Every axis before that is treated as a batch index — broadcast if needed, and passed through untouched.

A = torch.randn(8, 4, 3)        # 8 independent (4,3) matrices
B = torch.randn(8, 3, 5)        # 8 independent (3,5) matrices
(A @ B).shape                   # (8, 4, 5)   ← 8 independent matmuls

A = torch.randn(2, 8, 4, 3)     # (B=2, H=8) grid of (4,3) matrices
B = torch.randn(2, 8, 3, 5)
(A @ B).shape                   # (2, 8, 4, 5)  ← 16 independent matmuls

That second example is multi-head attention. (B, n_head, T, d_head) @ (B, n_head, d_head, T) → (B, n_head, T, T). Batch and head ride along; d_head is consumed; you get a T×T score matrix per head. That's the whole thing.

The four shapes of @

ABResultWhat happened
(k,)(k,)() scalarplain dot product
(m, k)(k,)(m,)matrix–vector; B is promoted to (k,1) then the 1 is dropped
(m, k)(k, n)(m, n)the classic
(…, m, k)(…, k, n)(…, m, n)batched; leading axes broadcast
nn.Linear does not do what its shape suggests

nn.Linear(in_features, out_features) stores its weight with shape (out_features, in_features) — transposed from what you'd expect — and computes x @ W.T + b.

lin = nn.Linear(512, 2048)
lin.weight.shape          # (2048, 512)   ← out first!
x = torch.randn(8, 128, 512)
lin(x).shape              # (8, 128, 2048)  ← only the LAST axis changes

The practical rule: nn.Linear rewrites the last axis and leaves every other axis alone. That's why you can feed it (B, T, C) without reshaping — it happily treats B×T as "a big pile of vectors".

An MLP layer is nn.Linear(4096, 11008). Input is (2, 1024, 4096). Output shape, and how many parameters in the weight?
(2, 1024, 11008); 45,088,768 weights
(2, 11008, 4096); 45,088,768 weights
(2, 1024, 4096); 11008 weights

(2, 1024, 11008), and 4096 × 11008 = 45,088,768 ≈ 45M weights (plus 11008 biases, though most modern LLMs set bias=False). Note the parameter count does not depend on batch or sequence length at all — only on the feature dimensions.
Which of these will raise a shape error?
torch.randn(8,4,3) @ torch.randn(3,5)
torch.randn(8,4,3) @ torch.randn(8,3,5)
torch.randn(1,4,3) @ torch.randn(8,3,5)
torch.randn(8,4,3) @ torch.randn(5,3)
The last one. The inner dimensions must match: 3 vs 5 — no. The first works because (3,5) broadcasts across the batch; the third works because a batch dimension of 1 broadcasts up to 8.

2.3 · Broadcasting — the rule that causes silent bugs

Broadcasting lets you combine tensors of different shapes without writing loops. It's wonderful, and it is the number one source of bugs that don't crash.

The complete rule

Align the two shapes from the right. Pad the shorter one with 1s on the left. Then, for each position, the dimensions are compatible if:

  • they are equal, or
  • one of them is 1 — in which case it is stretched to match the other

The bug that will bite you

scores = torch.randn(4, 8, 16, 16)   # (B, H, T, T)
mask   = torch.randn(16)             # (T,)   ← you meant a per-key mask

scores + mask     # (4, 8, 16, 16)   ← NO ERROR. Broadcast along the last axis.
                  #                     If you meant per-QUERY, you are now silently wrong.

Both interpretations produce a valid tensor of the right shape. Only one is what you wanted. The fix is to be explicit about which axis you mean:

mask[None, None, :, None]    # (1,1,T,1) → broadcasts across KEYS   (per-query mask)
mask[None, None, None, :]    # (1,1,1,T) → broadcasts across QUERIES (per-key mask)
The classic un-crashing catastrophe 
pred   = torch.randn(32, 1)     # (32, 1)
target = torch.randn(32)        # (32,)
loss = ((pred - target) ** 2).mean()

You expected 32 squared errors. Broadcasting gave you a (32, 32) matrix of all-pairs differences, and the mean over 1024 numbers. The loss is wrong, training is garbage, nothing crashes. Always assert pred.shape == target.shape before a loss.

2.4 · einsum: say what you mean

einsum lets you write the index equation directly instead of choreographing transposes. Once it clicks, you'll prefer it for anything non-trivial.

How to read an einsum string

Label every axis of every input with a letter. Write the output labels after ->. Then: any letter that appears in the inputs but not the output is summed over. Any letter repeated across inputs is multiplied elementwise before that sum.

import torch

A = torch.randn(4, 3)
B = torch.randn(3, 5)

torch.einsum('ik,kj->ij', A, B)     # matmul: k appears twice, not in output → summed
torch.einsum('ij->ji', A)           # transpose: no sum, just relabel
torch.einsum('ij->', A)             # sum everything: no output labels at all
torch.einsum('ij->i', A)            # row sums: j is dropped → summed over
torch.einsum('i,i->', v, w)         # dot product
torch.einsum('i,j->ij', v, w)       # outer product: nothing is summed

Attention in one line

q = torch.randn(2, 8, 100, 64)     # (B, H, T, D)
k = torch.randn(2, 8, 100, 64)
v = torch.randn(2, 8, 100, 64)

# scores: for each (batch, head), every query against every key
scores = torch.einsum('bhqd,bhkd->bhqk', q, k) / 64**0.5    # (2, 8, 100, 100)
#                          ^^^^ d is summed away — it's the dot product

attn = scores.softmax(dim=-1)                                # (2, 8, 100, 100)

out = torch.einsum('bhqk,bhkd->bhqd', attn, v)               # (2, 8, 100, 64)
#                        ^^^^ now k is summed away — the weighted average

Compare that to the transpose version. Same computation:

scores = (q @ k.transpose(-2, -1)) / 64**0.5
out    = attn @ v

The @ version is faster to type and typically dispatches to a slightly better-optimised path; the einsum version is self-documenting and impossible to get backwards. Real codebases use @ in the hot path and einsum everywhere else. Learn to read both.

einops: the same idea for reshaping

from einops import rearrange, repeat, reduce

x = torch.randn(2, 100, 512)                          # (B, T, C)

# The multi-head reshape — one readable line instead of view+transpose:
q = rearrange(x, 'b t (h d) -> b h t d', h=8)         # (2, 8, 100, 64)

# ...and back again after attention:
out = rearrange(q, 'b h t d -> b t (h d)')            # (2, 100, 512)

# Mean-pool over time:
pooled = reduce(x, 'b t c -> b c', 'mean')            # (2, 512)
Why (h d) and not (d h) matters

'b t (h d) -> b h t d' says the 512 features are laid out as 8 blocks of 64 — head 0 owns features 0–63, head 1 owns 64–127, and so on. Writing (d h) would mean features are interleaved across heads. Both are valid reshapes with the same output shape, but they scramble the weights differently. This is the single most common bug in from-scratch attention, and einops makes it visible instead of hidden inside a .view().

2.5 · Counting FLOPs — the skill that makes you sound senior

A matmul (m, k) @ (k, n) costs 2·m·k·n floating-point operations (one multiply and one add per term). That factor of 2 is the convention everyone uses.

For a transformer, the famous approximation is:

FLOPs per token ≈ 2 N   (forward)   ·   ≈ 6 N   (forward + backward) N = number of parameters. Backward costs roughly 2× forward.

So training on D tokens costs about 6ND FLOPs. That single formula is the basis of every scaling-law calculation in Chapter 21, and it's worth being able to derive:

  • Forward: each weight is used in exactly one multiply-accumulate per token → 2N.
  • Backward: you compute gradients w.r.t. both inputs and weights → about 2× the forward cost → 4N.
  • Total: 6N per token.
What 6ND leaves out

Attention's T×T score matrix costs FLOPs that don't scale with parameter count — roughly 12 · n_layer · d_model · T² per sequence. For short contexts this is a few percent and everyone ignores it. At T = 128k it can dominate. That crossover is exactly why sparse attention (Chapter 22) exists.

6ND = 6 × 7×10⁹ × 2×10¹² = 8.4 × 10²². For scale: an H100 does roughly 10¹⁵ bf16 FLOP/s at realistic utilisation, so this is ~8.4×10⁷ GPU-seconds ≈ 2.7 GPU-years ≈ 10 days on 100 H100s. Being able to do this estimate in your head is genuinely useful.

Answers

2.2Implement matmul three wayscode

Write matmul_loops, matmul_broadcast (no explicit loop over k — use broadcasting and a sum), and matmul_einsum. Verify all three agree with A @ B using torch.allclose. Then time them on 256×256 matrices.

Solution
def matmul_loops(A, B):
    m, k = A.shape; k2, n = B.shape
    assert k == k2
    C = torch.zeros(m, n)
    for i in range(m):
        for j in range(n):
            C[i, j] = (A[i, :] * B[:, j]).sum()
    return C

def matmul_broadcast(A, B):
    # A: (m,k) -> (m,k,1);  B: (k,n) -> (1,k,n)
    return (A[:, :, None] * B[None, :, :]).sum(dim=1)      # sum over k

def matmul_einsum(A, B):
    return torch.einsum('ik,kj->ij', A, B)

A, B = torch.randn(256, 256), torch.randn(256, 256)
ref = A @ B
for f in (matmul_loops, matmul_broadcast, matmul_einsum):
    assert torch.allclose(f(A, B), ref, atol=1e-4), f.__name__

Expect roughly: loops ≈ 4 s, broadcast ≈ 20 ms, einsum ≈ 1 ms, @ ≈ 0.5 ms. The broadcast version is instructive but note it materialises an (m,k,n) intermediate — 256³ = 16.7M floats = 67 MB. That "materialising a big intermediate" problem is exactly what FlashAttention solves in Chapter 17, at a much larger scale.

2.3Find the broadcasting bugessential

This causal-mask code runs without error and trains badly. Find the bug.

T = 8
scores = torch.randn(2, 4, T, T)              # (B, H, T, T)
mask = torch.tril(torch.ones(T, T))           # (T, T) lower triangular
scores = scores.masked_fill(mask == 0, -1e9)  # looks fine?

# ...later, with a padding mask:
pad = torch.tensor([1,1,1,1,1,0,0,0])         # (T,) 1 = real token
scores = scores.masked_fill(pad == 0, -1e9)
Answer

The causal mask is fine — (T,T) broadcasts correctly against (B,H,T,T).

The padding mask is the bug. pad has shape (T,), which right-aligns to the last axis — the key axis. That happens to be what you usually want for padding, so this specific case is accidentally right. But it is unreadable and one refactor away from disaster: if someone later makes pad shape (B, T), it will broadcast against (B,H,T,T) as (1,1,B,T) and silently mask the wrong thing whenever B == T, or crash otherwise.

Always write the mask at full rank:

pad = pad.view(1, 1, 1, T)      # (1,1,1,T) — explicitly "per key"
scores = scores.masked_fill(pad == 0, float('-inf'))
2.4FLOP budget for a real modelthinking

GPT-3 175B was trained on ~300B tokens.

  1. Estimate total training FLOPs.
  2. At 312 TFLOP/s peak bf16 per A100 and 40% achieved utilisation, how many A100-days?
  3. The paper reports 3.14×10²³ FLOPs. How close were you, and what does the gap tell you?
Answers
  1. 6 × 1.75×10¹¹ × 3×10¹¹ = 3.15 × 10²³ FLOPs.
  2. Effective rate = 312e12 × 0.4 = 1.25×10¹⁴ FLOP/s. 3.15e23 / 1.25e14 ≈ 2.52×10⁹ s ≈ 29,000 A100-days ≈ 1000 A100s for a month.
  3. Essentially exact (3.15 vs 3.14 ×10²³). The 6ND rule is remarkably good for dense transformers at moderate context length. It starts to break down for MoE models (where you use active parameters, not total) and for very long contexts (where attention FLOPs matter).
