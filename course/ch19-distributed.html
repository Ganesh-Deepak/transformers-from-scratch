19 · Distributed Training: DP, TP, PP, ZeRO

A 7B model needs 112 GB just for weights, gradients and optimizer state — before a single activation. An 80 GB GPU cannot hold it. Every frontier model is therefore split across hundreds or thousands of chips, along the batch, the layers, the stack and the sequence. This chapter derives what each cut costs in bytes on the wire, which is the only thing that decides whether a strategy works.

The whole chapter in five sentences

Mixed-precision Adam needs 16 bytes per parameter before a single activation, so anything past a few billion parameters must be split across GPUs. There are four things to split: the batch (data parallel, with ZeRO/FSDP sharding the redundant state), each layer (tensor parallel), the stack (pipeline parallel) and, for long context, the sequence (context parallel). Each pays in a different communication pattern, and what decides a design is bytes on the wire against the speed of the link they cross: the frequent, non-overlappable traffic goes on NVLink inside a node, the rest on the network. Activations are the other half of memory, and sequence parallelism, selective recomputation and FlashAttention each delete a specific term of a published formula. At thousands of GPUs failures arrive every few hours, so checkpoint cadence and restart time are part of the design, not an afterthought.

19.1 · The memory problem, stated exactly

From Ch 12, mixed-precision Adam keeps five things per parameter:

  bf16 weights            2 bytes
  bf16 gradients          2
  fp32 master weights     4      \
  fp32 Adam m             4       |  the "optimizer state", 12 bytes
  fp32 Adam v             4      /
                        ----
  TOTAL                  16 bytes per parameter
The number that forces everything else

16 bytes/param, so a model of P parameters needs 16P bytes of persistent state:

  1B params  ->   16 GB      fits on one 80 GB GPU
  7B params  ->  112 GB      does NOT fit
 70B params  -> 1120 GB      needs 14+ GPUs for state alone
671B params  -> 10.7 TB      needs 134+ GPUs before activations

And activations are on top of this, growing with batch and sequence length. The weights alone are only 2 bytes/param — seven-eighths of the memory is training machinery, which is why inference fits on hardware training never could.

19.2 · Data parallel: split the batch

The simplest cut. Every GPU holds a complete copy of the model and processes a different slice of the batch. Gradients are averaged across GPUs before the optimizer step, so all replicas stay identical.

GPU 0: full model, samples  0..31   -> grads_0  \
GPU 1: full model, samples 32..63   -> grads_1   |  all-reduce (mean)
GPU 2: full model, samples 64..95   -> grads_2   |  -> identical grads everywhere
GPU 3: full model, samples 96..127  -> grads_3  /

The communication is one all-reduce of the gradient buffer per step. The standard implementation is a ring: reduce-scatter around the ring, then all-gather back. Each phase moves (N-1)/N of the buffer per GPU, so:

traffic per GPU = 2 · N − 1N · (gradient bytes)   ⟶   2 × as N grows 
N GPUs    multiplier    7B model, bf16 grads (14 GB)
     2       1.0000      14.0 GB moved per GPU per step
     4       1.5000      21.0
     8       1.7500      24.5
    64       1.9688      27.6
   512       1.9961      27.9   <- converged; does NOT keep growing
Why ring all-reduce scales at all

The multiplier approaches 2 and stops. Doubling from 64 to 512 GPUs adds 1% more traffic per GPU, not 8×. That constant-cost property is why data parallelism scales to thousands of chips, and why it is the default. Its problem is not communication — it is that every GPU still needs all 16 bytes/param. DP does nothing for memory.

Two implementation details that matter

Overlap. Gradients for layer L are ready as soon as layer L's backward finishes — you do not need to wait for the whole backward pass. PyTorch DDP buckets gradients and launches each all-reduce as its bucket fills, so most communication happens underneath the remaining backward compute. Done well, all-reduce is nearly free.

The batch-size ceiling. Scaling DP means growing the global batch. Past a few million tokens per batch, extra samples stop improving the gradient estimate — you are averaging noise that was already averaged. Data parallelism therefore has a hard limit set by optimization, not hardware, and that limit is why the other two axes are mandatory at scale.

19.3 · ZeRO: keep data parallelism, delete the redundancy

In DP, all N GPUs store identical optimizer state. That is N copies of the same numbers. ZeRO's observation: each GPU only needs the state for the parameters it is about to update. Shard it, and gather on demand.

  stage             N=1     N=8    N=64   N=512
  DDP             16.00   16.00   16.00   16.00
  ZeRO-1          16.00    5.50    4.19    4.02   -> floor of 4

7B model on 64 GPUs:   112 GB/GPU (DDP)  ->  1.8 GB/GPU (ZeRO-3)
Read the floors

ZeRO-1 and -2 have asymptotes — 4 and 2 bytes/param — because they keep a full copy of the weights (and, for stage 1, the gradients) on every GPU. Only ZeRO-3 has no floor: everything is sharded, so memory per GPU falls indefinitely with N. That is why FSDP (PyTorch's ZeRO-3) is the modern default, and why it costs ~50% more communication — parameters must be all-gathered just before each layer runs and freed straight after.

ZeRO-3's trick is just-in-time materialisation: for each layer, all-gather its parameters, compute, then discard the shards you do not own. The full model never exists on any single GPU at any moment, yet the arithmetic is bit-identical to DDP. The cost is that this gather sits on the critical path, so it must be prefetched one layer ahead to stay hidden.

19.4 · Tensor parallel: split each layer

When a single layer is too large, split the matrices themselves. Megatron-LM's arrangement is built to minimise synchronisation, and the reason it works is worth seeing:

Derivation — why the MLP needs only one all-reduce
1
Split the first matrix by columns. With W1 = [W1(a), W1(b)], each GPU computes its own column block: 
GPU a:  h_a = act(x @ W1_a)     x is REPLICATED, h_a is a column slice
GPU b:  h_b = act(x @ W1_b)
No communication — and because the activation is elementwise, it applies independently per column. This is why the split must be by columns: a row split would need the full pre-activation summed first.
2
Split the second matrix by rows, matching: 
GPU a:  y_a = h_a @ W2_a        each y is a PARTIAL SUM of the true output
GPU b:  y_b = h_b @ W2_b
3
One all-reduce completes it. y = y_a + y_b. Total: one collective for the whole MLP, and the intermediate h — the widest tensor in the block — never leaves its GPU.
4
Attention splits the same way, along heads. Each GPU owns whole heads, computes their attention independently (heads never interact until the output projection), and the output projection is row-split like W2. One all-reduce per attention block.

So a transformer block costs 2 all-reduces forward, 2 backward. But these fire in the middle of every layer and cannot be overlapped — everything stalls until they finish:

activation tensor, B=8, T=2048, d=4096, bf16   =   134.2 MB
  TP=2:  0.54 GB per layer per step
  TP=4:  0.81 GB
  TP=8:  0.94 GB      x 80 layers = ~75 GB per step, all on the critical path
TP does not leave the node

That traffic is why tensor parallelism is confined to GPUs inside one server, connected by NVLink (~900 GB/s on H100) rather than InfiniBand (~50 GB/s per link). Cross the node boundary with TP and the 18× slower link turns a synchronous, non-overlappable collective into the dominant cost of the whole run. TP degree is therefore almost always ≤ 8 — the number of GPUs on one board. This is a networking fact masquerading as a hyperparameter.

19.5 · Pipeline parallel: split the stack

Give each GPU a contiguous group of layers. Activations flow forward, gradients flow back, and only the boundary activations cross the wire — tiny compared with TP, and it works fine over slow links.

The problem is idleness. With one batch in flight, GPU 3 waits for 0, 1 and 2 before it has anything to do:

naive, 4 stages, 1 batch          (F = forward, B = backward, . = IDLE)
  GPU0  F . . . B . . .
  GPU1  . F . . . B . .
  GPU2  . . F . . . B .
  GPU3  . . . F B . . .
                                  -> 75% of the machine is idle

The fix is to split the batch into microbatches and keep several in flight. With p stages and m microbatches:

bubble fraction = p − 1m + p − 1 
simulated by counting idle slots directly, vs the closed form
   p    m   simulated   (p-1)/(m+p-1)
   4    1     0.7500       0.7500
   4    8     0.2727       0.2727
   4   32     0.0857       0.0857
   8    8     0.4667       0.4667
   8   32     0.1795       0.1795
   8  128     0.0519       0.0519
The rule of thumb, and where it comes from

To keep the bubble under ~10% you need m ≳ 9(p − 1) — roughly ten microbatches per stage. That is the entire design pressure behind 1F1B scheduling (same bubble, far less activation memory, because a microbatch's activations are freed as soon as its backward runs) and interleaved 1F1B, which gives each GPU v non-contiguous chunks of layers and cuts the idle fraction to (p-1)/(vm+p-1) at the cost of v× more boundary messages (pv − 1 hand-offs per microbatch instead of p − 1). Narayanan et al. write the same result as (p-1)/(vm): that is bubble time divided by ideal compute time, not by total time, so check which convention a paper uses before comparing numbers.

It is a networking constraint. Two all-reduces per layer per direction, each moving a fraction of a ~134 MB activation, with the whole layer stalled until they finish. 8 is the number of GPUs sharing an NVLink domain in one server. The matrices do also get small (a §14.2 concern), but the link speed binds first.

7/15 = 0.4667, confirmed by simulation. Filling and draining the pipeline costs p−1 slots at each end regardless of m. The rule m ≥ 9(p − 1) gives m = 64 here, for a bubble of 9.9% (roughly ten microbatches per stage).
ZeRO-1 and ZeRO-2 flatten out at 4 and 2 bytes/param, but ZeRO-3 keeps falling. Why?
ZeRO-3 uses a more efficient compression scheme
ZeRO-3 shards the parameters too, so nothing is replicated; stages 1 and 2 still keep a full weight copy (and stage 1 a full gradient copy) on every GPU
ZeRO-3 offloads the remainder to CPU memory
ZeRO-1 and ZeRO-2 cannot shard past 64 GPUs
Whatever stays replicated becomes the floor. ZeRO-1 keeps bf16 weights + bf16 grads = 4 bytes on every GPU; ZeRO-2 keeps just the weights = 2. ZeRO-3 replicates nothing, so its per-GPU cost is 16/N with no asymptote — paid for with a ~1.5× communication increase from per-layer parameter all-gathers.

19.6 · Context parallelism: split the sequence

Every axis so far leaves one thing whole: each sequence. DP splits the batch into sequences, TP splits each layer's matrices, PP splits the stack, and every GPU still processes all T tokens of the sequences it holds. At T = 8192 that is fine. At T = 131,072 it is not: Chapter 10 §10.7 counted 98,338 saved elements per token per layer for an 8B model, which at 128k tokens is 25.8 GB per layer in bf16, and attention's FLOPs per sequence grow as T². Long-context training needs a fourth cut, along the sequence axis. That is context parallelism (CP), and it is how every model with a 128k-plus window is trained.

Most of a transformer does not care. The norms, the MLP, the projections and the residual adds are all per token: give each of cp ranks a contiguous slice of T/cp tokens and they run with no communication at all, exactly like data parallelism over tokens. Only attention mixes positions: each query needs the keys and values of every earlier token, and some of those live on other ranks. So context parallelism is entirely a question of how attention gets the K and V it is missing. There are three answers in use.

Ring attention: pass K and V around

Arrange the cp ranks in a ring. Each starts with its own Q, K and V blocks. In each of cp − 1 steps, every rank computes attention of its local queries against the K, V block it currently holds, accumulating with the online softmax of Chapter 17 (the same running max and sum that let FlashAttention process K in tiles), and simultaneously sends that block to the next rank and receives one from the previous. After cp − 1 steps each rank has seen every block, and its output is exact. Per rank per layer, forward:

ring bytes = (cp − 1) · 2 · Tcp · nkv · dhead · bytes K and V blocks, cp − 1 hops. Tends to 2·T·n_kv·d_head·bytes: it does NOT shrink as cp grows

The point of the ring is overlap: the transfer of the next block runs while the current block is being computed, so if the compute takes longer, the communication is free. A ring step with block size c = T/cp computes 4·c²·H·dhead FLOPs (scores and weighted sum) and moves 2·c·nkv·dhead·2 bytes. Setting compute time ≥ transfer time gives the condition (tfs.parallel.ring_overlap_min_block):

c ≥ FBW · nkvH F = peak FLOP/s, BW = link bytes/s · with n_kv = H this is Liu et al.'s c ≥ F/B 
H100 (989 TFLOP/s bf16), GQA with H/n_kv = 4
                         full mask    causal, unbalanced
  InfiniBand  50 GB/s      4,945          9,890     tokens per rank
  NVLink     450 GB/s        549          1,099     (one direction)
  MHA (n_kv = H), IB      19,780                    = F/B, the Ring Attention paper's bound

So on InfiniBand a rank needs about 5,000 tokens of its own before the ring hides its traffic, and with GQA it needs four times fewer than MHA, because only K and V travel. The causal mask complicates it: in a contiguous split, rank 0 owns the first T/cp tokens, whose queries see almost nothing, and the last rank owns queries that see everything. Counted in blocks of the lower triangle with cp = 4 and 8 chunks, contiguous ownership gives the four ranks 3, 7, 11 and 15 blocks of work: the slowest does 5× the fastest. The fix (Llama 3's, also called "zigzag"): cut the sequence into 2·cp chunks and give rank i chunks i and 2·cp − 1 − i, one early and one late. Each rank then owns 9, 9, 9, 9 blocks (test_zigzag_balances_causal_work).

All-gather CP: what Llama 3 actually did

Llama 3's 405B long-context stage used a simpler variant: all-gather the full K and V across the CP group, then compute local-query attention against all of it, with the 2·cp chunk balancing above. The bytes per rank are the same as the ring (an all-gather delivers (cp − 1)/cp of the result to each rank); what it gives up is overlap, and what it gains is simplicity and support for arbitrary attention masks (document masks, for instance). It works because with GQA the K, V being gathered are small: for 405B (8 KV heads of 128), a 131,072-token sequence at CP = 16 gathers about 0.5 GB per layer per rank, while each rank's local block is 8,192 tokens.

DeepSpeed-Ulysses: swap the sharded axis

Ulysses takes the opposite approach. Before attention, one all-to-all turns sequence-sharded q, k, v (each rank: T/cp tokens, all heads) into head-sharded q, k, v (each rank: all T tokens, H/cp heads). Attention is then completely local, since heads never interact. A second all-to-all turns the output back to sequence-sharded for the MLP. An all-to-all sends (cp − 1)/cp of each rank's local tensor, and that tensor is only T/cp tokens long:

Ulysses bytes = cp − 1cp · Tcp · (2H + 2nkv) · dhead · bytes q and the output at H heads, k and v at n_kv heads · FALLS as 1/cp
Worked example — ring or Ulysses for an 8B model at 128k?

Llama-3-8B attention shape: H = 32, nkv = 8, dhead = 128, T = 131,072, bf16. Bytes sent per rank per layer, forward (tfs.parallel):

  cp        ring       Ulysses     Ulysses / ring
   2      268 MB       671 MB         2.50
   4      403 MB       503 MB         1.25
   8      470 MB       294 MB         0.63
  16      503 MB       157 MB         0.31

The ratio is exactly (2H + 2nkv) / (2·nkv·cp) = 80 / (16·cp) = 5/cp. Ulysses moves fewer bytes once cp > 5 here. With MHA (nkv = H) the ratio is 2/cp and Ulysses wins from cp = 3. GQA tilts the balance toward the ring, because the ring only ever moves the small K and V.

But bytes are not the whole decision. Ulysses' all-to-alls sit on the critical path (nothing to overlap them with), and cp cannot exceed the number of KV heads without replicating them: here cp ≤ 8. The ring overlaps with compute but needs blocks of thousands of tokens on slow links.

The two compose: run Ulysses inside a node (fast all-to-all, degree up to the KV-head count) and a ring across nodes, which is what "unified" sequence parallelism implementations do. And CP composes with the other axes simply. For every per-token layer, a CP group behaves like a data-parallel group over tokens: its ranks hold identical weights and their gradients must be summed, so frameworks fold the CP group into the gradient reduction alongside DP. Activations per rank fall by cp (each rank holds T/cp tokens), which is the whole reason to do it.

19.7 · Activation memory, exactly

Section 19.1 counted the 16 bytes per parameter that every parallelism axis shards. Activations are the other half of the bill, and Korthikanti et al. (2022) give the per-layer formula that every Megatron-style system plans with. For a GPT layer (LayerNorm, GeLU MLP of width 4h, dropout, attention scores materialised), 2-byte activations and 1-byte dropout masks, with s = sequence length, b = micro-batch, h = hidden size, a = heads:

activation bytes per layer = s·b·h · (34 + 5·a·s / h) 34 = 11 (attention block) + 19 (MLP) + 4 (two norms), per s·b·h · the 5as/h term is the a·s² attention scores, softmax and dropout mask

Then each technique removes a specific piece (tfs.memory.korthikanti_bytes_per_layer):

Worked example — GPT-3 175B: s = 2048, b = 1, h = 12288, a = 96, 96 layers 
                                        per layer      all 96 layers
no parallelism       sbh(34 + 5as/h)     2.87 GB         275 GB
TP = 8               sbh(10 + 24/t + 5as/(ht))           55.6 GB     <- 10 sbh is NOT split by TP
TP = 8 + seq. par.   sbh(34 + 5as/h)/t                   34.4 GB
  + selective recomp.  sbh·34/t                          10.3 GB     <- re-run only the attention core
full recomputation   2sbh (just the layer input)          4.83 GB

Two lessons. The 10·sbh term is the norms and dropouts, which tensor parallelism leaves replicated on every rank. Sequence parallelism (a different thing from §19.6's context parallelism) shards those regions along the sequence axis and replaces each all-reduce with a reduce-scatter plus an all-gather, which moves the same bytes. And the 5as/h term is 80 of the 114 units here: the attention scores. Selective recomputation drops exactly that term and re-runs the attention core in backward; FlashAttention (Chapter 17) never stores it in the first place, which is why Chapter 10's count for a modern block has no s² term at all. Korthikanti et al. report a 5× activation reduction with selective recompute, for a few percent of extra FLOPs instead of the 30–40% of full recomputation.

Two more facts for planning. With 1F1B pipelining the first stage holds p micro-batches in flight, so total activation memory on it is s·b·h·L/t · (34 + 5as/h) regardless of p: the first stage needs as much as if it held the whole model's activations for one micro-batch. And for a Llama-style block the per-token count is Chapter 10's 24·C elements (48 bytes per C in bf16) rather than 34, because SwiGLU has three d_ff-wide tensors and there is no dropout.

19.8 · FP8 training at scale

Chapter 12 §12.6 explains the formats and the scaling recipes. At cluster scale three further things matter.

The speedup is less than 2×. An H100 peaks at 989 dense TFLOP/s in bf16 and 1,979 in fp8. Only the large matmuls run in fp8, though. DeepSeek-V3, the most detailed public account, runs the forward, activation-gradient and weight-gradient GEMMs in fp8 but keeps the embedding, the output head, the MoE gating, the norms and attention in bf16 or fp32, keeps master weights and optimizer state in higher precision, and adds work of its own: computing a scale for every 1×128 activation tile and 128×128 weight block, and promoting the tensor cores' partial sums to fp32 every 128 elements. Whatever is not a big GEMM, and whatever is communication, does not get faster.

Ask which peak an MFU is quoted against. Meta reports pretraining Llama 4 Behemoth in FP8 on 32K GPUs at 390 TFLOP/s per GPU. Against the fp8 peak that is 19.7% MFU; against the bf16 peak it is 39.4%, about where Llama 3 405B's bf16 run sat (380–430 TFLOP/s, 38–43%). Different models (Behemoth is an MoE), so not a controlled comparison, but it shows how an FP8 run can do more useful work per GPU while quoting a lower MFU.

Communication can use the narrow format too. The bytes of §19.2–19.4 are proportional to element size, so sending fp8 halves them. DeepSeek-V3 dispatches MoE tokens in fp8 (Chapter 20 §20.6), and FSDP implementations can all-gather fp8 weights. Gradient reductions generally stay in bf16 or fp32, for Chapter 10 §10.10's reason: sums need precision.

Validate on loss, not on op accuracy. DeepSeek's check was to train smaller models in both precisions for about a trillion tokens and compare: the fp8 run's loss stayed within 0.25% of bf16 (relative). An fp8 recipe that is fine at 1B parameters and 100B tokens can still fail at 100B parameters and 10T tokens, because outliers grow with scale and training length.

19.9 · Fault tolerance at thousands of GPUs

Big clusters fail constantly, and the arithmetic of what to do about it is short. Llama 3 reported 466 job interruptions in a 54-day window of 405B pretraining on 16,384 GPUs: 47 planned and 419 unexpected, of which about 78% were attributed to confirmed or suspected hardware issues, with GPU problems the largest single category (58.7%). Despite that the team reported more than 90% effective training time, with significant manual intervention needed only three times.

Worked example — how often should a 16,384-GPU run checkpoint?
1
Mean time between failures of the job: 54 days × 24 h ÷ 419 = 3.09 hours. Failures add up across devices: if every one of them were a single GPU failing independently, each GPU would fail once in about 5.8 years. Multiply a rare event by 16,384 and it happens every three hours.
2
The trade. Checkpointing every τ seconds costs δ seconds per checkpoint (the time training is blocked), so δ/τ of the run. A failure loses on average τ/2 of work since the last checkpoint, plus the restart time R. To first order:
waste(τ) = δ/τ + (τ/2 + R)/MTBF      best at   τ* = √(2 · δ · MTBF) Young (1974) and Daly (2006)

The lesson is in the shape of the formula. Waste at the optimum is about √(2δ/MTBF): to halve it you must cut δ by 4. That is why large runs make checkpoints asynchronous (copy the state to host memory in seconds, write it to storage in the background while training continues) and why restart time R gets as much engineering as δ. A 405B checkpoint is 405 B × 16 bytes = 6.48 TB of weights and optimizer state, so "just write it faster" only goes so far.

Beyond checkpoints, the operational toolkit is: health checks and burn-in to keep bad GPUs out of the job; fast detection (collective timeouts, watchdogs that notice a rank has stopped making progress); straggler detection, because in a synchronous job one slow GPU slows all of them; spare nodes so a failed node can be swapped without re-planning the mesh; and a restart path that reloads the sharded checkpoint in parallel. Every one of those is aimed at the R term or at the MTBF itself.

Check each row: 8 × 1 × 16 × 64 = 8,192, 8 × 1 × 16 × 128 = 16,384 and 8 × 16 × 16 × 8 = 16,384. Read them outward from the constraints. TP = 8 is one node. PP = 16 is set by 126 layers and the bubble. The batch is fixed at 16M tokens for optimization reasons, so going from 8K to 16K GPUs halves the batch per DP group, and MFU drops from 43% to 41%, which the paper attributes to that lower batch size per DP group. For the 128k stage the same 16M tokens is only 128 sequences, so CP = 16 takes 16 of DP's 128 ways and DP falls to 8.

The paper orders the axes [TP, CP, PP, DP] from innermost (fastest link) to outermost. That is this section's principle written as a list: the most frequent, least overlappable traffic gets the fastest wires.

HSDP: shard inside the node, replicate across nodes

ZeRO-3 / FSDP over all N GPUs makes every rank all-gather every parameter twice and reduce-scatter every gradient once per step, over the slowest link in the job. Hybrid sharding (HSDP, FSDP's HYBRID_SHARD) shards only within a group of s GPUs (a node, on NVLink) and runs a plain data-parallel all-reduce of each rank's gradient shard across the N/s groups. For a 7B model, bf16 parameters (14 GB), N = 64 as 8 nodes of 8 (tfs.parallel):

per GPU per step              intra-node (NVLink)   inter-node (InfiniBand)   state per GPU
DDP                                 —                    27.6 GB                 16 B/param
FSDP over 64                        —                    41.3 GB                 0.25 B/param
HSDP: shard 8, replicate 8       36.75 GB                 3.06 GB                 2 B/param

HSDP moves 13× less over the slow network than FSDP, in exchange for keeping 2 bytes per parameter (16 / 8) instead of 0.25. If the model's state fits at 16/s bytes per parameter, it is nearly always the better choice, and it is the default way FSDP is run across many nodes.

How to read any published training setup

Work outward from the constraints. TP is capped at the node size (8). CP is set by the sequence length: enough ranks that T/cp tokens of activations fit, and for a ring, blocks large enough to hide the transfer. PP is set by how many layers you have and how deep a bubble you tolerate: you need m ≳ 9(p − 1) microbatches, and microbatches come out of the batch you already fixed for optimization reasons. DP absorbs whatever GPUs remain. Almost every setup you will read is that calculation, and the surprising part is how little freedom there is.

An FP8 run reports 20% MFU and an otherwise similar bf16 run reports 40%. What should you check first?
Whether the FP8 run is diverging
Whether the FP8 run uses tensor parallelism
Which peak each MFU is quoted against: 390 TFLOP/s is 19.7% of the fp8 peak and 39.4% of the bf16 peak
Whether the FP8 run's batch is smaller
MFU is achieved FLOP/s over a peak, and FP8 doubles the peak. Compare achieved TFLOP/s (and tokens per second) first; the fp8 run may be doing more work per GPU.
A job fails every 3.1 hours on average and a checkpoint blocks training for 60 s. Roughly how often should it checkpoint?
About every 19 minutes: √(2 × 60 s × 3.09 h)
Every step
Every 3 hours, once per expected failure
Every 90 minutes, half the MTBF
Young–Daly: τ* = √(2δ·MTBF). That gives 19.3 minutes and about 10% waste before restart time. To halve the waste you must cut δ fourfold, which is why checkpoints are made asynchronous.
Why does HSDP usually beat FSDP across many nodes?
It uses less memory per GPU
Its per-layer parameter gathers stay on NVLink inside a node; only the gradient-shard all-reduce crosses the network, about 13× fewer inter-node bytes in the 7B example
It needs no gradient reduction at all
It avoids pipeline bubbles
Put the frequent traffic on the fast link. HSDP costs 2 bytes/param of state instead of 0.25 in that example, which is usually affordable; the 41.3 GB vs 3.06 GB of inter-node traffic per step is not.

19.2Simulate the pipeline bubblecode

Do not trust the formula — build the schedule and count idle slots, as the table in §19.5 does:

def bubble(p, m):
    busy, span = p * m, m + p - 1
    return 1 - busy / (span * p)

Confirm it matches (p-1)/(m+p-1) for p ∈ {2, 4, 8, 16}, m ∈ {1, …, 128}. Then extend it to interleaved 1F1B with v chunks per GPU and verify the idle fraction becomes (p-1)/(vm+p-1) (Narayanan et al.'s (p-1)/(vm) is the same bubble measured against ideal compute time). What does v cost you?

19.3Measure a real all-reducecode

Even on one machine you can measure the pattern. Use torch.distributed with the gloo backend and 4 CPU processes, time an all-reduce over buffers from 1 MB to 1 GB, and plot achieved bandwidth against size:

dist.init_process_group("gloo")
buf = torch.randn(n)
dist.barrier(); t0 = time.perf_counter()
dist.all_reduce(buf)
elapsed = time.perf_counter() - t0

Small buffers are latency-bound, large ones bandwidth-bound. Find the crossover. Then explain why DDP buckets gradients rather than all-reducing each parameter tensor separately — your plot is the argument.

19.4Implement tensor parallelism on one machinehard

Simulate TP=2 with plain tensors — no distributed runtime. Split an MLP column-wise then row-wise as in §19.4, and verify the result is bit-identical to the unsplit version:

W1_a, W1_b = W1.chunk(2, dim=1)     # column split
W2_a, W2_b = W2.chunk(2, dim=0)     # row split
y = act(x @ W1_a) @ W2_a + act(x @ W1_b) @ W2_b     # the "all-reduce"
assert torch.allclose(y, act(x @ W1) @ W2, atol=1e-5)

Then try it the wrong way round — row-split W1 — and explain precisely why it fails. Your explanation should name the nonlinearity.

19.6Simulate ring attention on one machinecode

Split a sequence of 1024 tokens into cp = 4 blocks. For each "rank", compute attention of its queries against the K, V blocks one at a time in ring order, merging partial results with the online-softmax update of Chapter 17 (keep a running max m and running sum l per query row). Check the result equals full causal attention to 1e-6, with both the contiguous and the zigzag assignment. Then count, for each rank, how many query-key blocks are fully masked and could be skipped.

What to look for

The merge is the same rescale-and-add FlashAttention does across key tiles: when a new block's max exceeds the running max, rescale the old sum and accumulator by exp(m_old − m_new). Fully masked blocks are the upper triangle; with contiguous ownership rank 0 skips almost everything and the last rank skips nothing, which is the imbalance zigzag removes (3, 7, 11, 15 blocks vs 9, 9, 9, 9 at 8 chunks).

19.7Price a checkpoint policythinking

A 70B model trains on 4,096 GPUs. Assume failures scale with GPU count from Llama 3's rate (419 unexpected in 54 days on 16,384 GPUs). State is 16 bytes per parameter; a synchronous checkpoint blocks for δ = 120 s, an asynchronous one for δ = 5 s. Restart takes 10 minutes.

  1. The job's MTBF.
  2. τ* and the expected waste for each δ.
  3. How much GPU time per day the asynchronous checkpoint saves.
Answers
MTBF = 3.09 h × 16,384 / 4,096 = 12.4 h = 44,540 s
δ = 120 s:  τ* = √(2·120·44,540) = 3,270 s (54 min)   waste = 120/3270 + (1635 + 600)/44540 = 8.7%
δ =   5 s:  τ* = √(2·5·44,540)   =   667 s (11 min)   waste =   5/667  + ( 334 + 600)/44540 = 2.8%
saving ≈ 5.8% of 4,096 GPUs × 24 h ≈ 5,700 GPU-hours per day

Note that with δ = 5 s the restart time is now the larger term: the next engineering target is R, not δ.
