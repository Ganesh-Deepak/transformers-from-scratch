19 · Distributed Training: DP, TP, PP, ZeRO

A 7B model needs 112 GB just for weights, gradients and optimizer state — before a single activation. An 80 GB GPU cannot hold it. Every frontier model is therefore split across hundreds or thousands of chips, and there are exactly four ways to cut it up. This chapter derives what each cut costs in bytes on the wire, which is the only thing that decides whether a strategy works.

The one idea in this chapter

There are only three things you can split: the batch (data parallel), each layer (tensor parallel), or the stack of layers (pipeline parallel). Each splits a different axis of the same computation, and each pays for it with a different communication pattern. Real systems combine all three, and the shape of the combination is dictated entirely by which links are fast.

19.1 · The memory problem, stated exactly

From Ch 12, mixed-precision Adam keeps five things per parameter:

  bf16 weights            2 bytes
  bf16 gradients          2
  fp32 master weights     4      \
  fp32 Adam m             4       |  the "optimizer state", 12 bytes
  fp32 Adam v             4      /
                        ----
  TOTAL                  16 bytes per parameter
The number that forces everything else

16 bytes/param, so a model of P parameters needs 16P bytes of persistent state:

  1B params  ->   16 GB      fits on one 80 GB GPU
  7B params  ->  112 GB      does NOT fit
 70B params  -> 1120 GB      needs 14+ GPUs for state alone
671B params  -> 10.7 TB      needs 134+ GPUs before activations

And activations are on top of this, growing with batch and sequence length. The weights alone are only 2 bytes/param — seven-eighths of the memory is training machinery, which is why inference fits on hardware training never could.

19.2 · Data parallel: split the batch

The simplest cut. Every GPU holds a complete copy of the model and processes a different slice of the batch. Gradients are averaged across GPUs before the optimizer step, so all replicas stay identical.

GPU 0: full model, samples  0..31   -> grads_0  \
GPU 1: full model, samples 32..63   -> grads_1   |  all-reduce (mean)
GPU 2: full model, samples 64..95   -> grads_2   |  -> identical grads everywhere
GPU 3: full model, samples 96..127  -> grads_3  /

The communication is one all-reduce of the gradient buffer per step. The standard implementation is a ring: reduce-scatter around the ring, then all-gather back. Each phase moves (N-1)/N of the buffer per GPU, so:

traffic per GPU = 2 · N − 1N · (gradient bytes)   ⟶   2 × as N grows 
N GPUs    multiplier    7B model, bf16 grads (14 GB)
     2       1.0000      14.0 GB moved per GPU per step
     4       1.5000      21.0
     8       1.7500      24.5
    64       1.9688      27.6
   512       1.9961      27.9   <- converged; does NOT keep growing
Why ring all-reduce scales at all

The multiplier approaches 2 and stops. Doubling from 64 to 512 GPUs adds 1% more traffic per GPU, not 8×. That constant-cost property is why data parallelism scales to thousands of chips, and why it is the default. Its problem is not communication — it is that every GPU still needs all 16 bytes/param. DP does nothing for memory.

Two implementation details that matter

Overlap. Gradients for layer L are ready as soon as layer L's backward finishes — you do not need to wait for the whole backward pass. PyTorch DDP buckets gradients and launches each all-reduce as its bucket fills, so most communication happens underneath the remaining backward compute. Done well, all-reduce is nearly free.

The batch-size ceiling. Scaling DP means growing the global batch. Past a few million tokens per batch, extra samples stop improving the gradient estimate — you are averaging noise that was already averaged. Data parallelism therefore has a hard limit set by optimization, not hardware, and that limit is why the other two axes are mandatory at scale.

19.3 · ZeRO: keep data parallelism, delete the redundancy

In DP, all N GPUs store identical optimizer state. That is N copies of the same numbers. ZeRO's observation: each GPU only needs the state for the parameters it is about to update. Shard it, and gather on demand.

StageShardsBytes/param per GPUExtra communication
DDPnothing16—
ZeRO-1optimizer state4 + 12/Nnone (adds an all-gather of weights, replaces part of the all-reduce)
ZeRO-2+ gradients2 + 14/Nnone
ZeRO-3 / FSDP+ parameters16/N~1.5× — parameters are gathered per layer, twice per step
 
bytes per parameter, on each GPU
  stage             N=1     N=8    N=64   N=512
  DDP             16.00   16.00   16.00   16.00
  ZeRO-1          16.00    5.50    4.19    4.02   -> floor of 4
  ZeRO-2          16.00    3.75    2.22    2.03   -> floor of 2
  ZeRO-3          16.00    2.00    0.25    0.03   -> floor of 0

7B model on 64 GPUs:   112 GB/GPU (DDP)  ->  1.8 GB/GPU (ZeRO-3)
Read the floors

ZeRO-1 and -2 have asymptotes — 4 and 2 bytes/param — because they keep a full copy of the weights (and, for stage 1, the gradients) on every GPU. Only ZeRO-3 has no floor: everything is sharded, so memory per GPU falls indefinitely with N. That is why FSDP (PyTorch's ZeRO-3) is the modern default, and why it costs ~50% more communication — parameters must be all-gathered just before each layer runs and freed straight after.

ZeRO-3's trick is just-in-time materialisation: for each layer, all-gather its parameters, compute, then discard the shards you do not own. The full model never exists on any single GPU at any moment, yet the arithmetic is bit-identical to DDP. The cost is that this gather sits on the critical path, so it must be prefetched one layer ahead to stay hidden.

19.4 · Tensor parallel: split each layer

When a single layer is too large, split the matrices themselves. Megatron-LM's arrangement is built to minimise synchronisation, and the reason it works is worth seeing:

Derivation — why the MLP needs only one all-reduce
1
Split the first matrix by columns. With W_1 = [W_1^{(a)}, W_1^{(b)}], each GPU computes its own column block: 
GPU a:  h_a = act(x @ W1_a)     x is REPLICATED, h_a is a column slice
GPU b:  h_b = act(x @ W1_b)
No communication — and because the activation is elementwise, it applies independently per column. This is why the split must be by columns: a row split would need the full pre-activation summed first.
2
Split the second matrix by rows, matching: 
GPU a:  y_a = h_a @ W2_a        each y is a PARTIAL SUM of the true output
GPU b:  y_b = h_b @ W2_b
3
One all-reduce completes it. y = y_a + y_b. Total: one collective for the whole MLP, and the intermediate h — the widest tensor in the block — never leaves its GPU.
4
Attention splits the same way, along heads. Each GPU owns whole heads, computes their attention independently (heads never interact until the output projection), and the output projection is row-split like W_2. One all-reduce per attention block.

So a transformer block costs 2 all-reduces forward, 2 backward. But these fire in the middle of every layer and cannot be overlapped — everything stalls until they finish:

activation tensor, B=8, T=2048, d=4096, bf16   =   134.2 MB
  TP=2:  0.54 GB per layer per step
  TP=4:  0.81 GB
  TP=8:  0.94 GB      x 80 layers = ~75 GB per step, all on the critical path
TP does not leave the node

That traffic is why tensor parallelism is confined to GPUs inside one server, connected by NVLink (~900 GB/s on H100) rather than InfiniBand (~50 GB/s per link). Cross the node boundary with TP and the 18× slower link turns a synchronous, non-overlappable collective into the dominant cost of the whole run. TP degree is therefore almost always ≤ 8 — the number of GPUs on one board. This is a networking fact masquerading as a hyperparameter.

19.5 · Pipeline parallel: split the stack

Give each GPU a contiguous group of layers. Activations flow forward, gradients flow back, and only the boundary activations cross the wire — tiny compared with TP, and it works fine over slow links.

The problem is idleness. With one batch in flight, GPU 3 waits for 0, 1 and 2 before it has anything to do:

naive, 4 stages, 1 batch          (F = forward, B = backward, . = IDLE)
  GPU0  F . . . B . . .
  GPU1  . F . . . B . .
  GPU2  . . F . . . B .
  GPU3  . . . F B . . .
                                  -> 75% of the machine is idle

The fix is to split the batch into microbatches and keep several in flight. With p stages and m microbatches:

bubble fraction = p − 1m + p − 1 
simulated by counting idle slots directly, vs the closed form
   p    m   simulated   (p-1)/(m+p-1)
   4    1     0.7500       0.7500
   4    8     0.2727       0.2727
   4   32     0.0857       0.0857
   8    8     0.4667       0.4667
   8   32     0.1795       0.1795
   8  128     0.0519       0.0519
The rule of thumb, and where it comes from

To keep the bubble under ~10% you need m \gtrsim 9(p-1) — roughly ten microbatches per stage. That is the entire design pressure behind 1F1B scheduling (same bubble, far less activation memory, because a microbatch's activations are freed as soon as its backward runs) and interleaved 1F1B, which gives each GPU v non-contiguous chunks of layers and cuts the bubble to (p-1)/(vm) at the cost of v\times more boundary messages.

19.6 · Putting it together: the 4-D mesh

Real runs use every axis at once, and the assignment follows one principle: match each parallelism's communication pattern to the link that can carry it.

a typical 1024-GPU layout
  TP = 8      within each node        (NVLink, 900 GB/s)
  PP = 16     across nodes            (InfiniBand, small messages)
  DP = 8      the remaining axis      (8 x 16 x 8 = 1024)
How to read any published training setup

Work outward from the constraints. TP is capped at the node size (8). PP is set by how many layers you have and how deep a bubble you tolerate — you need m \gtrsim 9(p-1) microbatches, and microbatches come out of the batch you already fixed for optimization reasons. DP absorbs whatever GPUs remain. Almost every setup you will read is that calculation, and the surprising part is how little freedom there is.

Activation checkpointing, the fifth lever

None of the above touches activations, which grow with B \times T \times d \times \text{layers} and often dominate. Gradient checkpointing stores only layer boundaries and recomputes the interior during backward: memory drops from O(L) to O(\sqrt{L}) with an optimal schedule, for roughly 30% more compute. Since Ch 14 established that most of training is memory-bound anyway, trading FLOPs for bytes is usually a win — the recompute frequently costs less wall-clock time than it saves.

Why is tensor parallelism almost never used across more than 8 GPUs?
Attention heads cannot be split more than 8 ways
The all-reduce becomes numerically unstable
Beyond 8 GPUs the matrices become too small to be efficient
TP's all-reduces sit mid-layer and cannot be overlapped, so they must run on NVLink (~900 GB/s) rather than inter-node InfiniBand (~50 GB/s)
It is a networking constraint. Two all-reduces per layer per direction, each moving a fraction of a ~134 MB activation, with the whole layer stalled until they finish. 8 is the number of GPUs sharing an NVLink domain in one server. The matrices do also get small (a §14.2 concern), but the link speed binds first.
You have 8 pipeline stages and use 8 microbatches. What fraction of the machine is idle?
0% — 8 microbatches exactly fill 8 stages
~47%: (p−1)/(m+p−1) = 7/15
~12.5%, one stage's worth
~25%
7/15 = 0.4667, confirmed by simulation. Filling and draining the pipeline costs p−1 slots at each end regardless of m. You need roughly 10 microbatches per stage — here about 72 — to push the bubble under 10%.
ZeRO-1 and ZeRO-2 flatten out at 4 and 2 bytes/param, but ZeRO-3 keeps falling. Why?
ZeRO-3 uses a more efficient compression scheme
ZeRO-3 shards the parameters too, so nothing is replicated; stages 1 and 2 still keep a full weight copy (and stage 1 a full gradient copy) on every GPU
ZeRO-3 offloads the remainder to CPU memory
ZeRO-1 and ZeRO-2 cannot shard past 64 GPUs
Whatever stays replicated becomes the floor. ZeRO-1 keeps bf16 weights + bf16 grads = 4 bytes on every GPU; ZeRO-2 keeps just the weights = 2. ZeRO-3 replicates nothing, so its per-GPU cost is 16/N with no asymptote — paid for with a ~1.5× communication increase from per-layer parameter all-gathers.

19.7 · Exercises

19.1Plan a 70B run on 256 GPUsessential

Given 256×H100 (80 GB each, 8 per node), a 70B model with 80 layers, and a global batch of 4M tokens at sequence length 8192, work out a full parallelism plan. Justify each number:

  1. Total bytes of persistent state, and how many GPUs that alone requires.
  2. TP degree — and why it cannot exceed 8.
  3. PP degree, and the microbatch count needed to hold the bubble under 10%.
  4. The resulting DP degree, checked against 256.
  5. Whether activations fit, with and without checkpointing.

Then compare with the parallelism section of the Llama 3 paper. Where you differ, work out which constraint they weighted differently — there is usually one.

19.2Simulate the pipeline bubblecode

Do not trust the formula — build the schedule and count idle slots, as the table in §19.5 does:

def bubble(p, m):
    busy, span = p * m, m + p - 1
    return 1 - busy / (span * p)

Confirm it matches (p-1)/(m+p-1) for p \in \{2,4,8,16\}, m \in \{1,\ldots,128\}. Then extend it to interleaved 1F1B with v chunks per GPU and verify the bubble becomes (p-1)/(vm). What does v cost you?

19.3Measure a real all-reducecode

Even on one machine you can measure the pattern. Use torch.distributed with the gloo backend and 4 CPU processes, time an all-reduce over buffers from 1 MB to 1 GB, and plot achieved bandwidth against size:

dist.init_process_group("gloo")
buf = torch.randn(n)
dist.barrier(); t0 = time.perf_counter()
dist.all_reduce(buf)
elapsed = time.perf_counter() - t0

Small buffers are latency-bound, large ones bandwidth-bound. Find the crossover. Then explain why DDP buckets gradients rather than all-reducing each parameter tensor separately — your plot is the argument.

19.4Implement tensor parallelism on one machinehard

Simulate TP=2 with plain tensors — no distributed runtime. Split an MLP column-wise then row-wise as in §19.4, and verify the result is bit-identical to the unsplit version:

W1_a, W1_b = W1.chunk(2, dim=1)     # column split
W2_a, W2_b = W2.chunk(2, dim=0)     # row split
y = act(x @ W1_a) @ W2_a + act(x @ W1_b) @ W2_b     # the "all-reduce"
assert torch.allclose(y, act(x @ W1) @ W2, atol=1e-5)

Then try it the wrong way round — row-split W_1 — and explain precisely why it fails. Your explanation should name the nonlinearity.
