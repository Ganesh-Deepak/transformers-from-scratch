15.1 · PagedAttention — virtual memory for the KV cache

The naive approach pre-allocates a contiguous buffer of max_length per sequence. If a user's generation stops at 200 tokens out of a 4096 reservation, 95% of that memory is wasted. vLLM's authors measured real systems wasting 60–80% of their KV memory to this.

The fix, borrowed wholesale from operating systems

Split the cache into fixed-size blocks (typically 16 tokens). A sequence gets a block table mapping logical positions to physical blocks, which need not be contiguous. Allocate blocks on demand as generation proceeds. This is paged virtual memory, applied to attention — hence the name.

Contiguous allocationPagedAttention
Internal fragmentationup to max_len − actual_len< 1 block (≈16 tokens)
External fragmentationsignificantnone — all blocks are the same size
Memory utilisation20–40%> 90%
Sharing a common prefiximpossiblefree — just point at the same blocks

That last row is the sleeper feature. Copy-on-write block sharing means parallel samples from one prompt, or a thousand users hitting the same system prompt, share cache blocks physically. Combined with prefix caching (persist those blocks across requests), a long shared system prompt becomes nearly free after the first request — often the single biggest latency win available to an application developer.

15.2 · Continuous batching

Static batching waits for every sequence in a batch to finish. If one user asks for 20 tokens and another for 2000, the short request's GPU slot idles for the whole 2000 steps.

Static batching (bad):
  seq A: ####----------------------------   done at step 4, slot wasted for 28
  seq B: ################################
  seq C: ########------------------------
         ^ batch cannot retire until B finishes

Continuous batching (good):
  seq A: ####
  seq D:     ############
  seq B: ################################
  seq C: ########
  seq E:         ####################
         ^ finished sequences are evicted and replaced every single step

Because the model weights are read once per step regardless of batch composition (Chapter 12), keeping the batch full is nearly pure profit. Reported throughput gains over static batching are typically 2–4×, sometimes over 20× on skewed length distributions. Every serious server — vLLM, TensorRT-LLM, SGLang, TGI — does this.

15.3 · Speculative decoding

The cleverest idea in inference. It exploits the fact from Chapter 12 that decode is memory-bound: verifying k tokens costs almost exactly the same as generating 1, because either way you read all the weights once.

The algorithm
  1. A small, fast draft model proposes k tokens autoregressively (cheap).
  2. The big target model scores all k in one forward pass (one weight read).
  3. A rejection-sampling rule accepts the longest prefix that's consistent with the target's own distribution, and resamples at the first disagreement.
  4. You advance by 1 to k+1 tokens for the price of roughly one target forward pass.
The guarantee that makes it usable

The acceptance rule (Leviathan et al. 2023; Chen et al. 2023) is constructed so the output distribution is provably identical to sampling from the target model alone. Accept draft token x with probability min(1, ptarget(x) / pdraft(x)); on rejection, sample from the normalised residual max(0, ptarget − pdraft). This is not an approximation with a quality knob — it is exact. That's why it can be turned on by default.

Draft sourceTypical speedupNote
Small model of the same family (e.g. 1B drafting for 70B)2–3×needs a matching tokenizer
Medusa / EAGLE — extra heads on the target itself2–4×no separate model to host
n-gram / prompt lookup1.5–3× on summarisation, RAG, editingzero extra parameters; drafts by copying from the prompt
Multi-token prediction (trained in, e.g. DeepSeek-V3)~1.8×the model learns to draft for itself

Speedup depends entirely on the acceptance rate. Predictable text (code, structured output, summarising a provided document) accepts most drafts; creative text accepts few. And note the trade: at large batch sizes you're already compute-bound, so the free verification capacity disappears and speculative decoding can be a net loss. It is a low-batch / low-latency optimisation.

Why quantizing weights speeds up decode

Because decode is bandwidth-bound. Int4 weights are 4× fewer bytes to read from HBM, so you get roughly 4× the token rate — even though the arithmetic is dequantized back to fp16 before the matmul. You're not saving FLOPs, you're saving traffic. This also means quantization helps decode far more than prefill.

Evaluate quantized models on your actual task

Perplexity barely moves under 4-bit quantization, which has led to a lot of "lossless" claims. Multi-step reasoning, long-context retrieval, and code generation degrade noticeably earlier than perplexity suggests — the errors compound across steps. Always test the thing you actually care about, not a proxy.

15.5 · Prefill–decode disaggregation

Chapter 12 showed prefill is compute-bound and decode is memory-bound. Running them on the same GPU in the same batch means each interferes with the other — a long prefill stalls every decode in flight ("head-of-line blocking"), which shows up as inter-token latency jitter.

The 2024–2026 answer is to run them on separate GPU pools: prefill workers produce the KV cache and transfer it over the interconnect to decode workers. Prefill nodes optimise for throughput, decode nodes for bandwidth and batch size. Systems like DistServe, Splitwise, Mooncake and current vLLM/SGLang builds support this, and it's now standard in large deployments. An intermediate option — chunked prefill, which slices long prompts into pieces interleaved with decode steps — gets much of the benefit on a single pool.

Why does speculative decoding give a speedup at all, given it does more total work?
The draft model is more accurate
Decode is memory-bound, so verifying k tokens in one pass costs about the same as generating 1 — the extra FLOPs are free capacity
It skips layers of the target model
It reduces the KV cache
Free FLOPs in a bandwidth-bound regime. One target forward pass reads all the weights whether you score 1 token or 8. Speculative decoding converts idle arithmetic capacity into tokens. This also predicts its failure mode: at large batch sizes you're compute-bound already, the capacity isn't free, and the technique stops helping.
Your service has 1000 users sharing a 2000-token system prompt. Biggest single win?
Speculative decoding
Int4 weight quantization

Prefix caching. Without it you recompute 2000 tokens of prefill 1000 times. With it, that cost is paid once and every subsequent request starts at token 2001 — often a 5–10× reduction in time-to-first-token and a large drop in prefill compute. The others help too, but none eliminates a redundancy this large.
A 70B model quantized to int4 runs ~4× faster in decode. Why?
Weight bytes read from HBM drop 4×, and decode is bandwidth-bound
Int4 arithmetic is 4× faster than bf16
The KV cache shrinks 4×
Fewer layers are executed
Bandwidth. 140 GB → 35 GB per forward pass. The math is usually still done in fp16 after dequantization, so arithmetic throughput is unchanged, and weight quantization does nothing to the KV cache (that's quantized separately). Prefill, being compute-bound, speeds up far less.

15.7 · Exercises

15.1Implement speculative decodinghard

Using two models from the same family (e.g. GPT-2 small as draft, GPT-2 large as target), implement speculative decoding with the exact acceptance rule. Then verify the guarantee empirically: generate 2000 tokens with (a) plain sampling from the target and (b) speculative decoding, both at T=1.0, and compare the resulting unigram distributions with a chi-squared test.

Core loop
def speculative_step(target, draft, ids, k=4):
    # 1. draft k tokens autoregressively
    draft_ids, q_probs = [], []
    cur = ids
    for _ in range(k):
        q = draft(cur)[:, -1].softmax(-1)
        t = torch.multinomial(q, 1)
        draft_ids.append(t); q_probs.append(q.gather(-1, t))
        cur = torch.cat([cur, t], dim=1)

    # 2. ONE target pass scores all k+1 positions
    p_all = target(cur)[:, -(k+1):].softmax(-1)

    # 3. accept/reject left to right
    n = 0
    for i in range(k):
        p_i = p_all[:, i].gather(-1, draft_ids[i])
        if torch.rand(1) < min(1.0, (p_i / q_probs[i]).item()):
            n += 1
        else:
            # resample from the normalised residual
            resid = (p_all[:, i] - draft(...)[i]).clamp(min=0)
            return torch.cat([ids, *draft_ids[:n],
                              torch.multinomial(resid / resid.sum(), 1)], dim=1)
    # all k accepted → bonus token from the target's (k+1)-th distribution
    return torch.cat([ids, *draft_ids, torch.multinomial(p_all[:, k], 1)], dim=1)

Report your acceptance rate. On natural text with a same-family draft, expect 60–80%; on code, higher. The chi-squared test should show no significant difference — that's the distributional guarantee, verified rather than assumed.

15.2Simulate PagedAttentioncode

Write a block allocator: BlockManager(total_blocks, block_size) with allocate(seq_id, n_tokens), append(seq_id), free(seq_id), and fork(parent, child) (copy-on-write). Simulate 1000 requests with lengths drawn from a lognormal distribution and compare memory utilisation against contiguous max_len allocation.

Expected result

With lognormal lengths (mean 300, max 4096) the contiguous scheme wastes 70–90% of its allocation. Paged wastes under 3%. That ratio is why vLLM's throughput numbers looked implausible when it launched — the gain was almost entirely from not wasting memory, not from faster kernels.

15.3Benchmark a real serverapplied

Serve any small model with vLLM. Measure time-to-first-token and inter-token latency at concurrency 1, 4, 16, 64. Plot throughput (total tok/s) and per-user latency against concurrency.

What the curves show

Total throughput rises steeply then saturates; per-user latency is flat then degrades. The knee is where you stop being memory-bound and start being compute-bound (Chapter 12) — and it is the operating point you should actually deploy at. Running below it wastes GPU; running above it breaks your latency SLA. Almost nobody measures this, and almost everyone should.
