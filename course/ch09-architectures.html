The whole chapter in five sentences

One block, three arrangements: bidirectional (encoder-only), causal (decoder-only), or an encoder whose output a causal decoder cross-attends to. Decoder-only won because a causal mask gives a training signal at every position and every task can be phrased as continuing a text. A forward pass is a fixed sequence of about twenty shape changes, from (B, T) IDs to (B, T, V) logits, and you should be able to recite it. The parameter count follows from the config, about 12·L·d² plus the embeddings, and the FLOPs follow from the parameter count. That is also how an encoder-decoder can have twice the parameters of a decoder at the same cost. Retrieval still runs on encoder-shaped models, trained with a contrastive loss so that matching texts end up close together.

Why decoder-only won

Training efficiency. With a causal mask, a single forward pass over a sequence of length T produces T supervised predictions, because every position predicts the one after it. BERT-style masking only supervises the ~15% of positions that were masked. So a decoder gets roughly 6× more learning signal per FLOP. Add the fact that any task can be phrased as continuing a text, and there was little reason left for a second architecture.

Encoder-only: BERT

# Training objective: mask 15% of tokens, predict them from BOTH sides.
"the cat [MASK] on the mat"  →  predict "sat"
# No causal mask — position 2 sees positions 0..5 freely.
# Cannot generate: there is no notion of "next".

Encoders are still the right tool for embeddings and reranking, where you want a rich bidirectional representation of a fixed text and do not need to generate anything. Modern retrieval systems still run BERT-family encoders.

Decoder-only: GPT and everything after it

# Training objective: predict token t+1 from tokens 0..t, at EVERY position at once.
input:  [the, cat, sat, on,  the]
target: [cat, sat, on,  the, mat]
# One forward pass = 5 predictions. The causal mask makes this valid.

Encoder–decoder: T5

# Encoder reads the source bidirectionally.
# Decoder generates causally, and CROSS-ATTENDS to the encoder output:
#     Q from decoder  (T_dec, d)
#     K, V from encoder output  (T_enc, d)
#     → output (T_dec, d)   — decoder length preserved, any encoder length

Encoder-decoders still lead where the input and output are truly different modalities or languages. Whisper (audio to text) is the clearest current example.

9.2 · The full shape trace

This is the main part of the chapter. A decoder-only model with B=2, T=6, V=32000, d_model=512, n_head=8, d_head=64, d_ff=1376, n_layer=6. Step through every tensor.

The off-by-one that everyone writes at least once 
logits  = model(ids)               # (B, T, V)
loss = F.cross_entropy(logits.reshape(-1, V), ids.reshape(-1))   # ← WRONG

This asks the model to predict the token it was just given, a task it solves perfectly by copying, so the loss goes to ~0 while the model learns nothing. You have to shift:

loss = F.cross_entropy(
    logits[:, :-1, :].reshape(-1, V),      # predictions for positions 0..T-2
    ids[:, 1:].reshape(-1))                # targets are positions 1..T-1

Diagnostic: if your training loss drops toward ln(1)≈0 unreasonably fast, or below the entropy of your data, you have this bug. Some Hugging Face models shift internally when you pass labels=, so check before doing it yourself, or you will shift twice.

9.3 · The complete model, in one file

import torch, torch.nn as nn, torch.nn.functional as F
from dataclasses import dataclass

@dataclass
class Config:
    vocab_size: int = 32000
    d_model:    int = 512
    n_layer:    int = 6
    n_head:     int = 8
    d_ff:       int = 1376
    max_T:      int = 1024
    rope_base:  float = 10000.0

class GPT(nn.Module):
    def __init__(self, cfg):
        super().__init__()
        self.cfg   = cfg
        self.embed = nn.Embedding(cfg.vocab_size, cfg.d_model)
        self.blocks = nn.ModuleList([Block(cfg) for _ in range(cfg.n_layer)])
        self.norm  = RMSNorm(cfg.d_model)
        self.head  = nn.Linear(cfg.d_model, cfg.vocab_size, bias=False)

        cos, sin = build_rope_cache(cfg.max_T, cfg.d_model // cfg.n_head, cfg.rope_base)
        self.register_buffer("cos", cos, persistent=False)
        self.register_buffer("sin", sin, persistent=False)

        self.apply(self._init)

    def _init(self, m):
        if isinstance(m, nn.Linear):
            nn.init.normal_(m.weight, std=0.02)
            if m.bias is not None: nn.init.zeros_(m.bias)
        elif isinstance(m, nn.Embedding):
            nn.init.normal_(m.weight, std=0.02)

    def forward(self, ids, targets=None):
        B, T = ids.shape                                    # (B, T)
        x = self.embed(ids)                                 # (B, T, C)
        cos, sin = self.cos[:T], self.sin[:T]

        for blk in self.blocks:
            x = blk(x, cos, sin)                            # (B, T, C)

        x = self.norm(x)                                    # (B, T, C)
        logits = self.head(x)                               # (B, T, V)

        loss = None
        if targets is not None:
            loss = F.cross_entropy(
                logits[:, :-1].reshape(-1, logits.size(-1)),
                targets[:, 1:].reshape(-1),
                ignore_index=-100)
        return logits, loss
Why std=0.02?

GPT-2 chose it and everyone kept it. The idea is that activations should have roughly unit variance after each layer, which needs std ≈ 1/√d_model (0.044 at d_model=512). GPT-2 used a flat 0.02, plus an extra 1/√(2·n_layer) scaling on the residual output projections (W_o and the MLP down projection), to stop the residual stream's variance growing linearly with depth. That second detail matters and is often left out; see Exercise 9.3.

The attn @ v matmul (and the scores that produced it)

RMSNorm
Only in attention. The MLP, both norms, RoPE and the LM head all work on each position separately: you could run them on a single token in isolation and get the same answer. Attention is the only operation in a transformer that mixes positions. Remember that, because it means every claim about how information flows through the model is a claim about attention.
Which tensor in the trace is the largest, and why does that matter?
The residual stream, because it appears at every layer
The attention scores, always
It depends on T: logits (B·T·V) are larger at short T, and attention scores (B·H·T²) are larger at long T
The QKV projection
It depends on sequence length. Here, with T=6 and V=32000, the logits have 2×6×32000 = 384k elements against 576 for the scores, at 2×8×36. But the scores grow like T² while the logits grow like T. For these numbers they cross at about T = V/H = 4000. At T=32k the scores are far larger, which is the regime FlashAttention was built for.
Your loss starts at 10.4 for a 32000-token vocabulary. Is that expected?
Yes: ln(32000) ≈ 10.37, which is the loss of a uniform random guess
No, it should start near 0
No, it should start near 1
Only if the model is broken
ln(V) is the expected starting loss. An untrained model outputs nearly uniform logits, so the cross-entropy is −ln(1/V) = ln(V) = ln(32000) ≈ 10.37. Always check this at step 0. If it starts much lower, your initialisation is too large or you have the label-shift bug. If it starts much higher, your initialisation is broken. It is the cheapest sanity check in deep learning.

9.4 · Parameter counting, exactly

You should be able to work out a model's parameter count from its config. Here is how:

def count_params(cfg, tied=False, swiglu=True):
    C, F_, L, V = cfg.d_model, cfg.d_ff, cfg.n_layer, cfg.vocab_size

    embed  = V * C
    attn   = 4 * C * C                       # W_q, W_k, W_v, W_o (MHA, no bias)
    mlp    = (3 if swiglu else 2) * C * F_
    norms  = 2 * C                           # two RMSNorms per block
    per_layer = attn + mlp + norms

    total = embed + L * per_layer + C        # + final norm
    if not tied:
        total += V * C                       # separate LM head
    return total

# GPT-2 small: C=768, F=3072, L=12, V=50257, GELU MLP, tied
count_params(Config(768, 3072, 12, 50257), tied=True, swiglu=False)
# 123,551,232. The famous 124,439,808 (exactly, to the parameter) adds three
# things GPT-2 has and this modern recipe does not:
#   learned position table 1024 × 768          =    786,432
#   biases on qkv, proj, fc, fc-proj (× 12)     =     82,944
#   LayerNorm biases (2 per block + final)       =     19,200
The shortcut worth memorising

For a dense transformer with d_ff = 4·d_model: N ≈ 12 · n_layer · d_model² (not counting embeddings). Attention is 4C² and the MLP is 8C². Check it: Llama-2-7B has L=32 and C=4096, so 12 × 32 × 4096² ≈ 6.4B, and the true non-embedding count is ~6.5B. That is close enough to do in your head.

9.5 · Decoder-only vs encoder-decoder, in FLOPs

You will hear both "encoder-decoder models are more expensive" and "they are cheaper", and both are wrong unless you say what is held fixed. Count it. A forward pass costs about 2 FLOPs per parameter for each token that passes through those parameters (Chapter 2), ignoring the attention-score matmuls. Say a task reads an input of S tokens and produces an output of T tokens.

  • Decoder-only with N parameters: the input and output are one sequence, and every one of the S + T tokens passes through all N. The cost is 2·N·(S + T).
  • Encoder-decoder with Ne + Nd: the S input tokens pass through the encoder only, and the T output tokens through the decoder only. The cost is 2·Ne·S + 2·Nd·T.

For a T5-base-sized split (110M + 110M) against a 220M decoder, on a 512-token input and a 128-token output (tfs.foundations.encdec_vs_decoder_flops):

decoder-only, 220 M params:   2 × 220M × (512 + 128)            = 281.6 GFLOP
encoder-decoder, 110M + 110M: 2 × 110M × 512 + 2 × 110M × 128   = 140.8 GFLOP     half, at the same parameter count
decoder-only, 110 M params:   2 × 110M × 640                    = 140.8 GFLOP     the same as the 220M enc-dec

So with equal parameters an encoder-decoder costs half as much (each token visits half the model), and at equal compute it has twice the parameters. The T5 paper made this comparison when choosing its architecture: an encoder-decoder with 2P parameters costs the same as a P-parameter decoder-only model. What the count leaves out cuts both ways. The decoder's cross-attention adds K and V projections over the encoder output in every decoder layer, plus its score matmuls, and at generation time the cross-attention K and V of the encoder output must be cached in every decoder layer, next to the decoder's own self-attention cache. On the other side, the decoder-only model's KV cache holds all S + T positions in every layer.

So why did decoder-only win, if not on FLOPs? It won on simplicity and generality: one stack, one objective, no fixed line between input and output (a chat mixes both), a KV cache that can be reused across turns, and a training signal at every position (§9.1). The encoder-decoder's advantages are real where the input and output are truly different, such as audio and text in Whisper, and where the input is long and the output short.

9.6 · Embedding and reranker models

Retrieval (search, RAG, deduplication, clustering) runs on a different kind of model from the one that generates the answer. Two shapes are used, and an engineer building retrieval needs both.

Bi-encoder (embedding model)Cross-encoder (reranker)
Inputone text at a timequery and document concatenated
Outputone vector, (d,)one relevance score
Scorecosine of two precomputed vectorsa forward pass per (query, document) pair
Cost to search N documentsembed the query once, then a vector searchN forward passes
Accuracygoodbetter: every query token attends to every document token
Used forfirst-stage retrieval over millions of documentsre-scoring the top 20–200 candidates

Both are traditionally encoder-only, BERT-shaped models (§9.1): bidirectional attention gives every token of the text a view of all the others, which is what you want for a representation of a whole passage. The vector is pooled from the last layer, by averaging the token vectors or taking the first token's. Since 2024 strong embedding models have also been built from decoder LLMs (E5-Mistral and Qwen3-Embedding among them), usually using the last token's vector, because under a causal mask it is the only one that has seen the whole text.

How they are trained: contrastive learning

An embedding model is not trained to predict tokens. It is trained so that a query and its relevant document end up close together, and irrelevant documents far away. The standard loss is InfoNCE with in-batch negatives. Take a batch of B (query, positive document) pairs, embed them all, L2-normalise, and form the (B, B) matrix of cosine similarities. Row i's correct column is i, and every other document in the batch is a negative at no extra cost. Then it becomes a classification problem over the batch:

ℒ = − 1B Σi log exp(sii / τ)Σj exp(sij / τ) cross-entropy over the rows of the similarity matrix, with temperature τ (typically 0.01–0.05)
Worked example — three pairs, and the role of τ
1
Similarities (tfs.foundations.info_nce, after normalising three 3-d query and document vectors). The diagonal holds the positives: 
            doc 0    doc 1    doc 2
query 0    0.948    0.269    0.416
query 1    0.491    0.959    0.358
query 2    0.265    0.538    0.971
2
At τ = 1, row 0's logits are the similarities themselves, and the softmax gives 0.477 0.242 0.280: the positive gets under half the probability even though it is clearly the best match. The mean loss over the batch is 0.759. Cosines lie in [−1, 1], so without a temperature the loss can never become confident.
3
At τ = 0.05 the logits are 20× larger, 18.96 5.37 8.32, and the positive gets 0.99997. The mean loss is ≈ 10−4: this batch is solved and adds almost no gradient.
4
A hard negative. Replace doc 1 with one that is closer to query 0 than its own positive (similarity 0.966 against 0.948). At τ = 0.05 the loss jumps to 0.777. The batch is useful again, and the gradient pushes exactly the confusable pair apart.

Steps 3 and 4 hold most of the skill in training embedding models. Random in-batch negatives soon become too easy, so training pipelines mine hard negatives (documents that an earlier model ranked highly but that are not relevant) and use large batches, because every extra pair adds B − 1 negatives to every row. The same loss, with images and captions, is CLIP.

Why are search systems usually built as a bi-encoder followed by a cross-encoder, not a cross-encoder alone?
Cross-encoders cannot be fine-tuned
Bi-encoders are more accurate
Cross-encoders only work on short documents
A cross-encoder needs one forward pass per (query, document) pair, far too many for millions of documents; the bi-encoder's precomputed vectors narrow the field cheaply, and the cross-encoder then re-scores the shortlist
Cost first, then accuracy. Document vectors are computed once, offline, so a query costs one forward pass plus a vector search. The more accurate cross-encoder is used only where it changes the answer.
Training an embedding model with InfoNCE, the loss quickly falls near zero and quality stops improving. What is the most likely fix?
Mine harder negatives (or use larger batches, or both), so that each batch contains documents the model confuses with the positive
Raise the temperature to 1
Remove the normalisation
Switch to a causal mask
Easy negatives give no gradient. In the worked example a solved batch has a loss of 10−4, and one hard negative brings it back to 0.78. Raising τ only makes the loss less confident everywhere, without teaching the model which documents are easy to confuse.

9.2Verify causality empiricallyessential

Do not trust your mask; test it. Change token t and confirm that the outputs at positions < t are bit-identical:

ids = torch.randint(0, 32000, (1, 10))
out1, _ = model(ids)

ids2 = ids.clone()
ids2[0, 7] = (ids2[0, 7] + 1) % 32000       # perturb position 7 only
out2, _ = model(ids2)

assert torch.allclose(out1[0, :7], out2[0, :7], atol=1e-6), "CAUSALITY VIOLATED"
assert not torch.allclose(out1[0, 7], out2[0, 7]),           "position 7 should change"
print("causal ✓")

Run this on every model you write. A slightly broken mask leaks the future, which makes the training loss look fantastic and generation look absurd, and that failure has cost people weeks.

9.3The residual-scaling initialisationcode

GPT-2 scales the residual output projections at initialisation by 1/√(2·n_layer). Implement it, then measure why it is there:

for name, p in model.named_parameters():
    if name.endswith('proj.weight') or name.endswith('down.weight'):
        nn.init.normal_(p, std=0.02 / math.sqrt(2 * cfg.n_layer))

With and without it, run one forward pass and print x.std() after each block.

What you'll see

Without the scaling, the residual stream's standard deviation grows roughly like √n_layer, because each block adds an independent contribution and variances add up. At 48 layers that is about 7× growth, which pushes the final norm and the logits into a bad range and makes early training unstable. With the scaling, the std stays roughly flat with depth. Those two lines of code separate a training run that spikes from one that does not.

9.5Size a retrieval systemthinking

You index 10 million passages with a 335M-parameter bi-encoder that produces 1024-dimensional fp16 vectors. Passages are 256 tokens long on average. You rerank the top 100 per query with a cross-encoder of the same size on (query + passage) ≈ 300 tokens.

  1. The index memory, and the forward FLOPs needed to build it.
  2. The forward FLOPs per query for embedding (query ≈ 20 tokens) and for reranking.
  3. Which stage dominates the compute per query, and what is the obvious thing to change?
Answers
1. 10^7 × 1024 × 2 bytes                     = 20.5 GB of vectors
   2 × 335e6 × 256 × 10^7                    = 1.7 × 10^18 FLOPs to embed the corpus, once
2. query embedding: 2 × 335e6 × 20           = 1.3 × 10^10 FLOPs
   reranking:       2 × 335e6 × 300 × 100    = 2.0 × 10^13 FLOPs   (1,500× the embedding)
3. reranking. Rerank fewer candidates, use a smaller reranker, or truncate passages.

The vector search itself (a dot product with 107 vectors: 2 × 1010 FLOPs by brute force, far less with an approximate index) costs about as much as the query embedding. The cross-encoder is where the money goes, which is why the shortlist size is the first setting a retrieval team tunes.

9.6Predict, then measure: temperature and batch size in InfoNCEcode

Using tfs.foundations.info_nce: (1) for random unit vectors in 256 dimensions, with the positive equal to the query plus a little noise, predict how the loss at τ = 0.05 changes as B goes from 8 to 512. (2) Then predict the loss when every query and document is random (no signal at all). Measure both.

What to expect

(1) With a clear positive the loss is tiny and grows with B: 1.5 × 10−6 at B = 8 and 1.9 × 10−4 at B = 512, because more negatives give more chances that one is close by accident. (2) With no signal you might predict ln B, the loss of a uniform guess (2.08 at B = 8, 6.24 at B = 512). The measurement is higher: 3.23 and 7.02. Random 256-dimensional unit vectors have cosines with standard deviation 1/√256 = 0.0625, and dividing by τ = 0.05 turns those into logits with standard deviation σ = 1.25, so the model is confidently wrong instead of uniform. For random logits the expected loss is about ln B + σ²/2 = 6.24 + 0.78 = 7.02, which matches at B = 512 (at B = 8 the sample is too small for the approximation). So the chance level of InfoNCE depends on τ and d, not only on B, and that formula, not ln B, is the number to compare an untrained model against.
