The whole chapter in five sentences

One block, three arrangements: bidirectional (encoder-only), causal (decoder-only), or an encoder whose output a causal decoder cross-attends to. Decoder-only won because a causal mask gives a training signal at every position and every task can be phrased as continuation. A forward pass is a fixed sequence of about twenty shape changes, from (B, T) ids to (B, T, V) logits, and you should be able to recite it. The parameter count follows from the config, about 12·L·d² plus the embeddings, and the FLOPs from the parameter count, which is also how an encoder-decoder can have twice the parameters of a decoder at the same cost. Retrieval still runs on encoder-shaped models, trained contrastively so that matching texts land close together.

Why decoder-only won

Training efficiency. With a causal mask, a single forward pass over a length-T sequence produces T supervised predictions — every position predicts its successor. BERT-style masking only supervises the ~15% of positions that were masked. So a decoder extracts roughly 6× more learning signal per FLOP. Add that any task can be phrased as text continuation, and the case for a second architecture largely evaporated.

Encoder-only: BERT

# Training objective: mask 15% of tokens, predict them from BOTH sides.
"the cat [MASK] on the mat"  →  predict "sat"
# No causal mask — position 2 sees positions 0..5 freely.
# Cannot generate: there is no notion of "next".

Still the right tool for embeddings and reranking, where you want a rich bidirectional representation of a fixed text and don't need generation. Modern retrieval stacks still run BERT-family encoders.

Decoder-only: GPT and everything after it

# Training objective: predict token t+1 from tokens 0..t, at EVERY position at once.
input:  [the, cat, sat, on,  the]
target: [cat, sat, on,  the, mat]
# One forward pass = 5 predictions. The causal mask makes this valid.

Encoder–decoder: T5

# Encoder reads the source bidirectionally.
# Decoder generates causally, and CROSS-ATTENDS to the encoder output:
#     Q from decoder  (T_dec, d)
#     K, V from encoder output  (T_enc, d)
#     → output (T_dec, d)   — decoder length preserved, any encoder length

Still dominant where input and output are genuinely different modalities or languages — Whisper (audio→text) is the clearest current example.

9.2 · The full shape trace

This is the centrepiece of the chapter. A decoder-only model with B=2, T=6, V=32000, d_model=512, n_head=8, d_head=64, d_ff=1376, n_layer=6. Step through every tensor.

The off-by-one that everyone writes at least once 
logits  = model(ids)               # (B, T, V)
loss = F.cross_entropy(logits.reshape(-1, V), ids.reshape(-1))   # ← WRONG

This asks the model to predict the token it was just given — a task it solves perfectly by copying, and the loss goes to ~0 while the model learns nothing. You must shift:

loss = F.cross_entropy(
    logits[:, :-1, :].reshape(-1, V),      # predictions for positions 0..T-2
    ids[:, 1:].reshape(-1))                # targets are positions 1..T-1

Diagnostic: if your training loss drops below ln(1)≈0-ish absurdly fast, or below the entropy of your data, you have this bug. Some HF models shift internally when you pass labels=; check before doing it yourself, or you'll shift twice.

9.3 · The complete model, in one file

import torch, torch.nn as nn, torch.nn.functional as F
from dataclasses import dataclass

@dataclass
class Config:
    vocab_size: int = 32000
    d_model:    int = 512
    n_layer:    int = 6
    n_head:     int = 8
    d_ff:       int = 1376
    max_T:      int = 1024
    rope_base:  float = 10000.0

class GPT(nn.Module):
    def __init__(self, cfg):
        super().__init__()
        self.cfg   = cfg
        self.embed = nn.Embedding(cfg.vocab_size, cfg.d_model)
        self.blocks = nn.ModuleList([Block(cfg) for _ in range(cfg.n_layer)])
        self.norm  = RMSNorm(cfg.d_model)
        self.head  = nn.Linear(cfg.d_model, cfg.vocab_size, bias=False)

        cos, sin = build_rope_cache(cfg.max_T, cfg.d_model // cfg.n_head, cfg.rope_base)
        self.register_buffer("cos", cos, persistent=False)
        self.register_buffer("sin", sin, persistent=False)

        self.apply(self._init)

    def _init(self, m):
        if isinstance(m, nn.Linear):
            nn.init.normal_(m.weight, std=0.02)
            if m.bias is not None: nn.init.zeros_(m.bias)
        elif isinstance(m, nn.Embedding):
            nn.init.normal_(m.weight, std=0.02)

    def forward(self, ids, targets=None):
        B, T = ids.shape                                    # (B, T)
        x = self.embed(ids)                                 # (B, T, C)
        cos, sin = self.cos[:T], self.sin[:T]

        for blk in self.blocks:
            x = blk(x, cos, sin)                            # (B, T, C)

        x = self.norm(x)                                    # (B, T, C)
        logits = self.head(x)                               # (B, T, V)

        loss = None
        if targets is not None:
            loss = F.cross_entropy(
                logits[:, :-1].reshape(-1, logits.size(-1)),
                targets[:, 1:].reshape(-1),
                ignore_index=-100)
        return logits, loss
Why std=0.02?

It's GPT-2's choice and it stuck. The principle is that activations should have roughly unit variance after each layer, which needs std ≈ 1/√d_model (0.044 at d_model=512). GPT-2 used a flat 0.02, plus an extra 1/√(2·n_layer) scaling on the residual output projections (W_o and MLP-down) to stop the residual stream's variance growing linearly with depth. That second detail is genuinely important and often omitted — see Exercise 9.3.

Only in attention. The MLP, both norms, RoPE and the LM head all operate on each position independently — you could run them on a single token in isolation and get the same answer. Attention is the only cross-position operation in a transformer. That's worth holding onto: it means every claim about "how information flows through the model" is a claim about attention.
Which tensor in the trace is the largest, and why does that matter?
The residual stream, because it appears at every layer
The attention scores, always

It depends on sequence length. Here with T=6, V=32000: logits are 2×6×32000 = 384k elements vs scores at 2×8×36 = 576. But scores grow as T² while logits grow as T. Crossover for these numbers is around T = V/H = 4000. At T=32k the scores dominate overwhelmingly — which is exactly the regime FlashAttention was built for.

No, it should start near 0

ln(V) is the expected initial loss. An untrained model outputs near-uniform logits, so cross-entropy = −ln(1/V) = ln(V) = ln(32000) ≈ 10.37. Always check this on step 0. If it starts much lower, your initialisation is too large or you have the label-shift bug. If much higher, your initialisation is broken. It's the cheapest sanity check in deep learning.

9.4 · Parameter counting, exactly

You should be able to derive a model's parameter count from its config. Here's the recipe:

def count_params(cfg, tied=False, swiglu=True):
    C, F_, L, V = cfg.d_model, cfg.d_ff, cfg.n_layer, cfg.vocab_size

    embed  = V * C
    attn   = 4 * C * C                       # W_q, W_k, W_v, W_o (MHA, no bias)
    mlp    = (3 if swiglu else 2) * C * F_
    norms  = 2 * C                           # two RMSNorms per block
    per_layer = attn + mlp + norms

    total = embed + L * per_layer + C        # + final norm
    if not tied:
        total += V * C                       # separate LM head
    return total

# GPT-2 small: C=768, F=3072, L=12, V=50257, GELU MLP, tied
count_params(Config(768, 3072, 12, 50257), tied=True, swiglu=False)
# 123,551,232. The famous 124,439,808 (exactly, to the parameter) adds three
# things GPT-2 has and this modern recipe does not:
#   learned position table 1024 × 768          =    786,432
#   biases on qkv, proj, fc, fc-proj (× 12)     =     82,944
#   LayerNorm biases (2 per block + final)       =     19,200
The shortcut worth memorising

For a dense transformer with d_ff = 4·d_model: N ≈ 12 · n_layer · d_model² (non-embedding). Attention is 4C², MLP is 8C². Check it: Llama-2-7B has L=32, C=4096 → 12 × 32 × 4096² ≈ 6.4B, and the true non-embedding count is ~6.5B. Close enough to do in your head.

9.5 · Decoder-only vs encoder-decoder, in FLOPs

"Encoder-decoder models are more expensive" and "they are cheaper" are both heard, and both are wrong without saying what is held fixed. Count it. A forward pass costs about 2 FLOPs per parameter per token that passes through those parameters (Chapter 2), ignoring the attention-score matmuls. A task reads an input of S tokens and produces an output of T tokens.

  • Decoder-only with N parameters: the input and the output are one sequence, and every one of the S + T tokens passes through all N. Cost 2·N·(S + T).
  • Encoder-decoder with Ne + Nd: the S input tokens pass through the encoder only, the T output tokens through the decoder only. Cost 2·Ne·S + 2·Nd·T.

For a T5-base-sized split (110M + 110M) against a 220M decoder, on a 512-token input and a 128-token output (tfs.foundations.encdec_vs_decoder_flops):

decoder-only, 220 M params:   2 × 220M × (512 + 128)            = 281.6 GFLOP
encoder-decoder, 110M + 110M: 2 × 110M × 512 + 2 × 110M × 128   = 140.8 GFLOP     half, at the same parameter count
decoder-only, 110 M params:   2 × 110M × 640                    = 140.8 GFLOP     the same as the 220M enc-dec

So at equal parameters an encoder-decoder costs half as much (each token visits half the model), and at equal compute it has twice the parameters. This is the comparison the T5 paper made when choosing its architecture: an encoder-decoder with 2P parameters has the same cost as a P-parameter decoder-only model. What the count leaves out works in both directions. The decoder's cross-attention adds K and V projections over the encoder output in every decoder layer, and its score matmuls; at generation time the encoder output's cross-attention K and V must be cached in every decoder layer, alongside the decoder's own self-attention cache. On the other side, the decoder-only model's KV cache holds all S + T positions in every layer.

Why, then, did decoder-only win? Not on FLOPs. It won on simplicity and generality: one stack, one objective, no fixed boundary between "input" and "output" (a chat is an interleaving of both), a KV cache that can be reused across turns, and a training signal at every position (§9.1). The encoder-decoder's advantages are real where the input and output are genuinely different, such as audio and text in Whisper, and where the input is long and the output short.

9.6 · Embedding and reranker models

Retrieval (search, RAG, deduplication, clustering) runs on a different kind of model from the one generating the answer. Two shapes are used, and an engineer building retrieval needs both.

Bi-encoder (embedding model)Cross-encoder (reranker)
Inputone text at a timequery and document concatenated
Outputone vector, (d,)one relevance score
Scorecosine of two precomputed vectorsa forward pass per (query, document) pair
Cost to search N documentsembed the query once, then a vector searchN forward passes
Accuracygoodbetter: every query token attends to every document token
Used forfirst-stage retrieval over millions of documentsre-scoring the top 20–200 candidates

Both are classically encoder-only, BERT-shaped models (§9.1): bidirectional attention gives every token of the text a view of all the others, which is what a representation of a whole passage wants. The vector is pooled from the last layer, by averaging the token vectors or taking the first token's. Since 2024 strong embedding models have also been built from decoder LLMs (E5-Mistral, Qwen3-Embedding among them), usually taking the last token's vector, since under a causal mask it is the only one that has seen the whole text.

How they are trained: contrastive learning

An embedding model is not trained to predict tokens. It is trained so that a query and its relevant document end up close, and irrelevant ones far apart. The standard loss is InfoNCE with in-batch negatives. Take a batch of B (query, positive document) pairs, embed all of them, L2-normalise, and form the (B, B) matrix of cosine similarities. Row i's correct column is i; every other document in the batch serves as a negative, for free. Then it is a classification problem over the batch:

ℒ = − 1B Σi log exp(sii / τ)Σj exp(sij / τ) cross-entropy over the rows of the similarity matrix, with temperature τ (typically 0.01–0.05)
Worked example — three pairs, and the role of τ
1
Similarities (tfs.foundations.info_nce, after normalising three 3-d query and document vectors). The diagonal holds the positives: 
            doc 0    doc 1    doc 2
query 0    0.948    0.269    0.416
query 1    0.491    0.959    0.358
query 2    0.265    0.538    0.971
2
At τ = 1, row 0's logits are the similarities themselves, and the softmax is 0.477 0.242 0.280: the positive gets under half the probability even though it is clearly the best match. Mean loss over the batch: 0.759. Cosines live in [−1, 1], so without a temperature the loss can never become confident.
3
At τ = 0.05 the logits are 20× larger, 18.96 5.37 8.32, and the positive gets 0.99997. Mean loss ≈ 10−4: this batch is solved, and contributes almost no gradient.
4
A hard negative. Replace doc 1 with one that is closer to query 0 than its own positive (similarity 0.966 vs 0.948). At τ = 0.05 the loss jumps to 0.777. The batch is informative again, and the gradient pushes exactly the confusable pair apart.

Step 3 and step 4 are the whole craft of training embedding models. Random in-batch negatives are quickly too easy, so training pipelines mine hard negatives (documents that a previous model ranked highly but that are not relevant) and use large batches, because every extra pair adds B − 1 negatives to every row. The same loss, with images and captions, is CLIP.

An encoder-decoder with 110M + 110M parameters and a 220M decoder-only model process a 512-token input and a 128-token output. Ignoring attention scores, how do their forward FLOPs compare?

The encoder-decoder costs half: each token passes through only one 110M stack
The encoder-decoder costs twice as much: it has two stacks

140.8 vs 281.6 GFLOP. FLOPs follow parameters per token, and each token visits half of the encoder-decoder. Equivalently, at equal cost it can have twice the parameters.
Why are search systems usually built as a bi-encoder followed by a cross-encoder, not a cross-encoder alone?
Cross-encoders cannot be fine-tuned
Bi-encoders are more accurate
Cross-encoders only work on short documents
A cross-encoder needs one forward pass per (query, document) pair, far too many for millions of documents; the bi-encoder's precomputed vectors narrow the field cheaply, and the cross-encoder re-scores the shortlist
Cost, then accuracy. Document vectors are computed once, offline; a query costs one forward pass plus a vector search. The more accurate cross-encoder is spent only where it changes the answer.
Training an embedding model with InfoNCE, the loss quickly falls near zero and quality stops improving. What is the most likely fix?
Mine harder negatives (and/or use larger batches), so each batch contains documents the model confuses with the positive
Raise the temperature to 1
Remove the normalisation
Switch to a causal mask
Easy negatives give no gradient. In the worked example a solved batch has loss 10−4; one hard negative brings it back to 0.78. Raising τ just makes the loss less confident everywhere without teaching the model which documents are confusable.

9.2Verify causality empiricallyessential

Don't trust your mask — test it. Change token t and confirm that outputs at positions < t are bit-identical:

ids = torch.randint(0, 32000, (1, 10))
out1, _ = model(ids)

ids2 = ids.clone()
ids2[0, 7] = (ids2[0, 7] + 1) % 32000       # perturb position 7 only
out2, _ = model(ids2)

assert torch.allclose(out1[0, :7], out2[0, :7], atol=1e-6), "CAUSALITY VIOLATED"
assert not torch.allclose(out1[0, 7], out2[0, 7]),           "position 7 should change"
print("causal ✓")

Run this on every model you ever write. A subtly broken mask leaks the future, which makes training loss look fantastic and generation look insane — a failure mode that has cost people weeks.

9.3The residual-scaling initialisationcode

GPT-2 scales the residual-output projections at init by 1/√(2·n_layer). Implement it, then measure why:

for name, p in model.named_parameters():
    if name.endswith('proj.weight') or name.endswith('down.weight'):
        nn.init.normal_(p, std=0.02 / math.sqrt(2 * cfg.n_layer))

With and without it, run one forward pass and print x.std() after each block.

What you'll see

Without the scaling, the residual stream's standard deviation grows roughly as √n_layer — each block adds an independent contribution and variances sum. At 48 layers that's a ~7× growth, which pushes the final norm and the logits into a bad range and makes early training unstable. With the scaling, std stays roughly flat with depth. Two lines of code, and it's the difference between a training run that spikes and one that doesn't.

9.6Predict, then measure: temperature and batch size in InfoNCEcode

Using tfs.foundations.info_nce: (1) for random unit vectors in 256 dimensions with the positive equal to the query plus small noise, predict how the loss at τ = 0.05 changes as B goes from 8 to 512. (2) Then predict the loss when every query and document is random (no signal). Measure both.

What to expect

(1) With a clear positive the loss is tiny and rises with B: 1.5 × 10−6 at B = 8, 1.9 × 10−4 at B = 512, because more negatives mean more chances that one is close by accident. (2) With no signal you might predict ln B, the loss of a uniform guess (2.08 at B = 8, 6.24 at B = 512). The measurement is higher: 3.23 and 7.02. Random 256-d unit vectors have cosines with standard deviation 1/√256 = 0.0625, and dividing by τ = 0.05 turns that into logits with standard deviation σ = 1.25: the model is confidently wrong rather than uniform. For random logits the expected loss is about ln B + σ²/2 = 6.24 + 0.78 = 7.02, which matches at B = 512 (at B = 8 the sample is too small for the approximation). So the chance level of InfoNCE depends on τ and d, not just B, and that formula, not ln B, is the number to compare an untrained model against.
