The whole chapter in five sentences

Users feel TTFT, TPOT and their tails; the business pays per GPU-hour, and goodput (requests that met their SLO) is the number that connects the two. Batch size trades latency for cost per token, and memory for the KV cache caps the batch long before compute does, so PagedAttention and KV quantization raise throughput by raising the cap. Prefill and decode are different machines, and chunked prefill or disaggregation keeps one from spoiling the other. Fewer bytes per step is the universal lever: fp8 and fp4 weights, speculative decoding's free FLOPs, prefix caches kept in CPU memory instead of recomputed. MoE and multi-LoRA are bandwidth problems in disguise: experts need large batches per expert, which is why they are served across hundreds of GPUs, and every distinct adapter in a batch is extra traffic.

18.1 · PagedAttention — virtual memory for the KV cache

The naive approach pre-allocates a contiguous buffer of max_length per sequence. If a user's generation stops at 200 tokens out of a 4096 reservation, 95% of that memory is wasted. vLLM's authors measured real systems wasting 60–80% of their KV memory to this.

The fix, borrowed wholesale from operating systems

Split the cache into fixed-size blocks (typically 16 tokens). A sequence gets a block table mapping logical positions to physical blocks, which need not be contiguous. Allocate blocks on demand as generation proceeds. This is paged virtual memory, applied to attention — hence the name.

Contiguous allocationPagedAttention
Internal fragmentationup to max_len − actual_len< 1 block (≈16 tokens)
External fragmentationsignificantnone — all blocks are the same size
Memory utilisation20–40%> 90%
Sharing a common prefiximpossiblefree — just point at the same blocks

That last row is the sleeper feature. Copy-on-write block sharing means parallel samples from one prompt, or a thousand users hitting the same system prompt, share cache blocks physically. Combined with prefix caching (persist those blocks across requests), a long shared system prompt becomes nearly free after the first request — often the single biggest latency win available to an application developer.

18.2 · Continuous batching

Static batching waits for every sequence in a batch to finish. If one user asks for 20 tokens and another for 2000, the short request's GPU slot idles for the whole 2000 steps.

Static batching (bad):
  seq A: ####----------------------------   done at step 4, slot wasted for 28
  seq B: ################################
  seq C: ########------------------------
         ^ batch cannot retire until B finishes

Continuous batching (good):
  seq A: ####
  seq D:     ############
  seq B: ################################
  seq C: ########
  seq E:         ####################
         ^ finished sequences are evicted and replaced every single step

Because the model weights are read once per step regardless of batch composition (Chapter 15), keeping the batch full is nearly pure profit. Reported throughput gains over static batching are typically 2–4×, sometimes over 20× on skewed length distributions. Every serious server — vLLM, TensorRT-LLM, SGLang, TGI — does this.

18.3 · What users feel: SLOs, percentiles and goodput

A serving system is judged on numbers its users feel, and they are not "throughput":

E2E latencyTTFT + TPOT × (output tokens − 1)both, and the output length
Throughputtokens (or requests) per second, summed over usersbatch size

A service-level objective (SLO) states targets for the first two, at a percentile: "TTFT under 500 ms and TPOT under 30 ms for 99% of requests". Percentiles, not means, because the users who leave are the ones in the tail, and averages hide tails. A mean TTFT of 300 ms is consistent with one request in ten waiting 2 seconds.

Throughput counts every token, including those of requests that missed their SLO and whose user has already given up. Goodput counts only the requests that met it. DistServe (Zhong et al., 2024) made it the headline metric: the highest request rate a system can sustain while a target fraction (say 90%) of requests meets both SLOs.

18.6 · Speculative decoding

The cleverest idea in inference. It exploits the fact from Chapter 15 that decode is memory-bound: verifying k tokens costs almost exactly the same as generating 1, because either way you read all the weights once.

The algorithm
  1. A small, fast draft model proposes k tokens autoregressively (cheap).
  2. The big target model scores all k in one forward pass (one weight read).
  3. A rejection-sampling rule accepts the longest prefix that's consistent with the target's own distribution, and resamples at the first disagreement.
  4. You advance by 1 to k+1 tokens for the price of roughly one target forward pass.
The guarantee that makes it usable

The acceptance rule (Leviathan et al. 2023; Chen et al. 2023) is constructed so the output distribution is provably identical to sampling from the target model alone. Accept draft token x with probability min(1, ptarget(x) / pdraft(x)); on rejection, sample from the normalised residual max(0, ptarget − pdraft). This is not an approximation with a quality knob — it is exact. That's why it can be turned on by default.

Worked example — how much speculative decoding actually buys

One number governs it: α, the probability that a drafted token is accepted. Draft k tokens, verify in one target pass.

1
How many tokens survive? Acceptance is sequential — the first rejection stops everything after it. So with k = 4, α = 0.7: 
accept exactly 0:  0.3000     (first draft token rejected)
accept exactly 1:  0.2100     = 0.7 × 0.3
accept exactly 2:  0.1470
accept exactly 3:  0.1029
accept all 4:      0.2401     = 0.7⁴  (plus a free bonus token)
2
Expected tokens per target forward pass.
E = 1 − αk+11 − α 
α=0.7, k=4  ->  E = (1 − 0.7⁵) / 0.3 = 2.77 tokens
You still pay one target pass, but advance 2.77 positions. 2.77× fewer target passes.
3
The full picture — and where it stops paying. 
  α      k=2     k=4     k=8
0.3     1.39    1.43    1.43     <- bad draft: more k barely helps
0.5     1.75    1.94    2.00
0.7     2.19    2.77    3.20
0.9     2.71    4.10    6.13     <- great draft: k pays off
Look at the α=0.3 row: going from k=4 to k=8 gains nothing, because the draft almost never survives 4 tokens anyway — you just burn draft compute. Tune k to your measured α, not upward on principle.

Why α varies so much. Predictable text — boilerplate code, summarising a document you supplied, structured output — accepts 80–90%. Creative prose accepts far less. This is also why n-gram/prompt-lookup drafting works so well for RAG and editing: when the answer largely copies the input, α is enormous and the draft costs nothing.

def expected_tokens(alpha, k):
    """Tokens advanced per target forward pass."""
    return (1 - alpha**(k + 1)) / (1 - alpha)

assert round(expected_tokens(0.9, 8), 2) == 6.13

Speedup depends entirely on the acceptance rate. Predictable text (code, structured output, summarising a provided document) accepts most drafts; creative text accepts few. And note the trade: at large batch sizes you're already compute-bound, so the free verification capacity disappears and speculative decoding can be a net loss. It is a low-batch / low-latency optimisation.

Why quantizing weights speeds up decode

Because decode is bandwidth-bound. Int4 weights are 4× fewer bytes to read from HBM, so you get up to 4× the token rate, even if the arithmetic is dequantized back to bf16 before the matmul. You're not saving FLOPs, you're saving traffic. This also means weight-only quantization helps decode far more than prefill.

Three decisions fall out of the table:

  • Hopper vs Blackwell changes what 4-bit buys. On an H100, MXFP4 or NVFP4 weights are a storage and bandwidth format: the kernel loads 4-bit values and scales, dequantizes in registers and multiplies in bf16 or fp8. Decode gets faster; prefill does not. Blackwell's tensor cores multiply fp4 directly at twice the fp8 rate (Chapter 14 §14.8), so prefill gets faster too, if activations are quantized as well.
  • NVFP4 costs a quarter of a bit more than MXFP4 (a scale per 16 values instead of 32, in e4m3 instead of a power of two). The finer, more precise scaling is why NVIDIA reports it tracking fp8 accuracy more closely; the bandwidth cost is 6%.
  • fp8 is the safe default for weights on H100-class hardware: half the bytes, native matmuls, and quality differences that are usually within noise. DeepSeek-V3 was trained and released in fp8 with 128 × 128 weight blocks, so its fp8 weights are not a post-hoc approximation. gpt-oss ships its MoE weights in MXFP4, which is how the 117 B-parameter model fits on one 80 GB GPU (Chapter 0, Chapter 20).
Evaluate quantized models on your actual task

Perplexity barely moves under 4-bit quantization, which has led to a lot of "lossless" claims. Multi-step reasoning, long-context retrieval, and code generation degrade noticeably earlier than perplexity suggests — the errors compound across steps. Always test the thing you actually care about, not a proxy.

18.8 · Prefill–decode disaggregation

Chapter 15 showed prefill is compute-bound and decode is memory-bound. Running them on the same GPU in the same batch means each interferes with the other — a long prefill stalls every decode in flight ("head-of-line blocking"), which shows up as inter-token latency jitter.

The 2024–2026 answer is to run them on separate GPU pools: prefill workers produce the KV cache and transfer it over the interconnect to decode workers. Prefill nodes optimise for throughput, decode nodes for bandwidth and batch size. Systems like DistServe, Splitwise, Mooncake and current vLLM/SGLang builds support this, and it's now standard in large deployments. An intermediate option, chunked prefill (§18.4, and Chapter 15 §15.7 for exactness), which slices long prompts into pieces interleaved with decode steps, gets much of the benefit on a single pool. Disaggregation's own cost is the cache hand-off: a prefill node must ship each request's KV cache to a decode node (1 GiB for 8k tokens of Llama-3-8B), which is why it is deployed on fast interconnects and pairs naturally with the cache-transfer layers of §18.11.

18.9 · Serving MoE: expert parallelism

Chapter 20 §20.7 derived the fact that shapes MoE serving: a batch of b decoding tokens, each choosing k of E experts, reads E(1 − (1 − k/E)b) distinct experts per layer, so DeepSeek-V3 reads 87% of its routed experts at a batch of 64. Sparsity saves FLOPs, not bandwidth. The serving question is what to do about it, and the answer is to make the batch per expert large.

Worked example — how big a batch makes an expert compute-bound?
1
Tokens per expert. With uniform routing, each routed expert sees b · k / E of the batch's tokens. A global decode batch of 4,096 tokens on DeepSeek-V3 (256 experts, top-8) gives each expert 4,096 × 8 / 256 = 128 tokens per step.
2
The ridge, in tokens. An expert's matmul with n tokens does 2n FLOPs per weight, and an fp8 weight is 1 byte, so its intensity is 2n FLOP/byte. On an H100's fp8 ridge of 590.7 (Chapter 14), it is compute-bound at n ≈ 295 tokens per expert, which needs a global batch of 295 × 256 / 8 ≈ 9,451 tokens.
3
Memory per expert. One routed expert of one layer is a SwiGLU with d_model 7,168 and expert width 2,048: 3 × 7,168 × 2,048 = 44.0 M parameters. Across 58 MoE layers that is 2.55 B parameters, 2.55 GB in fp8: one expert slot per layer fits easily on a GPU, with the rest of HBM left for cache.

tokens_per_expert, batch_for_compute_bound_experts; test_moe_expert_parallel.

No single GPU can hold a batch of 9,451 sequences' caches, but a cluster can, if the experts are spread across it. That is expert parallelism (EP) for inference: attention runs data-parallel (each GPU holds its own sequences and their caches), and before each MoE layer an all-to-all sends every token to the GPUs holding its chosen experts and back (Chapter 20 §20.6). Every GPU then runs few experts on many tokens, which is the regime a GPU is good at. DeepSeek's report (§3.4) describes exactly this split:

  • Prefill on units of 4 nodes, 32 GPUs: attention with 4-way tensor parallelism and sequence parallelism, 8-way data parallelism; MoE with EP32, plus 32 redundant copies of the most-loaded experts.
  • Decode on units of 40 nodes, 320 GPUs: MoE with EP320, each GPU hosting a single routed expert (per layer), with 64 GPUs holding redundant and shared experts, and the all-to-all over InfiniBand using direct GPU-initiated transfers to keep latency low.

Two consequences worth carrying away. Load balance becomes a serving problem: the busiest expert's GPU sets the step time for the whole cluster, which is why the deployment duplicates hot experts, re-chosen from observed load statistics. And MoE is cheap per token only at scale: on a single 8-GPU node at modest batch, an MoE reads most of its experts every step and behaves like a dense model of its total size. Small deployments of large MoEs are bandwidth-bound; the economics of §18.5 arrive only when the batch per expert does.

18.10 · Many fine-tunes on one GPU: multi-LoRA serving

LoRA (Hu et al., 2021; Chapter 23) fine-tunes a model by learning a low-rank update to chosen weight matrices instead of changing them: W' = W + (α/r) · B A, with A of shape (r, din) and B of shape (dout, r), and r small (8 to 64). A product with a thousand customer fine-tunes is then one base model plus a thousand small adapters, and the serving question is how to batch requests that use different adapters.

Worked example — a rank-16 adapter on Llama-3-8B
1
Size. Adapting all seven matrices of every block (q, k, v, o, gate, up, down) adds r(din + dout) per matrix: 
per layer: 16 × [(4096+4096) + 2×(4096+1024) + (4096+4096) + 2×(4096+14336) + (14336+4096)]
         = 16 × 81,920 = 1,310,720
× 32 layers = 41,943,040 parameters = 83.9 MB in bf16      0.52% of the base model
A thousand adapters are 84 GB, on disk or in CPU memory; a thousand full fine-tunes would be 16 TB.
2
The batch cost nobody mentions. FLOPs per token rise by 0.52%, nothing. But in a decode step each distinct adapter in the batch must be read from HBM, like the weights. A batch of 64 requests using 64 different adapters reads 64 × 83.9 MB = 5.37 GB of adapter weights per step, a third of the base model's 16.06 GB. Batching requests that share adapters is worth real throughput.

lora_params, lora_batch_bytes; test_multi_lora.

Systems such as Punica (Chen et al., 2023) and S-LoRA (Sheng et al., 2023) make this work: the base model's matmul runs once for the whole batch, and a custom kernel (Punica's segmented gather matrix-vector multiply, SGMV) applies each request's own A and B in one launch, gathering the right adapter per row. S-LoRA adds paging for adapters, keeping the hot ones in GPU memory in the same pool as the KV cache and fetching cold ones from CPU memory on demand, and reports serving thousands of adapters on one GPU. vLLM and SGLang support multi-LoRA batching on the same principles. The alternative, merging each adapter into a full copy of the weights, is fastest per request and hopeless beyond a handful of fine-tunes.

18.11 · Where the cache lives: offload tiers

Prefix caching (§18.1) only helps if the cached prefix is still there when the next request needs it. HBM is small, so engines evict, and an evicted prefix must be recomputed by prefill. The alternative is a hierarchy: keep evicted KV blocks in CPU memory, then on local SSD, then in a shared store, and copy them back when a request hits them. Whether that pays depends on one comparison: reload time vs recompute time.

Worked example — an 8,192-token prefix of Llama-3-8B 
cache to restore:   8,192 × 128 KiB                              = 1.00 GiB

reload over PCIe 5.0 x16 (~64 GB/s)                               =  16.8 ms
reload from a local NVMe SSD (~7 GB/s)                             = 153.4 ms
recompute by prefill:  2N·T + 2·n_layer·d·T²  = 1.49 × 10¹⁴ FLOPs
                       at 50% of 989.4 TFLOP/s                     = 301.5 ms

From CPU memory the prefix comes back 18× faster than recomputing it; even from SSD, 2× faster, and the GPU is free to do other work during a transfer while recompute occupies it. The ratio improves with context length, because recompute grows with T² (attention) while reload grows with T. reload_vs_recompute, test_kv_offload_break_even; link speeds are round assumptions, check your hardware.

This is what LMCache (an open-source KV-cache layer for vLLM) and Moonshot AI's Mooncake (the "KVCache-centric" architecture behind its Kimi service, Qin et al., 2024) build: a pool of CPU memory and SSD across the cluster, holding KV blocks addressed by a hash of the token prefix, so a long document or a multi-turn conversation is prefilled once and reused by whichever GPU serves the next turn. Prefill–decode disaggregation (§18.8) needs the same machinery, since prefill nodes hand their caches to decode nodes. The limits are the links: PCIe is about 50× slower than HBM (Chapter 14 §14.9), so offload holds caches between requests, never during attention.

18.12 · Structured output inside the engine

Chapter 13 §13.4 showed how a grammar becomes a token mask. Inside a serving engine the issue is timing. The mask for step t+1 depends on the token chosen at step t, it is computed on the CPU, and the GPU's decode step for a small model can take only a few milliseconds. A slow mask idles the GPU for every structured request in the batch. Three engineering moves make it cheap:

  • Precompute what you can. XGrammar caches masks for context-independent tokens per automaton state and checks only the few stack-dependent tokens live (Dong et al., 2024, report mask generation up to 100× faster than earlier engines).
  • Overlap. Compute the next mask on the CPU while the GPU runs the forward pass, so it is ready when the logits are.
  • Skip the model where the grammar decides. When only one continuation is legal (the rest of a JSON key, a closing "},), there is nothing to sample. SGLang's jump-forward decoding (Zheng et al., 2023) appends those tokens directly, which can make structured output faster than free text. It has to respect token boundaries: forcing in characters must not leave the model with a non-canonical tokenization (Chapter 13 §13.4), so the engine re-tokenizes at the jump.

vLLM and SGLang expose structured output through backends including XGrammar, llguidance and Outlines; a request carries a JSON schema or a grammar, and the engine attaches a matcher to that sequence.

Why do large MoE deployments spread one model's experts over hundreds of GPUs (DeepSeek's EP320) rather than replicate the whole model on 8-GPU nodes?
The model does not fit on 8 GPUs at all
Each expert needs hundreds of tokens per step to be compute-bound; only a very large global batch, spread over many GPUs, gives every expert that many
Expert parallelism removes the all-to-all
It reduces the KV cache
Batch per expert. Tokens per expert = b·k/E. At 256 experts, top-8, an fp8 expert on an H100 needs ~295 tokens, a global batch of ~9,451: possible across a cluster, not on one node.
A batch of 64 decoding requests uses 64 different rank-16 LoRA adapters on Llama-3-8B. What extra cost dominates?
The adapters' FLOPs, which double the step
Nothing: adapters are free
Merging each adapter into the weights every step
Reading 64 distinct adapters, 5.37 GB per step, about a third of the base weights' traffic
Bandwidth again. The extra FLOPs are 0.5%. Each distinct adapter must be read once per step, so batch requests that share adapters where you can.
Is it worth offloading an evicted 8k-token prefix to CPU memory rather than recomputing it later?
Yes: reloading 1 GiB over PCIe takes ~17 ms; recomputing it takes ~300 ms of GPU time
No: PCIe is slower than recomputing
Only for prefixes under 100 tokens
Only if the prefix is in fp32
18× faster, and the GPU is not busy while it waits. And the gap grows with length, because recompute pays the T² attention term.
What does jump-forward decoding do?
Skips layers of the model for easy tokens
Drafts tokens with a smaller model
Appends tokens the grammar forces (only one legal continuation) without running the model for them
Jumps to the end of the prompt during prefill
No choice, no sampling. When the grammar allows exactly one continuation, append it. The engine must re-tokenize so the model is not left on a non-canonical token path.

18.1Implement speculative decodinghard

Using two models from the same family (e.g. GPT-2 small as draft, GPT-2 large as target), implement speculative decoding with the exact acceptance rule. Then verify the guarantee empirically: generate 2000 tokens with (a) plain sampling from the target and (b) speculative decoding, both at T=1.0, and compare the resulting unigram distributions with a chi-squared test.

Core loop
def speculative_step(target, draft, ids, k=4):
    # 1. draft k tokens autoregressively
    draft_ids, q_probs = [], []
    cur = ids
    for _ in range(k):
        q = draft(cur)[:, -1].softmax(-1)
        t = torch.multinomial(q, 1)
        draft_ids.append(t); q_probs.append(q.gather(-1, t))
        cur = torch.cat([cur, t], dim=1)

    # 2. ONE target pass scores all k+1 positions
    p_all = target(cur)[:, -(k+1):].softmax(-1)

    # 3. accept/reject left to right
    n = 0
    for i in range(k):
        p_i = p_all[:, i].gather(-1, draft_ids[i])
        if torch.rand(1) < min(1.0, (p_i / q_probs[i]).item()):
            n += 1
        else:
            # resample from the normalised residual
            resid = (p_all[:, i] - draft(...)[i]).clamp(min=0)
            return torch.cat([ids, *draft_ids[:n],
                              torch.multinomial(resid / resid.sum(), 1)], dim=1)
    # all k accepted → bonus token from the target's (k+1)-th distribution
    return torch.cat([ids, *draft_ids, torch.multinomial(p_all[:, k], 1)], dim=1)

Report your acceptance rate. On natural text with a same-family draft, expect 60–80%; on code, higher. The chi-squared test should show no significant difference — that's the distributional guarantee, verified rather than assumed.

18.7Predict, then measure: prefix caching and offloadapplied

Prediction first: with vLLM serving a 7–8B model, a 6,000-token shared document, and 50 different short questions about it, how much lower will mean TTFT be with prefix caching on than off? Then measure it. If your vLLM build supports CPU offload of KV blocks (or LMCache), shrink GPU memory for the cache until the document is evicted between requests, and measure TTFT with and without offload.

How to read it

With caching, every question after the first skips about 6,000 tokens of prefill, so TTFT should fall several-fold. With an evicted prefix, offload should land between the cached and uncached TTFT, close to cached if the link is fast: §18.11's 1 GiB in ~17 ms over PCIe against hundreds of milliseconds to recompute. If offload is slower than recompute, check whether the transfer overlaps compute and whether the blocks went to SSD instead of CPU memory.
