10 · The Backward Pass, Derived

Everything so far said "autograd handles it". That is a hole. This chapter derives every gradient in a transformer by hand — softmax, cross-entropy, RMSNorm, attention — and checks each one against autograd. After this you can implement a backward pass, debug a wrong one, and read a CUDA kernel.

Builds onCh 05 — the forward attention you are about to differentiate
Ch 08 — RMSNorm and the residual
Leads toCh 11 — where these gradients get used
Ch 17 — why the backward pass can recompute tiles
Ch 19 — activation memory, sharded
Why this chapterThe layer under "autograd handles it", and the memory bill it sends. Every number is computed in tfs/memory.py and asserted in tests/test_training.py.
The whole chapter in five sentences

Backprop is one rule applied repeatedly: given ∂L/∂output, produce ∂L/∂input and ∂L/∂weights, and the chain rule stitches the layers together. The shapes nearly force each formula, and the interesting ones (softmax, cross-entropy's p − y, RMSNorm's correction term, attention) reduce to elementwise work plus a few reductions. Every backward formula needs values from the forward pass, so autograd saves them, and those saved activations (24 × d_model numbers per token per layer here) are what decide whether a long sequence fits. Checkpointing every layer and never materialising the vocabulary-sized logits cut that bill by more than ten times. Gradients may be stored in bf16 but must be summed in fp32, because a low-precision running total quietly drops what you add to it.

10.1 · The only rule

Write the network as a chain of functions. The loss is a scalar at the end:

x → f1 → h1 → f2 → h2 → … → L

Each layer receives the upstream gradient ∂L/∂hi — a tensor the same shape as its own output — and must return ∂L/∂hi−1, the same shape as its input.

Shapes make backprop almost mechanical

A gradient always has the same shape as the thing it is a gradient of. x.grad.shape == x.shape, always. So if the forward was 4, 3 @ 3, 5 → 4, 5, then backward takes a 4, 5 and must produce a 4, 3 and a 3, 5. There is usually only one way to contract the indices that gives those shapes — which is often enough to derive the formula.

Matmul, the base case

For C = A B with A of shape (m,k) and B of shape (k,n):

∂L∂A = ∂L∂C BT      ∂L∂B = AT ∂L∂C shapes: (m,n)(n,k) = (m,k) ✓  ·  (k,m)(m,n) = (k,n) ✓

Read those shapes. dL/dC is (m,n); to get something (m,k) you must multiply by something (n,k), and the only candidate is BT. The formula is forced.

10.2 · Softmax: the dense Jacobian

Softmax is the first genuinely interesting one, because every output depends on every input. So its derivative is not a vector but a full (n, n) Jacobian.

Let si = exi / Σj exj. Differentiate with the quotient rule, splitting on whether the index matches:

Derivation — two cases
1
Case i = j. Let Z = Σkexk. 
ds_i/dx_i = (e^x_i · Z − e^x_i · e^x_i) / Z²
          = (e^x_i/Z) · (1 − e^x_i/Z)
          = s_i(1 − s_i)
2
Case i ≠ j. The numerator exi does not depend on xj, only Z does: 
ds_i/dx_j = (0 · Z − e^x_i · e^x_j) / Z²
          = −s_i s_j
3
Combine with the Kronecker delta (δij is 1 when i=j, else 0):
∂si∂xj = si(δij − sj)   i.e.   J = diag(s) − s sT
=
Checked numerically at x = [1.0, 2.0, 0.5], so s = [0.2312, 0.6285, 0.1402]: 
autograd Jacobian        diag(s) − s sᵀ
[ 0.1778 −0.1453 −0.0324]   [ 0.1778 −0.1453 −0.0324]
[−0.1453  0.2335 −0.0881] = [−0.1453  0.2335 −0.0881]
[−0.0324 −0.0881  0.1206]   [−0.0324 −0.0881  0.1206]
Note it is symmetric, and every row sums to zero — because the outputs must keep summing to 1, so any increase somewhere is exactly paid for elsewhere.

The vector-Jacobian product, which is what actually runs

Frameworks never build that (n,n) matrix. They compute JTg directly for upstream gradient g:

∂L∂x = s ⊙ (g − (g·s)) one elementwise multiply and one dot product — O(n), not O(n²) 
def softmax_backward(s, g):
    """s: forward output. g: upstream gradient. Both (..., n)."""
    return s * (g - (g * s).sum(-1, keepdim=True))

# equals the full Jacobian product, without ever forming it
x = torch.tensor([1.0, 2.0, 0.5], requires_grad=True)
s = x.softmax(0); g = torch.tensor([0.3, -1.2, 0.7])
s.backward(g)
assert torch.allclose(x.grad, softmax_backward(s.detach(), g), atol=1e-6)

10.3 · Cross-entropy + softmax: why it collapses to p − y

Here is the most satisfying result in the chapter. Softmax alone has that dense Jacobian. Compose it with cross-entropy and almost everything cancels.

With L = −log pc for correct class c, and p = softmax(z):

Derivation — three lines
1
Gradient of the loss w.r.t. the probabilities. Only the correct class appears in the loss: 
dL/dp_i = −1/p_c   if i = c,   else 0
2
Chain through the softmax Jacobian. Only the i=c term survives step 1: 
dL/dz_j = Σ_i (dL/dp_i)(dp_i/dz_j)
        = (−1/p_c) · p_c(δ_cj − p_j)
        = −(δ_cj − p_j)
        = p_j − δ_cj
3
In vector form, with y the one-hot target:
∂L∂z = p − y
=
Checked at logits = [2.0, 1.0, 0.1], target class 0: 
p        = [ 0.6590,  0.2424,  0.0986]
p − y    = [−0.3410,  0.2424,  0.0986]
autograd = [−0.3410,  0.2424,  0.0986]   ✓
Read what p − y says

The gradient on each logit is simply "how much probability you assigned minus how much you should have". The correct token gets a negative gradient proportional to how much mass it was missing; every wrong token gets a positive one proportional to the mass it stole. It is the prediction error, nothing more.

And this is why you must never softmax before cross_entropy. PyTorch's F.cross_entropy takes logits precisely so it can use this fused, stable form. Feed it probabilities and you apply softmax twice — the loss still decreases, so it looks like it works, while the gradients are wrong.

10.4 · RMSNorm: where the gradient gets a correction term

Forward (dropping γ for clarity): y = x / r where r = √(mean(x²)).

The subtlety: r depends on every element of x, so changing x1 changes all the outputs. That produces a second term:

∂L∂x = 1r [ g ⊙ γ − x (g ⊙ γ) · xd · r² ] first term: the obvious rescale. second: the correction because r moved too.
Verified, and what the correction term does

x = [3, 1, 4, 8], rms = 4.7434, upstream g = [1, 0, 0, 0]:

autograd:  [ 0.189737, −0.007027, −0.028109, −0.056218]
formula :  [ 0.189737, −0.007027, −0.028109, −0.056218]   ✓

Look at what happened: we pushed only on element 0, yet elements 1–3 received negative gradient. Raising x0 would raise the RMS, which would shrink everything else — so the gradient pre-emptively pushes them the other way.

The geometric fact: dot(grad, x) = 0.0, exactly. The gradient is orthogonal to x. Normalisation makes the layer invariant to the scale of its input, so the gradient carries no component that would merely rescale x — that direction cannot change the loss, so it gets zero gradient. This is the mechanism behind "normalisation stabilises training", stated precisely.

def rmsnorm_backward(x, g, gamma, eps=0.0):
    d = x.shape[-1]
    r = x.pow(2).mean(-1, keepdim=True).add(eps).sqrt()
    gg = g * gamma
    return (gg - x * (gg * x).sum(-1, keepdim=True) / (d * r**2)) / r

x = torch.tensor([3., 1., 4., 8.], requires_grad=True)
gamma = torch.ones(4); g = torch.tensor([1., 0., 0., 0.])
(x / x.pow(2).mean().sqrt() * gamma).backward(g)
assert torch.allclose(x.grad, rmsnorm_backward(x.detach(), g, gamma), atol=1e-6)
assert abs(torch.dot(x.grad, x.detach())) < 1e-5          # orthogonal

10.5 · Attention backward, all three gradients

Now assemble. Forward: S = QKT/√d, P = softmax(S), O = PV. Given dO, we need dQ, dK, dV.

Derivation — walk the chain backwards
1
O = PV, so by the matmul rule: 
dV = Pᵀ @ dO           (T,T)ᵀ(T,d) -> (T,d) ✓
dP = dO @ Vᵀ           (T,d)(d,T)  -> (T,T) ✓
2
Through the softmax, row by row, using §10.2's VJP: 
dS = P ⊙ (dP − rowsum(dP ⊙ P))
3
S = QKT/√d, matmul rule again: 
dQ = dS  @ K / √d
dK = dSᵀ @ Q / √d
=
All three verified against autograd for random (T=4, d=3) inputs — match to 1e-5. 
def attention_backward(q, k, v, P, dO):
    dk_ = q.shape[-1]
    dV = P.transpose(-2, -1) @ dO
    dP = dO @ v.transpose(-2, -1)
    dS = P * (dP - (dP * P).sum(-1, keepdim=True))       # softmax VJP
    dQ = dS @ k / dk_**0.5
    dK = dS.transpose(-2, -1) @ q / dk_**0.5
    return dQ, dK, dV
Now Chapter 17 makes sense at the kernel level

Look at what step 2 needs: P and a row sum. No (T,T) Jacobian is ever constructed — the softmax backward is elementwise plus one reduction. That is exactly why FlashAttention can throw P away in the forward pass and recompute it tile by tile in the backward: each tile of dS needs only the corresponding tile of P and a running row statistic. Without this structure, the recomputation trick would be impossible.

10.6 · The residual connection, quantified

Chapter 4 asserted that y = x + f(x) gives ∂y/∂x = 1 + f′(x). Here is what that does over depth.

Why 100 layers train at all
1
Plain stack. The gradient reaching layer 1 is a product of every Jacobian above it. If each has magnitude 0.9: 
20 layers:  0.9²⁰ = 0.1216      <- 8× weaker
50 layers:  0.9⁵⁰ = 0.0052      <- 190× weaker
100 layers: 0.9¹⁰⁰ = 0.0000266  <- 37,600× weaker, effectively dead
2
Residual stack. Each term is (1 + f′). Even when f′ is small, the 1 survives, so the product stays near 1 and the gradient reaches layer 1 essentially undamped.
=
Verified: f(x)=0.3x² at x=2 gives f′=1.2, and autograd returns 2.2000 for d(x+f)/dx — exactly 1 + 1.2.
Why does F.cross_entropy take logits rather than probabilities?
Probabilities would be slower to compute
Fusing softmax with the loss lets the gradient collapse to the stable, exact p − y
Logits use less memory
It doesn't matter; both work
The fused gradient. Separately, softmax has a dense Jacobian and log of a tiny probability is numerically nasty. Fused, everything cancels to p − y — one subtraction, no cancellation error. If you softmax first and then call cross_entropy, you apply softmax twice; loss still falls, so it looks like it works, while gradients are wrong.
You push upstream gradient on one element of an RMSNorm output. Why do the other elements receive nonzero gradient?
A bug — they should be zero
Because γ mixes the channels
Because the RMS depends on every element, so changing one changes all the outputs
Because of the epsilon term
The normaliser couples them. Raising one element raises the RMS, which shrinks every other output — so the gradient includes a correction pushing them the other way. The result is a gradient exactly orthogonal to x: the direction that merely rescales the input cannot change the loss, so it receives no gradient. (γ is elementwise and does not mix channels.)
What does the softmax backward need, and why does that matter for FlashAttention?
Only P and a row sum — elementwise plus one reduction, so P can be recomputed tile by tile
The full (T,T) Jacobian, which must be stored
The original logits S, which must be stored
Nothing — softmax has no gradient
P and a row sum. dS = P ⊙ (dP − rowsum(dP ⊙ P)) is elementwise plus one reduction. No Jacobian is materialised, and each tile is independent given its row statistic — which is precisely what lets FlashAttention discard P in the forward pass and rebuild it in SRAM during backward.

10.7 · What backward keeps: the memory bill

Every formula above needs something from the forward pass. The matmul rule needs the input A to form ∂L/∂B = AT ∂L/∂C. The softmax VJP needs the output s. RMSNorm needs x and r. Autograd's answer is simple: during the forward pass, every operation saves the tensors its backward will need and holds them until backward has used them. Those saved tensors are the activations, and in any real training run they are the largest thing in memory that is not a weight.

You can count them exactly. PyTorch lets you intercept every tensor autograd saves (torch.autograd.graph.saved_tensors_hooks). tfs.memory.measure_saved uses that hook, counts each storage once, and skips the weights (they exist anyway). Run it over one Block of the course's own model and read off what is kept, per token:

one tfs Block, per token, weights excluded          elements
  RMSNorm 1   x, 1/rms, x·(1/rms), output                3C + 1
  attention   q, k, v (as SDPA receives them)            3·H·dh     <- k, v ALREADY expanded to H heads
              SDPA output (= the o_proj input)            H·dh
              one logsumexp per head                      H
  RMSNorm 2   same as above                              3C + 1
  SwiGLU      gate(x), silu(gate), up(x), their product   4·d_ff
  ---------------------------------------------------------------
  total       6C + 2 + 4·H·dh + H + 4·d_ff

For the test configuration (C = 96, H = 4, dh = 24, d_ff = 256) that is 1,990 elements per token. With B = 2, T = 64 in fp32 the formula predicts 1990 × 128 × 4 = 1,018,880 bytes, and the hooks measure exactly 1,018,880 (test_saved_tensor_count_matches_autograd in tests/test_training.py). Four details in that table are worth a second look:

  • The norm saves its input and its output. They are different tensors (the output is what the next matmul needs), so a norm costs about 3C, not C.
  • The attention output and the o_proj input share storage. The kernel writes its output in a (B, T, H, dh) layout, so the transpose-and-reshape in tfs/model.py is a free view. Had it been a copy, you would pay another H·dh per token.
  • GQA saves nothing here. tfs/model.py calls repeat_interleave before scaled_dot_product_attention, so autograd saves K and V at all H heads, not the n_kv_head the model actually has. A GQA-aware kernel (SDPA's enable_gqa, FlashAttention) saves them at n_kv_head width. Chapter 16's saving is a KV-cache saving; whether it is also an activation saving depends on the kernel.
  • No (T, T) matrix. The attention probabilities are not saved. The kernel keeps one logsumexp per row and rebuilds P in backward, which is §10.5's structure turned into memory. Without it the table would have an H·T term per token, which at T = 8192 is larger than everything else combined.
Worked example — the activations of Llama-3-8B at 8k context

C = 4096, H = 32, dh = 128, KV heads = 8, d_ff = 14336, 32 layers, one sequence of T = 8192, bf16 (2 bytes per element).

1
Per token per layer: 
6·4096 + 2 + 4·32·128 + 32 + 4·14336
= 24,578 + 16,384 + 32 + 57,344 = 98,338 elements   = 24.0 × C
The MLP is 58% of it: four tensors of width d_ff = 3.5 C.
2
Per layer, then the whole model: 
98,338 × 8192 tokens × 2 bytes = 1.61 GB per layer
× 32 layers                     = 51.6 GB of activations       (the bf16 weights: 16 GB)
GQA-aware kernel (K, V at 8 heads): 92,194 per token  ->  48.3 GB
=
One 8k-token sequence needs three times the memory of the weights, before the optimizer state (Chapter 12's 16 bytes per parameter) and before the logits (§10.8). Activations scale with B × T × layers and weights do not, so at long context the activations decide what fits.

Activation checkpointing, derived

The fix trades compute for memory. Keep only each layer's input (one C-wide tensor per token, the "boundary"), throw the 24 C of internals away, and when backward reaches a layer, re-run its forward from the saved input to rebuild them. Generalise to a checkpoint every k layers, with a one layer's internals and b one boundary, both per token. You store L/k boundaries, and while backward works through one segment you hold that segment's k layers of internals:

M(k) = Lk · b + k · (a + b)      minimised at   k* = √(L · b / (a + b)) the classic √L result is the special case a ≈ b

Chen et al. (2016) derived checkpointing for networks whose internals and boundaries are about the same size; then k* ≈ √L and memory falls from O(L) to O(√L). A transformer is not that network. Its internals are 24× its boundary, so k* = √(32/25) = 1.13: checkpoint every layer. With tfs.memory.checkpoint_memory on the Llama-3-8B numbers:

checkpoint every k layers      activation memory, T = 8192
  k = 1                        3.83 GB     <- 32 boundaries (2.15 GB) + one layer re-run (1.68 GB)
  k = 2                        4.43 GB
  k = 4                        7.25 GB
  k = 8                       13.69 GB
  none                        51.6 GB

The price is one extra forward per layer. Backward costs about twice the forward, so a step goes from 3 forward-equivalents to 4: about 33% more compute for a 13× memory cut. That is why per-layer checkpointing is a standard switch in every large-scale framework, and why Chapter 19's selective recomputation (re-run only the wide, cheap parts) is worth the trouble: it recovers most of the memory for a few percent of the compute.

from torch.utils.checkpoint import checkpoint

for blk in model.blocks:                       # keep only each block's input
    x, _ = checkpoint(blk, x, cos, sin, use_reentrant=False)

10.8 · The vocabulary-sized logits

After checkpointing, the biggest activation is usually not in any layer. It is at the very end. The LM head produces one logit per vocabulary entry per position, a (B·T, V) tensor, and V is large. Llama 3's vocabulary has 128,256 entries:

N = B·T = 8192 positions, V = 128,256
  logits, bf16                     2.10 GB
  log-softmax, fp32 (saved)        4.20 GB     <- what F.cross_entropy keeps for backward
  dL/dlogits, fp32 (in backward)   4.20 GB
  ----------------------------------------
                                  10.5 GB      vs 3.83 GB for ALL 32 checkpointed layers

Measured: F.cross_entropy on a (4096, 8000) fp32 logit matrix saves one (4096, 8000) fp32 tensor, 131 MB: the log-probabilities it needs to form p − y (test_cross_entropy_saves_a_vocab_sized_tensor). Checkpointing the layers does not touch it.

The fix: never build the whole matrix

§10.3 already contains the escape. The gradient of the loss with respect to the logits is (p − y)/N, and each row depends only on its own position. So split the N positions into chunks. For each chunk, compute its logits, its share of the loss, its p − y, and immediately push that gradient through the head matmul to get the chunk's share of ∂L/∂h and ∂L/∂W. Then discard the chunk's logits. That is the idea behind Liger Kernel's fused linear cross-entropy and Cut Cross-Entropy, and tfs.memory.chunked_cross_entropy does it in about 25 lines:

for s in range(0, N, chunk):
    z   = h[s:s+chunk] @ W.T                       # (n, V)   only this chunk exists
    lse = torch.logsumexp(z, -1)                   # (n,)
    loss += (lse - z.gather(1, t[s:s+chunk, None]).squeeze(1)).sum()
    g = (z - lse[:, None]).exp()                   # softmax
    g[range(n), t[s:s+chunk]] -= 1                 # p - y   (section 10.3)
    g /= N
    grad_h[s:s+chunk] = g @ W                      # (n, C)
    grad_W += g.T @ h[s:s+chunk]                   # (V, C)
# backward() just returns grad_h and grad_W, scaled by the incoming gradient

It matches F.cross_entropy to 1e-12 in float64, the loss and both gradients (test_chunked_cross_entropy_is_exact). What it saves for backward is ∂L/∂h and ∂L/∂W, (N + V)·C elements and nothing of size N·V (measured, same test as above). The largest temporary is one chunk: 1024 × 128,256 × 4 bytes = 0.53 GB instead of 10.5 GB. The FLOPs are unchanged; it is the same matmuls in a different order.

Two ways the logits bite that are not about memory

Do the softmax in fp32. The logits may be bf16, but the logsumexp over 128k entries is a reduction and needs fp32 (§10.10 and Chapter 12). Mind the tied embedding. With tie_embed=True, W is also the embedding table, so its gradient is the head gradient plus the embedding's scatter-add (§10.9). Autograd adds them; a hand-fused kernel must too.

Why does training need memory proportional to B × T × layers beyond the weights?
Autograd stores a copy of the weights for each token
Autograd stores the full Jacobian of every layer
Each op's backward needs some of its forward inputs or outputs, so they are saved until backward uses them
Gradients for every intermediate tensor are computed during the forward pass
Backward formulas consume forward values. ∂L/∂B = Aᵀ ∂L/∂C needs A, so A must survive until backward reaches that matmul. Every per-token tensor some backward needs is kept, which is why the bill scales with tokens and layers. No Jacobian is ever stored.
For a transformer the best checkpoint interval comes out near 1 layer, not √L. Why?
Each layer's internals (~24 C per token) dwarf its boundary (C), so boundaries are cheap to store and several layers of internals are expensive to hold
Transformers have too few layers for √L to matter
Recomputation is free on GPUs
The residual stream cannot be checkpointed
k* = √(L·b/(a+b)). With a = 24b and L = 32, k* = 1.13. The √L rule assumes a ≈ b. Computed: one checkpoint per layer needs 3.83 GB, one every 4 layers 7.25 GB.
You checkpoint every layer of an 8B model at T = 8192 with a 128k vocabulary, and memory is still dominated by one place. Which?
The attention probability matrices
The embedding lookup
The RoPE cos/sin tables
The (B·T, V) logits and the fp32 log-softmax cross-entropy saves for backward
About 10.5 GB at the very end (bf16 logits, fp32 log-probabilities, fp32 gradient) against 3.83 GB for all checkpointed layers. The fix is a chunked or fused cross-entropy.
How can a chunked cross-entropy avoid saving any vocabulary-sized tensor for backward?
It stores the logits in fp8
The logit gradient is p − y row by row, so it can be formed during the forward pass and pushed straight through the head matmul into ∂L/∂h and ∂L/∂W
It drops rare tokens from the vocabulary
It approximates the softmax by sampling
The gradient is local and known in closed form (§10.3), so it need not wait for backward. The result is exact to 1e-12, and the saved state is (N + V)·C instead of N·V.

10.9 · Three more backward passes: embedding, SwiGLU, RoPE

The chapter so far covered every op with an interesting Jacobian. Three more appear in every modern model, and each has one idea worth knowing.

The embedding: a gather, so a scatter-add

The forward pass is a lookup: row ids[i] of the table becomes position i's vector. Nothing is multiplied, so the backward is bookkeeping: each position's upstream gradient is added into the row it came from. A token that appears three times gets the sum of three gradients; a token that does not appear gets exactly zero.

def embedding_backward(ids, grad_out, V):        # ids (N,), grad_out (N, C)
    g = torch.zeros(V, grad_out.shape[-1])
    return g.index_add_(0, ids, grad_out)           # (V, C): a scatter-ADD, not a scatter

E = nn.Embedding(10, 4); ids = torch.tensor([3, 7, 3, 3, 1])
E(ids).backward(g)
assert torch.allclose(E.weight.grad, embedding_backward(ids, g, 10))   # row 3 = g[0] + g[2] + g[3]

Two consequences. The gradient is sparse in rows: in a batch of 8k tokens drawn from a 128k vocabulary most rows get nothing, so the Adam moments of rare tokens update rarely (one reason some recipes turn off weight decay on embeddings, Chapter 11). And the scatter-add has collisions: positions with the same id write to the same row, which on a GPU means atomic adds or a sort first. Atomic fp32 adds in a different order give slightly different sums, one of the sources of run-to-run nondeterminism.

SwiGLU: the product rule, twice

y = silu(a) ⊙ b, with a = x Wgate and b = x Wup. The product rule splits the gradient between the branches, and silu's derivative follows from silu(a) = a·σ(a):

∂L/∂b = g ⊙ silu(a)      ∂L/∂a = g ⊙ b ⊙ σ(a) (1 + a (1 − σ(a))) σ is the sigmoid; both then flow back through their matmuls (§10.1)

Read what backward needs: a, b and silu(a), all d_ff wide. That is the 4·d_ff in §10.7's table (the fourth is the product, which down needs). silu(a) is cheap to recompute from a, which makes it a textbook target for selective recomputation: keep a and b, drop silu(a) and the product, and the MLP's saved memory halves for two elementwise ops in backward. tfs.memory.swiglu_backward is checked against autograd in float64 (test_swiglu_backward).

RoPE: rotate the gradient back

RoPE (Chapter 7) multiplies each pair of dimensions by a 2×2 rotation R(θ). A rotation is orthogonal, so its transpose is its inverse: R(θ)T = R(−θ). The backward of "rotate by θ" is "rotate the gradient by −θ", which is the forward code with sin negated:

def rope_backward(g, cos, sin):                 # forward: x*cos + rotate_half(x)*sin
    return g * cos - rotate_half(g) * sin       # R(-theta): same cos, opposite sin

Nothing new needs saving (cos and sin are fixed buffers), and the gradient's norm is preserved exactly, because rotations preserve length (test_rope_backward_is_inverse_rotation checks both).

10.10 · Gradients in low precision

In a mixed-precision run (Chapter 12) the matmuls run in bf16, so the activation gradients they produce are bf16 too. A single bf16 gradient is fine: its rounding error of at most 0.4% is small next to minibatch noise. The damage happens where gradients are added up, because a running total in bf16 rounds every addend against the size of the total. Gradients are summed in three places: gradient accumulation across micro-batches, the data-parallel all-reduce, and inside the backward kernels themselves (∂L/∂W is a sum over all B·T tokens).

Measured with tfs.memory.accumulate: 64 micro-batch gradients of 100,000 entries each (mean 2e-3, spread 1e-3), summed with the running total held in each format, against a float64 sum:

running total in      relative error of the summed gradient
  bf16                7.4e-03        <- 0.74%: each add rounds to an 8-bit significand
  fp16                9.3e-04
  fp32                1.1e-07        <- about 65,000× better than bf16

0.74% does not sound like much, but it is not zero-mean noise. Once the total is large, every new addend is rounded relative to the total, so later micro-batches are systematically mis-counted and the error grows with the number of terms. It is Chapter 12's fp16 accumulator stall, one format over (test_gradient_accumulation_dtype).

The rule, and where each framework applies it

A gradient may live in bf16; a running sum of gradients may not. Tensor cores accumulate matmul partial sums in fp32, so the sum over tokens inside ∂L/∂W is safe. Under autocast, .grad has the parameter's dtype, which is fp32 for fp32 master weights, so micro-batch accumulation is safe too. The all-reduce is the one you choose: FSDP's MixedPrecision(reduce_dtype=...) and DDP's communication hooks let you reduce in bf16 to halve the bytes, and large runs sometimes do, accepting the error for the bandwidth. Chapter 19 prices that trade.

def check(fn_forward, manual_backward, *inputs):

    out = fn_forward(*ins)

    out.backward(g)

10.2Gradient checking from first principlesessential

Before autograd existed, this is how everyone verified a backward pass. Central differences:

∂L∂xi ≈ L(x + εei) − L(x − εei)2ε 
def grad_check(f, x, eps=1e-6):
    x = x.double()
    num = torch.zeros_like(x)
    for i in range(x.numel()):
        xp, xm = x.clone(), x.clone()
        xp.view(-1)[i] += eps; xm.view(-1)[i] -= eps
        num.view(-1)[i] = (f(xp) - f(xm)) / (2 * eps)
    xa = x.clone().requires_grad_(True); f(xa).backward()
    rel = (num - xa.grad).norm() / (num.norm() + xa.grad.norm())
    return rel.item()          # want < 1e-7 in float64
Why central and not forward differences

Forward differences (L(x+ε) − L(x))/ε have error O(ε); central differences have O(ε²). With ε=1e-6 the truncation errors are ~1e-6 and ~1e-12, but float64 rounding adds about machine-ε/ε ≈ 1e-10, so in practice the central difference lands near 1e-10 to 1e-11 — still four orders of magnitude better than the forward difference — enough to distinguish a correct formula from a subtly wrong one. Also: do this in float64. In float32 the subtraction of two nearly-equal numbers loses most of your significant digits, and everything looks wrong.

10.3Measure the residual's effect on gradient flowcode

Build a 40-layer stack of x -> tanh(Wx) with and without a residual connection. Do one backward pass and plot grad.norm() per layer on a log axis.

What you should see

Without residuals the gradient norm decays roughly geometrically with depth — a straight line on a log axis. How many orders of magnitude depends on the weight scale, which the exercise leaves open: with PyTorch's default nn.Linear init (std ≈ 1/√(3d)) it is about ten orders between layer 40 and layer 1; with std = 1/√d it is barely one. Fix the init and report it. With residuals it is nearly flat. That plot is the vanishing-gradient problem, and it is far more convincing than any prose about it.

10.4Break cross-entropy on purposethinking

Compute the loss two ways and compare both the value and the gradient:

logits = torch.randn(4, 10, requires_grad=True)
target = torch.randint(0, 10, (4,))

a = F.cross_entropy(logits, target)                    # correct
b = F.cross_entropy(logits.softmax(-1), target)        # softmax applied TWICE
c = F.nll_loss(logits.softmax(-1).log(), target)       # also correct, less stable
  1. Which two agree? By how much do the gradients differ?
  2. Now set logits = logits * 50 and compare a against c. What happens to c, and why?
Answers
  1. a and c agree. b is wrong — it softmaxes an already-normalised vector, which flattens it drastically, so the loss is far too uniform and the gradient direction is wrong. Critically b still decreases during training, which is why this bug survives code review.
  2. At ×50 the largest logits dominate completely; softmax underflows the small entries to exactly 0, and log(0) = −inf. Version a is fine because the fused kernel uses the log-sum-exp trick internally and never materialises a zero probability. This is what "numerically stable" buys you — not accuracy in the last decimal, but the difference between a number and inf.

10.7Fuse the loss, then measure the peakcode

On a GPU (or with tracemalloc-style accounting on CPU), compare peak memory of F.cross_entropy(h @ W.T, t) against tfs.memory.chunked_cross_entropy(h, W, t, chunk) for N = 8192, C = 1024, V = 128,256 and chunk ∈ {256, 1024, 4096}. Predict each peak from §10.8 first.

What you should find

The full version peaks at several N·V·4-byte tensors (4.2 GB each in fp32). The chunked version peaks near chunk·V·4 bytes plus the fixed ∂L/∂h and ∂L/∂W buffers, so its peak is linear in the chunk size and the step time is nearly flat until the chunk gets so small that the matmuls stop filling the GPU. That knee is the chunk size to use.

10.8Predict, then measure, a bf16 accumulatorthinking

Using the gap formula from Chapter 0, predict how many micro-batch gradients of size ≈ 2e-3 you can add to a bf16 running total before the next one changes it by less than half of its own value. Then measure it with tfs.memory.accumulate by sweeping the number of micro-batches from 8 to 512.

The prediction

bf16 has 8 significant bits, so the gap at a total of S is about S·2−7 (one step) and an addend is rounded to a multiple of that gap. An addend of 2e-3 starts losing half of itself once the gap reaches 2e-3, i.e. S ≈ 2e-3 · 27 ≈ 0.26, about 128 micro-batches. Below that the error is rounding noise; above it the total visibly stalls. fp32's gap is 216 times finer, which is the whole argument for fp32 accumulation.
