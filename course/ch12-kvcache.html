12 · The KV Cache and the Memory Wall

This chapter explains why serving an LLM is a fundamentally different engineering problem from training one, and why almost every architectural innovation since 2023 — GQA, MLA, MoE, speculative decoding — is aimed at the same bottleneck. It is not FLOPs. It is memory bandwidth.

12.1 · The waste in the naive loop

Look again at generation. To produce token 101, we feed tokens 1–100 through the model. To produce token 102, we feed tokens 1–101. We recompute K and V for tokens 1–100 a second time — and they are identical, because the causal mask means token 50's representation cannot depend on anything after it.

The insight

In a causal model, the K and V vectors for a token never change once computed. So compute them once and keep them. Generating token t+1 then only needs a single new query vector attending against the stored keys and values.

Without cacheWith cache

12.2 · Implementation

class CachedAttention(nn.Module):
    def forward(self, x, cache=None):
        """
        Training / prefill:  x is (B, T, C), cache is None
        Decoding:            x is (B, 1, C), cache holds (k_prev, v_prev)
        """
        B, T, C = x.shape
        q, k, v = self.qkv(x).split(C, dim=-1)
        q = q.view(B, T, self.nh, self.hd).transpose(1, 2)     # (B, nh, T, hd)
        k = k.view(B, T, self.nh, self.hd).transpose(1, 2)
        v = v.view(B, T, self.nh, self.hd).transpose(1, 2)

        q, k = apply_rope(q, k, self.cos[pos:pos+T], self.sin[pos:pos+T])

        if cache is not None:
            k_prev, v_prev = cache                             # (B, nh, T_past, hd)
            k = torch.cat([k_prev, k], dim=2)                  # (B, nh, T_past+T, hd)
            v = torch.cat([v_prev, v], dim=2)
        new_cache = (k, v)

        # During decode T=1, so this is (B, nh, 1, T_total) — a single row.
        # No causal mask needed: the one query is the newest token, it may see everything.
        y = F.scaled_dot_product_attention(q, k, v, is_causal=(T > 1))

        return self.proj(y.transpose(1, 2).reshape(B, T, C)), new_cache
Three cache bugs that produce subtly wrong output
  1. RoPE position offset. During decode the new token is at absolute position T_past, not 0. Using cos[0] every step makes every token think it's first. Symptom: coherent for a few tokens, then degenerates.
  2. is_causal=True during decode. With a single query row, PyTorch's causal mask aligns to the top-left, so the one query is treated as position 0 and can see only key 0. Symptom: output ignores the entire prompt.
  3. Not clearing the cache between sequences. The next request inherits the previous conversation's keys. Symptom: bizarre contamination that only appears under batching.

12.3 · Prefill vs decode — two different machines

This distinction is the core of LLM serving, and it is not obvious until someone points it out.

Prefill — process the prompt
  • All T prompt tokens, one pass
  • Big matmuls: (T, C) @ (C, C)
  • Compute-bound — saturates the GPU
  • Cost ∝ prompt length
  • Determines time to first token
Decode — generate, one token at a time
  • Exactly 1 token per pass
  • Skinny matmuls: (1, C) @ (C, C)
  • Memory-bandwidth-bound — GPU mostly idle
  • Cost ∝ number of output tokens
  • Determines tokens per second

Why decode is memory-bound — the arithmetic

Consider a single (4096, 4096) weight matrix in bf16, generating one token.

Bytes moved:   4096 × 4096 × 2 bytes            = 33.5 MB   (read the weights)
FLOPs done:    2 × 1 × 4096 × 4096              = 33.6 MFLOP

Arithmetic intensity = 33.6e6 / 33.5e6 ≈ 1.0 FLOP per byte

An H100 delivers roughly 990 TFLOP/s (bf16, with sparsity off) against 3.35 TB/s of HBM bandwidth. Its ridge point — the intensity above which you're compute-bound — is about 295 FLOP/byte.

1 FLOP/byte  ≪  295 FLOP/byte decode sits ~300× below the ridge: the GPU is a memory-transfer device that occasionally multiplies
The consequence, stated plainly

During decode, you read every weight in the model and every byte of the KV cache from HBM to produce one token. Your token rate is therefore approximately:

tokens/sec ≈ memory bandwidthmodel bytes + KV cache bytes

Sanity check: a 7B model in bf16 is 14 GB. On an H100 at 3.35 TB/s, that's 3350/14 ≈ 240 tokens/sec ceiling for batch size 1. Real systems hit 100–150 — the gap is overheads, and the KV cache. This calculation predicts real inference speed to within a factor of ~2, which is remarkable for a one-line model.

The fix: batching

Because the weights are read once regardless of how many sequences you process, batching is nearly free:

BatchWeight bytes readFLOPsIntensityRegime
114 GB14 GFLOP~1hopeless
3214 GB448 GFLOP~32better
25614 GB3.6 TFLOP~256approaching the ridge

Batch 256 gives you roughly 256× the throughput for the same weight traffic. This is why inference providers batch aggressively, and why your API latency is better when the service is busy than when it's idle. It is also why the KV cache matters so much: the cache is the thing that limits batch size.

12.4 · The cache size calculation

bytes = 2 × n_layer × n_kv_head × d_head × seq_len × batch × dtype_bytes the leading 2 is for K and V

Play with this. Notice how fast it grows, and what GQA and MLA do to it:

Worked example: Llama-3-70B

n_layer = 80, n_kv_head = 8, d_head = 128, bf16

per token per layer = 2 × 8 × 128 × 2 bytes  = 4,096 bytes
per token           = 4096 × 80              = 327,680 bytes ≈ 320 KB

At  8k context:  8192 × 320 KB   ≈  2.5 GB   per sequence
At 128k context: 131072 × 320 KB ≈  40 GB    per sequence

The model weights are 140 GB (needs 2×H100 at minimum, realistically 4). On 4×H100 = 320 GB, that leaves ~180 GB for cache — so 4 concurrent users at 128k context, or ~70 at 8k. Your maximum concurrency falls straight out of this arithmetic.

Without GQA, this model would be unservable

With n_kv_head = 64 (full MHA) instead of 8, the cache would be 8× larger: 20 GB at 8k, 320 GB at 128k — a single 128k-context user would not fit on 4 H100s at all. GQA is not a nice optimisation; it is what makes long-context serving possible. That's Chapter 13.

Why is decode memory-bound while prefill is compute-bound, given both use the same weights?
Decode uses a different kernel
The KV cache is only read during decode
Prefill does T tokens' worth of arithmetic per weight read; decode does 1 — so arithmetic intensity is T× lower
Decode can't use tensor cores
Arithmetic intensity. The weights read is identical; the work done per byte read differs by a factor of T. Prefill's (T,C)@(C,C) reuses each loaded weight T times; decode's (1,C)@(C,C) uses it once. That single ratio explains the entire difference in behaviour.

12.6 · Exercises

12.1Add a KV cache and measure itessential

Add caching to your Chapter 9 model. Then:

  1. Correctness: assert that cached generation produces token-identical output to uncached generation with the same seed and greedy decoding. This is non-negotiable — if they differ, you have one of the three bugs from §12.2.
  2. Speed: time generating 200 tokens with and without the cache. Plot time-per-token against position for both.
What the plot shows

Uncached: time per token grows linearly with position (each step reprocesses the whole prefix), so cumulative time is quadratic. Cached: time per token is nearly flat, rising only slightly as the attention row gets longer. At 200 tokens the speedup is typically 10–30×; at 2000 tokens it's 100×+. This is the single highest-leverage optimisation in LLM inference.

12.2Build a serving calculatorcode

Write plan(model_cfg, gpu_gb, gpu_bandwidth_tbs, context, dtype_bytes) returning: weight memory, KV bytes per token, max concurrent sequences, and estimated batch-1 tokens/sec. Validate it against the Llama-3-70B numbers in §12.4, then use it to answer:

  1. How many H100s to serve Llama-3-70B at 128k context to 20 concurrent users?
  2. What happens to that answer with fp8 KV cache?
Answers
  1. Weights 140 GB + 20 users × 40 GB = 800 GB of cache → 940 GB → 12 H100s (80 GB each), and realistically more for activations and fragmentation.
  2. fp8 halves the cache: 140 + 400 = 540 GB → 7 H100s. Cutting your fleet by 40% is why KV quantization is standard in production despite the small accuracy cost.
12.3Find the roofline crossoverthinking

For a 7B model on an H100 (990 TFLOP/s bf16, 3.35 TB/s), at what batch size does decode stop being memory-bound? Compare that to prefill with a 2000-token prompt at batch 1 — which regime is it in, and why?

Answer

Ridge point = 990e12 / 3.35e12 ≈ 295 FLOP/byte. Decode intensity ≈ batch size (each sequence does 2 FLOPs per weight byte... in bf16, 2 bytes/weight and 2 FLOPs/weight → ~1 FLOP/byte per sequence). So you need batch ≈ 300 to reach the ridge — which is why production serving runs batches in the hundreds.

Prefill with T=2000 at batch 1 has intensity ≈ 2000, comfortably compute-bound. This is the key asymmetry behind prefill–decode disaggregation: the two phases want different hardware and different batching strategies, so several 2025–2026 serving stacks now run them on separate GPU pools.
