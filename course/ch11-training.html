11 · Training a Transformer

You have a model that maps tokens to logits. Now you have to make it good. This chapter covers the loss, the optimizer, the schedule, and the dozen practical details that separate a run that works from one that spikes at step 4000 and never recovers.

The whole chapter in five sentences

Pretraining minimises next-token cross-entropy with AdamW under a warmup-then-decay schedule. Every loss must be read against ln V, and compared across tokenizers in bits per byte. Which tokens you train on matters as much as how: exact and MinHash deduplication, rule-based and classifier-based quality filters, mixture weights limited by how often a source can be repeated, and the best data kept for the final decay. The batch should follow the gradient noise scale, which grows as the loss falls, and the learning rate should come from a parameterisation (μP) that transfers from a small proxy, because you cannot sweep it at scale. Throughput is measured as MFU and diagnosed with a profiler. A long run survives by keeping its logits bounded (z-loss, QK-norm), rolling back past spikes, and checkpointing every piece of state, including the data position, so that a resumed run is the run you planned.

11.1 · The objective: predict the next token

That is all of it. Standard pretraining has no clever auxiliary loss.

ℒ = − 1T Σt=1T log Pθ(xt | x<t) average negative log-likelihood of the true next token 
loss = F.cross_entropy(logits[:, :-1].reshape(-1, V),   # (B*(T-1), V)
                       ids[:, 1:].reshape(-1))          # (B*(T-1),)

F.cross_entropy fuses the log-softmax and the negative log-likelihood into one numerically stable operation. Never write log(softmax(x)) yourself, because it overflows.

The habit: never quote a loss without saying which tokenizer produced it, and compare runs on bpb. Row 2 of step 2 shows the trap in one line: the model with nearly triple the loss is the better one.

Loss is NOT comparable across tokenizers

The table above assumes a BPE vocabulary of ~32k. Change the tokenizer and every number moves, because loss is measured per token and tokens carry different amounts of text. A character-level model on Shakespeare reaching a loss of 1.5 and a BPE-2048 model reaching about 4.95 are the same quality: each BPE token is worth ~3.3 characters, so 1.5 nats per character is 1.5 × 3.3 ≈ 4.95 nats per token. (At 5.8 the BPE model would be 17% worse in bits per byte.)

The comparable metric is bits per byte:

bpb = lossnats/tokenln(2) · bytes_per_token 
char-level Shakespeare, good small model   ~2.1 bits/byte
GPT-2 on web text                          ~1.0 bits/byte
strong modern LLMs                         ~0.6-0.8 bits/byte

Always report bits per byte when you compare runs with different vocabularies. tfs/train.py prints it as bpb on every evaluation line for this reason.

Teacher forcing, and its consequence

During training we always condition on the true prefix, never on the model's own predictions. That is what makes the causal-mask trick work, with all T predictions computed in one pass. But it creates exposure bias: at generation time the model conditions on its own (possibly flawed) output, a distribution it never trained on. This is one reason long generations drift, and part of the reason RL-based post-training (Part VI) helps: it trains on the model's own outputs.

11.2 · The optimizer: AdamW

Plain SGD does not train transformers well. Adam does, and AdamW is the correction that fixed Adam's weight decay.

# Adam: per-parameter adaptive step sizes from first and second gradient moments
m = β₁·m + (1-β₁)·g                 # momentum      (β₁ = 0.9)
v = β₂·v + (1-β₂)·g²                # second moment (β₂ = 0.95 for LLMs, 0.999 default)
m̂ = m / (1 - β₁ᵗ);  v̂ = v / (1 - β₂ᵗ)          # bias correction
θ = θ - lr · m̂ / (√v̂ + ε)

The key behaviour is that dividing by √v̂ gives parameters with consistently small gradients large steps, and the reverse. Transformers have very different gradient scales across embeddings, norms and attention, so this per-parameter normalisation matters a lot.

What the W in AdamW fixes

L2 regularisation adds λ‖θ‖² to the loss, so the gradient gains a λθ term, which is then divided by √v̂ along with everything else. Parameters with large gradients get less regularisation, which is not what anyone wanted.

AdamW separates the two: it applies weight decay directly to the parameters, outside the adaptive part.

θ = θ - lr · m̂/(√v̂ + ε) - lr · λ · θ      # ← decoupled decay term
# The standard LLM setup, with the parameter grouping people usually forget
decay, no_decay = [], []
for n, p in model.named_parameters():
    if not p.requires_grad: continue
    # Don't decay biases, norm gains, or (usually) embeddings —
    # they're not "weights" in the sense weight decay assumes.
    (no_decay if p.ndim < 2 else decay).append(p)

opt = torch.optim.AdamW(
    [{"params": decay,    "weight_decay": 0.1},
     {"params": no_decay, "weight_decay": 0.0}],
    lr=3e-4, betas=(0.9, 0.95), eps=1e-8, fused=True)

The memory cost of Adam

Adam stores m and v for every parameter, in fp32. That is 8 bytes per parameter on top of the weights: for a 7B model, 56 GB of optimizer state alone. Add fp32 master weights (28 GB) and gradients (28 GB), and you can see why training needs ZeRO or FSDP sharding while inference fits on one GPU.

2026 note: Muon

After about 9 years as the default, Adam now has real competition. Muon (Jordan et al., 2024) orthogonalises the momentum matrix with a Newton-Schulz iteration before each step, which in practice improves the loss per FLOP for the 2-D weight matrices. It is used for the hidden layers, with AdamW kept for the embeddings and the LM head. Kimi K2 (1T parameters) was trained with a Muon variant at scale, the strongest evidence so far that the gain is not limited to small models. It is still not the default, but it is worth knowing about.

11.3 · The learning-rate schedule

A constant learning rate leaves a lot of performance unused. The standard schedule is linear warmup, then cosine decay:

def lr_at(step, base_lr, warmup=2000, total=100_000, min_ratio=0.1):
    if step < warmup:                                   # 1. linear warmup
        return base_lr * (step + 1) / warmup
    if step > total:
        return base_lr * min_ratio
    p = (step - warmup) / (total - warmup)              # 2. cosine decay
    return base_lr * (min_ratio + (1 - min_ratio) * 0.5 * (1 + math.cos(math.pi * p)))
Why warmup is not optional

At step 0, Adam's second-moment estimate v is near zero, so m̂/√v̂ can be enormous and the very first updates are effectively unbounded. Combine that with a randomly initialised model whose gradients are large and carry little information, and a full-size first step can push the weights somewhere they never recover from. Warmup starts gently while v settles. Post-LN models need it badly; pre-LN models need it less, but everyone still uses it.

The WSD alternative

Cosine has an annoying property: you must fix total_steps in advance, and the checkpoints along the way are all in the middle of the decay, so none of them is usable as a final model. WSD (Warmup-Stable-Decay, made popular by MiniCPM and now used by several labs) keeps the LR constant for most of training and decays it only over the last ~10%. You can stop at any point, decay briefly, and get a good model, which makes continued pretraining and changes of data in the middle of a run far more practical. The decay is also when runs switch to their best data (§11.7).

11.4 · The training loop, complete

model = GPT(cfg).to(device)
model = torch.compile(model)                    # 1.3-2× speedup, one line

opt = torch.optim.AdamW([...], lr=6e-4, betas=(0.9, 0.95), fused=True)
ACC_STEPS = 8                                    # gradient accumulation

for step in range(total_steps):
    # ── learning rate ──────────────────────────────────
    lr = lr_at(step, base_lr=6e-4)
    for g in opt.param_groups:
        g["lr"] = lr

    # ── forward / backward with accumulation ──────────
    opt.zero_grad(set_to_none=True)
    total_loss = 0.0
    for micro in range(ACC_STEPS):
        ids, targets = next(train_iter)          # (B, T) each
        with torch.autocast(device_type="cuda", dtype=torch.bfloat16):
            _, loss = model(ids, targets)
            loss = loss / ACC_STEPS              # ← average, don't sum
        loss.backward()
        total_loss += loss.item()

    # ── clip, step ─────────────────────────────────────
    norm = torch.nn.utils.clip_grad_norm_(model.parameters(), 1.0)
    opt.step()

    if step % 100 == 0:
        print(f"step {step:6d}  loss {total_loss:.4f}  lr {lr:.2e}  gnorm {norm:.2f}")

The four practical techniques in that loop

TechniqueWhat it buysWhat it costs
Mixed precision (bf16)~2× speed, ~half activation memorynothing — bf16's fp32-range exponent means no loss scaling needed

Two accumulation bugs
  1. Forgetting to divide by ACC_STEPS. The gradient becomes 8× larger than you think. Under SGD that is an 8× learning rate, and the run diverges. Under AdamW the effect is quieter: Adam's step m̂/(√v̂ + ε) does not change when the gradient is scaled by a constant, so the trajectory is almost the same, and clip_grad_norm_ clips the inflated norm anyway. What it does break: your clipping threshold now means something different, every logged loss and gradient norm is 8× off, and switching optimizers (or changing the accumulation count) silently changes the run. Divide anyway; the companion notebook shows both cases.
  2. Calling opt.zero_grad() inside the micro-batch loop. Then you are not accumulating at all: you did 8× the work for one micro-batch's gradient.

11.5 · Data I: packing

Documents have different lengths. Padding each one to T wastes compute on <pad> tokens, sometimes 50% of it. The standard fix is to join everything together and slice it:

# Tokenize the whole corpus once, write to a flat uint16/uint32 memmap.
data = np.memmap("train.bin", dtype=np.uint16, mode="r")     # (N_total,)

def get_batch(B, T):
    ix = torch.randint(len(data) - T - 1, (B,))
    x = torch.stack([torch.from_numpy(data[i     : i+T  ].astype(np.int64)) for i in ix])
    y = torch.stack([torch.from_numpy(data[i + 1 : i+1+T].astype(np.int64)) for i in ix])
    return x, y                                              # (B,T), (B,T)

There is no padding, and 100% of the compute does useful work. The trade-off is that sequences can span document boundaries, so the model sometimes attends across a break between unrelated documents. Most pretraining just accepts this. If you care, you can pass a document-ID mask to block attention across documents (supported by FlashAttention's varlen API and PyTorch FlexAttention).

This is normal. The fastest win available is matching the overall token frequencies ("the" is common, "aardvark" is not), which gets you to roughly the unigram entropy, around 6 for English. Why use β₂ = 0.95 for LLMs instead of PyTorch's default of 0.999?
0.999 averages over ~1000 steps, so it adapts too slowly to LLM gradient statistics and reacts badly to outlier batches
0.95 uses less memory
0.999 causes NaN in bf16
It is arbitrary
Speed of adaptation. The effective averaging window is ~1/(1−β₂): 20 steps at 0.95 against 1000 at 0.999. LLM gradients are noisy and keep changing, and with a long window a single bad batch's huge gradient inflates v for a thousand steps afterwards, which suppresses learning. GPT-3, Llama, Chinchilla and most others use 0.95.
You want an effective batch of 512 sequences, but only 8 fit in memory. What do you do, and what must you not forget?
Reduce sequence length instead
Use gradient checkpointing; nothing else changes
Accumulate over 64 micro-batches, and call opt.step() after each one
Accumulate over 64 micro-batches, divide each loss by 64, and step once
Divide by the accumulation count, and step once. loss.backward() adds into .grad, so without the division you get the sum of 64 losses and a gradient 64× too large. With SGD that is a 64× learning rate; with AdamW the step barely changes (it ignores scale), but clipping thresholds, logged losses and gradient norms are all 64× off. Option C defeats the purpose entirely: it is just 64 small steps.

11.6 · Data II: removing duplicates

Packing decides how tokens are laid out. Everything else about data decides which tokens, and for a pretraining team that is most of the job. A web crawl is full of repetition: the same article syndicated on fifty sites, the same cookie banner on a million pages, the same page captured in every monthly crawl. Duplicated text costs compute without teaching anything new, and heavily repeated text gets memorised, which shows up later as copied training data and inflated benchmark scores. Every modern pipeline removes duplicates at three levels. Llama 3, for example, keeps the most recent version of each URL, runs a global MinHash pass over all documents, and then removes lines that appear more than 6 times in each bucket of 30 million documents (which strips boilerplate such as navigation menus without dropping the page).

Exact duplicates: hash the normalised text

Exact duplicates are cheap to remove. Normalise each document (lower-case it, collapse whitespace), hash it, and keep the first document for each hash. It takes one pass and one hash table, and tfs.data.exact_dedup is six lines. It catches a copy of an article whose only change is capitalisation, and nothing else: change one word and the hash changes completely.

Near duplicates: MinHash

The useful idea of a "near duplicate" is overlap of content. Represent a document as its set of shingles, the word n-grams it contains (FineWeb uses 5-grams), and compare two documents by their Jaccard similarity, the size of the intersection divided by the size of the union. Comparing every pair is impossible at web scale (1010 documents make 1020 pairs), and so is storing every set. MinHash replaces each set with a short signature of fixed length whose agreement rate estimates the Jaccard similarity.

Why the minimum of a random hash estimates Jaccard

Apply one random hash function h to every shingle of A and of B, and keep the smallest value from each. Consider the shingle in A ∪ B with the smallest hash. Every element of the union is equally likely to be that one, and the two minima are equal exactly when it lies in A ∩ B. So P[min h(A) = min h(B)] = |A ∩ B| / |A ∪ B| = J(A, B). Repeat with k independent hash functions, and the fraction of matching slots is an unbiased estimate of J, with standard error √(J(1 − J)/k).

Worked example — one news story, three ways (tfs/data.py, 112 hashes)

That miss is the design, not a bug. A band of 8 slots agrees with probability J8, so the probability of being caught by at least one of 14 bands is 1 − (1 − J8)14:

An S-curve centred near (1/14)1/8 = 0.72. FineWeb describes this setting as targeting documents that are at least 75% similar. C sits right on the slope and was unlucky; B is far above it. Clustering then has to be transitive: if A~B and B~E, keep one of the three, which tfs.data.dedup does with union-find.

Bands and rows are the settings to tune. More rows per band make each band stricter (the curve shifts right), and more bands give more chances (the curve shifts left and gets steeper). The cost grows linearly with the number of hashes, so pipelines pick the smallest signature whose S-curve is steep enough around their chosen threshold.

More deduplication is not always better

The FineWeb team expected global deduplication across all 96 Common Crawl snapshots to work best. It did not. Deduplicating globally left 4 trillion tokens and "showed little improvement"; deduplicating each crawl separately left 20 trillion and matched RefinedWeb. Their explanation: global dedup keeps a page only in the one crawl where it first appears and deletes the other copies, so in old crawls the surviving data is what nobody ever re-published, and the data it removed was of higher quality than the data it kept. Content that keeps being re-posted is, on average, content people value. So deduplication is a data-quality decision, and it has to be judged by training on the result.

11.7 · Data III: quality, mixtures and annealing

Filtering: rules first, then a model

Most of a raw crawl is not worth training on: menus, spam, machine-generated pages, keyword lists. The first pass is cheap rules. Gopher's MassiveWeb filters (Rae et al. 2021) are still the template, and tfs.data.gopher_rules implements them. Keep a document only if it has 50 to 100,000 words, a mean word length of 3 to 10 characters, at most 0.1 hash symbols or ellipses per word, no more than 90% of lines starting with a bullet or 30% ending with an ellipsis, at least 80% of words containing a letter, and at least two of the eight stop words the, be, to, of, and, that, have, with. The stop-word rule works well because real English prose cannot avoid those words and keyword spam rarely contains them. The news paragraph above passes every rule; "BUY NOW!!!" repeated 60 times fails exactly one, the stop-word rule.

Rules remove junk, but they cannot recognise good text. The second pass is a model. The pattern that took over in 2024 is to distil an expensive judge into a cheap classifier:

How FineWeb-Edu was built
1
Label a sample with a strong model. Llama-3-70B-Instruct scored 460,000 random web pages from 0 to 5 for educational value.
2
Train a cheap imitator. A linear regression head on frozen Snowflake-arctic-embed-m embeddings, trained on 410,000 of the labels and validated on 50,000, reached 82% F1 at the chosen threshold.
3
Run it over everything and cut. Keeping pages that scored 3 or above left 1.3 trillion tokens of the 15-trillion-token FineWeb, and models trained on it did much better on knowledge and reasoning benchmarks (MMLU, ARC) per token trained.

Llama 3 did the same with different parts: a fastText classifier trained to recognise text that Wikipedia would cite, and DistilRoberta classifiers trained on Llama 2's quality judgements, plus specialised classifiers for code and mathematical reasoning. tfs.data.QualityClassifier is the same idea at toy scale (logistic regression on hashed unigrams and bigrams, trained on a handful of labelled sentences), so you can see that the whole mechanism is a cheap model imitating an expensive one. The real difficulty is not the classifier. It is that a filter tuned for one family of benchmarks narrows the data: an educational-value filter helps MMLU and can hurt the model's ability to write casual dialogue or fiction. That is why the filtered set becomes one source in a mixture instead of the whole dataset.

Mixture weights: how often each source is seen

A pretraining corpus has several sources of very different size and value: web text, code, mathematics, books, papers and many languages. Sampling in proportion to size lets web text swamp everything else. The standard setting is temperature sampling: source i is drawn with probability proportional to ni1/τ. τ = 1 is proportional sampling, and larger τ flattens the mix toward uniform. The cost of flattening is repetition, because a small source that is sampled often is seen many times.

At τ = 1 every source is seen 1.07 times, which is fair, and math is 2% of what the model reads. At τ = 2 math rises to 9% of the mix, but the 50 B tokens of papers are now read 11.5 times. Chapter 21 §21.2 shows what repetition costs: up to around 4 epochs it is nearly free, by 16 epochs each repeat is worth about two-thirds as much as fresh data, and the model starts to memorise. So in practice mixtures are set by small-scale ablations (train a 1B model on candidate mixes and compare downstream scores), with a cap on epochs per source. Llama 3's final mix was roughly 50% general knowledge, 25% mathematics and reasoning, 17% code and 8% multilingual tokens.

Annealing: the best data, at the end

The last phase of training has an outsized effect. As the learning rate decays, the model settles into whatever the most recent data looks like, so pipelines keep their highest-quality data for that phase. This is where the WSD schedule of §11.3 pays off: the long plateau at constant LR runs on the broad mix, and the short decay at the end runs on a mix with more high-quality data. tfs.data.wsd_lr is the schedule:

def wsd_lr(step, base_lr, warmup, total, decay_frac=0.1, final_ratio=0.0):
    if step < warmup:          return base_lr * (step + 1) / warmup        # warmup
    d0 = int(total * (1 - decay_frac))
    if step < d0:              return base_lr                              # stable
    p = (step - d0) / (total - d0)
    return base_lr * (1 - (1 - final_ratio) * p)                           # decay: switch data here
# total=1000, warmup=100:  lr(500) = 3e-4,  lr(950) = 1.5e-4,  lr(999) = 3e-6

Why the order matters at all

At a high learning rate each update is large and the model keeps moving, so what it learned from data seen long ago is partly overwritten. As the rate decays, updates shrink and the weights settle in a region shaped by the recent batches. So the same tokens are worth more late than early, and spending the cleanest, most valuable data in the decay phase gets more out of it. It is also why "continued pretraining" on a new domain is usually done as a fresh short warmup and decay on a mix that still contains some of the original data: decaying on only the new domain makes the model forget the old one.

11.8 · Batch size: how much data per step

Batch size has a property the learning rate does not: up to a point, doubling it halves the number of steps you need, for the same total data. Past that point it stops helping, and you pay for data that does not speed anything up. Where that point is, and why it moves during training, is one of the few results in optimisation that makes accurate predictions.

The noise scale

Each step uses a gradient estimated from B examples. Its expected squared norm is the true gradient's plus a noise term that shrinks with B:

E |GB|² = |G|² + tr(Σ) / B      Bnoise = tr(Σ) / |G|² Σ = per-example gradient covariance · McCandlish et al. 2018's "simple noise scale"

When B ≪ Bnoise the gradient is mostly noise, and doubling B nearly halves the steps. When B ≫ Bnoise the gradient is already accurate and extra examples are wasted. McCandlish et al. showed that across many tasks, the steps S and examples E needed to reach a given loss lie on one curve, (S/Smin − 1)(E/Emin − 1) = 1, with a critical batch size Bcrit = Emin/Smin that Bnoise predicts well. At B = Bcrit you pay twice the minimum number of steps and twice the minimum data (tfs.trainkit.steps_and_examples(1000, 1000) returns exactly (2.0, 2.0)); at a tenth of it, 11× the steps for 1.1× the data.

Both unknowns can be estimated from two batch sizes, because the formula above is linear in 1/B. Measure |Gsmall|² and |Gbig|² and solve (tfs.trainkit.grad_noise_scale):

G2 = (B_big * g_big - B_small * g_small) / (B_big - B_small)        # |G|^2
S  = (g_small - g_big) / (1 / B_small - 1 / B_big)                  # tr(Sigma)
B_noise = S / G2
Measured on this course's model — the noise scale as training proceeds

The Exercise 11.1 model (character-level Tiny Shakespeare, 2,374,272 parameters, T = 128), trained with the exercise's settings, with Bnoise estimated at four points from 8 draws each of batch 4 and batch 64 (python -m tfs.trainkit):

step     B_noise (sequences)   = tokens     |G|²        tr(Σ)
   0            2.2               276      79.4       171

The noise scale grows 60-fold in 1,200 steps. At initialisation the true gradient is huge (|G|² = 79) and any two sequences agree on it, so a batch of 2 or 3 would do. As the loss falls the signal shrinks far faster than the noise, and by step 1,200 the efficient batch is about 137 sequences. The exercise trains at 32: well above Bnoise for the first hundred steps (wasting data), and below it from somewhere between step 100 and step 400 onward (wasting steps, which on one CPU is the cheaper thing to waste). The estimates are noisy (8 draws each), so treat them as accurate to a factor of two, not to three significant figures. test_noise_scale_grows_during_training checks the direction on a smaller model.

Why the batch grows during a big run

The noise scale grows as the loss falls. Early on, any batch points roughly downhill; later, the remaining signal is subtle and takes many examples to see. So the efficient batch is small at the start and large later, and large runs increase the batch size as they go. GPT-3 increased it linearly from 32k tokens to its full size over the first 4 to 12 billion tokens. Llama 3 405B started at 4M tokens per step (sequences of 4,096), doubled to 8M (sequences of 8,192) after 252M tokens, and doubled again to 16M after 2.87T. DeepSeek-V3 went from 3,072 to 15,360 sequences of 4,096 tokens (12.6M to 62.9M tokens per step) over its first 469B tokens. A batch above Bcrit does no harm; it only wastes data. The real ceiling is data parallelism's (Chapter 19 §19.2), because past Bcrit more GPUs stop making the run shorter.

Changing the batch means changing the learning rate

A larger batch gives a less noisy gradient, so it tolerates (and needs) a larger step. For SGD below Bcrit the best LR rises roughly linearly with B, for Adam closer to √B, and above Bcrit it stops rising. In practice: if you change the batch, re-tune the LR, and if you cannot, scale it by √(Bnew/Bold) as a first guess.

11.9 · A learning rate you cannot afford to sweep: μP

The learning rate matters more than any other hyperparameter, and its best value moves with model size (GPT-3's own table: 6e-4 at 125M, 0.6e-4 at 175B). You cannot sweep it at 70B. The obvious approach, sweeping on a small model and extrapolating, fails in the standard parameterisation, because the best value keeps drifting as width grows. Here is why, measured.

Measurement — how far one Adam step moves a layer's output (tfs.trainkit.adam_output_change)

A square linear layer of width n, standard initialisation (std 1/√n), one Adam step at a fixed learning rate of 1e-3, and the average change of each output coordinate:

width          256      1024      4096
standard       0.025    0.087     0.332     <- 13× larger at 16× the width
muP            0.025    0.022     0.021     <- LR scaled by 256/width: flat

Why it grows. Adam's first step is lr × sign(gradient) on every weight, an update of the same size per entry whatever the width. A change in the output y = Wx adds up n such entries, and because the update is aligned with the input that produced the gradient, they add in the same direction, so the output change grows like n·lr. The same learning rate is therefore a much larger step for a wide model, which is why the best value moves down as models get wider.

μP (the Maximal Update Parameterisation, Yang et al. 2022) fixes the scaling instead of re-tuning. For Adam, the hidden-layer learning rates scale as base_width / width, the output logits are multiplied by base_width / width, and attention scores are scaled by 1/dhead instead of 1/√dhead. Under those rules the size of each update to every layer's output does not depend on width (the "muP" row), so the best learning rate, initialisation scale and other hyperparameters found on a narrow proxy carry over to the wide model. The paper's headline result: tuning on a 40M-parameter proxy and transferring beat the published 6.7B GPT-3, at a tuning cost of 7% of one pretraining run.

What transfers, and what does not

μP transfers across width cleanly. Transfer across depth, batch size and training length needs more care (depth-μP variants exist, and the batch size interacts with the LR as above), and regularisation settings such as weight decay do not transfer automatically. In practice teams combine a μP-style parameterisation with small sweeps near the target scale, or fit how the best LR scales with model size from a ladder of small runs (DeepSeek's LLM papers fit the best LR and batch size as power laws in compute).

11.10 · Throughput: tokens per second and MFU

A training run has two speeds: how fast the loss falls per token (everything above), and how many tokens per second the hardware processes. The standard measure of the second is model FLOPs utilisation:

MFU = tokens per second × FLOPs per tokenpeak FLOP/s of the hardware FLOPs per token = 6·Nmatmul + 12·L·H·dhead·T  (PaLM's accounting)

"Model" FLOPs are the FLOPs the model mathematically needs, not what the hardware actually ran: recomputation for checkpointing does not count, so MFU penalises it. The 6N part counts the forward (2) and backward (4) pass for every weight matmul, including the LM head; the second term is attention's scores and weighted sum, which grows with context length (Chapter 21 §21.5 shows it dominating at 128k).

Finding the bottleneck

When MFU is low, the question is always which of four things is taking the time: matmuls that are too small (the GPU is not kept busy: raise the batch or the width, Chapter 14), memory-bound elementwise work (norms, activations, softmax, the optimizer step: fuse them with torch.compile or fused kernels), communication that is not overlapped (Chapter 19), and stalls (data loading, Python overhead, CPU-GPU synchronisation such as loss.item() every step). 11.11 · Debugging a training run

Case study: a real bug this course shipped, and what caught it

While the training script for this course was being built, get_batch returned a pre-shifted y = data[i+1 : i+1+T], and it was passed to a forward() that also shifts internally (logits[:, :-1] against targets[:, 1:]). The labels were shifted twice, so the model was trained to predict two tokens ahead.

Here is what that looked like on a model trained to memorise a short text:

train losschars correctgreedy output
correct0.0482100%'e we proceed any further, hear me speak.'
double-shifted0.045711%' ew rr rcedayfr e,haieode,ha er e,ha er'

The buggy version had the LOWER training loss. Predicting two tokens ahead is a perfectly learnable task; it just is not language modelling. There was no exception, no NaN and no suspicious curve. Every unit test on forward() still passed, because forward() was never wrong; the caller was.

What caught it was checking the output end to end. Train a model to memorise a short text, then check that greedy generation reproduces it. A model that has memorised its training data but cannot repeat it has a mismatch between training and inference. For this particular bug, the giveaway is that the teacher-forced output is off by exactly one token. That check is test_generation_reproduces_memorised_text in tests/test_tfs.py.

The overfit-one-batch test — do this first, always 
ids, targets = next(train_iter)
for step in range(500):
    opt.zero_grad()
    _, loss = model(ids, targets)      # SAME batch every time
    loss.backward(); opt.step()
    if step % 50 == 0: print(step, loss.item())

The loss must go to near zero. If the model cannot memorise 8 sequences, no amount of data will help: you have a bug, not a capacity problem. This test takes 30 seconds and catches label-shift errors, broken masks, frozen parameters and detached graphs.

11.12 · Loss spikes at scale

Small models rarely spike. Large ones do, and a spike that does not recover can cost days. PaLM (540B) reports loss spikes "roughly 20 times during training, despite the fact that gradient clipping was enabled", at irregular intervals and not tied to particular data. The defences come in three layers, roughly in the order a run meets them.

1. Make the logits and attention scores unable to grow

The most common root cause is a value that drifts upward until a softmax saturates: the output logits or the attention scores. Two cheap fixes target them directly.

  • z-loss on the output. Add coef · (log Z)2, where Z = Σ ezi is the softmax normaliser. Cross-entropy is unchanged by adding a constant to every logit, so nothing stops the logits drifting as a block; z-loss pins log Z near 0 and takes that freedom away. PaLM uses coef = 10−4. tfs.trainkit.z_loss is one line: 
    def z_loss(logits, coef=1e-4):
    return coef * torch.logsumexp(logits.float(), dim=-1).pow(2).mean()
loss = F.cross_entropy(logits.view(-1, V), targets.view(-1)) + z_loss(logits)
  • QK-norm. Apply RMSNorm to q and k, per head, before the dot product. The attention logit becomes a cosine similarity times a learned scale, so it cannot grow without limit. It was introduced for ViT-22B and adopted by OLMo 2, Gemma 3, Qwen3 and others, and it costs almost nothing.

OLMo 2's report is a good list of what a recipe focused on stability changed at once: QK-norm, a z-loss term, no weight decay on the embeddings, RMSNorm applied to the outputs of the attention and MLP sublayers, a plain normal initialisation with std 0.02, and Adam's ε lowered from 10−5 to 10−8. None of these is unusual, but together they turned spiky curves smooth.

2. Detect the spike

Gradient clipping (§11.4) handles a single bad batch. What clipping cannot handle is a run whose optimizer state has been pushed somewhere bad: Adam's second moment v adapted to small gradients, a sudden large gradient arrives, and m̂/√v̂ stays huge for many steps. A simple statistical trigger is enough to catch it: flag a step whose loss is many standard deviations above the recent mean (tfs.trainkit.SpikeDetector uses the mean and spread over the last 50 steps and a threshold of 6σ; the test feeds it a smooth curve at a loss of 2.00 and one step at 2.50, and checks that only the 2.50 fires). Watch the gradient norm the same way, because it usually moves first.

3. Roll back and skip

PaLM's procedure is the standard one: restart from a checkpoint roughly 100 steps before the spike started and skip roughly 200 to 500 batches around it. The authors found that the spikes were not caused by "bad data" alone (the same batches did not spike when replayed from a different state); they came from an interaction between particular batches and a particular optimizer state, and skipping batches changes that interaction. Other options, from cheapest to most expensive: lower the learning rate for a while, raise Adam's ε, or reset v. All of this only works if you checkpoint often enough to have somewhere to roll back to (§11.13), and if the loader can skip batches deterministically.

What "no spikes" looks like now

DeepSeek-V3's report states that over its 14.8 T-token run the team "did not experience any irrecoverable loss spikes or perform any rollbacks". That is the reward for the fixes on the architecture side: when logits and attention scores stay bounded, the remaining spikes are small and recover by themselves, and the expensive rollback machinery becomes insurance instead of routine.

11.13 · Checkpointing and exact resumption

A run of weeks on thousands of GPUs will be interrupted: Llama 3 recorded 466 interruptions in a 54-day window, 419 of them unexpected (Chapter 19 works out how often to checkpoint). Each interruption costs the work done since the last checkpoint. It must not also cost correctness: a resumed run should continue exactly as if it had never stopped. "Roughly the same" is not good enough, because you can no longer tell a real effect from a side effect of resuming, and a stretch of data that is silently repeated or skipped changes what the model learns.

The state that affects the next step includes more than the weights:

StateIf you forget it
Model weights (fp32 master copy)obviously, nothing works
Optimizer state: m, v, and the step countAdam restarts its bias correction and takes huge first steps: a self-inflicted spike
The step numberthe LR schedule restarts warmup or jumps
Data-loader position: seed, epoch, index into the permutationthe run re-reads data it already saw and never sees the rest

Loss scaler, if fp16 (Chapter 12)the scale restarts and the first steps overflow

tfs.trainkit.ResumableRun is a training loop built around that table. Its loader's entire state is three integers, so saving it is trivial:

class Loader:
    def _perm(self):                      # the permutation is a pure function of (seed, epoch)
        g = torch.Generator().manual_seed(self.seed * 100_003 + self.epoch)
        self.order = torch.randperm(self.n, generator=g)
    def state_dict(self):
        return {"seed": self.seed, "epoch": self.epoch, "pos": self.pos}

def state_dict(self):                     # ResumableRun
    return {"model": self.model.state_dict(), "opt": self.opt.state_dict(),
            "step": self.step, "loader": self.loader.state_dict(),
            "rng_torch": torch.get_rng_state(), "rng_python": random.getstate()}

The test defines what "exact" means (test_exact_resumption_is_bit_identical). Train 40 steps straight through. Separately, train 20, save, build a fresh run with a different random initialisation, load the checkpoint, and train 20 more. The 40 losses must be identical and every weight tensor must be equal bit for bit, and they are. The test then resets only the loader position to 0 and shows that the final weights differ: forgetting one integer is enough to make the resumption inexact.

What makes bit-identical hard on real hardware

On a CPU with a fixed thread count the test above is exact. On GPUs, exactness also needs deterministic kernels (atomic adds in scatter and in some backward kernels add up in a varying order, and torch.use_deterministic_algorithms(True) refuses the nondeterministic ones), the same parallel layout on resume (a different number of data-parallel ranks changes which samples are added together), and a loader that does not depend on worker timing. Large teams often settle for "same data order and same optimizer state, numerically close", and check it by replaying a few hundred steps after each restart and comparing loss curves.

11.3Plant a bug, then find itessential

Add each bug below one at a time, run 200 steps, and record what the loss curve looks like. Build yourself a lookup table so that you can diagnose these by sight later.

  1. Remove the label shift (predict the input instead of the next token)
  2. Remove the causal mask
  3. Forget opt.zero_grad()
  4. Use lr=1.0
  5. Forget to divide by ACC_STEPS
Signatures
  1. The loss crashes to ~0 within a few dozen steps, and generation is gibberish. Diagnostic: a loss below the data's entropy is impossible.
  2. The loss drops much faster than normal and reaches an implausibly low value, and generation is incoherent. It gives the same signal as (1): the model is cheating.
  3. Gradients accumulate forever. Under SGD the effective LR grows without limit and the loss explodes. Under AdamW, which normalises the ever-growing sum, the run stays finite but gets worse: every step uses a stale average of all past gradients, so the loss stalls well above the correct run.
  4. Under SGD, NaN within ~10 steps. Under AdamW the loss spikes far above ln V and the run is ruined, but it may not produce NaN straight away, so watch for the spike, not only for NaN.
  5. Under SGD it behaves like an 8× LR (divergence, or a high, noisy plateau). Under AdamW the loss curve looks almost normal, because Adam's step ignores the gradient's scale; the giveaway is that the logged gradient norm is 8× what the same run reports with the division.

The general lesson: (1) and (2) both produce a beautiful loss curve. Never trust a loss curve alone: always generate samples, and always check the loss against ln(V) at step 0.

11.4Deduplicate a corpuscode

Take Tiny Shakespeare, split it into documents of 40 lines, and plant near-duplicates: copy 50 random documents, and in each copy change k random words (k = 1, 3, 10) or add a footer. Run tfs.data.dedup with 14 × 8 bands and with 20 × 5.

  1. For each k, predict the 5-gram Jaccard similarity before measuring it (each changed word removes up to 5 shingles from the intersection).
  2. Measure the recall (planted duplicates caught) and the false-positive rate (distinct documents merged) for both band settings, and compare them with lsh_catch_probability.
What to expect

A 40-line document is a few hundred words, so k = 1 or 3 keeps J above 0.9, and both settings catch nearly all of them; at k = 10, J falls toward the midpoint of the S-curve and recall drops. 20 × 5 has its midpoint at (1/20)1/5 = 0.55, so it catches more edits but starts merging genuinely different scenes that share stock phrases; the false positives are the price. The measured recall should follow the S-curve to within sampling noise.

11.5Measure your own critical batchcode

Run python -m tfs.trainkit to get Bnoise along a training run. Then test the prediction: from the same checkpoint at step 400, train 200 more steps at batch sizes of 8, 32 and 128 sequences, scaling the LR by √(B/32), and record how many tokens each needs to reach the same loss.

How to read it

Below the noise scale, the number of tokens needed to reach a target loss is nearly the same at every batch size (doubling the batch halves the steps). Above it, the tokens needed rise with the batch: you are buying data that does not help. The crossover should be within a factor of a few of the measured Bnoise; the noise scale is a prediction of Bcrit, not its exact value.

11.6Break resumption on purposeessential

Starting from test_exact_resumption_is_bit_identical, remove one piece of state at a time from ResumableRun.state_dict (the optimizer state, the step number, the loader state, the RNG state), and record for each the largest difference in the final weights and in the loss curve after the resume.

What you'll see

Dropping the optimizer state is the most visible: Adam restarts with empty moments and a step count of 0, so its first steps are large and the loss jumps. Dropping the step number restarts the LR warmup. Dropping the loader state gives a smooth curve with different weights, the worst kind of bug, because nothing looks wrong. With no dropout in this model, the RNG state only matters if something samples; add dropout and it matters too.

11.7Estimate a frontier run's wall-clockthinking

A 70B dense model, 15T tokens at T = 8,192, on 8,192 H100s at 40% MFU (bf16 peak 989 TFLOP/s). Use 6N + 12·L·d·T FLOPs per token, with L = 80 and d = 8192.

Answer
per token: 6 × 70e9 + 12 × 80 × 8192 × 8192 = 4.20e11 + 6.44e10 = 4.84e11 FLOPs
total:     4.84e11 × 15e12                 = 7.27e24 FLOPs
cluster:   8192 × 989e12 × 0.40            = 3.24e18 FLOP/s
time:      7.27e24 / 3.24e18 = 2.24e6 s    ≈ 26 days

Add the interruptions from Chapter 19 §19.9 (about 10% lost at a sensible checkpoint interval) and the answer comes to about four weeks. Note that the attention term is 13% of the FLOPs at 8k context, and leaving it out underestimates the run by three days.
