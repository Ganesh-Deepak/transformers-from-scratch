23 · SFT, LoRA, RLHF, and PPO

A pretrained model predicts text. It is not an assistant. Ask it a question and it may well produce five more questions, because that is what documents with questions in them look like. This part of the course closes the gap between "models the internet" and "does what you asked". This chapter covers the first half of the toolkit: supervised fine-tuning; the way almost everyone actually runs it (LoRA, in a fraction of the memory); the data recipes that modern post-training is built from; and RLHF with PPO, worked out all the way to the per-token rewards and the advantage estimator.

The whole chapter in six sentences

SFT is pretraining on chosen conversations, with the loss masked to the assistant's tokens. LoRA freezes the model and trains a low-rank update BA beside each weight. That cuts the trainable parameters of an 8B model to 0.5% and its fine-tuning memory from 128 GB to 17 GB (6.4 GB with a 4-bit base). Most modern SFT data is generated, either by the model itself and then filtered (rejection sampling), or by a stronger teacher (distillation), ideally on the student's own samples. Preferences are easier to give than demonstrations, and a Bradley-Terry reward model turns them into a score. PPO maximises that score minus a KL penalty, which in practice is paid token by token as a shaped reward. GAE turns those per-token rewards and a learned value function into advantages, trading bias for variance with one parameter, λ.

23.2 · Supervised fine-tuning

Mechanically, SFT is identical to pretraining: the same loss and the same optimizer. There are two differences:

# 1. The data is formatted with a chat template (Chapter 3)
text = tokenizer.apply_chat_template([
    {"role": "user",      "content": "What is attention?"},
    {"role": "assistant", "content": "Attention lets each token..."}
], tokenize=False)

# 2. Loss is computed on the ASSISTANT tokens only.
labels = input_ids.clone()
labels[:len(prompt_ids)] = -100     # -100 = ignore_index in F.cross_entropy
Masking the prompt matters more than people expect

If you train on the prompt tokens too, the model spends capacity learning to generate user questions, a task you never want it to do. It also waters down the gradient signal on what you actually care about. Always mask, and always print a decoded example with the masked positions marked before you start a run.

Why SFT isn't enough

  • It can only imitate, never do better. SFT can only be as good as your demonstrations. If your annotators write mediocre answers, you get a mediocre model.
  • "Good" is easier to judge than to produce. Writing an excellent response is expensive, but comparing two responses is cheap. Preference data scales far better than demonstration data.
  • There is no signal about what to avoid. SFT only ever says "do this". It never says "not that", so no gradient pushes away from unhelpful or unsafe outputs.
The core argument for preference learning

For most of what we want from an assistant (helpfulness, tone, honesty about uncertainty) we cannot write down a loss function, and we cannot reliably produce ideal demonstrations. But we can reliably say which of two responses is better. Preference optimisation turns that comparison into a gradient. Before we get there, every fine-tuning run has two practical questions to answer first: how to fit it in memory (23.3), and where the data comes from (23.4).

23.3 · LoRA: fine-tuning a sliver of the model

Full fine-tuning updates every weight, so it needs every weight's gradient and optimizer state. Chapter 12 added up the bill for AdamW in mixed precision: a bf16 weight (2 bytes), its bf16 gradient (2), an fp32 master copy (4) and Adam's two moments (4 + 4). That is 16 bytes per parameter before a single activation. For an 8-billion-parameter model it is 128 GB, more than one 80 GB GPU holds. Yet fine-tuning makes only a small change. The model already knows the language, and we are adjusting its behaviour. Hu et al. (2021) bet that the update has low rank. It does, well enough to make this the default way to fine-tune.

The update ΔW = BA

Freeze the pretrained weight W of shape (out, in). Next to it, learn two thin matrices: A of shape (r, in) and B of shape (out, r). The rank r is 8 to 64, while in and out are in the thousands. The layer computes

h = W x + s · B (A x)      s = α / r W (out, in) frozen · A (r, in) · B (out, r) · ΔW = s·BA has rank at most r

Follow the shapes for one token. x is (in). A x is (r): the input squeezed through r directions. B (A x) is (out). The update is never built as an (out, in) matrix during training. Two thin matmuls cost r·(in + out) multiply-adds per token instead of in·out.

class LoRALinear(nn.Module):                                   # tfs/lora.py
    def __init__(self, base: nn.Linear, r=8, alpha=16.0, rslora=False):
        super().__init__()
        self.base = base
        for p in self.base.parameters():
            p.requires_grad_(False)                            # the base never trains
        d_out, d_in = base.weight.shape                        # nn.Linear stores (out, in)
        self.scaling = alpha / math.sqrt(r) if rslora else alpha / r
        self.A = nn.Parameter(torch.empty(r, d_in))            # (r, in)   random
        self.B = nn.Parameter(torch.zeros(d_out, r))           # (out, r)  ZERO
        nn.init.kaiming_uniform_(self.A, a=math.sqrt(5))

    def forward(self, x):                                      # x: (B, T, in)
        y = self.base(x)                                       # (B, T, out)
        return y + self.scaling * (x @ self.A.T) @ self.B.T    # (B, T, r) -> (B, T, out)

    @torch.no_grad()
    def merge(self):                                           # fold the update into W, once
        self.base.weight += self.scaling * (self.B @ self.A)   # (out, r) @ (r, in) -> (out, in)

Why B starts at zero, and A does not

Write g = ∂L/∂h for the gradient arriving at the layer's output. The two gradients are

∂L/∂B = s · g (A x)T      ∂L/∂A = s · BT g xT each factor's gradient is proportional to the OTHER factor
  • B = 0 makes ΔW = 0, so at step 0 the wrapped model is exactly the pretrained model. Fine-tuning starts from what you downloaded, not from a randomly disturbed copy of it.
  • A random keeps the gradient alive. ∂L/∂B depends on A x, which is nonzero, so B moves on the first step. ∂L/∂A depends on B, so A gets exactly zero gradient at step 0 and starts learning at step 1.
  • Both zero is a trap. Each gradient would be proportional to a zero matrix, forever. It is a saddle point that plain gradient descent never leaves, the same kind of bug as the top-1 router in Chapter 20.

The tests check all three. The outputs are bit-identical at init, A.grad is exactly zero and B.grad is not after one backward pass, and with both zero neither gradient ever moves.

Rank, alpha, and rsLoRA

The scale s = α/r is meant to let you change r without re-tuning the learning rate. In practice people set α = 16 or α = 2r and sweep r. Kalajdzievski (2023) pointed out the catch. Each entry of B(Ax) is a sum over r terms. If the entries of A and B have a fixed scale, the variance of that sum grows like r and its standard deviation like √r. Multiplying by α/r then leaves an update whose size shrinks like 1/√r. So raising the rank makes each adapter learn less, which is why many people found that rank 256 was no better than rank 8. rsLoRA scales by α/√r instead, and the update size stops depending on r. The test measures it. From r = 4 to r = 64 the update shrinks 4× (= √16) with α/r, and stays within 10% with α/√r. With α = 16 and r = 16 the two scales are 1.0 and 4.0. PEFT offers it as use_rslora=True.

Which matrices to adapt

The original paper adapted only Wq and Wv of attention. It found that, for a fixed parameter budget, spreading rank over more matrices beat putting it all in a few. Later work moved the default to every linear layer. QLoRA (Dettmers et al. 2023) found that adapting all of them was needed to match full fine-tuning. Thinking Machines' "LoRA Without Regret" study (Schulman et al. 2025) found that the MLP matrices matter most, and that LoRA's best learning rate is roughly 10× the one for full fine-tuning. Biderman et al. (2024), "LoRA Learns Less and Forgets Less", add two cautions. On large-scale continued training (new programming languages, lots of mathematics) LoRA falls clearly short of full fine-tuning. It also forgets less of what the base model knew. Use LoRA to adapt behaviour and style, for most SFT and RL, and switch to full fine-tuning when you are teaching a lot of new knowledge.

What LoRA does not save. First, activations. The backward pass still runs through every frozen layer to reach the adapters, so activation memory is unchanged and needs the usual gradient checkpointing. Second, most of the compute. Per token, training costs about 6N FLOPs (Ch 21), of which 2N computes the weight gradients that LoRA skips. So LoRA trains at roughly 4N: a third less compute, not 99% less.

QLoRA: a 4-bit base under a 16-bit adapter

QLoRA (Dettmers et al. 2023) stores the frozen base in NF4, a 4-bit format whose 16 levels sit at the quantiles of a normal distribution, because pretrained weights are roughly normal (Chapter 0 builds block-scaled formats from scratch). Each block of 64 weights shares one scale. Double quantisation then stores those scales in 8 bits, with a second-level fp32 scale per 256 blocks. The cost per weight is 4 + 8/64 + 32/(64·256) = 4.127 bits. During the forward and backward pass each block is converted back to bf16 on the fly, and the adapters and all their optimizer state stay in 16/32-bit. The 4-bit base costs little quality, because the adapter is trained on top of the quantised weights and learns to make up for them.

Merging, swapping, and DoRA

After training, merge() folds the update into the weight, W' = W + s·BA, and the model is an ordinary dense model again with zero inference overhead. unmerge() subtracts it, so one base can switch between adapters. The test checks that merged and unmerged outputs agree and that unmerging restores W. Merging into a quantised base loses information (you would have to re-quantise W'), so a QLoRA adapter is usually merged into the bf16 original.

DoRA (Liu et al. 2024) splits each weight into a magnitude and a direction, W' = m · (W + s·BA) / ‖W + s·BA‖, with the norm taken per output row. It learns the magnitude vector m directly and the direction with LoRA. Full fine-tuning tends to change magnitude and direction somewhat separately, while plain LoRA ties them together. DoRA reports steady gains over LoRA at the same rank, merges just like LoRA, and costs a little more memory in training. dora_weight implements the formula. With m set at the start to the row norms of W, it equals W at step 0, which the tests check.

Serving many adapters at once

An adapter for the 8B model above is 41.9 M parameters, 83.9 MB in bf16, 191× smaller than the 16.1 GB base. So a provider can keep one base model on a GPU and thousands of customers' adapters in memory, and serve a batch in which every request uses a different adapter. This is the continuous-batching problem of Chapter 18 with a twist. The base matmul is shared and batched over all requests, and only the thin r-wide part is gathered per request.

def multi_lora_linear(x, W, As, Bs, adapter_ids, s):   # x: (N, in), one row per request
    base = x @ W.T                                       # (N, out)      one big shared GEMM
    A = As[adapter_ids]                                  # (N, r, in)    each row's own A
    B = Bs[adapter_ids]                                  # (N, out, r)
    low = torch.einsum("nri,ni->nr", A, x)               # (N, r)
    return base + s * torch.einsum("nor,nr->no", B, low) # (N, out)

The adapter path adds 2·41.9 M FLOPs per token to the 2·6.98 G of the base Linears, which is 0.60%. Punica (Chen et al. 2023) and S-LoRA (Sheng et al. 2023) wrote the gather-matmul kernels and paged adapter memory that make this fast, and vLLM and SGLang ship them. The test checks the batched function against merging each request's adapter separately.

23.4 · Where the data comes from: the modern recipe

InstructGPT (2022) trained on tens of thousands of demonstrations written by contractors. Few post-training pipelines look like that now. Writing great demonstrations by hand is slow and expensive, and limited by the writers' skill. Meanwhile models have become good enough to produce, filter and grade most of the data themselves. Llama 3's post-training (Dubey et al. 2024) ran several rounds of rejection sampling filtered by a reward model. The open Tülu 3 recipe (Lambert et al. 2024) mixes chosen human data with large synthetic sets for each target skill. Four techniques do most of the work.

1. Synthetic SFT data

Prompt a capable model to write instructions and answers for a target skill, then filter. Self-Instruct (Wang et al. 2022) grew 52k instructions from 175 seed tasks this way. Current pipelines generate millions, conditioned on personas, topics or seed documents for variety. They filter by a judge model, by running the code, and by deduplication. Design against two failure modes. One is loss of variety (the generator's favourite phrasings everywhere). The other is benchmark leakage: a generator that memorised test items reproduces them, so decontaminate against every eval (Ch 26).

2. Rejection-sampling fine-tuning

Use the model you are training as the data generator. For each prompt, sample k responses, keep the ones a verifier accepts (or the top scorers under a reward model), and run SFT on the survivors. Repeat with the improved model. This is the idea behind STaR (Zelikman et al. 2022), RFT (Yuan et al. 2023), ReST and "expert iteration". It is reinforcement learning in disguise: SFT on the successful samples is a policy gradient with reward 1 for kept samples and 0 for the rest.

How many samples does it take? If the model solves a prompt with probability p per sample, the chance that k samples contain at least one keeper is 1 − (1 − p)k:

p = 0.2       k = 1: 0.200    k = 4: 0.590    k = 8: 0.832    k = 16: 0.972    k = 32: 0.999

Prompts the model already solves give easy data. Prompts it never solves (p ≈ 0) give nothing, however large k is. The same arithmetic comes back as pass@k in Chapter 26, and as GRPO's all-wrong groups in Chapter 25.

3. Distillation from a stronger model

If a stronger teacher exists, run SFT on its outputs. Sequence-level distillation (Kim & Rush 2016) is exactly that. It minimises cross-entropy on teacher samples, which minimises the forward KL(teacher ‖ student) over the teacher's distribution. For reasoning models it has worked startlingly well. DeepSeek-R1's report distilled about 800k samples of R1's reasoning traces into Qwen and Llama models from 1.5B to 70B. The distilled small models beat the same small models trained directly with large-scale RL. s1 (Muennighoff et al. 2025) got strong maths reasoning from just 1,000 carefully chosen traces. The traces carry the behaviour (checking work, backtracking) in a form SFT can copy.

4. On-policy distillation

Off-policy distillation has a flaw: the student learns from states the teacher visits. When the student makes its own early mistake, it is in a state it never saw in training, and the errors build up. On-policy distillation lets the student generate, then asks the teacher to grade every token of the student's own sample. It minimises the reverse KL(student ‖ teacher), estimated per token as log πstudent(yt) − log πteacher(yt). GKD (Agarwal et al. 2023) and MiniLLM (Gu et al. 2023) introduced it. Qwen3 used it to train its small models from the large ones, and Thinking Machines (2025) showed it reaching RL-level reasoning at a fraction of the cost. It is RL with a dense reward: every token is scored, instead of one number at the end. Notice the form. It is the per-token KL penalty of section 23.6, with the teacher in place of the reference model.

Worked example — forward and reverse KL choose different students

A teacher puts its weight on two modes: p = [0.45, 0.05, 0.45, 0.05]. There are two candidate students. cover = [0.25, 0.25, 0.25, 0.25] spreads out, and mode = [0.85, 0.05, 0.05, 0.05] commits to one mode.

Forward KL punishes missing any of the teacher's weight, so it prefers the student that covers both modes, even though that student puts half its weight where the teacher puts 10%. Reverse KL punishes putting weight where the teacher has little, so it prefers the student that does one thing the teacher would do. A small student cannot represent everything a large teacher does. On-policy distillation's mode-seeking makes it do some things well instead of everything vaguely.

23.5 · The reward model

Take a pretrained LM, replace the LM head with a scalar head, and train it to score responses.

class RewardModel(nn.Module):
    def __init__(self, base):
        super().__init__()
        self.base = base                                   # a pretrained transformer
        self.head = nn.Linear(base.cfg.d_model, 1, bias=False)

    def forward(self, ids, attn_mask):
        h = self.base.hidden_states(ids)                   # (B, T, C)
        last = attn_mask.sum(1) - 1                        # index of final real token
        return self.head(h[torch.arange(len(h)), last]).squeeze(-1)   # (B,)

The Bradley–Terry model

Humans give rankings, not scores. Bradley-Terry (1952) converts one into the other. It assumes each response has a hidden quality r, and that the probability of preferring yw over yl is a logistic function of their difference:

P(yw ≻ yl | x) = er(x,yw)er(x,yw) + er(x,yl) = σ(r(x,yw) − r(x,yl))

Maximum likelihood on that gives the reward-model loss:

ℒRM = − E(x,yw,yl) [ log σ(rφ(x,yw) − rφ(x,yl)) ] 
r_w = reward_model(chosen_ids,   chosen_mask)      # (B,)
r_l = reward_model(rejected_ids, rejected_mask)    # (B,)
loss = -F.logsigmoid(r_w - r_l).mean()

Now add 100 to both rewards in every row. The gap is unchanged, so every loss is identical. The model cannot tell 2 against 1 from 102 against 101.

That is why a reward score means nothing on its own. Only differences are learned, so "this response scored 7.3" tells you nothing without something to compare against. Scores from two different reward models cannot be compared at all. It is also why ln 2 = 0.6931 is your sanity check at step 0: an untrained reward model has no opinion, so the gap is 0. Remember this row. DPO's loss lands on exactly the same number for exactly the same reason (Chapter 24).

import math
for rw, rl in [(2,1), (5,1), (1,1), (1,2)]:

Only differences are identified

The loss depends only on r_w − r_l, so adding a constant to every reward changes nothing. The absolute scale has no meaning, so a reward of 3.7 tells you nothing on its own. This is why reward models are judged by ranking accuracy on held-out pairs, never by their raw outputs. Remember this fact. It is what makes DPO work in Chapter 24, and it is the same model Chatbot Arena fits to human votes (Chapter 26).

23.6 · PPO

Now optimise the policy against that reward. The objective:

maxπθ   Ex∼D, y∼πθ [ rφ(x, y) ]  −  β · KL(πθ(y|x) ‖ πref(y|x)) maximise reward, but stay close to the SFT model
Why the KL term is non-negotiable

The reward model only approximates human preference, and it was trained on a limited dataset. Optimise against it hard enough and the policy will find inputs where the approximation is badly wrong: outputs that score 10/10 and are nonsense. This is reward hacking, and without a KL constraint it happens almost every time. Typical failures seen in practice are responses that are absurdly long (length bias in the reward model), hedged too much, or that repeat flattering phrases the reward model liked.

The KL penalty, paid token by token

The objective above is about whole responses, but a language model acts one token at a time, and PPO wants a reward for every action. The standard implementation (InstructGPT, and every RLHF library since) turns the KL term into a per-token reward. Write log πt and log πref,t for the two models' log-probabilities of the token actually sampled at step t. Then

rt = − β ( log πt − log πref,t )    for every token,    plus rφ(x, y) on the last token Σt rt = rφ(x,y) − β log( π(y|x) / πref(y|x) ), whose expectation over y ∼ π is the objective

The sum works because log π(y|x) is the sum of the per-token log-probabilities (the chain rule of probability, the same fact that DPO's sequence log-probs rest on). Each token is charged for how much more likely the policy made it than the reference did. A token the policy made less likely earns a small bonus. This is reward shaping: the same total, delivered at every step, so that the value function in the next section has something to learn from at every step instead of one number at the end.

Advantages: from rewards to "was this token better than usual?"

The policy gradient for a token is its log-probability gradient times its advantage, At = Q(st, at) − V(st). That is how much better the outcome was after taking this token than the value V of the state predicted on average. The state st is the prompt plus the tokens so far, and the action at is the next token. We have the per-token rewards and a learned value model Vψ. There are two ways to estimate At, at opposite ends:

  • Monte Carlo: At ≈ Gt − V(st), where Gt = rt + γrt+1 + γ2rt+2 + … is the actual return. It is unbiased, but Gt depends on every later sampled token, so it has high variance.
  • One-step TD: At ≈ δt = rt + γV(st+1) − V(st). It has low variance, since it uses only one sampled reward, but it is biased whenever V is wrong, and early in training V is wrong.

GAE, derived

Generalised Advantage Estimation (Schulman et al. 2015) sits between them. Start from the n-step estimate, which uses n real rewards and then trusts V. Its key property is that it is a sum of TD errors, because the intermediate values cancel in pairs:

Σl=0..n−1 γl δt+l = Σl=0..n−1 γl ( rt+l + γV(st+l+1) − V(st+l) ) = rt + γrt+1 + … + γn−1rt+n−1 + γnV(st+n) − V(st) every V(st+1) … V(st+n−1) appears once with + and once with −, and cancels

Call that Â(n)t. n = 1 is TD, n = ∞ is Monte Carlo. GAE takes an exponentially weighted average over all n, with weight (1 − λ)λn−1:

ÂGAEt = (1 − λ) Σn≥1 λn−1 Â(n)t = (1 − λ) Σn≥1 λn−1 Σl<n γlδt+l = Σl≥0 γl δt+l · (1 − λ) Σn>l λn−1 = Σl≥0 (γλ)l δt+l swap the sums: δt+l appears in every Â(n) with n > l, and (1−λ)Σn>lλn−1 = λl

Two limits check it. λ = 0 leaves only δt (TD). λ = 1 gives Σγlδt+l, which by the cancelling identity is Gt − V(st) (Monte Carlo). And the sum has a one-line backward recursion, which is how everyone computes it:

Ât = δt + γλ · Ât+1      ÂT = 0      value target = Ât + V(st) 
def gae(rewards, values, gamma=1.0, lam=0.95):     # rewards (T,), values (T+1,), V(s_T) = 0
    deltas = rewards + gamma * values[1:] - values[:-1]       # (T,)  one TD error per token
    adv, running = torch.zeros_like(rewards), 0.0
    for t in reversed(range(len(rewards))):                   # right to left
        running = deltas[t] + gamma * lam * running
        adv[t] = running
    return adv, adv + values[:-1]                             # advantages, value targets

Read the λ = 1 row. This value model underestimates how good every early state is (the return from state 0 is 0.95, but V says 0.5), so Monte Carlo gives the early tokens large advantages. TD trusts the wrong V and gives them small ones. λ = 0.95 sits close to Monte Carlo while damping the noise of long tails. RLHF implementations usually use γ = 1 (a completion is a finite episode) and λ around 0.95. Every number here is asserted in test_gae_recursion_equals_definition_and_limits.

The clipped surrogate

PPO's contribution is a way to take large policy steps without wrecking the policy:

ℒCLIP = E [ min( ρtÂt,   clip(ρt, 1−ε, 1+ε)Ât ) ] ρt = πθ(at|st) / πθold(at|st)  ·  Â = the GAE advantage  ·  ε ≈ 0.2

The clip is one-sided, in the direction the advantage favours. With Â > 0 (a good action), once ρ exceeds 1 + ε the clipped term is the minimum and its gradient is zero. You cannot keep pushing a good action's probability up within one batch. With Â < 0 (a bad action), the gradient vanishes once ρ falls below 1 − ε, so you cannot keep pushing it down. But a bad action whose probability rose (ρ > 1 + ε, Â < 0) keeps its gradient, because there the unclipped term is the minimum. So PPO always corrects a step in the wrong direction. That asymmetry keeps updates close to the data they were collected from, and it makes PPO stable enough to use. The value model is trained alongside, by regressing V(st) onto the value targets Ât + V(st).

What running PPO for RLHF actually requires

Four models in memory, two of them getting gradients. Add a generation loop inside the training loop, advantage estimation, and a dozen hyperparameters that interact badly. RLHF with PPO is truly hard to get working, and that difficulty is the whole reason DPO exists. (LoRA helps here too. The policy and the value model can be adapters on one shared frozen base, and the reference is then the base with the adapters switched off.)

Why can't reward-model scores be compared across different reward models?
They use different architectures
They are trained on different data
The Bradley-Terry loss only constrains reward differences, so the absolute scale and offset are arbitrary
Scores are normalised differently
Only differences are pinned down. Add any constant to every reward and the loss is unchanged, and the scale is similarly loose up to the logistic's slope. A score of 5.2 from one model and 5.2 from another have nothing in common. Judge reward models by pairwise ranking accuracy.
You remove the KL penalty from PPO. Reward climbs to record levels. What has happened?
Reward hacking: the policy found unusual outputs that the reward model scores highly but humans would rate poorly
The model really got much better
The reward model is broken
Nothing; the KL term is only for stability
Reward hacking, almost guaranteed. The reward model approximates human preference from a limited sample. Optimising without limits against any approximation finds where it fails: Goodhart's law, automated. The KL term keeps the policy in the region where the reward model was actually trained, and where it can therefore be trusted.
How many models are in memory during PPO-based RLHF, and which are trained?
2: policy and reward model, both trained
4: policy, reference, reward, value; policy and value are trained
3: policy, reward, value; all trained
1: only the policy
Four models, two trained. This is the practical burden that led to DPO: memory, coordination, and many hyperparameters to tune. For a 7B policy in bf16 you are holding roughly 4×14 GB of weights before optimizer state or activations.
In the per-token reward rt = −β(log πt − log πref,t), what does the sum over a completion equal?
The exact KL divergence between the two models
Zero, on average
The reward-model score
−β times the log of π(y|x)/πref(y|x) for this completion: a one-sample estimate of the sequence-level KL penalty, because sequence log-probs are sums of token log-probs
The chain rule turns a sequence penalty into token penalties. Its expectation over completions sampled from π is −β·KL(π ‖ πref), exactly the term in the objective. Any single completion gives a noisy estimate, and in the worked example it is −0.05.
Setting GAE's λ = 1 gives which advantage estimate, and what is its weakness?
One-step TD; biased by errors in the value model
The Monte Carlo return minus V(st); unbiased but high variance, because it depends on every later sampled token
The reward-model score; ignores the KL
Zero; λ = 1 disables the advantage
λ trades bias for variance. The cancelling identity turns Σδt+l into Gt − V(st). λ = 0 is the other end: just δt, low variance, and as wrong as V is. In the worked example the two ends give 0.45 and 0.12 for the first token.

23.7 · The data

{
  "prompt":   "Explain why the sky is blue to a 6-year-old.",
  "chosen":   "Sunlight looks white but is really made of all the colours...",
  "rejected": "Rayleigh scattering causes shorter wavelengths to scatter more..."
}

Note that the rejected response is not wrong. It is less suited to the request. Most preference data is about fit and tone, not correctness.

  • Human preference: highest quality, but expensive and slow, and annotators usually agree only 60 to 75% of the time. That noise limits everything downstream.
  • AI feedback (RLAIF / Constitutional AI): a strong model judges. It is far cheaper and now the most common in practice. The risk is inheriting the judge's biases.
  • Verifiable signals: for maths and code, check the answer. No preference model is needed at all. That is Chapter 25.
Known biases in preference data

Both human and AI annotators measurably prefer longer responses, more confident phrasing and formatted output (headers, bullet lists), largely regardless of actual quality. Models trained on this data inherit all three. If your aligned model became wordy and started using bullets for everything, the bug is in your data, not your training code. Removing length bias from the reward model, or using length-controlled evaluation, is now standard practice.

23.8 · How you know it worked

Training loss tells you almost nothing here. SFT loss falls whether or not the model became more useful. A reward model's score rises fastest when the policy is hacking it. A judge model's win rate rises when answers get longer. Post-trained models are evaluated in three ways, each with a trap that Chapter 26 works through in detail:

  • Capability benchmarks (maths, code, knowledge), to check that post-training did not damage what pretraining built. The trap: most benchmarks are too small to detect a 2-point change.
  • Win rates against a baseline, graded by a judge model. The trap: judges prefer the first answer, the longer answer and answers from their own model family. Report length-controlled win rates with both orderings.
  • A private eval of your actual task, with human labels on a subset to calibrate the judge. This is the one that should decide what ships.

23.4Predict, then measure: does rank matter?exploration

With s = α/r at a fixed learning rate, higher ranks often do no better, and sometimes worse, because their effective step shrinks. 23.5Implement GAE and check it three wayscode

Write GAE with the backward recursion. Check it against: (a) the explicit sum Σ(γλ)lδt+l; (b) λ = 0 gives the TD errors; (c) λ = 1 gives discounted returns minus V. Use the four-token example of 23.6 and reproduce A = [0.4171, 0.3127, 0.2450, 0.1000] at λ = 0.95.

A common bug

Common mistakes: forgetting that V(sT) = 0 after the final token, or bootstrapping across the boundary into the next completion in a packed batch. Both make the last advantages wrong, and the last token is the one that carries the reward-model score.

23.6Train a reward model and find its biasescode

Train a Bradley-Terry reward model on a public preference dataset. Then probe it:

  1. Ranking accuracy on a held-out split. (Above 70% is respectable. Humans agree with each other ~65 to 75% of the time.)
  2. Length bias: plot reward against response length. Fit a line. How much of the variance is length?
  3. Format bias: take 50 responses, reformat them with bullet points without changing content, and measure the reward change.
What you'll find

Length correlation is usually strong, often r > 0.3 and sometimes much higher. Adding bullets usually raises the reward measurably. Now you can see concretely why RLHF-trained models became wordy and fond of lists around 2023-24. Once you can measure a bias you can correct it: subtract a baseline fitted on length from the reward and evaluate again.

23.7Induce reward hacking on purposethinking

Using your reward model, run best-of-N sampling with N ∈ {1, 4, 16, 64, 256} and plot (a) mean reward and (b) your own quality rating of a sample of outputs, against N.

The expected divergence

Reward rises steadily with N. Quality as judged by a human rises, peaks around N=16 to 64, then falls. Best-of-N optimises against the reward model with no KL term, so large N is exactly where hacking appears. This is the clearest demonstration of why the KL term exists, and it takes no RL machinery at all to reproduce.
