This is where everything comes together. You will build a small language model with a current architecture (RMSNorm, RoPE, GQA, SwiGLU, KV cache). Milestone 1 — Tokenizer

M1Train a byte-level BPE tokenizer~1 hr

Train it on the corpus you chose. Provide encode, decode and the special tokens <|bos|>, <|eos|>, <|user|> and <|assistant|>.

Tests that must pass:

assert tok.decode(tok.encode(s)) == s          # for 1000 random corpus slices
assert tok.decode(tok.encode("🤖 émoji ñ 中文")) == "🤖 émoji ñ 中文"   # byte-level
assert len(tok.encode(text)) < len(text.encode()) * 0.4   # compression ≥ 2.5×
assert all(i < cfg.vocab_size for i in tok.encode(text))

Milestone 2 — The model

M2Implement the architecture~2 hrs

Build RMSNorm, build_rope_cache/apply_rope, GroupedQueryAttention, SwiGLU, Block and Model.

Tests that must pass (do not skip any of them):

# 1. Shapes
logits, loss = model(ids)                 # ids: (2, 16)
assert logits.shape == (2, 16, cfg.vocab_size)

# 2. Loss at init ≈ ln(V)                                        [Ch 9]
assert abs(loss.item() - math.log(cfg.vocab_size)) < 0.3

# 3. CAUSALITY — perturb one token, earlier outputs must not move [Ch 9]
ids2 = ids.clone(); ids2[0, 8] = (ids2[0, 8] + 1) % cfg.vocab_size
assert torch.allclose(model(ids)[0][0, :8], model(ids2)[0][0, :8], atol=1e-5)
assert not torch.allclose(model(ids)[0][0, 8], model(ids2)[0][0, 8])

# 4. RoPE encodes RELATIVE position                               [Ch 7]
assert abs(score(5, 8) - score(50, 53)) < 1e-5

# 5. GQA grouping is correct (loop vs vectorised)                 [Ch 16]
assert torch.allclose(gqa_loop(x), gqa_vectorised(x), atol=1e-5)

# 6. Every parameter receives a gradient
loss.backward()
for n, p in model.named_parameters():
    assert p.grad is not None and p.grad.abs().sum() > 0, n

# 7. Parameter count matches your hand calculation                [Ch 9]
assert abs(count_params(cfg) - sum(p.numel() for p in model.parameters())) < 10

Test 3 is the one people skip and then regret. Test 6 catches a sub-module that is not connected, which otherwise looks like "the model just learns slowly".

Milestone 3 — Training

M3Train it~1-2 hrs

Corpus options, from least to most interesting: TinyStories (best results at this scale), Tiny Shakespeare (fastest), or ~20 MB of any text you like.

Before the real run, do the overfit-one-batch test from Chapter 11. The loss must reach < 0.1 on a single fixed batch within 500 steps. If it cannot, stop and debug, because nothing after this will work.

Suggested: batch 32 × seq 256, lr 3e-4, warmup 200, ~5000 steps,
grad clip 1.0, eval every 250 steps.

Deliverables: train/val loss curves, final val perplexity, 500 tokens of generated text, and the check of loss against ln(V) at step 0.

Target numbers

On TinyStories with 12.6M parameters, expect a val loss of around 1.6 to 2.2 (perplexity 5 to 9) and truly coherent short stories with consistent characters. TinyStories was designed so that small models can actually succeed. On Shakespeare, expect a loss of ~1.4 to 1.8, with convincing form and no meaning. Either counts as a pass, but TinyStories is much more satisfying.

Milestone 4 — Efficient inference

M4KV cache + samplers~1 hr

Add KV caching and the full sampler suite (temperature, top-k, top-p, min-p).

# The test that catches all three cache bugs from Ch 15:
torch.manual_seed(0); a = generate(model, prompt, 100, use_cache=False, temperature=0)
torch.manual_seed(0); b = generate(model, prompt, 100, use_cache=True,  temperature=0)
assert torch.equal(a, b), "cache changes the output — check RoPE offset & is_causal"

Deliverables: a plot of time per token against position, cached and uncached; the measured speedup at 100, 200 and 400 tokens; and generated samples at three temperatures.

Milestone 5 — Alignment

M5SFT then DPO~2 hrs

Build a small preference dataset; 200 to 500 triples is enough. At this scale, the easiest way to make the effect visible is to pick a style difference you can generate synthetically:

  • short answers (chosen) against rambling ones (rejected)
  • stories that end happily (chosen) against ones that end abruptly (rejected)
  • always staying in character against breaking character

Then do (a) SFT with prompt masking and (b) DPO with β=0.1. Log the loss, implicit rewards, margin, ranking accuracy, and the absolute chosen/rejected log-probs.

Deliverables:

  1. Reward-margin and ranking-accuracy curves. Accuracy should reach > 0.8.
  2. Side-by-side generations from base, SFT, and DPO models on 10 held-out prompts.
  3. A β sweep {0.01, 0.1, 0.5} with samples from each, and a paragraph on what β=0.01 did.
  4. The implicit-reward evaluation from Exercise 24.3: does β·log(π/π_ref) rank held-out pairs above chance?
What success looks like

The DPO model should clearly follow your preference while staying coherent. At β=0.01 you will probably see it collapse into very short outputs, repetition or broken grammar. That is the KL constraint being too weak, exactly as Chapter 24 predicts. Seeing that failure yourself is the most valuable part of this milestone.

Milestone 6 — LoRA

M6Fine-tune with LoRA, then merge~1 hr

Repeat the SFT step of M5, but this time freeze the pretrained model and train LoRA adapters (Ch 23.3) on all seven projections (q_proj k_proj v_proj o_proj gate up down) at r = 8, α = 16. Write your own LoRALinear, and check it against tfs/lora.py afterwards.

Tests that must pass:

# 1. Your hand count matches the model                               [Ch 23]
assert trainable_params(model) == 325_632            # r·(in+out) summed: 2.59% of 12,587,904
# (q and v only would be 61,440 = 0.49%)

# 2. At step 0 the wrapped model IS the pretrained model
assert torch.equal(lora_model(ids)[0], base_model(ids)[0])

# 3. After one backward pass: only B has a gradient, the base has none
assert all(m.A.grad.abs().max() == 0 and m.B.grad.abs().max() > 0 for m in lora_modules(model))
assert all(p.grad is None for n, p in model.named_parameters() if not p.requires_grad)

# 4. After training, merging changes nothing and unmerging restores the weights
y = model(ids)[0]; merge_all(model)
assert torch.allclose(model(ids)[0], y, atol=1e-5)

Deliverables:

  1. Validation loss curves for full SFT and LoRA SFT on the same data and steps, on one plot.
  2. A rank sweep r ∈ {2, 8, 32} with α/r and with rsLoRA's α/√r (exercise 23.4).
  3. Run M5's DPO on top of the LoRA-SFT model, with the policy as a second adapter and the reference as the base with the adapters off. Does the reward margin curve match the full-model run?
What success looks like

At this scale the memory saving does not matter (the whole model's optimizer state is 201 MB, and the adapters' is 5.2 MB), so the point is the mechanics. For a style preference, LoRA should come close to full SFT. If it lags badly, check the learning rate first (LoRA usually wants a larger one), and then the scaling. Running DPO with two adapters on one base is how real RLHF systems fit the policy, reference and value model into one GPU's memory.

Milestone 7 — Evaluation

M7Measure what you built, with error bars~1-2 hrs

Using Chapter 26, evaluate every checkpoint you have (pretrained, SFT, DPO, LoRA-SFT) on two things.

(a) Held-out perplexity. On a validation split that no checkpoint trained on, report perplexity and bits per byte (Ch 11), so the number still means something if the tokenizer changes. Report a bootstrap interval over documents, not tokens, because tokens within a document are not independent.

(b) A tiny task benchmark you write. Use 300 held-out prompts scored by a program on your M5 preference (for example "the story ends with a happy sentence" by a keyword rule, or "the answer is under 40 words"). If you did the GRPO stretch goal, add 300 two-digit additions scored by exact match. Sample n = 10 completions per prompt at temperature 0.8.

Tests that must pass:

# 1. The benchmark is not in the training data                        [Ch 26.3]
assert max(ngram_overlap(item, train_ngrams, n=13) for item in benchmark) == 0.0

# 2. Your scorer agrees with you: hand-check 30 scored outputs
assert scorer_errors_on_30_hand_checked <= 1

# 3. Your pass@k matches the unbiased estimator                         [Ch 26.6]
assert abs(my_pass_at_k(10, 3, 5) - (1 - math.comb(7, 5) / math.comb(10, 5))) < 1e-12

Deliverables:

  1. One table: each checkpoint's perplexity, task pass@1 (averaged over the 10 samples) and pass@5, each with a 95% interval.
  2. The paired bootstrap interval for DPO − SFT on the task (26.5). Is it significant? Then the unpaired one from the same data, and the ratio of their widths.
  3. Using the measured disagreement rate between SFT and DPO, how many prompts would you need to detect a 2-point change (n_items_paired)?
What success looks like

Perplexity usually gets slightly worse after SFT and DPO (the model moved away from the pretraining distribution on purpose), while the task score improves. Seeing both is the reason to measure both. With 300 prompts, expect intervals of several points, and expect the paired interval to be clearly narrower than the unpaired one. If DPO's gain is real, it usually survives the paired test. If it only shows up in a judge model's win rate and not in your program's score, the length bias of Chapter 26 is the first suspect.

Self-assessment

You have understood this course if you can answer these without looking anything up:

Why is √dk the right scaling factor?
It normalises the vector lengths
It makes attention weights sum to 1
Var(q·k) = d_k for unit-variance inputs, so std = √d_k, and dividing by it keeps the softmax out of saturation
It compensates for the number of heads
Ch 5. Variances add over the d_k summed terms, and the standard deviation is the square root.
Why is LLM decoding memory-bound?
The KV cache is larger than the model
One token's forward pass reads every weight but does only ~1 FLOP per byte read, hundreds of times below the GPU's ridge point
GPUs have slow memory
Attention is quadratic
Ch 15. The arithmetic intensity is ≈ 1, against a ridge point of around 295 FLOP/byte on an H100.
Why does GQA reduce memory but not FLOPs?
All query heads still attend over the full sequence; only the number of K,V heads stored and read shrinks
It skips some attention computations
It uses lower precision for K and V
It reduces the sequence length
Ch 16. K and V are expanded back up (or re-read) before the matmul.
Why is FlashAttention faster despite doing the same or more arithmetic?
It approximates the softmax
It uses fewer attention heads
It runs in lower precision
It never writes the N×N matrix to HBM, because tiling plus the online softmax keep everything in SRAM
Ch 17. It is exact, and the whole gain is in data movement.
Why does DPO not need a reward model?
It uses a fixed heuristic reward
The KL-constrained optimum lets you express reward as β·log(π/π_ref) + β·log Z(x), and Z(x) cancels in the Bradley-Terry difference
It trains the reward model implicitly through a second head
It uses verifiable rewards instead
Ch 24. The policy is the reward model, and the intractable term cancels exactly.
Why does GRPO not need a value model?
It uses the reference model's values
It does not compute advantages
Sampling G completions per prompt makes the group mean a measured baseline for the advantage
The reward model provides per-token values
Ch 25. It trades a learned critic for G× generation.
Why is LoRA's B matrix initialised to zero and A to random values?
B = 0 makes the update BA zero, so training starts exactly at the pretrained model; A random keeps B's gradient, s·g(Ax)T, nonzero
To save memory
So that A can be quantised
Either can be zero; it makes no difference
Ch 23. Each factor's gradient is proportional to the other, so with both at zero you sit on a saddle that never moves.
Your DPO model beats your SFT model by 3 points on a 300-prompt task. How should you test whether that is real?
Check whether the two models' 95% intervals overlap
Run the eval again with a different seed
Use a larger judge model
A paired bootstrap over prompts on the per-prompt score differences, since both models answered the same prompts
Ch 26. Pairing cancels the difficulty noise both models share. Checking whether separate intervals overlap is the unpaired test, and it misses real gains.

Where to go next

This course is the first of eleven in the library (the Library button in the top bar). Everyone should take Evaluation Ch 01 next, because no later skill can be checked without it. Then follow a track: systems (GPU programming, then inference engineering), applied (retrieval, then agents), or model (post-training). The others are below, with outside reading.

  • Interpretability: Transformer Circuits, sparse autoencoders, superposition. It is the most intellectually interesting open problem in the field.
  • Systems: read the vLLM or SGLang source, and write a Triton kernel. Chapters 15 to 18 are the prerequisites, and you now have them.
  • Post-training: the RLHF Book, then reproduce a GRPO run on a real benchmark.
  • Build things: the fastest way to keep learning is to deploy a model and find out which of Chapters 13 to 18 you only thought you understood.
One last thing

In structure, the architecture in this capstone is the same as that of a frontier model. The differences are scale, data and a huge amount of engineering. The idea is the same. If you built this, you have built the thing. Everything else is more of it.
