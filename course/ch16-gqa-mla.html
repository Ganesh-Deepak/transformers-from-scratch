16 · MQA, GQA, and Multi-Head Latent Attention

Chapter 15 established the problem: the KV cache limits how many users fit on a GPU. This chapter is the sequence of answers — from a blunt 2019 hack, through the 2023 compromise that everyone adopted, to DeepSeek's 2024 low-rank scheme that is both smaller and better than what it replaced.

16.1 · The idea: share the K/V heads

Standard MHA gives every query head its own key head and value head. But the cache is proportional to n_kv_head, and there's no law saying it must equal n_head.

16.2 · MQA — one KV head for everybody

self.q_proj  = nn.Linear(d_model, n_head * d_head, bias=False)   # (C, 4096)
self.k_proj  = nn.Linear(d_model,      1 * d_head, bias=False)   # (C,  128)  ← tiny
self.v_proj  = nn.Linear(d_model,      1 * d_head, bias=False)   # (C,  128)

All 32 query heads attend against the same keys and values. A 32× cache reduction, for free.

It works, but not without cost: Shazeer reported quality degradation, and later work found MQA models can be unstable to train. The problem is intuitive — heads specialise partly by having their own notion of what to match against, and MQA removes that.

16.3 · GQA — the compromise that won

Group the query heads. Each group shares one K/V head.

class GroupedQueryAttention(nn.Module):
    def __init__(self, d_model, n_head, n_kv_head, d_head):
        super().__init__()
        assert n_head % n_kv_head == 0
        self.nh, self.nkv, self.hd = n_head, n_kv_head, d_head
        self.rep = n_head // n_kv_head                 # queries per KV head
        self.q_proj = nn.Linear(d_model, n_head    * d_head, bias=False)
        self.k_proj = nn.Linear(d_model, n_kv_head * d_head, bias=False)
        self.v_proj = nn.Linear(d_model, n_kv_head * d_head, bias=False)
        self.o_proj = nn.Linear(n_head * d_head, d_model,    bias=False)

    def forward(self, x, cos, sin, cache=None):
        B, T, _ = x.shape
        q = self.q_proj(x).view(B, T, self.nh,  self.hd).transpose(1, 2)  # (B, nh,  T, hd)
        k = self.k_proj(x).view(B, T, self.nkv, self.hd).transpose(1, 2)  # (B, nkv, T, hd)
        v = self.v_proj(x).view(B, T, self.nkv, self.hd).transpose(1, 2)  # (B, nkv, T, hd)

        q, k = apply_rope(q, k, cos, sin)

        if cache is not None:
            k = torch.cat([cache[0], k], dim=2)        # cache holds only nkv heads!
            v = torch.cat([cache[1], v], dim=2)
        new_cache = (k, v)

        # Expand KV heads to match query heads for the matmul.
        k = k.repeat_interleave(self.rep, dim=1)       # (B, nh, T, hd)
        v = v.repeat_interleave(self.rep, dim=1)       # (B, nh, T, hd)

        y = F.scaled_dot_product_attention(q, k, v, is_causal=(T > 1))
        y = y.transpose(1, 2).reshape(B, T, self.nh * self.hd)
        return self.o_proj(y), new_cache
repeat_interleave vs repeat — this ordering bug is real

With nkv=2, rep=2: repeat_interleave gives head order [k0, k0, k1, k1], which matches query heads [q0,q1 | q2,q3] grouped contiguously. repeat gives [k0, k1, k0, k1] — an interleaved grouping. Both run. Both produce plausible losses. Only one matches how the weights were trained. If you ever load Llama weights into your own GQA implementation and quality is mysteriously mediocre, check this line first.

The expansion is a memory trick, not a FLOP saving

After repeat_interleave you're doing exactly the same attention FLOPs as MHA. The win is entirely in what you store and read: the cache holds n_kv_head heads, not n_head. Since decode is memory-bound (Ch 15), reducing bytes read is reducing time. Fused kernels skip the materialisation entirely and just re-read the same K head for each query in the group.

And note 576 is not 2 × something × 128 — MLA has escaped the formula entirely. There is no "number of KV heads" any more; there is a compressed latent whose width you choose directly.

The conceptual jump. GQA turns a dial that already existed — it stores fewer heads. MLA changes what is stored at all: not heads, but a low-rank summary from which every head's K and V are reconstructed on the fly. That is why it can land between GQA-4 and MQA on size while beating full MHA on quality.

Why g = 8 keeps appearing

Ainslie et al. found the quality/cache curve is strongly non-linear: going from MHA to 8 groups costs almost nothing, while going from 8 groups to 1 (MQA) costs a lot. There's also a practical reason — 8 KV heads divides evenly across 8-GPU tensor-parallel setups, one KV head per GPU. Llama-2-70B, Llama-3 (all sizes), Mistral, Qwen2.5 and Gemma all landed on 8 or fewer.

16.4 · MLA — Multi-head Latent Attention

DeepSeek-V2 (2024) asked a different question. GQA reduces the cache by deleting heads. What if instead you compress the KV information into a low-rank latent, and decompress it on the fly?

The core idea

Don't cache K and V. Cache a single small latent vector cKV per token, from which every head's K and V can be reconstructed by a learned up-projection. You store the compressed form; the heads still get full, distinct keys and values.

cKVt = WDKV ht      kCt = WUK cKVt      vCt = WUV cKVt D = down-projection (compress), U = up-projection (decompress). Only cKV is cached.

Per-head q/k dim = 128 + 64 = 192. Cached per token per layer = 512 + 64 = 576 elements.

The problem RoPE creates, and the "decoupled" fix

Here is the subtle part, and the reason MLA looks more complicated than it "should".

The whole point of caching a latent is that you never have to materialise per-head keys. That works because of an absorption identity — the up-projection can be folded into the query side:

(qC)T kC = (WUQcQ)T (WUKcKV) = (cQ)T (WUQ)TWUK cKV the highlighted product is a fixed matrix — precompute it once, attend directly in latent space

Now insert RoPE. RoPE applies a position-dependent rotation Rm between the query and key:

(RmWUQcQ)T(RnWUKcKV) = (cQ)T(WUQ)T Rn−m WUK cKV Rn−m sits between the two matrices and depends on the token pair — the product can no longer be precomputed

DeepSeek's fix is to split the head dimension in two:

  • 128 dims with no RoPE — these go through the latent and enjoy absorption.
  • 64 dims with RoPE — computed directly from the hidden state, bypassing the latent. Crucially the RoPE key is shared across all 128 heads, so it costs only 64 extra cached values per token, not 64×128.
# Sketch of the MLA forward pass (shapes for DeepSeek-V3, one layer)
#   h: (B, T, 7168)

# ---- keys/values: compress to a latent, plus a shared RoPE key ----
c_kv  = self.W_dkv(h)                       # (B, T, 512)   ← CACHE THIS
k_rope = self.W_kr(h)                       # (B, T, 64)    ← AND THIS (shared by all heads)
k_rope = apply_rope_1head(k_rope, cos, sin)

#   total cached per token per layer: 512 + 64 = 576 values

# ---- at attention time, decompress ----
k_nope = self.W_uk(c_kv).view(B, T, 128, 128)     # (B, T, n_head, 128)
v      = self.W_uv(c_kv).view(B, T, 128, 128)     # (B, T, n_head, 128)

# ---- queries: also low-rank, also split ----
c_q    = self.W_dq(h)                             # (B, T, 1536)
q_nope = self.W_uq(c_q).view(B, T, 128, 128)      # (B, T, n_head, 128)
q_rope = self.W_qr(c_q).view(B, T, 128, 64)       # (B, T, n_head, 64)
q_rope = apply_rope(q_rope, cos, sin)

# ---- concatenate the two halves; RoPE key is broadcast across heads ----
q = torch.cat([q_nope, q_rope], dim=-1)                          # (B, T, 128, 192)
k = torch.cat([k_nope, k_rope[:, :, None].expand(-1,-1,128,-1)],
              dim=-1)                                            # (B, T, 128, 192)

attn_out = attention(q, k, v)                                    # (B, T, 128, 128)
out = self.W_o(attn_out.flatten(2))                              # (B, T, 7168)

At 128k context, one sequence:   70 KB × 131072     ≈ 9.2 GB
A number you'll see quoted, with the caveat

The DeepSeek-V2 paper reports a 93.3% KV cache reduction. That figure compares MLA against DeepSeek 67B's attention, not against a same-config MHA — so it isn't the same ratio as the 57× above. Both numbers are correct about different comparisons. When you see cache-reduction claims, always check what the baseline was.

The genuinely surprising result

MLA caches less than GQA with ~2.25 KV heads, yet DeepSeek's ablations show it outperforms full MHA on quality. Compression usually costs accuracy. The likely explanation is that the low-rank bottleneck acts as a useful inductive bias — full-rank per-head K/V has more capacity than the task needs, and forcing shared structure regularises it. That is a much better trade than GQA's, which is purely "give something up to save memory."

What MLA costs

  • More FLOPs. You do down- and up-projections that MHA doesn't. During compute-bound prefill this is a real cost.
  • Much more implementation complexity. The absorption trick, two attention code paths (prefill vs decode), and the RoPE split make MLA substantially harder to write than GQA. This is a large part of why adoption outside DeepSeek has been slower than the quality numbers alone would suggest.
  • Kernel support. It needs bespoke kernels (DeepSeek released FlashMLA) rather than reusing stock FlashAttention.
Why does MLA need a separate "decoupled" RoPE dimension instead of just applying RoPE to the decompressed keys?
RoPE only works on 64-dimensional vectors
A position-dependent rotation sits between WUQ and WUK, breaking the absorption that lets you attend in latent space
RoPE would make the latent too large
It's purely a numerical-stability measure
It breaks matrix absorption. Without RoPE, (W_UQ)ᵀW_UK is a constant you precompute once, so you never decompress the keys at all. With RoPE, R_{n−m} depends on the specific query–key pair and sits between them, so the product can't be folded. Splitting off a small RoPE-carrying slice preserves absorption for the other 128 dims.
Why is the RoPE key shared across all 128 heads while the RoPE query is per-head?
The key is cached, so per-head RoPE keys would cost 128× more cache; queries aren't cached, so per-head is free
Queries need more positional resolution than keys
It's an arbitrary choice
Sharing keys improves quality
Cache economics. A per-head RoPE key would add 128 × 64 = 8192 values per token per layer — 14× more than the entire 576-value MLA cache, destroying the whole point. Queries are recomputed fresh each step and never stored, so per-head costs nothing in cache. Every asymmetry in MLA traces back to "is this thing cached?"
A team wants to cut KV cache 4× on an existing Llama-style model with minimal risk. Best choice?
Switch to MQA
Convert to MLA from scratch
Reduce the number of layers
GQA with n_kv_head = n_head/4, or fp8 KV quantization — both are low-risk and composable
GQA or KV quantization. GQA at g=4 is well-trodden and needs only light continued pretraining (uptraining) to recover quality. fp8 quantization needs no retraining at all. MQA costs more quality than necessary, and converting a trained model to MLA is a research project — though note that's now an active area (e.g. TransMLA and related 2025 work on converting GQA checkpoints to MLA).

Where this sits in 2026

GQA remains the safe default and is in the overwhelming majority of open models. MLA has proven itself at trillion-parameter scale in the DeepSeek and Kimi lineages, and published ablations consistently rank MLA > GQA > MHA on quality-per-cached-byte. The barrier to wider adoption is engineering, not evidence. Meanwhile the newest frontier isn't compressing the cache further — it's not attending to most of it, which is sparse attention (Chapter 22).

Hint on the absorption check
# Direct: decompress, then dot
k_nope = (W_uk @ c_kv.T).T.view(T, H, 128)
q_nope = (W_uq @ c_q.T ).T.view(T, H, 128)
s1 = torch.einsum('qhd,khd->hqk', q_nope, k_nope)

# Absorbed: fold W_uk into the query side, attend in latent space
A  = torch.einsum('hdr,hds->hrs', W_uq.view(H,128,-1), W_uk.view(H,128,-1))
s2 = torch.einsum('qr,hrs,ks->hqk', c_q, A, c_kv)

assert torch.allclose(s1, s2, atol=1e-4)

When this passes, you've understood the actual engine of MLA — and why the RoPE split has to exist.

16.3Cache economics across a real fleetthinking

You serve a 70B-class model at 32k context on 8×H100 (640 GB). Weights are 140 GB in bf16. For MHA (64 KV heads), GQA-8, and an MLA-style 576-value cache, compute the max concurrent users. Then: what does fp8 KV do to each?

Worked answer
Available for cache: 640 - 140 - ~40 (activations/overhead) ≈ 460 GB
Per-token-per-layer values × 80 layers × 2 bytes × 32768 tokens:

MHA (2×64×128 = 16384) : 16384×80×2×32768 =  85.9 GB/user →   5 users
GQA-8 (2×8×128 = 2048) :  2048×80×2×32768 =  10.7 GB/user →  42 users
MLA  (576)             :   576×80×2×32768 =   3.0 GB/user → 152 users

With fp8 KV (1 byte): roughly double each →  10 / 85 / 305 users

That's a 30× difference in revenue per GPU between MHA and MLA at identical model quality. When you read that DeepSeek's API pricing undercut competitors substantially, this table is a large part of the explanation — architecture choices show up directly on the invoice.
