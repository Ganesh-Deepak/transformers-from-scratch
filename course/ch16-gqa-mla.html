16 · MQA, GQA, and Multi-Head Latent Attention

Chapter 15 set out the problem: the KV cache limits how many users fit on a GPU. This chapter walks through the answers in order. First a blunt fix from 2019, then the 2023 compromise that everyone adopted, and finally DeepSeek's 2024 low-rank scheme, which is both smaller and better than what it replaced.

The whole chapter in five sentences

The cache is a product of factors (2 · n_layer · n_kv_head · d_head · tokens · bytes), and each scheme in this chapter divides a different one. MQA and GQA divide n_kv_head by sharing key/value heads among query heads, and GQA with 8 groups costs almost no quality. MLA replaces the heads with a 576-value latent. That is smaller than GQA and, in DeepSeek's ablations, better than MHA. The price is a separate RoPE slice and two code paths. At decode, absorbed MLA is multi-query attention over that latent. It does about 30× more FLOPs per cached byte than GQA, which suits a phase that is short of bandwidth. CLA and YOCO divide n_layer by sharing one cache across layers, a choice you have to make before pretraining.

16.1 · The idea: share the K/V heads

Standard MHA gives every query head its own key head and value head. But the cache is proportional to n_kv_head, and nothing says it must equal n_head.

16.2 · MQA — one KV head for everybody

self.q_proj  = nn.Linear(d_model, n_head * d_head, bias=False)   # (C, 4096)
self.k_proj  = nn.Linear(d_model,      1 * d_head, bias=False)   # (C,  128)  ← tiny
self.v_proj  = nn.Linear(d_model,      1 * d_head, bias=False)   # (C,  128)

All 32 query heads attend against the same keys and values. That cuts the cache 32×, at no extra cost.

It works, but it has a cost. Shazeer reported lower quality, and later work found that MQA models can be unstable to train. The reason makes sense: heads specialise partly by having their own idea of what to match against, and MQA takes that away.

16.3 · GQA — the compromise that won

Group the query heads. Each group shares one K/V head.

class GroupedQueryAttention(nn.Module):
    def __init__(self, d_model, n_head, n_kv_head, d_head):
        super().__init__()
        assert n_head % n_kv_head == 0
        self.nh, self.nkv, self.hd = n_head, n_kv_head, d_head
        self.rep = n_head // n_kv_head                 # queries per KV head
        self.q_proj = nn.Linear(d_model, n_head    * d_head, bias=False)
        self.k_proj = nn.Linear(d_model, n_kv_head * d_head, bias=False)
        self.v_proj = nn.Linear(d_model, n_kv_head * d_head, bias=False)
        self.o_proj = nn.Linear(n_head * d_head, d_model,    bias=False)

    def forward(self, x, cos, sin, cache=None):
        B, T, _ = x.shape
        q = self.q_proj(x).view(B, T, self.nh,  self.hd).transpose(1, 2)  # (B, nh,  T, hd)
        k = self.k_proj(x).view(B, T, self.nkv, self.hd).transpose(1, 2)  # (B, nkv, T, hd)
        v = self.v_proj(x).view(B, T, self.nkv, self.hd).transpose(1, 2)  # (B, nkv, T, hd)

        q, k = apply_rope(q, k, cos, sin)

        if cache is not None:
            k = torch.cat([cache[0], k], dim=2)        # cache holds only nkv heads!
            v = torch.cat([cache[1], v], dim=2)
        new_cache = (k, v)

        # Expand KV heads to match query heads for the matmul.
        k = k.repeat_interleave(self.rep, dim=1)       # (B, nh, T, hd)
        v = v.repeat_interleave(self.rep, dim=1)       # (B, nh, T, hd)

        y = F.scaled_dot_product_attention(q, k, v, is_causal=(T > 1))
        y = y.transpose(1, 2).reshape(B, T, self.nh * self.hd)
        return self.o_proj(y), new_cache
repeat_interleave vs repeat — this ordering bug is real

With nkv=2, rep=2, repeat_interleave gives the head order [k0, k0, k1, k1]. That matches query heads [q0,q1 | q2,q3] grouped contiguously. repeat gives [k0, k1, k0, k1], an interleaved grouping. Both run, and both give believable losses. Only one matches how the weights were trained. If you ever load Llama weights into your own GQA code and quality is oddly mediocre, check this line first.

The expansion is a memory trick, not a FLOP saving

After repeat_interleave you do exactly the same attention FLOPs as MHA. The whole gain is in what you store and read: the cache holds n_kv_head heads, not n_head. Decode is memory-bound (Ch 15), so reading fewer bytes is saving time. Fused kernels skip building the repeated tensor and simply re-read the same K head for each query in the group.

The big idea. GQA turns a dial that already existed: it stores fewer heads. MLA changes what is stored. Instead of heads, it stores a low-rank summary, and rebuilds every head's K and V from it on the fly. That is how it can land between GQA-4 and MQA on size while beating full MHA on quality.

Why g = 8 keeps appearing

Ainslie et al. found that the curve of quality against cache size is far from a straight line. Going from MHA to 8 groups costs almost nothing, while going from 8 groups to 1 (MQA) costs a lot. There is also a practical reason: 8 KV heads split evenly across 8-GPU tensor-parallel setups, one KV head per GPU. Llama-2-70B, Llama-3 (all sizes), Mistral and Qwen2.5 use 8 or fewer. Gemma 2 27B uses 16 (for 32 query heads), still a 2× cut.

16.4 · MLA — Multi-head Latent Attention

DeepSeek-V2 (2024) asked a different question. GQA shrinks the cache by deleting heads. What if you compress the KV information into a low-rank latent instead, and decompress it on the fly?

The core idea

Don't cache K and V. Cache one small latent vector cKV per token. A learned up-projection rebuilds every head's K and V from it. You store the compressed form, and the heads still get full, distinct keys and values.

cKVt = WDKV ht      kCt = WUK cKVt      vCt = WUV cKVt D = down-projection (compress), U = up-projection (decompress). Only cKV is cached.

Per-head q/k dim = 128 + 64 = 192. Cached per token per layer = 512 + 64 = 576 elements.

The problem RoPE creates, and the "decoupled" fix

Here is the subtle part, and the reason MLA looks more complicated than you might expect.

The point of caching a latent is that you never have to build per-head keys. That works because of an absorption identity: the up-projection can be folded into the query side.

(qC)T kC = (WUQcQ)T (WUKcKV) = (cQ)T (WUQ)TWUK cKV the highlighted product is a fixed matrix — precompute it once, attend directly in latent space

Now insert RoPE. RoPE applies a position-dependent rotation Rm between the query and key:

(RmWUQcQ)T(RnWUKcKV) = (cQ)T(WUQ)T Rn−m WUK cKV Rn−m sits between the two matrices and depends on the token pair — the product can no longer be precomputed

DeepSeek's fix is to split the head dimension in two:

  • 128 dims with no RoPE. These go through the latent and can use absorption.
  • 64 dims with RoPE. These are computed directly from the hidden state and skip the latent. The RoPE key is shared across all 128 heads, so it costs only 64 extra cached values per token, not 64×128.
# Sketch of the MLA forward pass (shapes for DeepSeek-V3, one layer)
#   h: (B, T, 7168)

# ---- keys/values: compress to a latent, plus a shared RoPE key ----
c_kv  = self.W_dkv(h)                       # (B, T, 512)   ← CACHE THIS
k_rope = self.W_kr(h)                       # (B, T, 64)    ← AND THIS (shared by all heads)
k_rope = apply_rope_1head(k_rope, cos, sin)

#   total cached per token per layer: 512 + 64 = 576 values

# ---- at attention time, decompress ----
k_nope = self.W_uk(c_kv).view(B, T, 128, 128)     # (B, T, n_head, 128)
v      = self.W_uv(c_kv).view(B, T, 128, 128)     # (B, T, n_head, 128)

# ---- queries: also low-rank, also split ----
c_q    = self.W_dq(h)                             # (B, T, 1536)
q_nope = self.W_uq(c_q).view(B, T, 128, 128)      # (B, T, n_head, 128)
q_rope = self.W_qr(c_q).view(B, T, 128, 64)       # (B, T, n_head, 64)
q_rope = apply_rope(q_rope, cos, sin)

# ---- concatenate the two halves; RoPE key is broadcast across heads ----
q = torch.cat([q_nope, q_rope], dim=-1)                          # (B, T, 128, 192)
k = torch.cat([k_nope, k_rope[:, :, None].expand(-1,-1,128,-1)],
              dim=-1)                                            # (B, T, 128, 192)

attn_out = attention(q, k, v)                                    # (B, T, 128, 128)
out = self.W_o(attn_out.flatten(2))                              # (B, T, 7168)

A number you'll see quoted, with the caveat

The DeepSeek-V2 paper reports a 93.3% KV cache reduction. That figure compares MLA with the attention of DeepSeek 67B, not with an MHA model of the same config. So it is not the same ratio as the 57× above. Both numbers are correct; they compare different things. Whenever you see a claim of cache reduction, check what the baseline was.

The genuinely surprising result

MLA caches less than GQA with ~2.25 KV heads, yet DeepSeek's ablations show it beats full MHA on quality. Compression usually costs accuracy. The likely explanation is that the low-rank bottleneck is a helpful built-in assumption. Full-rank per-head K/V has more capacity than the task needs, and forcing the heads to share structure regularises them. GQA, by contrast, simply gives something up to save memory.

Decode with absorption: MLA turns into MQA

Follow the absorption identity all the way through one decode step, and something unexpected appears. Fold WUK into the query. Each head's 128-dim no-RoPE query becomes a 512-dim query in latent space, q̃h = (WUKh)T qh. Add its 64-dim RoPE query on the end. Now every head scores against the same cached vector [cKV ; kR], which is 576 wide. On the value side, the attention weights multiply cKV directly, and WUV is applied once to the 512-dim result (in a real model it folds into the output projection).

scoreh,t = [q̃h ; qRh] · [cKVt ; kRt]      outh = WUVh Σt ph,t cKVt 128 query heads, ONE shared "key/value head": keys 576 wide, values 512 wide

That is multi-query attention (§16.2), with a head dimension of 576 instead of 128. MLA stores a cache smaller than GQA's and, at decode time, runs the kernel shape that is cheapest to feed. Every byte of cache read is used by all 128 heads. tfs/mla.py implements both forms, and test_mla_absorbed_equals_naive checks they agree to 10−5.

Worked example — attention FLOPs per byte of cache, at decode

One new query token against one cached token. Each query head does a k-dim dot product (2k FLOPs) and a v-dim weighted add (2v FLOPs). Bytes are what is cached per token per layer, in bf16.

                          heads × (2k + 2v)          cached bytes    FLOP/byte
MHA, 128 × 128            128 × (256 + 256)  = 65,536    65,536          1.0
GQA-8, Llama-3-70B         64 × (256 + 256)  = 32,768     4,096          8.0
MLA absorbed, DeepSeek-V3 128 × (1152 + 1024) = 278,528    1,152        241.8

That is 30 times the arithmetic intensity of GQA, close to the H100's ridge of 295 (Chapter 14). Decode attention, the kernel in serving that is shortest of bandwidth, becomes nearly compute-bound. DeepSeek's FlashMLA kernel shows both regimes. Its README reports up to 3,000 GB/s in a memory-bound setup and up to 660 TFLOP/s in a compute-bound one on an H800 SXM5. See decode_attention_intensity, asserted in test_decode_attention_intensity.

Why there are two code paths. Absorption has a cost. Per cached token, the absorbed form does 278,528 FLOPs against 81,920 for the decompressed form (128 heads × (2·192 + 2·128)). That is 3.4× the attention arithmetic, in exchange for reading 57× fewer bytes. In decode, bandwidth is the limit, so the trade is excellent. In prefill, the whole prompt is processed at once, attention is compute-bound, and the decompressed form wins. So MLA code decompresses during prefill and absorbs during decode. That is the "implementation complexity" cost listed below.

What MLA costs

  • More FLOPs. You do down- and up-projections that MHA does not. During compute-bound prefill this is a real cost.
  • Much more implementation complexity. The absorption trick, two attention code paths (prefill and decode), and the RoPE split make MLA much harder to write than GQA. This is a large part of why models outside DeepSeek have taken it up more slowly than the quality numbers alone would suggest.
  • Kernel support. It needs custom kernels (DeepSeek released FlashMLA) instead of the stock FlashAttention ones.
Why does MLA need a separate "decoupled" RoPE dimension instead of just applying RoPE to the decompressed keys?
RoPE only works on 64-dimensional vectors
A position-dependent rotation sits between WUQ and WUK, breaking the absorption that lets you attend in latent space
RoPE would make the latent too large
It is only there for numerical stability
It breaks matrix absorption. Without RoPE, (W_UQ)ᵀW_UK is a constant you compute once ahead of time, so you never decompress the keys at all. With RoPE, Rn−m depends on the particular query and key and sits between them, so the product cannot be folded. Splitting off a small slice that carries RoPE keeps absorption for the other 128 dims.
Why is the RoPE key shared across all 128 heads while the RoPE query is per-head?
The key is cached, so per-head RoPE keys would cost 128× more cache; queries are not cached, so per-head queries are free
Queries need more positional resolution than keys
It is an arbitrary choice
Sharing keys improves quality
Cache cost. A per-head RoPE key would add 128 × 64 = 8192 values per token per layer. That is 14× more than the whole 576-value MLA cache, which would defeat the purpose. Queries are computed fresh each step and never stored, so per-head queries cost nothing in cache. Every asymmetry in MLA comes down to one question: is this thing cached?
A team wants to cut the KV cache 4× on an existing Llama-style model with as little risk as possible. What is the best choice?
Switch to MQA
Convert to MLA from scratch
Reduce the number of layers
GQA with n_kv_head = n_head/4, or fp8 KV quantization; both are low-risk and can be combined
GQA or KV quantization. GQA at g=4 is well tested and needs only light continued pretraining (uptraining) to recover quality. fp8 quantization needs no retraining at all. MQA costs more quality than it needs to, and converting a trained model to MLA is a research project. That is now an active area, though (for example TransMLA and related 2025 work on converting GQA checkpoints to MLA).

16.5 · Sharing the cache across layers: CLA and YOCO

Every scheme so far shrinks the cache within a layer. The formula has another factor we have not touched: n_layer. Chapter 15 said layer 7's keys are useless to layer 8 because they live in different representation spaces. That is true of a model trained with separate caches. But if you train a model expecting to share, neighbouring layers can learn to use one set of keys and values.

  • Cross-Layer Attention (CLA; Brandon et al., 2024). Groups of s neighbouring layers share one K/V. The first layer in each group computes and caches it, and the others compute only queries and attend to it. CLA2 (s = 2) halves the cache. The paper reports that MQA plus CLA2 gives a 2× smaller cache than MQA alone at about the same perplexity. That beats cutting the head count further, for the same trade of accuracy against memory.
  • YOCO, "You Only Cache Once" (Sun et al., 2024). The bottom half of the network is a self-decoder. It uses a cheap form of attention that keeps only a fixed-size cache (the paper uses sliding-window and gated-retention variants). It produces one global K/V cache, and every layer of the top half, the cross-decoder, attends to it. The cache no longer grows with depth.
  • In production, Character.AI described sharing K/V across neighbouring layers in its own models (2024). It did this on top of MQA and local attention, as part of cutting its cache by more than ten times.

The cost: you must train for it

GQA can be added to an MHA checkpoint with light continued pretraining, and fp8 KV needs no training at all. Cross-layer sharing changes what every layer computes, so it is an architecture decision made before pretraining. YOCO also changes how prefill works: the self-decoder can produce the global cache without running the cross-decoder over the prompt, which the paper uses to cut prefill time. Both can be combined with GQA, MLA and quantization, because they act on a different factor of the same product.

Where this sits in 2026

GQA is still the safe default and is in the vast majority of open models. MLA has proven itself at trillion-parameter scale in the DeepSeek and Kimi model families, and published ablations consistently rank MLA > GQA > MHA on quality per cached byte. What holds back wider adoption is engineering effort; the evidence is already there. Meanwhile the newest work goes further: it skips attending to most of the cache. That is sparse attention (Chapter 22).

What makes absorption win at decode is the ratio of cached bytes between the two forms.

16.5Stack the factorsthinking

Start from a 32-layer MHA model (32 heads × 128, bf16) at 32k context. Apply, cumulatively: GQA-8, then CLA2, then fp8 KV. Give the cache per user after each step, and the factor each step contributed. Then say which steps need retraining and which do not.

Answer
MHA:        2 × 32 × 32 × 128 × 32768 × 2 = 16 GiB
+ GQA-8:    ÷ 4  ->  4 GiB
+ CLA2:     ÷ 2  ->  2 GiB
+ fp8 KV:   ÷ 2  ->  1 GiB          16× in total

fp8 KV needs no training (you only calibrate scales). GQA can be uptrained from an MHA checkpoint. CLA changes the architecture, and in practice that means pretraining with it from the start.
