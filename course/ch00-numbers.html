0 · Numbers in a Machine: int8 to fp32, bf16, fp8 and NVFP4

Every number in a neural network is a pattern of bits. The formats (int8, fp32, bf16, fp8, NVFP4) are different decisions about what those patterns mean. This chapter gives you one recipe for all of them: from the number of exponent bits and mantissa bits alone, you will work out the largest value, the smallest value and the precision of any format, including formats that do not exist yet. You do not need anything from later in the course.

The whole chapter in four sentences

N bits give you 2N patterns, and a format decides which 2N numbers they stand for. Integers spread those numbers evenly. Floats spread them logarithmically: the exponent picks a bucket (a power of two) and the mantissa picks a slot inside the bucket. Exponent bits buy range and mantissa bits buy precision, and every format used in AI splits the same bit budget in a different way.

0.1 · A number format is a budget of bits

Start with something small enough to hold in your head: three bits. That gives exactly 23 = 8 patterns, and no more. The format decides what they mean. Here are two different decisions for the same eight patterns:

pattern   as an unsigned integer     as the magnitude of an fp4 number
  000              0                          0
  001              1                          0.5
  010              2                          1
  011              3                          1.5
  100              4                          2
  101              5                          3
  110              6                          4
  111              7                          6
                   evenly spaced              crowded near 0, sparse far away

Neither one is "right". The integer reading has a gap of 1 between every pair of neighbours. The float reading has gaps of 0.5 near zero and a gap of 2 at the top, so small numbers get fine resolution and large numbers get coarse resolution. That trade is the whole idea of floating point, and the right-hand column is a real format (fp4 e2m1, §0.6) that Blackwell GPUs use for matrix multiplies.

Integers: the easy case, done properly

An unsigned n-bit integer is plain binary: the patterns mean 0 to 2n − 1. A signed integer uses two's complement: the top bit is worth −2n−1 instead of +2n−1, and every other bit keeps its usual value.

Worked example — read int8 patterns with one rule
1
The bit weights of int8 are −128, 64, 32, 16, 8, 4, 2, 1. To read a pattern, add up the weights of the bits that are 1.
2
00000101  =                     4 + 1  =    5
11111011  = -128 + 64+32+16+8   + 2 + 1 =  -5
11111111  = -128 + 127                  =  -1
10000000  = -128                        = -128   the most negative
01111111  =  64+32+16+8+4+2+1           =  127   the most positive
3
So int8 covers −128 … 127, not −127 … 127. There are 256 patterns. One of them is zero, which leaves an odd number, 255, for the non-zero values, and two's complement gives the extra one to the negative side. Quantization schemes usually throw away −128 so that the range is symmetric (§0.7).
typebitsrangeformula
uint880 … 2550 … 2n−1
int44−8 … 7−2n−1 … 2n−1−1
int88−128 … 127
int3232−2,147,483,648 … 2,147,483,647
Integer overflow wraps around, silently

In int8, 100 + 100 gives −56 (measured with torch.int8). The true answer, 200, needs 9 bits; the 9th bit is dropped, and 200 − 256 = −56. No error is raised. This is why int8 matrix multiplies on GPUs add their products into int32: a dot product of int8 values grows far past 127 long before it is finished.

0.APractice — integerspractice

P1. What range does uint4 cover? And int4?

Answer

uint4: 0 … 15 (24−1). int4: −8 … 7 (−23 … 23−1). int4 is the format behind "4-bit" weight quantization schemes like GPTQ and AWQ.

P2. How many bits do you need to store every integer from 0 to 1000?

Answer

10. 9 bits reach 511, 10 bits reach 1023. In general ⌈log2(N+1)⌉.

P3. Write −5 in int8 using the rule "invert every bit of +5, then add 1". Check it with the bit weights.

Answer

+5 = 00000101 → invert → 11111010 → add 1 → 11111011. Check: −128 + 64 + 32 + 16 + 8 + 2 + 1 = −5. ✓ The invert-and-add-one rule and the bit-weight rule are the same rule written two ways.

P4. In int8, what is 127 + 1?

Answer

−128. 01111111 + 1 = 10000000, which is the pattern for −128. The integers wrap around like a clock.

0.2 · Floats are scientific notation in binary

You already know floating point in base 10. Avogadro's number is +6.022 × 1023: a sign, a significand (6.022) and an exponent (23). Change the exponent and the decimal point moves, or floats, which is where the name comes from. A float stores exactly those three things, in base 2:

value = (−1)S × 1.M2 × 2(E − bias) S is one bit · E is the exponent field read as an unsigned integer · M is the mantissa bits written after a binary point

Two details in that formula do most of the work, and both are easier to understand than to memorise.

The hidden 1

In decimal you write 6.022 × 1023, never 0.6022 × 1024: you move the point until exactly one non-zero digit sits in front of it. In binary the only non-zero digit is 1, so after the move the number always starts with 1., and a digit that is always there does not need storing. Floats store only the digits after the point and assume the 1. That free bit is why fp16, which stores 10 mantissa bits, has 11 bits of precision.

The bias

The exponent sometimes has to be negative (for numbers below 1). Instead of giving it a sign bit, the format stores the exponent as an unsigned integer and subtracts a fixed offset, the bias, which is always 2E−1 − 1. For an 8-bit exponent the bias is 127, so a stored 127 means 20, 128 means 21 and 124 means 2−3. This has a useful side effect: ignoring the sign, larger floats have larger bit patterns, so hardware can compare two positive floats as if they were integers.

Worked example — decode a 32-bit float by hand
1
The bits (fp32 is 1 sign, 8 exponent, 23 mantissa): 
0  01111100  01000000000000000000000
S  E         M
2
Sign: S = 0, so positive. Exponent: 01111100 is 124, and 124 − 127 = −3. Mantissa: the digits after the point are 01, so the significand is 1.012 = 1 + 0/2 + 1/4 = 1.25.
3
Multiply: 1.25 × 2−3 = 1.25 / 8 = 0.15625. That is exactly the pattern PyTorch prints for torch.tensor(0.15625).
Worked example — encode −6.5 into fp16 by hand
1
Write the magnitude in binary. 6 = 1102 and 0.5 = 0.12, so 6.5 = 110.12.
2
Slide the point until one 1 is in front: 110.12 = 1.1012 × 22. So the true exponent is 2 and the stored mantissa is 101 followed by zeros.
3
Bias the exponent. fp16 has a 5-bit exponent, so bias = 24 − 1 = 15, and the field is 2 + 15 = 17 = 10001. The sign is 1 for negative. 
1  10001  1010000000      = 1100011010000000   (matches torch.tensor(-6.5, dtype=torch.float16))

P7. Why is the bf16 encoding of 0.75 identical to the first 16 bits of its fp32 encoding?

Answer

Because bf16 is fp32 with the bottom 16 mantissa bits removed: the same sign bit, the same 8-bit exponent and the same bias, 127. When those removed bits are already zero, as they are for 0.75, the conversion loses nothing. Chapter 12 is built on this fact.

0.3 · The mental model: buckets and slots

This is the picture to remember. Forget the bits for a moment and look at where the numbers a format can hold sit on the number line. Below is a toy format with a 2-bit mantissa, so each bucket holds 22 = 4 slots:

Three things can be read off that picture, and they hold for every float format:

  1. The exponent chooses a bucket: the interval [2k, 2k+1).
  2. The mantissa cuts that bucket into 2M equal slots. So the gap between neighbours inside bucket k is
gap = 2k / 2M = 2k − M the single most useful formula in this chapter — the spacing of representable numbers near any value
  1. Relative precision is constant. Every bucket has the same number of slots, so the gap is always about 2−M of the value. A float is as precise at 0.001 as at 1000 in relative terms, and very different in absolute terms.
Worked example — why 256 + 1 = 256 in bf16
1
Find the bucket. 256 is 28, so it sits in bucket [256, 512), k = 8.
2
Find the gap. bf16 has M = 7, so the gap is 28 − 7 = 2. The numbers bf16 can hold here are 256, 258, 260, …, so 257 does not exist.
3
Round. 257 is exactly halfway between 256 and 258. A tie goes to the neighbour whose last mantissa bit is 0 (§0.8), which is 256. So 256 + 1 == 256 in bf16, as PyTorch confirms ✓. And 256 + 2 == 258, because 2 is a full gap.
A consequence that breaks real optimizers

Adam keeps a running average with decay β2 = 0.999. Just below 1 the bucket is [0.5, 1), where the bf16 gap is 2−1−7 = 0.0039, so the nearest numbers bf16 can hold are 0.99609375 and 1.0, and 0.999 is closer to 1.0. In bf16, 0.999 is exactly 1. We measured it: multiplying a bf16 value by 0.999 a thousand times leaves it at 1.0, where the true answer is 0.368. The average never decays. That is one reason optimizer state is kept in fp32 (Ch 12).

The rule of thumb for "how many digits"

A format with M stored mantissa bits has M + 1 significant bits (counting the hidden 1). Each bit is worth log10 2 ≈ 0.301 decimal digits, so:

decimal digits  ≈  (M + 1) × 0.301

fp32   24 bits  ≈ 7.2 digits      fp16   11 bits ≈ 3.3 digits
bf16    8 bits  ≈ 2.4 digits      e4m3    4 bits ≈ 1.2 digits

The largest integer below which every integer is exact is 2M+1; above it the gap becomes 2. For fp32 that is 16,777,216, for fp16 2,048, and for bf16 only 256. Token counts, step counters and indices must never be stored in bf16.

P1. What is the gap between neighbouring fp16 numbers near 1000? So what does fp16 store for 1000.3?

Working

1000 is in [512, 1024), so k = 9 and M = 10, giving a gap of 29−10 = 0.5. The neighbours are 1000 and 1000.5, and 1000.3 is closer to 1000.5 (measured ✓).

P2. The same question for bf16 near 100, storing 100.3.

Working

100 is in [64, 128), so k = 6 and M = 7, giving a gap of 2−1 = 0.5. 100.3 → 100.5. bf16 at 100 is exactly as coarse as fp16 at 1000: bf16 has three fewer mantissa bits, and the two buckets, [64, 128) and [512, 1024), are exactly 23 apart.

P3. In fp32, is 1e8 + 1 == 1e8?

Working

108 is in [226, 227) (226 ≈ 6.7e7), where the gap is 226−23 = 8. Adding 1 moves the value by less than half a gap, so yes, it stays the same. fp32 is not exact for all integers.

P4. List every e4m3 value in [1, 2). What is the gap in [8, 16)?

Working

M = 3 gives 8 slots: 1, 1.125, 1.25, 1.375, 1.5, 1.625, 1.75, 1.875. In [8, 16), k = 3, so the gap is 23−3 = 1: 8, 9, …, 15. e4m3 cannot store 8.5.

P5. Which is more precise for the number 0.001, fp16 or bf16? And for 1e-6?

Working

For 0.001 it is fp16: both formats have a full mantissa there, and fp16 has 10 bits to bf16's 7, so fp16's gap is 8× finer. For 1e-6 the answer flips. 1e-6 is below fp16's smallest normal number (6.1e-5), so fp16 stores it as a subnormal (§0.4) with only a few significant bits. We measured it: fp16 gives 1.0133e-6, a 1.3% error. bf16 still has all 8 of its bits there.

P6. Why is "bf16 is less precise than fp16" true but incomplete?

Answer

Within fp16's range, fp16 is always 8× more precise. But fp16's range ends at 65504 and its normal range starts at 6.1e-5, while bf16 covers 1.2e-38 to 3.4e38. Precision is the gap within a bucket; range is how many buckets a format has. Different bits pay for each.

In a float format, what does one more mantissa bit do?
Doubles the largest representable value
Adds one more power-of-two bucket at each end of the range
Halves the gap between neighbouring values in every bucket
Adds a second hidden bit
It halves every gap. The gap is 2k−M, so M + 1 halves it everywhere, which is what precision means. Options A and B describe what one more exponent bit buys: about twice as many buckets, which roughly squares the range. The hidden bit is always exactly one.

0.4 · Deriving any format's range yourself

Here is what this chapter promised. Give me only E (exponent bits) and M (mantissa bits), and these five formulas produce everything that torch.finfo reports. We checked them against PyTorch for fp32, fp16, bf16, e4m3 and e5m2, and they agree exactly.

bias = 2E−1 − 1      max = (2 − 2−M) × 2emax      min normal = 21 − bias

min subnormal = 21 − bias − M      eps = 2−M emax = (largest usable exponent field) − bias · in IEEE formats the all-ones field is reserved, so the largest usable field is 2E − 2 and emax = bias

Where each formula comes from:

  • max: the largest bucket, with every mantissa bit set: 1.111…12 = 2 − 2−M.
  • min normal: the smallest exponent field that still means a normal number is 1, which gives 21−bias. (Field 0 is reserved; see below.)
  • min subnormal: one slot above zero in the bottom bucket, which is 21−bias divided into 2M slots.
  • eps: the gap at 1.0. That is bucket k = 0, so 20−M.
Worked example — derive fp16 from (E = 5, M = 10)
1
Bias: 24 − 1 = 15. Largest usable field 25 − 2 = 30, so emax = 30 − 15 = 15.
2
Max: (2 − 2−10) × 215 = 1.9990234375 × 32768 = 65504. That odd-looking limit everyone quotes for fp16 comes straight from this formula.
3
Min normal: 21−15 = 2−14 ≈ 6.10 × 10−5. Min subnormal: 2−14−10 = 2−24 ≈ 5.96 × 10−8. Eps: 2−10 ≈ 9.77 × 10−4. All four match torch.finfo(torch.float16).
Worked example — derive bf16 from (E = 8, M = 7), and see why it is "fp32's range"
1
Bias 127, emax = 254 − 127 = 127, the same as fp32, because the exponent field is the same.
2
Max: (2 − 2−7) × 2127 ≈ 3.39 × 1038 (fp32: (2 − 2−23) × 2127 ≈ 3.40 × 1038). Min normal: 2−126 ≈ 1.18 × 10−38, the same as fp32.
3
Eps: 2−7 = 0.0078125. So bf16 has fp32's range and about two and a half decimal digits of precision. That was the design goal.

The special patterns: zero, subnormals, infinity, NaN

The two exponent fields at the ends are not ordinary buckets. In an IEEE-style format:

exponent fieldmantissameaning
all zeroszero±0 (yes, there is a negative zero)
all zerosnon-zerosubnormal: (−1)S × 0.M2 × 21−bias — no hidden 1
1 … 2E−2anythingnormal: the formula from §0.2
all oneszero±infinity
all onesnon-zeroNaN (not a number)

Subnormals fill the gap between zero and the smallest normal number with evenly spaced values. They use the exponent 1 − bias rather than 0 − bias so that they continue smoothly from the bottom normal bucket with the same spacing. The cost is that they lose the hidden 1, so a subnormal has fewer significant bits the closer it gets to zero. This is called gradual underflow, and Chapter 12 measures what it does to gradients.

Where exactly does a number become zero?

Not at the minimum subnormal, but at half of it, because rounding picks the nearest value. In fp16 the minimum subnormal is 2−24 ≈ 5.96 × 10−8, so 3e-8 rounds up to 5.96 × 10−8 and 2.5e-8 rounds to 0. The real threshold for flushing to zero is 2−25 ≈ 2.98 × 10−8 (exactly 2−25 is a tie and goes to the even neighbour, 0). Both were measured in PyTorch.

tf32: the format you use without choosing it

NVIDIA tensor cores from Ampere on have a 19-bit internal format, tf32: 1 sign bit, 8 exponent bits and 10 mantissa bits. The formulas give it fp32's range (8 exponent bits) and fp16's precision (10 mantissa bits). Your tensors stay fp32 in memory; the multiply rounds its inputs to tf32 and adds up the results in fp32. PyTorch leaves it off by default for matmuls, and torch.set_float32_matmul_precision("high") turns it on. That is usually a large speed-up for an "fp32" model, at the cost of rounding inputs as coarsely as fp16.

P4. What is the smallest positive number that does not become zero in bf16?

Working

P5. Invent a format: 1 sign bit, 6 exponent bits, 9 mantissa bits (16 bits in all). Work out its max and eps. Is it better than bf16 for gradients?

Working

0.5 · Eight-bit floats: e4m3 and e5m2

With only 7 bits after the sign there is very little to share out, so there are two fp8 formats that split it differently. Hopper (H100), Ada and Blackwell GPUs run both in hardware. Work them out; one of them uses a clever trick to gain range.

e5m2 (5 exponent bits, 2 mantissa bits) follows the IEEE rules, as you worked out in practice 0.D: max 57,344, eps 0.25. It is fp16 with the low 8 mantissa bits deleted, so it has fp16's range.

e4m3 (4 exponent bits, 3 mantissa bits) is more interesting. The IEEE rules give:

bias = 2^3 - 1 = 7
IEEE: largest usable field = 2^4 - 2 = 14  ->  emax = 14 - 7 = 7
      max = (2 - 2^-3) * 2^7 = 1.875 * 128 = 240

But the real e4m3 tops out at 448. With so few patterns, spending a whole exponent field on infinity and NaN wastes 16 of the 256 codes, one in sixteen. The OCP fp8 standard's e4m3 (PyTorch's float8_e4m3fn, where "fn" means finite) has no infinity at all and keeps only one NaN pattern per sign, S 1111 111. Every other pattern in the top exponent field becomes an ordinary number:

e4m3fn: the top field 1111 is usable, except mantissa 111 (that is NaN)
        max = 1.110_2 * 2^(15 - 7) = 1.75 * 256 = 448
        bits of 448:  0 1111 110
You just derived a non-IEEE format from first principles

The five formulas still hold; only the rule for the largest usable field and mantissa has changed. Every new format you meet will be (E, M) plus a statement of which patterns are reserved, and that is all you need to ask about it. (AMD's MI300 uses yet another variant, e4m3fnuz: bias 8, no negative zero, NaN at 1 0000 000, max 240, measured with torch.float8_e4m3fnuz.)

With no infinity, a number that is too large has to go somewhere. PyTorch's cast saturates: we measured 500 → 448. Hardware conversion instructions offer both a saturating mode and a NaN-producing mode, and frameworks choose saturation for fp8 training, because a single huge activation turning into NaN would spread NaN through everything after it.

Which one, where — and how that changed

The original recipe (Micikevicius et al. 2022, NVIDIA Transformer Engine) is hybrid: e4m3 for the forward pass, which needs precision, and e5m2 for gradients, which need range. DeepSeek-V3 (2024) instead used e4m3 for all tensors. It could do that because it scaled much more finely, with one scale per 1×128 tile of activations and per 128×128 block of weights, so each small block only needed e4m3's narrow range. The finer scaling gave back the range, and the extra mantissa bit improved accuracy. That idea, a separate scale for each small block, is the subject of the next section.

P3. Decode the e5m2 pattern 0 11111 00. Why could that pattern not exist in e4m3fn?

Working

All-ones exponent with a zero mantissa means +infinity. e4m3fn has no infinity: in that format, 0 1111 000 is the ordinary number 1.0 × 28 = 256.

P4. An activation tensor has values up to 2000. What happens if you cast it straight to e4m3? What is the fix?

Answer

Everything above 448 saturates to 448, so the large values, often the most important ones, are clipped. The fix is to scale: divide the tensor by s = 2000/448 before the cast, store s next to it, and multiply back afterwards. fp8 training does exactly this, per tensor or per block.

P5. How many distinct finite values does e4m3fn have?

Working

256 patterns, minus 2 NaNs (S 1111 111 for each sign), leaves 254 patterns. Two of those are +0 and −0, which are the same value, so there are 253 distinct finite values. That is every value an fp8 matmul can work with.

  0 10 1   3.0
  0 11 0   4.0            E = 11: 1.M x 2^2   (usable: no inf, no NaN)
  0 11 1   6.0            max = 1.5 x 4 = 6
  ...and the same eight with S = 1, negative.

There are fifteen distinct values from −6 to 6, and nothing at all between 0 and 0.5. A weight matrix full of values around 0.01 would become entirely zero. So fp4 is never used alone. It always comes with a scale factor: store x / s in fp4 and keep s elsewhere, so that the block's values land in the part of the number line fp4 covers.

Per tensor or per block? The outlier problem

One scale for a whole tensor is cheap, but one outlier ruins it. Take 15 small weights plus one 8.0, quantized to symmetric int4 (−7 … 7):

per-tensor scale = 8.0 / 7 = 1.143    ->  every one of the 15 small weights rounds to 0
per-block  scale, blocks of 8:
   block 1 (no outlier): scale 0.0171  ->  0.1029 -0.0686 0.0343 0.0857 -0.1200 ...  all kept
   block 2 (outlier)   : scale 1.143   ->  8.0000 0 0 0 0 0 0 0                     still lost

Blocks limit the damage: an outlier only wrecks its own block. The smaller the block, the fewer values an outlier hurts, and the more scales you have to store. Every modern low-bit format is a choice along that trade.

MX: the industry standard (OCP, 2023)

The Open Compute Project's Microscaling (MX) specification fixes the block at 32 elements and the scale at one byte in E8M0: an 8-bit exponent with no sign and no mantissa, so every scale is an exact power of two, from 2−127 to 2127 (the pattern 11111111 is NaN). The elements can be MXFP8 (e4m3 or e5m2), MXFP6 (e2m3 or e3m2), MXFP4 (e2m1) or MXINT8.

bits per value = element bits + 8 / 32      MXFP4 = 4.25    MXFP6 = 6.25    MXFP8 = 8.25

The scale is chosen so that the block's largest magnitude lands in the top bucket of the element format: X = 2⌊log2(amax)⌋ − emax, where emax = 2 for e2m1 (its top bucket is [4, 8)). Values that still land above 6 saturate.

NVFP4: NVIDIA's refinement (Blackwell)

NVFP4 keeps e2m1 elements but scales them differently in two ways: blocks of 16 instead of 32, and a block scale stored in fp8 e4m3 instead of E8M0, so the scale can be any e4m3 value, not only a power of two. Because e4m3's own range is narrow, NVFP4 adds a second level: one fp32 scale per tensor first moves the whole tensor into range.

x ≈ stensor × sblock × fp4      bits per value = 4 + 8 / 16 = 4.5
Worked example — one block, both ways (computed, not hand-rounded)
1
The block: [0.72, −1.9, 0.05, 3.3, −0.4, 0.0, 2.2, −0.9], amax = 3.3. (8 values for readability; the formats use 32 and 16.)
2
MX-style scale: ⌊log2 3.3⌋ = 1, so X = 21−2 = 0.5. 
x / X       1.44  -3.8   0.1   6.6   -0.8   0   4.4  -1.8
fp4         1.5   -4     0     6     -1     0   4    -2      (6.6 saturates to 6)
x 0.5       0.75  -2     0     3     -0.5   0   2    -1      RMS error 0.143
The power-of-two scale forced the largest value, 3.3, down to 3.0: the block max cannot be placed exactly on fp4's top value.
3
NVFP4-style scale: amax / 6 = 0.55, stored in e4m3 as 0.5625. 
x / s       1.28  -3.38  0.09  5.87  -0.71  0   3.91  -1.6
fp4         1.5   -3     0     6     -0.5   0   4     -1.5
x 0.5625    0.84  -1.69  0     3.375 -0.28  0   2.25  -0.84   RMS error 0.105
A fractional scale maps the block max onto 6, using the whole fp4 range: 26% less error on this block. That, plus halving the block size, is why NVIDIA reports NVFP4 matching fp8 more closely than MXFP4 does.
Where 4-bit actually runs today

Inference came first: OpenAI's gpt-oss (2025) shipped its MoE weights in MXFP4, at 4.25 bits per weight, which is what lets the 117B-parameter model fit on a single 80 GB GPU. Training is newer. NVIDIA's report Pretraining Large Language Models with NVFP4 (2025) trained a 12B model on 10 trillion tokens in NVFP4, with loss and downstream accuracy close to an fp8 baseline. It used stochastic rounding for gradients (§0.8) and kept a minority of layers in bf16. Blackwell tensor cores run both MXFP4 and NVFP4 in hardware.

0.FPractice — 4-bit and block scalingpractice

P1. What does fp4 e2m1 store for 2.4? For 5? For 0.2?

Working

2.4 lies between 2 and 3, so 2. 5 lies between 4 and 6, a tie, which goes to the even mantissa: 4 (0 11 0). 0.2 lies between 0 and 0.5, below the 0.25 midpoint, so 0.

P2. A 4096 × 4096 weight matrix in NVFP4. How many bytes does it take, counting block scales (ignore the one fp32 tensor scale)? How does that compare with bf16?

Working

16.8M values × 4.5 bits = 75.5M bits = 9.44 MB (8.39 MB of values plus 1.05 MB of scales). bf16 takes 2 bytes each, 33.6 MB, so NVFP4 is 3.56× smaller, not 4×: the scales cost 12.5%.

P3. An MX block has amax = 0.09. What E8M0 scale does the rule pick for MXFP4, and what does the block max become?

Working

log2 0.09 ≈ −3.47, which rounds down to −4, so X = 2−4−2 = 2−6 = 1/64. Then 0.09 × 64 = 5.76 → fp4 6 → 6/64 = 0.09375, a 4% error on the largest value.

P4. Why is E8M0 a sensible format for a scale but a useless format for data?

Answer

A scale only has to say how many buckets to shift, and multiplying by a power of two is exact and almost free in hardware: it just adds to the exponent. As data, E8M0 could hold only powers of two, so 3 would have to become 2 or 4. NVFP4's e4m3 scale is a decision to pay for a mantissa in the scale.

0.7 · Integers for inference: scale and zero-point

Integer formats need a scale for the same reason fp4 does (int8 holds only the whole numbers from −128 to 127), but here the scale does more work, because integers have no exponent at all. The standard mapping is affine:

q = clamp(round(x / s) + z, qmin, qmax)      x̂ = s × (q − z) s = scale (a float), z = zero-point (an integer); the error on any in-range value is at most s / 2
Worked example — symmetric int8, the usual choice for weights
1
Weights [0.12, −0.5, 0.33, 0.04]. Symmetric means z = 0 and the range −127 … 127 (−128 is dropped so that the grid is symmetric about zero). s = amax / 127 = 0.5 / 127 = 0.003937.
2
x / s      30.48   -127   83.82   10.16
q             30   -127      84      10
x_hat     0.1181   -0.5  0.3307  0.0394      max error 0.00189  (bound s/2 = 0.00197)
Worked example — asymmetric uint8, for values that are not centred on zero
1
Activations between [−1, 6]. A symmetric scheme would need s = 6/127 and would waste the whole range below −1. Use uint8 0 … 255 instead: s = (6 − (−1)) / 255 = 0.02745 and z = round(1 / s) = 36, the integer that stands for 0.0.
2
x          -1      0     2.7     6
q           0     36     134   255
x_hat  -0.988      0   2.690  6.012
Zero is represented exactly (q = 36), which matters: padding and ReLU outputs are exact zeros and should stay that way.

Granularity matters here just as in §0.6. Per-tensor int8 is common for activations, per-channel int8 (one scale per output row) for weights, and 4-bit weight-only schemes such as GPTQ and AWQ use groups of 64 or 128 weights per scale. Integer and fp4 grids also differ in shape: int4's 16 levels are evenly spaced, while fp4's crowd near zero. That suits weights better, because their values are roughly bell-shaped around zero.

0.GPractice — integer quantizationpractice

P1. Symmetric int8 with amax = 2.54. What is the scale, and what does 1.0 quantize to?

Working

s = 2.54/127 = 0.02. 1.0/0.02 = 50 → q = 50 → x̂ = 1.0. The largest possible error anywhere in range is s/2 = 0.01.

P2. Same scale. What happens to 3.0?

Working

3.0/0.02 = 150, which is clamped to 127 → x̂ = 2.54. The clipping error is 0.46, 46× the rounding bound. Choosing the scale means choosing what to clip.

P3. Why does an int8 GEMM accumulate in int32 instead of int16?

Working

Each product can be as large as 127 × 127 = 16,129, already close to int16's 32,767. A dot product over 4096 elements can reach 4096 × 16129 ≈ 6.6 × 107, far beyond int16 and well inside int32's 2.1 × 109. It is the same reason bf16 products are added up in fp32.

P4. You quantize ReLU activations (all ≥ 0, max 6) with symmetric int8. What fraction of the 255 levels are ever used?

Working

Only q = 0 … 127 are used, so 128 of 255 levels, about half. The step is 6/127 ≈ 0.047; asymmetric uint8 would give 6/255 ≈ 0.024, half the error, from the same 8 bits.

Why does NVFP4 need a per-tensor fp32 scale in addition to its per-block scales?
To store the sign of each block
Its block scales are e4m3, whose range (about 2−9 to 448) is too narrow to cover a whole tensor on its own
fp4 needs fp32 to represent zero
It replaces the hidden bit
Two levels of scaling. MX's E8M0 scales span 2−127…2127, so one level is enough. NVFP4 gives up that range to get a mantissa in the scale; the fp32 tensor scale moves the whole tensor into the window that the e4m3 block scales can then fine-tune.
MXFP4 stores 4.25 bits per value. Where does the 0.25 come from?
A sign bit shared by four values
Padding to align to bytes
A per-tensor fp32 scale amortised over a large tensor
One 8-bit E8M0 scale per block of 32: 8 / 32 = 0.25
The block scale. 8 bits are shared by 32 values. NVFP4's 8-bit scale covers 16 values and costs 0.5, hence 4.5 bits. Option C is NVFP4's second level, which costs almost nothing per value.
A tensor has one huge outlier. Which change most directly protects the other values?
Make the scaling blocks smaller
Switch from symmetric to asymmetric quantization
Use round-to-nearest-even instead of truncation
Increase the per-tensor scale
Smaller blocks limit the damage. The outlier sets the scale only for its own block, and every other block gets a scale fitted to its own values. A larger per-tensor scale causes the problem; it does not fix it.

0.8 · Rounding: how a real number lands on the grid

Almost every operation produces a real result that falls between two numbers the format can hold. The rule for choosing one of them is part of the format, and it has effects you can measure.

Round to nearest, ties to even is the default everywhere. Pick the closer neighbour; on an exact tie, pick the one whose last mantissa bit is 0. Measured in bf16, where the gap at 256 is 2:

257 -> 256     tie between 256 (...000) and 258 (...001): even wins
258 -> 258     exact
259 -> 260     tie between 258 (...001) and 260 (...010): even wins
261 -> 260     tie between 260 (...010) and 262 (...011): even wins

Why ties to even and not ties up? Half the ties go up and half go down, so rounding errors do not drift in one direction over millions of operations. But it is still deterministic, and that leaves one weakness:

Measurement — adding 1 to 256, a thousand times, in bf16
1
Round to nearest: every 256 + 1 rounds back to 256. After 1000 additions the total is 256, while the exact answer is 1256. A thousand updates, each too small to register on its own, are all lost. This is exactly what happens when a small gradient update is added to a large weight.
2
Stochastic rounding: round up with a probability equal to how far the value is towards the upper neighbour. 257 is halfway, so it becomes 258 half the time. Each rounding is now noisy but unbiased on average. Measured over 2000 runs: mean 1255.8 (exact 1256), with each single run off by about ±58.

Stochastic rounding turns a steady loss into noise, and gradient descent copes with noise far better than with a steady loss. That is why the NVFP4 pretraining recipe uses it for gradients, and why recent accelerators build it into the hardware instead of leaving it to software.

0.HPractice — roundingpractice

P1. fp16 near 4096 has a gap of 4. What do 4097, 4098 and 4099 round to?

Working

The neighbours are 4096 and 4100. 4097 → 4096 (nearer). 4098 → 4096: an exact tie, and 4096's mantissa ends in 0 while 4100's ends in 1. 4099 → 4100 (nearer). All measured ✓.

P2. Under stochastic rounding in bf16, what is the probability that 256.5 is stored as 258?

Working

It sits 0.5 of the way across a gap of 2, so the probability is 0.5/2 = 25%; the other 75% of the time it becomes 256. The expected value is 0.25 × 258 + 0.75 × 256 = 256.5, exactly the input, which is what "unbiased" means.

P3. Why don't we use stochastic rounding for the forward pass?

Answer

It would add noise to every value and gain nothing. A single forward pass is not a long chain of additions, so there is no steady drift to remove, only new error and runs that differ from each other. Stochastic rounding helps specifically when many small updates are added up repeatedly, which is the gradient and weight-update path.

How to read any format you have never seen

Ask four questions. How many exponent bits? That sets the range, through the bias. How many mantissa bits? That sets the gap, 2k−M. Which patterns are reserved? That sets the max. What scale travels with the values, and over how many of them? For anything under 8 bits, that is where most of the usable range comes from. Those four answers describe the whole format.

0.1Write a decoder for every format at onceessential

Write one function that decodes a bit pattern for any (E, M, flavour), then check it against every pattern of PyTorch's real fp8 types:

import torch

def decode(bits, E, M, flavour="ieee"):
    s = (bits >> (E + M)) & 1
    e = (bits >> M) & ((1 << E) - 1)
    m = bits & ((1 << M) - 1)
    bias = (1 << (E - 1)) - 1
    if flavour == "ieee" and e == (1 << E) - 1:
        return float("nan") if m else (-1) ** s * float("inf")
    if flavour == "fn" and e == (1 << E) - 1 and m == (1 << M) - 1:
        return float("nan")
    if e == 0:                       # subnormal: no hidden 1, exponent 1 - bias
        v = (m / (1 << M)) * 2.0 ** (1 - bias)
    else:
        v = (1 + m / (1 << M)) * 2.0 ** (e - bias)
    return -v if s else v

ref = torch.arange(256, dtype=torch.uint8).view(torch.float8_e4m3fn).float()

Compare all 256 patterns for float8_e4m3fn (flavour "fn") and float8_e5m2 (flavour "ieee"). Then use your decoder to list every fp4 value.

What you should find

All 256 patterns match for both formats; this course's own engine passes the same check in tests/check_numfmt.js. Be careful when comparing NaNs: nan == nan is False, so test them with math.isnan. fp4 gives 0, 0.5, 1, 1.5, 2, 3, 4, 6 and their negatives.

0.2Map the gap across the whole rangecode

For fp16 and bf16, plot the gap between neighbours against the value, for values from 10−8 to 104, on log-log axes. Use torch.nextafter to find each neighbour.

x = torch.logspace(-8, 4, 2000, dtype=torch.float32)
for dt in (torch.float16, torch.bfloat16):
    v = x.to(dt)
    gap = torch.nextafter(v, torch.full_like(v, float("inf"))) - v
What you should see

You get a staircase. The gap is constant within each bucket and doubles at every power of two, so on log-log axes it follows a straight line of slope 1, which means constant relative precision. fp16's line sits 8× below bf16's. Below 6.1e-5 fp16's line goes flat: that is the subnormal region, where the gap stops shrinking and relative precision falls apart. bf16's line stays straight all the way down.

One line of code fails in three different ways. bf16 at 0.999 cannot represent the decay at all. bf16 at 0.99 represents a different decay, 0.98828, and the difference compounds. fp16 at 0.95 decays correctly until it reaches the minimum subnormal, 5.96e-7, where 5.96 × 10−7 × 0.95 rounds back to itself and it stalls. The general rule: a factor 1 − δ only works if δ is clearly larger than the gap just below 1, 2−(M+1), and the value stays well above the format's floor.
