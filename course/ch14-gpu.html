14 · The GPU: Memory, Tensor Cores, and the Roofline

Every performance claim in the rest of this course — the KV cache, GQA, FlashAttention, continuous batching — is an argument about one machine. This chapter is that machine. By the end you will be able to look at any operation and predict, with arithmetic and before running it, whether it is limited by compute or by memory. That single prediction explains almost every design decision in Parts IV and V.

Why this chapterWithout it, "memory-bound" is a phrase you repeat. With it, it is a number you compute.
The one idea in this chapter

A GPU can do arithmetic far faster than it can fetch numbers to do arithmetic on. An H100 can perform about 295 floating-point operations in the time it takes to read one byte from its main memory. So the only question that matters for any operation is: how many FLOPs do I get per byte I move? Below 295, you are waiting on memory and your expensive silicon is idle. Above it, you are actually computing.

14.1 · The hierarchy, and the only number that matters

A GPU is not one memory. It is a pyramid, and each level down is roughly an order of magnitude bigger and an order of magnitude slower. Figures below are for an H100 SXM5:

                         size            bandwidth        ~latency
  registers              256 KB / SM     ~100 TB/s        ~1 cycle
  shared memory / L1     up to 228 KB    ~20 TB/s         ~30 cycles      <- FlashAttention lives here
  L2 cache               50 MB total     ~10 TB/s         ~200 cycles
  HBM3 ("VRAM")          80 GB           3.35 TB/s        ~500 cycles     <- everything you allocate
  host RAM over PCIe     TBs             ~60 GB/s         ~microseconds

  compute: 989 TFLOP/s bf16 dense, across 132 SMs
Where the whole chapter comes from

Divide the top two numbers:

ridge point = 989.4 × 1012 FLOP/s3.35 × 1012 byte/s = 295 FLOP/byte

That is the exchange rate between the two resources. An operation that does fewer than 295 FLOPs per byte it touches cannot reach peak compute, no matter how good the kernel is, because the arithmetic units will run dry waiting for data.

The ridge point is a property of the chip, and it has been getting worse, not better — compute has outrun bandwidth for a decade:

                  compute        bandwidth      ridge point
  A100 80GB       312 TFLOP/s    2.04 TB/s      153 FLOP/byte
  H100 SXM5       989 TFLOP/s    3.35 TB/s      295 FLOP/byte
  H200 SXM        989 TFLOP/s    4.80 TB/s      206 FLOP/byte
  B200           2250 TFLOP/s    8.00 TB/s      281 FLOP/byte

H200 is the interesting row: same die as H100, only more bandwidth, and the ridge point drops to 206. A lower ridge means more workloads land on the compute side of the line. That is what you are buying when you buy memory bandwidth — not throughput directly, but the ability to keep the compute you already own busy.

14.2 · Arithmetic intensity: computing the number yourself

For any operation, define:

AI = FLOPs performedbytes moved to and from HBM   compare against   295

Do it for a matmul. Multiplying M, K by K, N gives M, N:

Derivation — the arithmetic intensity of a matmul
1
Count FLOPs. Each output element is a dot product of length K: that is K multiplies and K adds. There are MN outputs. 
FLOPs = 2 · M · K · N
2
Count bytes. Read both inputs, write the output. In bf16 each element is 2 bytes: 
bytes = 2 · (M·K + K·N + M·N)
3
Divide. The 2s cancel: 
AI = M·K·N / (M·K + K·N + M·N)
4
Set M = N = K = n. Numerator n³, denominator 3n²: 
AI = n / 3
Arithmetic intensity grows linearly with matrix size. Small matmuls are memory-bound; large ones are compute-bound; and the crossover is exactly n = 3 × 295 ≈ 886. 
square bf16 matmul on H100 (ridge 295):
   n= 128   AI=   42.7   MEMORY-bound
   n= 256   AI=   85.3   MEMORY-bound
   n= 512   AI=  170.7   MEMORY-bound
   n=1024   AI=  341.3   COMPUTE-bound
   n=4096   AI= 1365.3   COMPUTE-bound
Why "bigger batches are more efficient" is not folklore

It is AI = n/3. A 512-wide matmul reaches at most 171/295 = 58% of the H100's peak even with a perfect kernel — the hardware is simply starved. This is also why very small models are wasteful on big GPUs, and why tiny per-head matrices get batched together rather than run one at a time (Ch 06's reshape dance is partly a performance measure).

14.3 · The result that explains Part IV

Now apply it to a real transformer. Take a 7B model in bf16 — 14 GB of weights — and compute one token.

Generating a single token requires reading every weight exactly once and doing about 2P FLOPs with them (one multiply and one add per parameter). So:

7B model, bf16, batch 1, one decoded token
  bytes moved   = 14 GB   (every weight, once)
  FLOPs done    = 14 GFLOP
  AI            = 1 FLOP/byte          <- against a ridge of 295

  time if memory-bound   14e9 / 3.35e12  =  4.179 ms
  time if compute-bound  14e9 /  989e12  =  0.014 ms   (300x faster)

  -> MEMORY bound, by a factor of ~300
  -> hard ceiling: 239 tokens/second, batch 1, on an H100
Read the last line carefully

239 tokens/second is not a software limit. It is 14 GB divided by 3.35 TB/s. No kernel, compiler, or framework can beat it, because the weights must physically cross the memory bus once per token. The GPU is idle 99.7% of the time, waiting. Every technique in Ch 15–Ch 18 is an attack on this one number — either move fewer bytes (quantization, GQA, MLA) or do more work per byte moved (batching, speculative decoding).

Prefill is a completely different machine

Process 2048 prompt tokens at once and the weights are still read once — but now they are used 2048 times:

                     AI          memory time    compute time    verdict
  decode 1 token        1.0        4.179 ms        0.014 ms     MEMORY bound
  prefill 2048       2048.0        4.179 ms       28.979 ms     COMPUTE bound

Same weights, same GPU, opposite bottleneck. Prefill spends 29 ms computing and 4 ms fetching; decode spends 4 ms fetching and 14 microseconds computing. This is why serving stacks treat them as two different problems, schedule them separately, and report time-to-first-token and time-per-output-token as separate metrics (Ch 18).

Batching, quantified

In decode with batch B, the weights are still read once but used for 2B FLOPs. So AI = B, exactly:

batch B     AI          fraction of peak compute reachable
      1       1                 0.3%
      8       8                 2.7%
     32      32                10.8%
    128     128                43.3%
    256     256                86.7%
    295     295                99.9%   <- the ridge point, in batch units
Continuous batching, explained in one line

You need ~295 concurrent sequences before an H100 stops being bandwidth-starved during decode. That is the entire economic argument for continuous batching: a request served alone wastes 99.7% of the machine, and serving 256 at once costs almost exactly the same wall-clock time per token as serving one. It is also why the KV cache's memory footprint is so precious — cache size is what limits how many sequences fit, and therefore what limits B, and therefore what limits your position on this table.

14.4 · Tensor cores, and what they ask of your shapes

The 989 TFLOP/s figure is not from general-purpose arithmetic units. It comes from tensor cores: fixed-function hardware that multiplies small matrix tiles in one instruction. On Ampere and Hopper, the bf16/fp16 instruction has shape:

mma.sync.aligned.m16n8k16  —  a 16, 16 × 16, 8 → 16, 8 tile, per instruction

Crucially, it multiplies in bf16 and accumulates in fp32 — the hardware embodiment of §12.5's rule about accumulators. You get the wider accumulator for free, and cannot turn it off.

Any dimension that is not a multiple of the tile is padded to one, and you pay full price for the padding. That is the hard rule tensor cores impose: the dimensions of every matmul should be multiples of 16 for bf16 (and of 32 for fp8, whose instruction tile is twice as deep). It is why vocabulary sizes are padded (GPT-2's 50,257 becomes 50,304 in nanoGPT, a multiple of 64, for a measurable speedup) and why d_ff is rounded to a multiple of 256 (Ch 08).

So why is dhead almost always 64 or 128?
1
Not because other sizes are impossible. Real models ship 80 (Phi-2), 96 (Phi-3-mini, GPT-NeoX-20B), 192 for queries and keys (DeepSeek-V3's MLA) and 256 (Gemma). All are multiples of 16, so tensor cores handle them without padding.
2
Because the attention kernels are tuned for a short list. A FlashAttention-style kernel keeps a tile of Q, K and V for one head in shared memory and registers, and its tile sizes, register budget and pipelining are hand-tuned per head size. Libraries ship compiled versions for a few values (FlashAttention-2 covers multiples of 32 up to 256), and the most-optimised paths are for 64 and 128. Pick an unusual size and you may fall back to a slower path or a padded one; pick 256 and each tile holds fewer tokens, so the kernel does less work per byte it stages.
3
And because of what dhead buys. Too small and each head has little room to express a query (Ch 06); too large and you get fewer heads for the same d_model. 64–128 is the range where both concerns are satisfied, it divides common d_model values cleanly (4096 = 32 × 128, 768 = 12 × 64), and once the ecosystem standardised on it, kernels, inference engines and quantization tools optimised for it first. The convention is now self-reinforcing.
A number you have seen before, now explained

Whenever a config says d_model=4096, n_head=32, that is dhead = 128. When it says d_model=768, n_head=12, that is 64. It looks like a free modelling choice. In practice it is a choice constrained by tensor-core tiles (a multiple of 16) and steered by kernel support (64 and 128 get the fastest paths). If you design a new architecture, check which head sizes your attention kernel and your inference engine support before you train.

14.5 · Coalescing: the same bytes, 32× the traffic

A GPU executes threads in groups of 32, called a warp, in lockstep. When a warp issues a load, the hardware merges the 32 addresses into as few 128-byte transactions as it can. If the threads read consecutive 4-byte words, all 32 fall in one line:

32 threads x 4 bytes = 128 bytes = exactly one cache line

  stride 1   ->   1 line per warp    perfect  (100% of fetched bytes used)
  stride 2   ->   2 lines per warp   2x the traffic, half of it discarded
  stride 4   ->   4 lines per warp   4x
  stride 32  ->  32 lines per warp   32x - every thread pulls its own line
This is why memory layout is a correctness-adjacent concern

A strided access pattern moves the same useful bytes but consumes up to 32× the bandwidth — and you already know bandwidth is the binding constraint. This is the real reason .contiguous() appears after transposes in attention code, and why the reshape dance is written to keep dhead as the last, fastest-varying axis: so that threads reading across a head's features read consecutive addresses. The axis order in your tensor is a bandwidth decision.

14.6 · Kernel fusion, and what FlashAttention is really doing

Every separate kernel launch means a round trip to HBM: read inputs, write outputs. Chain several elementwise operations and you pay that repeatedly for no arithmetic gain.

unfused:  x -> [read, gelu, write] -> [read, mul, write] -> [read, add, write]
          3 round trips to HBM, ~3 FLOPs per element  ->  AI well under 1

fused:    x -> [read, gelu, mul, add, write]
          1 round trip, same FLOPs                    ->  3x the intensity

Elementwise ops are always memory-bound — they do O(1) work per element — so their runtime is essentially "how many times did I touch HBM". Fusion is the only lever, which is what torch.compile spends most of its effort on.

FlashAttention is this idea applied to the one operation where it is hardest. Naive attention materialises the T, T score matrix in HBM — for T = 8192 that is 128 MB per head, written and read back, when the L2 cache is only 50 MB. FlashAttention never writes it: it tiles Q, K and V into shared memory (the 228 KB level, ~6× the bandwidth of HBM: ~20 TB/s against 3.35 TB/s), computes each tile's contribution, and keeps only a running softmax. The FLOPs are identical. The bytes moved drop by orders of magnitude. On this chapter's roofline that is the whole speedup — see Ch 17 for the algorithm and the online-softmax proof that makes it exact.

Prefill uses different kernels

14.7 · MFU, and the third regime: overhead

The roofline gives two ceilings. Practitioners summarise how close a real workload gets to them with one number, Model FLOPs Utilisation (Chowdhery et al., 2022, in the PaLM paper):

MFU = (FLOPs the model needs per token) × (tokens per second)peak FLOP/s of the hardware training: 6N FLOPs per token · inference: 2N · attention FLOPs usually left out, so MFU is slightly conservative

"The model needs" is the point: if you recompute activations in the backward pass (Chapter 19), the GPU does more arithmetic, but MFU does not credit it. (Counting it gives hardware FLOPs utilisation, HFU, which flatters a run that recomputes a lot.) A worked example: an 8.03 B-parameter model training at 9,000 tokens per second per H100 does 6 × 8.03 × 109 × 9,000 = 4.34 × 1014 FLOP/s, which is 43.8% MFU against 989.4 TFLOP/s. Well-tuned large dense training runs report around 40%: Meta gives 38–43% bf16 MFU for Llama 3 405B on 16k H100s. Inference decode, being memory-bound, has an MFU in single digits by design, so for decode quote bandwidth utilisation (bytes moved per second ÷ HBM bandwidth) instead.

When neither ceiling binds: the overhead-bound regime

A GPU only works on what the CPU has handed it. Every kernel costs a launch: the host-side framework (Python, PyTorch's dispatcher) decides what to run, and the driver enqueues it, a cost of order microseconds per kernel. If the kernels are tiny, the GPU finishes each one before the next arrives, and the step time is set by the number of launches, not by bytes or FLOPs. Horace He calls this the third regime: overhead-bound.

Worked example — when does launch overhead matter?

Assume ~4 µs of launch cost per kernel (order of magnitude; measure your own stack) and an unfused Llama-style block of 11 kernels (norm, QKV, RoPE, attention, output projection, add, norm, gate+up, SiLU·mul, down, add), plus 3 for embedding, final norm and LM head.

1
An 8B model, bf16, batch 1. 32 layers → 32 × 11 + 3 = 355 kernels. 
memory floor  16.06 GB / 3.35 TB/s  = 4.79 ms
launch floor  355 × 4 µs            = 1.42 ms      -> memory-bound, but overhead is 30% of it
2
A 125M model (GPT-2 small size, 0.25 GB in bf16), 12 layers. 135 kernels. 
memory floor  0.25 GB / 3.35 TB/s   =  75 µs
launch floor  135 × 4 µs            = 540 µs      -> OVERHEAD-bound, 7x over the memory floor
A faster GPU does nothing here. Neither does a better matmul kernel.

tfs/gpu.py: kernels_per_decode_step and decode_step_floor, asserted in test_launch_overhead. You have already seen this regime: Chapter 15's measured cached decode on a CPU takes about 11 ms per token whether the context is 16 tokens or 500, because a model that small is all overhead.

The fixes, in the order you reach for them:

  • Fusion (§14.6): fewer, larger kernels. torch.compile fuses elementwise chains.
  • CUDA graphs: record the whole sequence of kernel launches for one decode step once, then replay it with a single launch. The CPU cost per step drops to almost nothing. The catch is that a graph is captured for fixed shapes and addresses, so engines such as vLLM and SGLang capture one graph per batch size in a list (padding a batch of 13 up to the next captured size), and keep the KV cache at fixed addresses, which PagedAttention's block tables (Chapter 18) make possible.
  • Bigger batches: the launch cost is per step, not per sequence, so batching amortises it exactly as it amortises weight reads.

14.8 · Lower precision is a faster chip

Tensor cores run narrower formats at higher rates: each halving of the operand width roughly doubles the peak. Datasheet figures, dense (vendor headline numbers are often quoted with 2:4 structured sparsity, which doubles them again and which almost no LLM workload uses):

GPUbf16fp8fp4HBMridge bf16ridge fp8ridge fp4
H100 SXM989 TF1,979 TF—3.35 TB/s295591—
H200989 TF1,979 TF—4.8 TB/s206412—
B2002,250 TF4,500 TF9,000 TF8.0 TB/s281562.51,125

Ridge points are in FLOPs per byte, and that is the subtle part. A narrower format raises the peak and shrinks the bytes, so the batch needed to saturate decode does not move:

decode batch to saturate = ridge × (bytes per weight) / 2 H100 bf16: 295 × 2 / 2 = 295 · H100 fp8: 591 × 1 / 2 = 295 · B200 fp4: 1125 × 0.5 / 2 = 281

So moving decode from bf16 to fp8 does not change when you become compute-bound; it halves the time of every step on the way there, because you move half the bytes. Prefill, which is compute-bound, gets the doubled peak directly. Hopper has no fp4 tensor cores: 4-bit weights on an H100 are weight-only quantization (stored in 4 bits, dequantized to bf16 or fp8 before the matmul), which saves bandwidth but not FLOPs. Blackwell executes MXFP4 and NVFP4 (Chapter 0 §0.6) natively. Chapter 18 turns these formats into serving decisions.

Peak is not achieved

fp8 matmuls need scaling factors (per tensor, per row or per block) applied and accumulated in higher precision, and fp4 needs block scales (Chapter 0). Real kernels reach a smaller fraction of the fp8 and fp4 peaks than of the bf16 one, and small matmuls fall short of all of them. Use the table for ceilings and ratios; measure for anything you will plan capacity on.

14.9 · Beyond one GPU: the interconnect ladder

The hierarchy of §14.1 does not stop at HBM. Once a model or a batch spans several GPUs, the links between them become the next, much slower, level. Per GPU, one direction (datasheets often quote the sum of both directions):

LinkGB/s per directionConnects
HBM3 (H100)3,350GPU to its own memory, for comparison
NVLink 5 (B200)900GPUs in one NVLink domain (1.8 TB/s bidirectional)
NVLink 4 (H100)450the 8 GPUs of an HGX node (900 GB/s bidirectional, 18 links)
PCIe 5.0 x16~64GPU to CPU memory; GPUs without NVLink
InfiniBand NDR, one 400 Gb/s port50node to node (typically one port per GPU)

Each step down is roughly 7× to 10×. To feel it, all-reduce 1 GB of gradients across 8 GPUs with a ring (each GPU sends and receives 2(n−1)/n of the buffer):

inside a node, NVLink 4:   2 × 7/8 × 1 GB / 450 GB/s  =  3.89 ms
across nodes, IB NDR:      2 × 7/8 × 1 GB /  50 GB/s  = 35.0  ms

That factor of 9 is why tensor parallelism, which communicates inside every layer, stays inside a node (Chapter 19), why MoE expert parallelism tries to keep its all-to-all inside NVLink (Chapter 20), and why offloading a KV cache to CPU memory over PCIe (Chapter 18) is a real but limited escape hatch: the link is 50× slower than HBM.

14.10 · Writing a kernel: a first look at Triton

Everything above is an argument for writing fused kernels. CUDA C++ is the full-control way; Triton (Tillet et al., 2019, now developed by OpenAI and the backend that torch.compile generates for GPUs) is the productive way. You write a function for one program (one tile of the problem) in Python-like syntax over blocks of values, and the compiler handles threads, coalescing and shared memory. Here is a fused row softmax, the kernel at the heart of Chapter 17:

import torch, triton
import triton.language as tl

@triton.jit
def softmax_kernel(x_ptr, y_ptr, n_cols, row_stride, BLOCK: tl.constexpr):
    row  = tl.program_id(0)                          # one program per row
    cols = tl.arange(0, BLOCK)                       # (BLOCK,) column offsets, a power of 2
    mask = cols < n_cols                             # the tail of the row is padding
    x = tl.load(x_ptr + row * row_stride + cols, mask=mask, other=-float("inf"))
    x = x - tl.max(x, axis=0)                        # stable softmax: subtract the row max
    num = tl.exp(x)
    y = num / tl.sum(num, axis=0)
    tl.store(y_ptr + row * row_stride + cols, y, mask=mask)

def softmax(x):                                      # x: (n_rows, n_cols), contiguous rows
    n_rows, n_cols = x.shape
    y = torch.empty_like(x)
    softmax_kernel[(n_rows,)](x, y, n_cols, x.stride(0),
                              BLOCK=triton.next_power_of_2(n_cols))
    return y

Read it against this chapter. The row is loaded from HBM once, max, exp, sum and divide all happen in registers, and the result is written once: 2 bytes of traffic per element per direction in bf16, against roughly 4 to 5 round trips for the same ops launched separately (a max kernel, a subtract, an exp, a sum, a divide, each reading its input from HBM). tl.arange over consecutive columns makes the loads coalesced (§14.5), and mask handles rows whose length is not a power of two, the same padding problem tensor cores have. This version needs a whole row to fit in one block; Chapter 17's online softmax is how you remove that limit.

14.1Build the roofline calculatoressential

Write a function that takes an operation's FLOPs and bytes and returns the predicted time, the bottleneck, and the achievable fraction of peak:

def roofline(flops, bytes_moved, peak_flops=989.4e12, bw=3.35e12):
    t_compute, t_memory = flops / peak_flops, bytes_moved / bw
    return dict(ai=flops / bytes_moved,
                bound="compute" if t_compute > t_memory else "memory",
                seconds=max(t_compute, t_memory),
                frac_of_peak=min(1.0, (flops / bytes_moved) / (peak_flops / bw)))

Now use it on every operation in a transformer block for d = 4096, B = 1, T = 1: the four attention projections, the three SwiGLU matrices, RMSNorm, the residual add, and the softmax. attn:    12 × 80 × 8192 × 8192 = 6.44e10 FLOPs/token  vs  6N = 4.24e11  ->  +15%

67% would be an exceptional figure, so ask whether the report counted attention, or recomputation, or quoted peak with sparsity. The 6N rule understates the work at long context by about 15% here, which is why careful reports state which convention they use.

14.6Predict, then measure: find the overhead floorcode

Prediction first: for the Chapter 9 model on your machine, will one cached decode step at batch 1 take noticeably less time than at batch 8? Write down a number. Then time it at batch 1, 2, 4, …, 64, and plot step time against batch. Repeat with torch.compile(model, mode="reduce-overhead") on a GPU, which uses CUDA graphs.

What the curve shows

A flat region at small batch: that is the overhead floor, where adding sequences is free because the step is waiting on launches, not on bytes or FLOPs. The curve bends upward only when the batch makes the work large enough to matter. CUDA graphs lower the flat region; they do nothing to the slope.

14.7Write and benchmark the Triton softmaxhard

Run the §14.10 kernel on a GPU for an (8192, 4096) bf16 tensor. Check it against torch.softmax, then time it, eager PyTorch built from separate ops (x - x.max(-1, keepdim=True).values, exp, sum, divide) and torch.softmax. Convert each time to effective bandwidth: 2 × bytes(x) / seconds.

How to judge your result

A fused softmax is memory-bound, so the right yardstick is the HBM bandwidth from §14.1. The fused kernel should reach a large fraction of it; the eager chain should take several times longer, because it moves the tensor through HBM once per op. If your kernel is far from the bandwidth line, check that rows are contiguous (coalescing, §14.5) and that BLOCK is not much larger than the row.
