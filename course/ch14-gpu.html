14 · The GPU: Memory, Tensor Cores, and the Roofline

Every performance claim in the rest of this course — the KV cache, GQA, FlashAttention, continuous batching — is an argument about one machine. This chapter is that machine. By the end you will be able to look at any operation and predict, with arithmetic and before running it, whether it is limited by compute or by memory. That single prediction explains almost every design decision in Parts IV and V.

Why this chapterWithout it, "memory-bound" is a phrase you repeat. With it, it is a number you compute.
The one idea in this chapter

A GPU can do arithmetic far faster than it can fetch numbers to do arithmetic on. An H100 can perform about 295 floating-point operations in the time it takes to read one byte from its main memory. So the only question that matters for any operation is: how many FLOPs do I get per byte I move? Below 295, you are waiting on memory and your expensive silicon is idle. Above it, you are actually computing.

14.1 · The hierarchy, and the only number that matters

A GPU is not one memory. It is a pyramid, and each level down is roughly an order of magnitude bigger and an order of magnitude slower. Figures below are for an H100 SXM5:

                         size            bandwidth        ~latency
  registers              256 KB / SM     ~100 TB/s        ~1 cycle
  shared memory / L1     up to 228 KB    ~20 TB/s         ~30 cycles      <- FlashAttention lives here
  L2 cache               50 MB total     ~10 TB/s         ~200 cycles
  HBM3 ("VRAM")          80 GB           3.35 TB/s        ~500 cycles     <- everything you allocate
  host RAM over PCIe     TBs             ~60 GB/s         ~microseconds

  compute: 989 TFLOP/s bf16 dense, across 132 SMs
Where the whole chapter comes from

Divide the top two numbers:

ridge point = 989.4 × 1012 FLOP/s3.35 × 1012 byte/s = 295 FLOP/byte

That is the exchange rate between the two resources. An operation that does fewer than 295 FLOPs per byte it touches cannot reach peak compute, no matter how good the kernel is, because the arithmetic units will run dry waiting for data.

The ridge point is a property of the chip, and it has been getting worse, not better — compute has outrun bandwidth for a decade:

                  compute        bandwidth      ridge point
  A100 80GB       312 TFLOP/s    2.04 TB/s      153 FLOP/byte
  H100 SXM5       989 TFLOP/s    3.35 TB/s      295 FLOP/byte
  H200 SXM        989 TFLOP/s    4.80 TB/s      206 FLOP/byte
  B200           2250 TFLOP/s    8.00 TB/s      281 FLOP/byte

H200 is the interesting row: same die as H100, only more bandwidth, and the ridge point drops to 206. A lower ridge means more workloads land on the compute side of the line. That is what you are buying when you buy memory bandwidth — not throughput directly, but the ability to keep the compute you already own busy.

14.2 · Arithmetic intensity: computing the number yourself

For any operation, define:

AI = FLOPs performedbytes moved to and from HBM   compare against   295

Do it for a matmul. Multiplying M, K by K, N gives M, N:

Derivation — the arithmetic intensity of a matmul
1
Count FLOPs. Each output element is a dot product of length K: that is K multiplies and K adds. There are MN outputs. 
FLOPs = 2 · M · K · N
2
Count bytes. Read both inputs, write the output. In bf16 each element is 2 bytes: 
bytes = 2 · (M·K + K·N + M·N)
3
Divide. The 2s cancel: 
AI = M·K·N / (M·K + K·N + M·N)
4
Set M = N = K = n. Numerator n³, denominator 3n²: 
AI = n / 3
Arithmetic intensity grows linearly with matrix size. Small matmuls are memory-bound; large ones are compute-bound; and the crossover is exactly n = 3 × 295 ≈ 886. 
square bf16 matmul on H100 (ridge 295):
   n= 128   AI=   42.7   MEMORY-bound
   n= 256   AI=   85.3   MEMORY-bound
   n= 512   AI=  170.7   MEMORY-bound
   n=1024   AI=  341.3   COMPUTE-bound
   n=4096   AI= 1365.3   COMPUTE-bound
Why "bigger batches are more efficient" is not folklore

It is AI = n/3. A 512-wide matmul reaches at most 171/295 = 58% of the H100's peak even with a perfect kernel — the hardware is simply starved. This is also why very small models are wasteful on big GPUs, and why tiny per-head matrices get batched together rather than run one at a time (Ch 06's reshape dance is partly a performance measure).

14.3 · The result that explains Part IV

Now apply it to a real transformer. Take a 7B model in bf16 — 14 GB of weights — and compute one token.

Generating a single token requires reading every weight exactly once and doing about 2P FLOPs with them (one multiply and one add per parameter). So:

7B model, bf16, batch 1, one decoded token
  bytes moved   = 14 GB   (every weight, once)
  FLOPs done    = 14 GFLOP
  AI            = 1 FLOP/byte          <- against a ridge of 295

  time if memory-bound   14e9 / 3.35e12  =  4.179 ms
  time if compute-bound  14e9 /  989e12  =  0.014 ms   (300x faster)

  -> MEMORY bound, by a factor of ~300
  -> hard ceiling: 239 tokens/second, batch 1, on an H100
Read the last line carefully

239 tokens/second is not a software limit. It is 14 GB divided by 3.35 TB/s. No kernel, compiler, or framework can beat it, because the weights must physically cross the memory bus once per token. The GPU is idle 99.7% of the time, waiting. Every technique in Ch 15–Ch 18 is an attack on this one number — either move fewer bytes (quantization, GQA, MLA) or do more work per byte moved (batching, speculative decoding).

Prefill is a completely different machine

Process 2048 prompt tokens at once and the weights are still read once — but now they are used 2048 times:

                     AI          memory time    compute time    verdict
  decode 1 token        1.0        4.179 ms        0.014 ms     MEMORY bound
  prefill 2048       2048.0        4.179 ms       28.979 ms     COMPUTE bound

Same weights, same GPU, opposite bottleneck. Prefill spends 29 ms computing and 4 ms fetching; decode spends 4 ms fetching and 14 microseconds computing. This is why serving stacks treat them as two different problems, schedule them separately, and report time-to-first-token and time-per-output-token as separate metrics (Ch 18).

Batching, quantified

In decode with batch B, the weights are still read once but used for 2B FLOPs. So AI = B, exactly:

batch B     AI          fraction of peak compute reachable
      1       1                 0.3%
      8       8                 2.7%
     32      32                10.8%
    128     128                43.3%
    256     256                86.7%
    295     295                99.9%   <- the ridge point, in batch units
Continuous batching, explained in one line

You need ~295 concurrent sequences before an H100 stops being bandwidth-starved during decode. That is the entire economic argument for continuous batching: a request served alone wastes 99.7% of the machine, and serving 256 at once costs almost exactly the same wall-clock time per token as serving one. It is also why the KV cache's memory footprint is so precious — cache size is what limits how many sequences fit, and therefore what limits B, and therefore what limits your position on this table.

14.4 · Tensor cores, and why d_head is 64 or 128

The 989 TFLOP/s figure is not from general-purpose arithmetic units. It comes from tensor cores: fixed-function hardware that multiplies small matrix tiles in one instruction. On Ampere and Hopper, the bf16/fp16 instruction has shape:

mma.sync.aligned.m16n8k16  —  a 16, 16 × 16, 8 → 16, 8 tile, per instruction

Crucially, it multiplies in bf16 and accumulates in fp32 — the hardware embodiment of §12.5's rule about accumulators. You get the wider accumulator for free, and cannot turn it off.

Any dimension that is not a multiple of the tile is padded to one, and you pay full price for the padding. So d_{head} should be a multiple of 16. But that alone would permit 48, 80, 96 — and you never see those. The sharper constraint is the memory system:

Why 64 and 128 specifically
1
A memory transaction is 128 bytes. That is the cache line — 4 sectors of 32 B. You cannot fetch less; a request for 1 byte still moves 32.
2
One head's slice of a row is d_{head} values × 2 bytes. For that slice to sit in whole cache lines with no waste: 
d_head    bytes    cache lines
   32        64      0.50   ragged - two heads share a line
   48        96      0.75   ragged
   64       128      1.00   CLEAN
   80       160      1.25   ragged
   96       192      1.50   ragged
  128       256      2.00   CLEAN
  256       512      4.00   CLEAN
3
Only multiples of 64 are clean, and 64/128 are the two that also keep \sqrt{d_{head}} in a sensible range for attention (Ch 05). Hence: essentially every production model uses 64 or 128, and FlashAttention kernels are compiled as separate template instantiations for exactly those values.
A number you have seen before, now explained

Whenever a config says d_model=4096, n_head=32, that is d_{head} = 128. When it says d_model=768, n_head=12, that is 64. It looks like a modelling choice. It is a cache-line choice that has been stable since 2018 and will stay stable as long as the line is 128 bytes.

14.5 · Coalescing: the same bytes, 32× the traffic

A GPU executes threads in groups of 32, called a warp, in lockstep. When a warp issues a load, the hardware merges the 32 addresses into as few 128-byte transactions as it can. If the threads read consecutive 4-byte words, all 32 fall in one line:

32 threads x 4 bytes = 128 bytes = exactly one cache line

  stride 1   ->   1 line per warp    perfect  (100% of fetched bytes used)
  stride 2   ->   2 lines per warp   2x the traffic, half of it discarded
  stride 4   ->   4 lines per warp   4x
  stride 32  ->  32 lines per warp   32x - every thread pulls its own line
This is why memory layout is a correctness-adjacent concern

A strided access pattern moves the same useful bytes but consumes up to 32× the bandwidth — and you already know bandwidth is the binding constraint. This is the real reason .contiguous() appears after transposes in attention code, and why the reshape dance is written to keep d_{head} as the last, fastest-varying axis: so that threads reading across a head's features read consecutive addresses. The axis order in your tensor is a bandwidth decision.

14.6 · Kernel fusion, and what FlashAttention is really doing

Every separate kernel launch means a round trip to HBM: read inputs, write outputs. Chain several elementwise operations and you pay that repeatedly for no arithmetic gain.

unfused:  x -> [read, gelu, write] -> [read, mul, write] -> [read, add, write]
          3 round trips to HBM, ~3 FLOPs per element  ->  AI well under 1

fused:    x -> [read, gelu, mul, add, write]
          1 round trip, same FLOPs                    ->  3x the intensity

Elementwise ops are always memory-bound — they do O(1) work per element — so their runtime is essentially "how many times did I touch HBM". Fusion is the only lever, which is what torch.compile spends most of its effort on.

FlashAttention is this idea applied to the one operation where it is hardest. Naive attention materialises the T, T score matrix in HBM — for T = 8192 that is 128 MB per head, written and read back, when the L2 cache is only 50 MB. FlashAttention never writes it: it tiles Q, K and V into shared memory (the 228 KB level, ~7× the bandwidth of HBM), computes each tile's contribution, and keeps only a running softmax. The FLOPs are identical. The bytes moved drop by orders of magnitude. On this chapter's roofline that is the whole speedup — see Ch 17 for the algorithm and the online-softmax proof that makes it exact.

A 7B bf16 model decodes at 239 tokens/s at batch 1 on an H100. You write a much better kernel. What happens?
Roughly 2× faster — kernels usually leave that much on the table
Up to ~300× faster, since the GPU is 99.7% idle
Essentially nothing: 14 GB ÷ 3.35 TB/s = 4.18 ms is a bandwidth floor, not a software one
Slower, because better kernels use more registers
The weights must cross the bus once per token. The GPU is idle 99.7% of the time, but that idleness is unreachable by faster arithmetic — it is time spent waiting for bytes. The only ways forward are moving fewer bytes (quantize, GQA/MLA) or doing more per byte (batch, speculate).
Why is d_head almost always 64 or 128, rather than 48 or 96?
Powers of two are faster to index
At 2 bytes per value, only multiples of 64 fill whole 128-byte cache lines; 48 and 96 leave ragged fractions
Attention requires d_head to be a power of two
Because √d_head must be an integer
Cache lines, then tensor-core tiles. 48 and 96 are valid multiples of the 16-wide tensor-core k-dimension — so tile alignment alone doesn't rule them out. What does is the 128-byte transaction: 96 × 2 = 192 B = 1.5 lines. 64 × 2 = 128 B exactly; 128 × 2 = 256 B exactly.
Prefill on 2048 tokens is compute-bound; decoding one token with the same weights is memory-bound. Why?
Prefill uses different kernels
Decode has to read the KV cache as well
The KV cache makes decode read more memory than prefill
Both read the weights once, but prefill does 2048× more arithmetic with them — AI goes from 1 to 2048, crossing the ridge at 295
Same bytes, 2048× the work. Arithmetic intensity is FLOPs ÷ bytes, and only the numerator changed. Measured: memory time 4.18 ms for both; compute time 0.014 ms vs 28.98 ms. The KV cache does add decode traffic, but it is not what flips the verdict — the ratio is.

14.7 · Exercises

14.1Build the roofline calculatoressential

Write a function that takes an operation's FLOPs and bytes and returns the predicted time, the bottleneck, and the achievable fraction of peak:

def roofline(flops, bytes_moved, peak_flops=989.4e12, bw=3.35e12):
    t_compute, t_memory = flops / peak_flops, bytes_moved / bw
    return dict(ai=flops / bytes_moved,
                bound="compute" if t_compute > t_memory else "memory",
                seconds=max(t_compute, t_memory),
                frac_of_peak=min(1.0, (flops / bytes_moved) / (peak_flops / bw)))

Now use it on every operation in a transformer block for d = 4096, B = 1, T = 1: the four attention projections, the three SwiGLU matrices, RMSNorm, the residual add, and the softmax. Rank them by predicted time. Which are memory-bound? What fraction of a decode step is spent in operations that do essentially no arithmetic?
