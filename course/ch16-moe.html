16 · Mixture of Experts

Chapter 8 established that two-thirds of a transformer's parameters live in the MLP, and that every token passes through all of them. MoE breaks that link: keep a very large number of parameters, but use only a small slice per token. It is how a 671-billion-parameter model runs at the cost of a 37-billion one.

16.1 · The idea

Decouple capacity from compute

Replace the single MLP in each block with N independent MLPs ("experts") plus a small router that picks k of them per token. Parameters scale with N; FLOPs scale with k. With N=256 and k=8 you get 32× the parameters for the same per-token compute.

class MoELayer(nn.Module):
    def __init__(self, d_model, d_ff, n_expert, top_k):
        super().__init__()
        self.router  = nn.Linear(d_model, n_expert, bias=False)   # tiny
        self.experts = nn.ModuleList([SwiGLU(d_model, d_ff) for _ in range(n_expert)])
        self.top_k   = top_k

    def forward(self, x):                       # x: (B, T, C)
        B, T, C = x.shape
        x = x.view(-1, C)                       # (B*T, C) — routing is PER TOKEN

        logits = self.router(x)                 # (B*T, n_expert)
        weights, idx = logits.softmax(-1).topk(self.top_k, dim=-1)   # (B*T, k) each
        weights = weights / weights.sum(-1, keepdim=True)            # renormalise

        out = torch.zeros_like(x)
        for e, expert in enumerate(self.experts):
            mask = (idx == e).any(dim=-1)       # which tokens chose expert e
            if not mask.any(): continue
            tokens = x[mask]                                  # (n_e, C)
            w = weights[mask][(idx[mask] == e)].unsqueeze(-1) # (n_e, 1)
            out[mask] += w * expert(tokens)
        return out.view(B, T, C)

This loop is for clarity. Production kernels sort tokens by expert and run grouped GEMMs (MegaBlocks, grouped_gemm) so no expert stalls the others.

Routing is per token, not per sequence

Notice the x.view(-1, C). Every token in the batch independently picks its own experts, and the choice changes at every layer. There is no "the maths expert" — a single sentence will touch dozens of different experts on its way through the network. Expert specialisation is real but far more granular and less interpretable than the name suggests.

16.2 · The load-balancing problem

Left alone, routers collapse. An expert that happens to be slightly better early gets picked more, trains more, gets better, gets picked more. You end up with 4 experts doing all the work and 252 dead ones — all the memory cost of a huge model with the capacity of a small one.

Solution 1: auxiliary loss (Switch Transformer, GShard)

ℒaux = α · N · Σi=1N fi · Pi fi = fraction of tokens routed to expert i  ·  Pi = mean router probability for expert i

This product is minimised when both are uniform, so it pushes toward balanced routing. Typically α ≈ 0.01. The drawback is real: you are adding a term that fights the language-modelling objective. Too much and you damage quality by forcing tokens to experts that suit them poorly.

Solution 2: auxiliary-loss-free balancing (DeepSeek-V3, 2024)

# Add a per-expert BIAS to the routing logits, used only for top-k SELECTION.
# The bias is not learned by gradient descent — it's adjusted by a control rule.
scores = router(x)                       # (n_tok, n_expert)
idx = (scores + self.bias).topk(k, -1).indices     # bias affects WHO is chosen
weights = scores.gather(-1, idx).sigmoid()         # but NOT the output weighting

# After each step, nudge the bias toward balance:
with torch.no_grad():
    load = count_tokens_per_expert(idx)
    self.bias += gamma * (load.mean() - load).sign()   # under-used → bias up
Why this is better

The bias steers selection without adding any gradient to the loss. There is no interference term fighting the language-modelling objective, so you get balance and the best achievable quality. DeepSeek reported this outperforms auxiliary-loss balancing, and the technique has spread quickly.

Capacity factor and token dropping

In expert-parallel training each expert lives on a device with a fixed buffer: capacity = capacity_factor × tokens / n_expert. Tokens overflowing that buffer are dropped — they skip the MoE layer entirely and pass through on the residual connection only. A capacity factor of 1.0 drops a lot; 1.25 is a common compromise. Modern "dropless" implementations (MegaBlocks) use block-sparse kernels to avoid the issue altogether.

16.3 · DeepSeekMoE: fine-grained + shared experts

Two refinements that are now widely copied:

Fine-grained experts

Instead of 8 large experts choosing 2, use 256 small experts choosing 8 (each 1/4 the size). Same active parameters, but the number of possible expert combinations explodes from C(8,2)=28 to C(256,8)≈1014. Far more precise specialisation for the same compute.

Shared experts

Designate 1–2 experts that every token uses, always. Common knowledge (grammar, basic syntax) lives there instead of being redundantly duplicated across all 256 routed experts — which frees the routed experts to specialise properly.

# DeepSeek-V3 MoE layer
out = shared_expert(x)                       # ALWAYS runs, for every token
for e in top_8_of_256_routed:
    out = out + weight[e] * expert[e](x)     # plus 8 routed experts

The trend since 2024 is unmistakable: more experts, sparser routing, smaller active fraction. DeepSeek-V3 activates 5.5% of its parameters; gpt-oss-120b activates 4.4%.

The catch: memory

MoE reduces FLOPs, not memory. All 671B parameters must be resident somewhere — DeepSeek-V3 needs roughly 1.3 TB in bf16, i.e. ~17 H100s just to hold the weights. MoE trades "cheap to run, expensive to host" against dense models' "expensive to run, cheap to host". It is a great deal at datacentre scale and a poor one on a single GPU, which is exactly why frontier labs use MoE and local-inference enthusiasts mostly don't.

DeepSeek-V3 is 671B parameters but "only 37B active". What does active mean?
Only 37B parameters are trained; the rest are frozen
Each token's forward pass uses ~37B parameters, so per-token FLOPs match a 37B dense model
Only 37B fit in GPU memory at once
37B is the number after quantization
Per-token compute. All 671B are trained and all must be in memory. But any given token touches attention + shared expert + 8 of 256 routed experts ≈ 37B parameters. So it costs like a 37B model to run and stores like a 671B model — and, critically, learns more like a 671B model.
Why do MoE models need explicit load balancing?
To make training deterministic
To keep all GPUs at the same temperature
Because the router is randomly initialised
Because routing has a rich-get-richer dynamic that collapses onto a few experts, wasting the rest
Self-reinforcing collapse. A slightly-preferred expert gets more tokens → more gradient → better → more tokens. Without a counter-pressure you end up paying for 256 experts and using 4. (Uneven load also does cause GPU stalls in expert-parallel training — but the quality collapse is the fundamental problem.)
Why does DeepSeek use 256 small experts with top-8 rather than 8 large experts with top-1?
Far more expert combinations for the same active parameters, enabling finer specialisation
Smaller experts train faster
It uses less total memory
Top-8 routing is cheaper to compute than top-1
Combinatorics. C(256,8) ≈ 4×10¹⁴ distinct expert subsets versus 8. The active parameter count is comparable, but the model can express vastly more distinct "modes". Total memory is the same, routing is slightly more expensive, and small experts don't train faster.

16.5 · Practical notes

  • Not every layer is MoE. DeepSeek-V3 keeps its first 3 layers dense; Llama 4 alternates. Early layers seem to do general-purpose work that doesn't benefit from specialisation.
  • Fine-tuning MoE is harder. Routing distributions shift under a new data distribution, some experts receive almost no gradient, and results are less stable than dense fine-tuning.
  • Expert parallelism is its own distributed-training strategy: experts are sharded across devices and tokens are all-to-all'd to reach them. The all-to-all is often the communication bottleneck of the entire training run.
  • MoE and MLA compose. DeepSeek-V3 uses both — MLA for the attention/KV cache, MoE for the MLP. They address orthogonal costs.

16.6 · Exercises

16.1Build an MoE layer and watch it collapseessential

Implement MoELayer with 8 experts, top-2. Train a small model on Tiny Shakespeare without any load-balancing loss, logging the token count per expert every 100 steps.

  1. Plot expert utilisation over time. Does it collapse? How fast?
  2. Add the auxiliary loss with α ∈ {0, 0.001, 0.01, 0.1}. Plot final LM loss and a balance metric (e.g. the coefficient of variation of expert loads) for each.
  3. Implement the bias-based aux-loss-free scheme and compare.
What you'll see

Collapse usually begins within a few hundred steps and is severe by ~2000. α=0.01 gives good balance at negligible LM-loss cost; α=0.1 balances perfectly but measurably hurts the LM loss — you can see the objective conflict in the numbers. The bias method should reach comparable balance with LM loss closer to the α=0 run, which is exactly the claim DeepSeek makes.

16.2Do the MoE arithmeticthinking

For a model with d_model=4096, d_ff=14336, 32 layers, SwiGLU:

  1. Dense parameter count of all MLPs.
  2. Same, but each MLP replaced by 64 experts with top-4 routing (experts each 1/8 the width).
  3. Active parameters per token in case 2.
  4. Memory to serve each in bf16, and FLOPs per token for each.
Answers
1. Dense: 3 × 4096 × 14336 × 32              = 5.64 B
2. Expert d_ff = 14336/8 = 1792
   per expert: 3 × 4096 × 1792               = 22.02 M
   × 64 experts × 32 layers                  = 45.1 B      (8× the dense count)
3. Active: 4 experts × 22.02 M × 32 layers   = 2.82 B      (half the dense count!)
4. Memory: 11.3 GB dense  vs  90.2 GB MoE    (8× more)

8× the parameters at half the compute. That's the trade in one line — and the 8× memory bill is why it's a datacentre technique.

What the literature finds

Specialisation is real but weaker and more syntactic than expected. The Mixtral paper found routing correlates strongly with token identity and local syntax (indentation, punctuation, numerals) and only weakly with semantic domain. Consecutive tokens are often routed to the same expert. The "one expert for biology" mental model is wrong; think of experts as specialised computational routines rather than topic specialists.
