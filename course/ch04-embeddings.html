4 · Embeddings and the Residual Stream

Two ideas here. The first is mechanical and easy: an embedding is a lookup table. The second is the most useful mental model in this entire course — the residual stream — and it is what turns a transformer from "a stack of mystery boxes" into something you can reason about.

Builds onCh 03 — you need token ids before you can look them up
Leads toCh 08 — every block reads and writes this stream
Ch 09 — the stream is the model's spine
Why this chapterThe residual stream is the single most useful mental model in this course.
The whole chapter in five sentences

An embedding is a row lookup in a (V, C) table, and the output head is a (C, V) matmul that may share the same weights. Every layer reads from and adds to one (B, T, C) residual stream, whose shape never changes. The stream's scale grows with depth, which is why initialisation scales the residual projections down and pre-norm normalises what each block reads. The output side has its own stability tools: logit soft-capping, z-loss, and a vocabulary padded for the hardware. Because the stream lives in one space throughout, the final head can decode any layer (the logit lens), and that space holds more features than it has dimensions (superposition).

4.1 · An embedding is a lookup, not a matmul

nn.Embedding(V, C) holds a single weight matrix of shape (V, C): one row per vocabulary entry, each row a C-dimensional vector.

import torch, torch.nn as nn

V, C = 50257, 768
emb = nn.Embedding(V, C)
emb.weight.shape                  # (50257, 768)  → 38.6M parameters

ids = torch.tensor([[15496, 995, 0],
                    [  464, 3797, 3332]])    # (B=2, T=3)
x = emb(ids)
x.shape                           # (2, 3, 768)   ← (B, T, C)
What just happened, shape-wise

Every integer in a (B, T) tensor was replaced by a vector of length C. So the rank went up by one and the last axis appeared: (B, T) → (B, T, C). This is the only place in the whole model where the rank increases like this. From here to the very end, the shape stays (B, T, C).

It is equivalent to a one-hot matmul (but never implemented that way)

onehot(i)  ·  WE  =  row i of WE (1, V) @ (V, C) → (1, C) 
# These are numerically identical:
onehot = torch.zeros(1, V); onehot[0, 15496] = 1.0
(onehot @ emb.weight)          # (1, 768)  — 50257 multiplies, 50256 of them by zero
emb.weight[15496]              # (768,)    — one memory read
Worked example — the same answer, two ways

50,257× more arithmetic for the same answer.

Two things follow from this. (1) An embedding is a linear layer — which is why weight tying with the output projection is even coherent. (2) The gradient reaches exactly one row per token occurrence, because every other row was multiplied by zero. That sparsity is precisely the mechanism behind the under-trained "glitch tokens" of Chapter 3: a token seen once gets one gradient, ever. (With AdamW its row keeps moving after that gradient, but briefly on momentum: Adam's step decays like (β1/√β2)t, under 1% of its first size within about 45 steps. What keeps acting for hundreds of steps is weight decay, which shrinks the row every step, so a rare token's row ends up somewhere between a single update and zero: never trained, but not untouched either. The companion notebook measures both.)

The one-hot view is conceptually useful (it explains why an embedding layer is a linear layer, and why gradients flow to exactly one row per token). The lookup view is what actually runs.

Consequence: embeddings are sparse to train

Each training step only computes a gradient for the rows of tokens that actually appeared in the batch (the optimizer may still move other rows through momentum and weight decay). A token appearing once in 10 billion gets one gradient, ever — which is precisely the mechanism behind the under-trained "glitch tokens" from Chapter 3.

4.2 · Weight tying

At the end of the model you need to go the other way: from a C-dimensional vector back to a score for every vocabulary entry.

lm_head = nn.Linear(C, V, bias=False)     # weight shape (V, C)
logits = lm_head(x)                        # (B, T, C) → (B, T, V)

Notice lm_head.weight has shape (V, C) — the same shape as the embedding matrix. That is not a coincidence, and many models share the same tensor for both:

model.lm_head.weight = model.embed.weight     # weight tying
ApproachParamsUsed byRationale
TiedV·CGPT-2, Gemma, Qwen3-small, most <3B modelsSaves a lot of parameters when V·C is a big fraction of the model. Acts as a regulariser.
Untied2·V·CLlama-3-8B+, DeepSeek-V3, most large models"What a token means as input" and "what predicts it as output" are genuinely different functions. At large scale the extra parameters are cheap and help.

Rule of thumb: tie when the model is small (embeddings dominate the parameter count), untie when it's large (they're a rounding error and the extra capacity pays for itself).

4.3 · The residual stream — the model you should carry in your head

Here is the mental model. It comes from mechanistic interpretability work at Anthropic, and once you have it, transformers stop looking like a stack of boxes.

The residual stream

A transformer maintains, for each token position, one vector of size d_model that persists from the embedding all the way to the output. Call it the residual stream.

Every layer reads from the stream, computes something, and adds its result back. No layer ever replaces the stream. It is a running total — a shared blackboard that every layer writes to and every later layer can read.

x = embed(tokens)                 # (B, T, C)  ← the stream is born

for block in blocks:
    x = x + block.attn(block.ln1(x))     # attention writes into the stream
    x = x + block.mlp (block.ln2(x))     # MLP writes into the stream

logits = lm_head(final_norm(x))   # (B, T, V) ← the stream is read out

Look at the shape of x. It is (B, T, C) on every single line. A 70-billion parameter model with 80 layers has exactly one tensor shape running through its spine.

Why this model is so useful

  • It explains why gradients flow. The + means the gradient has a direct highway from the loss back to layer 1, bypassing every non-linearity. This is the whole reason ResNets and transformers can be 100+ layers deep. (§4.4)
  • It explains what layers "do". A layer isn't a transformation of everything; it's a specialist that reads a subspace and writes a subspace. Early layers write syntactic features; later layers write semantic ones.
  • It explains the logit lens. Because the stream lives in the same space throughout, you can apply the final unembedding to an intermediate layer's stream and get readable predictions. Doing so shows the model's guess sharpening layer by layer — an experiment you'll run in the notebook.
  • It explains "superposition". With d_model = 4096 but far more than 4096 concepts to represent, features must share dimensions at near-orthogonal angles. That's the central puzzle of interpretability research.
Bandwidth, precisely

The residual stream is a fixed-width communication channel. Every attention head and every MLP in the whole network competes for the same d_model dimensions. That is a real constraint, and it is one reason d_model scales with depth in practice: wider models can be deeper before the blackboard gets crowded.

4.4 · Why x + f(x) instead of f(x)

Consider the derivative of a residual block versus a plain block:

plain:   y = f(x)  →  ∂y∂x = f′(x)        residual:   y = x + f(x)  →  ∂y∂x = 1 + f′(x) the identity term is what keeps the gradient alive through 100 layers

Stack L plain layers and the gradient is a product of L Jacobians — if each has magnitude 0.9, after 80 layers you have 0.980 ≈ 0.0002 and the early layers learn nothing. With residuals, the product is of terms like (1 + f′), which stays near 1. That's it. That's the whole trick, and it's why He et al.'s ResNet paper (2015) is one of the most-cited papers in science.

The identity term. Without it, backprop multiplies L Jacobians and the signal dies exponentially in depth. With it, there's an unobstructed highway from the loss to every layer. Note it costs a small amount of extra compute and memory, not less.

4.5 · Scale: initialisation, √d, and a stream that grows

The residual stream is a sum: the embedding, plus every block's output. If each block adds an update that is roughly independent of what is already there, variances add. After l blocks that each add variance σ², the stream's RMS is about √(σ0² + l·σ²): it grows like √l. Nothing in the architecture stops it. Two design decisions manage it, and you can measure both with tfs.foundations.residual_norms, which builds a 12-layer, d = 256 model from tfs.model at initialisation and records the stream's RMS after the embedding and after every block:

                                   embed   block 1   block 4   block 8   block 12
GPT-2 init (residual outputs
  scaled by 1/√(2L))               0.020    0.022     0.029     0.044     0.058     2.9× growth
same model, all weights std 0.02   0.020    0.045     0.159     0.250     0.320    16× growth

Scaled initialisation. GPT-2's paper scales the weights of the layers that write into the stream (the attention output projection and the MLP's down projection) by 1/√N, N the number of residual layers; tfs.model uses 0.02/√(2·n_layer). Each block's update starts small enough that their sum stays the same order as the embedding. Without it, the stream at layer 12 is already 16 times the embedding's scale, and the embedding (the only place token identity enters) is a rounding error in it.

Pre-norm. Every block in this course reads norm(x), not x (Chapter 8). So however large the stream grows, each block sees an input of RMS ≈ 1 and its update has a fixed scale. That keeps every block's arithmetic well conditioned. The price is dilution: a block's fixed-size update moves a stream of RMS ∝ √l by a relative amount ∝ 1/√l, so later blocks in a deep pre-norm model change the stream less than early ones. It is one reason the post-sublayer "sandwich" norms of Chapter 8 exist.

Why some models multiply the embedding by √d

The original Transformer (Vaswani et al. 2017) multiplies the embedding by √d_model before adding positions, and Gemma does the same (its embedding output is scaled by √hidden_size, about 55 for d = 3072). The reason is the tied table. A shared (V, C) matrix is also the output head, and an output head wants small weights: initialised with std 1/√C, each logit has variance about 1. But then each input row has RMS 1/√C too, tiny next to block updates of order 1. Multiplying by √C brings the input to RMS ≈ 1 without changing the head. Untied models can simply initialise the two tables differently, and most do not scale.

4.6 · The output side: soft-capping, z-loss, padding

The last operation of the model, logits = head(norm(x)), gets three pieces of special treatment in modern models.

Final-logit soft-capping (Gemma 2). Squash every logit smoothly into (−cap, cap):

logits ← cap · tanh(logits / cap) Gemma 2: cap = 30 for the final logits (and 50 for attention logits, Chapter 5)

Near zero it is the identity; far away it saturates. tfs.foundations.softcap with cap 30 maps 10 → 9.65, 30 → 22.85, 60 → 28.92, 100 → 29.92. So no token can ever be more than e60 times likelier than another, and a few runaway directions in the stream cannot produce the enormous logits that make the loss spike. (It also interacts with fused cross-entropy and FlashAttention kernels that do not implement it, and Gemma 3 later dropped the attention cap in favour of QK-norm, Chapter 8.)

z-loss (PaLM). Softmax is unchanged if you add a constant to every logit, so nothing in the cross-entropy stops the logits drifting upward together until bf16 rounding of a large log Z costs precision. PaLM adds a small penalty on the log-partition function:

ℒz = 10−4 · (log Z)²     log Z = log Σv elogitv logits [10, 9, 2]: log Z = 10.3135, penalty 0.0106  ·  it pulls the whole logit vector toward log Z = 0

The penalty does not change which token is predicted; it only removes the free drift. It is cheap, and it is now a standard line in large-scale training recipes (Chapter 11's loss-spike discussion). The MoE router uses the same trick on its own logits (Chapter 20).

Vocabulary padding. The head is a (C, V) matmul, usually the largest single one in a small model. Chapter 2 §2.6 shows why V is padded to a multiple of 64 or 128: GPT-2's 50,257 becomes 50,304 in nanoGPT. The padded rows are never targets, so training drives their logits down, and a correct sampler must never return them (mask them to −∞ if you load a padded checkpoint into a tokenizer of the real size).

It fixes a free direction. Adding c to every logit leaves softmax unchanged, so the cross-entropy cannot see that drift; z-loss can. With a coefficient of 10−4 it barely competes with the main loss anywhere else.

4.7 · What embeddings actually learn

The classic word2vec result — king − man + woman ≈ queen — holds, weakly, in transformer input embeddings too. But the more important modern finding is about the output side.

Because the unembedding maps the stream to vocabulary logits, directions in the residual stream correspond to "makes token X more likely". The final layernorm plus lm_head is a readout head, and you can apply it early:

# The "logit lens": decode an intermediate layer as if it were the last one.
with torch.no_grad():
    x = model.embed(ids)
    for i, blk in enumerate(model.blocks):
        x = blk(x)
        logits_i = model.lm_head(model.final_norm(x))     # (B, T, V)
        top = logits_i[0, -1].argmax().item()
        print(f"layer {i:2d}: {tokenizer.decode([top])!r}")

A logit-lens run you can reproduce

Here is the experiment on the repo's own model, small enough to train in the test suite. tfs.foundations.train_toy_copy_model trains a 2-layer tfs.model.Model (d = 64, 4 heads, RoPE) for 300 steps on sequences whose second half repeats the first. After the midpoint the next token is predictable, but only by attending back to the right earlier position, which takes an induction head: one layer to find "the token after the previous occurrence of this one", composed with another. logit_lens decodes the stream after the embedding and after each block with the model's own final norm and head, and scores the predictable half:

decoded fromtop-1 accuracyp(correct token)
embedding3.2%0.032
after block 13.3%0.032
after block 2 (the output)100%0.993

Chance is 1/31 = 3.2%, so after block 1 the stream still says nothing decodable about the answer, and after block 2 it is certain. That is what an induction circuit looks like through the lens: the first layer writes "what came before me" into the stream in a form the head cannot read, and only the second layer turns it into a prediction. In large models the picture is the same but smeared over dozens of layers.

The lens can lie: the tuned-lens caveat

The logit lens assumes an intermediate layer's stream is already in the basis the final head reads. It need not be: early layers can carry the answer in directions the head ignores, and then the lens reports "nothing yet" when the information is there. Belrose et al. (2023) found the plain logit lens unreliable on several model families and proposed the tuned lens: train one small affine map per layer to translate that layer's stream into the final layer's basis, then decode. Treat a plain logit-lens result as a lower bound on what a layer knows.

Run this and you typically see generic/frequent tokens early, snapping to the correct answer in the last third of the network. It is one of the most striking things you can observe in a language model with ten lines of code.

4.8 · Superposition, in one toy model

§4.3 claimed the stream holds more features than it has dimensions. Elhage et al. (2022, "Toy Models of Superposition") made that precise with a model small enough to draw. Take 5 features, each zero with probability S (the sparsity) and otherwise uniform in [0, 1]. Squeeze them into 2 dimensions and back: x̂ = ReLU(Wᵀ W x + b) with W of shape (2, 5), trained to reconstruct x. Column i of W is where feature i lives in the 2-D "stream"; a column of length ≈ 1 means the feature is represented, ≈ 0 means it was dropped. superposition_toy trains it for 4,000 Adam steps:

sparsity Scolumn norms of Wfeatures represented in 2 dims
0.0 (always on)0.89 0.36 0.89 0.36 0.422: one per dimension, the rest dropped
0.71.01 1.01 1.01 0.00 1.014
0.91.10 1.10 1.10 1.10 1.095, at angles 72° apart: a pentagon

When features are dense, two features collide whenever both are on, so the model does the PCA thing: represent two, drop three. When features are sparse, two are rarely on at once, so it pays to store all five at non-orthogonal angles and accept occasional interference; the ReLU and the negative bias clean up the small cross-talk. The pentagon is the geometry that minimises the worst-case overlap. Language features are overwhelmingly sparse (any given concept is absent from almost every token), which is why a 4,096-dimensional stream can carry far more than 4,096 of them, and why individual neurons and dimensions are so hard to interpret: features are directions, not axes. The test test_ch04_superposition checks the counts and the 72° spacing.

In the 2-layer copy model, the logit lens after block 1 is at chance (3.3%), yet the full model is 100% accurate. What does that show?

The logit lens is broken for small models

Composition. An induction head needs a previous-token step and a matching step. Remove block 1 and the copy task fails; the lens only shows that its output is not yet in the head's vocabulary basis. That is exactly the tuned-lens caveat in miniature.
In the toy model, why does increasing feature sparsity make the model store all 5 features in 2 dimensions?
Sparse features are smaller in magnitude
The optimiser runs longer
Sparse inputs make W orthogonal

Interference is paid only when features co-occur. At S = 0.9 two given features are both on 1% of the time. Non-orthogonal storage costs a little then and gains a lot the rest of the time.
What does superposition imply for interpreting a single neuron or residual dimension?
It usually responds to several unrelated features, because features are stored as directions shared across dimensions
Each neuron encodes exactly one concept
Neurons in later layers are always interpretable
Nothing: superposition only happens in toy models
Polysemanticity. If more features than dimensions share a space, no basis aligns with all of them. That is the motivation for sparse autoencoders, which look for the directions rather than the axes.

4.9 · Exercises

4.1Embedding = one-hot matmulwarm-up

Prove the equivalence numerically. Build emb = nn.Embedding(10, 4), then show that emb(torch.tensor([3])) equals F.one_hot(torch.tensor([3]), 10).float() @ emb.weight. Then time both for V=50000. What's the speed ratio, and where does it come from?

Answer

They match exactly. The lookup is typically 100–1000× faster because the matmul does V×C multiply-adds (49,999 of every 50,000 by zero) plus materialises a (B, T, V) one-hot tensor, while the lookup does C memory reads. It's the same computation with completely different arithmetic intensity — a theme that returns in Chapter 15.

4.2Nearest neighbours in embedding spacecode

Load GPT-2's embedding matrix. Write nearest(word, k=10) that returns the k tokens whose embeddings have highest cosine similarity to a given token's embedding.

W = model.transformer.wte.weight            # (50257, 768)
Wn = W / W.norm(dim=-1, keepdim=True)       # normalise rows → cosine = dot

def nearest(token_str, k=10):
    i = tokenizer.encode(token_str)[0]
    sims = Wn @ Wn[i]                       # (50257,)
    top = sims.topk(k + 1).indices[1:]      # skip itself
    return [(tokenizer.decode([j]), sims[j].item()) for j in top]

Try " king", " Monday", " Paris", " 7". Note the leading spaces — Chapter 3 explains why they matter.

What to expect

" Monday" gives you the other weekdays, which is a clean win. " king" gives royalty-adjacent words but also a lot of noise. Input embeddings in a transformer are less semantically clean than word2vec vectors, because the model can defer meaning to later layers — the embedding only needs to be a useful starting point, not a finished representation.

4.3Break the residual streamessential

Take any small transformer implementation and change x = x + attn(ln(x)) to x = attn(ln(x)) in every block. Train both on the same tiny dataset for the same number of steps. Plot both loss curves.

What you'll see, and why

The residual-free model trains dramatically worse, and in a pre-norm model the gap is already large at 2 layers (the companion notebook measures it). The gradient check is the surprising part: inspect block[0].attn.weight.grad.norm() in both, and the non-residual model's first-layer gradient is not orders of magnitude smaller; it is about as large or larger. With a norm in front of every sublayer, each block rescales its input, so the gradient does not vanish. What the residual-free model loses is the identity path itself: every layer must re-encode everything the layers before it knew, instead of adding a small correction to a stream that already carries it. (In a post-norm or norm-free stack, the textbook vanishing gradient does appear; Ch 8's exercise 8.2 measures that.)

4.4Predict, then measure: residual growthcode

Using tfs.foundations.residual_norms, predict and then measure the stream's RMS after the last block for a 24-layer and a 48-layer version of the §4.5 model (same width), with and without the scaled initialisation. Then check the √l model: is the growth closer to linear or to √l in the number of blocks?

What to look for

With the scaled init, each block's update variance falls like 1/L, so the total added variance stays roughly constant as L grows: the final RMS is 0.058, 0.059 and 0.062 at 12, 24 and 48 layers. Without it, the variance added per block is fixed and the final RMS keeps growing with depth: 0.32, 0.47, 0.69. The early blocks of the unscaled model grow faster than √l, because a block's output is correlated with its input (attention averages the same stream it reads), which is a useful reminder that "independent updates" is an approximation.

4.6Superposition with unequal importanceexploration

Modify superposition_toy so feature i's reconstruction error is weighted by 0.7i, as in Elhage et al. Sweep sparsity from 0 to 0.95. At what sparsity does the third feature first get represented, and which features does the model drop first?

What the paper finds

Dense: the two most important features get the two dimensions. As sparsity rises, less important features are added in order of importance, through intermediate arrangements (antipodal pairs, then larger polygons), with sharp transitions between them. Importance decides who gets stored first; sparsity decides how many can share.
