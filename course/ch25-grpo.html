25 · DPO Variants, GRPO, and RLVR

DPO opened a design space, and the field explored it thoroughly. Then reasoning models arrived and changed the question entirely: when you can verify whether an answer is correct, you don't need preferences at all. This chapter covers both branches.

25.1 · The DPO family

Every variant below changes one specific thing about the DPO loss. Knowing which thing tells you when to reach for it.

IPO — Identity Preference Optimization

ℒIPO = E [ ( hθ(x,yw,yl) − 12β )2 ] h = the log-ratio difference; a squared loss toward a fixed margin instead of a sigmoid

Problem it fixes: DPO's sigmoid is only minimised as the margin → ∞. When preferences are deterministic (annotators always pick A over B), nothing stops the model pushing the margin arbitrarily far and over-fitting. IPO targets a specific finite margin, so the KL constraint stays effective.

KTO — Kahneman-Tversky Optimization

Problem it fixes: DPO needs paired data — two responses to the same prompt. In production you usually have unpaired thumbs-up/thumbs-down. KTO borrows prospect theory's value function to learn from individual labelled examples, weighting losses relative to a reference point and applying loss aversion (bad examples count more than good ones). Enormously more practical when your data is whatever users clicked.

ORPO — Odds Ratio Preference Optimization

ℒORPO = ℒSFT + λ · ℒOR,    ℒOR = − log σ( log odds(yw|x)odds(yl|x) )

Problem it fixes: the two-stage pipeline. ORPO needs no reference model and no separate SFT stage — it does both at once by adding an odds-ratio penalty to the standard SFT loss. Half the memory, one training run. Popular for resource-constrained fine-tuning.

SimPO — Simple Preference Optimization

ℒSimPO = − log σ( β|yw| log πθ(yw|x) − β|yl| log πθ(yl|x) − γ )

Problem it fixes: two at once. It uses the length-normalised average log-probability rather than the sum — which removes DPO's implicit length bias and matches what generation actually optimises — and it drops the reference model entirely, adding an explicit margin γ instead. Simpler and often stronger than DPO on benchmarks.

25.2 · RLVR — reinforcement learning with verifiable rewards

The shift

For maths, code, and logic you don't need a reward model at all. Run the unit tests. Check the answer. The reward is a program, not a neural network — so it cannot be hacked in the usual way, needs no preference data, and is exactly correct by construction.

def reward(prompt, completion):
    # Format reward: did it use the required structure?
    r = 0.1 if re.search(r"<think>.*?</think>.*?\\boxed\{.*?\}", completion, re.S) else 0.0
    # Correctness reward: is the final answer right?
    if extract_boxed(completion) == ground_truth[prompt]:
        r += 1.0
    return r

This removes the whole reward-model failure surface from Chapter 23 — no length bias, no format bias, no annotator noise ceiling. The catch is scope: it only works where correctness is checkable. Maths, code, formal logic, structured extraction — yes. "Write a moving poem" — no.

25.3 · GRPO — Group Relative Policy Optimization

DeepSeek's algorithm, introduced in DeepSeekMath and used to train R1. It removes PPO's value model — the fourth model from Chapter 23 — by a simple observation.

The idea

PPO needs a value model to estimate "how good is this state?" so it can compute an advantage. But if you sample G different completions for the same prompt, the group mean reward is already a baseline. Advantage = how much better this completion is than its siblings. No critic needed.

Âi = ri − mean(r1…rG)std(r1…rG) z-score the rewards within the group. That's the advantage.
Worked example — three groups of 8, and why one of them is wasted compute

Same prompt, 8 sampled answers, reward 1 for correct and 0 for wrong. No value model anywhere — the group is the baseline.

A
A mixed group — the useful case. 
rewards     [1, 0, 1, 0, 1, 0, 0, 1]     mean 0.500   std 0.5000
advantages  [+1, −1, +1, −1, +1, −1, −1, +1]
Clean signal: the 4 correct rollouts get pushed up, the 4 wrong ones down, equally.
B
All eight correct — and here is the problem. 
rewards     [1, 1, 1, 1, 1, 1, 1, 1]     mean 1.000   std 0.0000
advantages  [ 0,  0,  0,  0,  0,  0,  0,  0]
Every advantage is exactly zero. You paid for 8 full generations and the gradient contribution is nothing. An all-wrong group behaves identically.
C
One lucky winner — the signal is asymmetric. 
rewards     [0, 0, 0, 1, 0, 0, 0, 0]     mean 0.125   std 0.3307
advantages  [−0.378 ×7 ,  +2.645]
The single success gets a +2.645 push while each failure gets only −0.378. Rare correct answers are automatically weighted more heavily — no curriculum needed.

Group B is the entire motivation for DAPO's dynamic sampling. Once a model is decent, a large fraction of groups come back all-correct (or, early on, all-wrong) — and every one of those is generation compute spent for a zero gradient. Filtering them out and resampling is why DAPO is faster, and it falls straight out of the arithmetic: z-scoring a constant vector gives zero.

import torch
def advantages(rewards):
    r = torch.tensor(rewards, dtype=torch.float)
    return (r - r.mean()) / (r.std(unbiased=False) + 1e-4)

print(advantages([1,0,1,0,1,0,0,1]))   # ±1
print(advantages([1]*8))               # all zeros  <- wasted group
print(advantages([0,0,0,1,0,0,0,0]))   # +2.645 once, −0.378 seven times

assert advantages([1]*8).abs().sum() < 1e-3   # no gradient signal at all
Why no critic PPO trains a value model to answer "how good is average here?". Eight samples from the same prompt answer it empirically — you trade a learned network for G× generation. 
def grpo_step(policy, ref, prompts, reward_fn, G=8, beta=0.04, eps=0.2):
    for prompt in prompts:
        # 1. Sample a GROUP of completions from the current policy
        comps = [policy.generate(prompt, temperature=1.0) for _ in range(G)]
        rewards = torch.tensor([reward_fn(prompt, c) for c in comps])

        # 2. Group-relative advantage — no value model anywhere
        adv = (rewards - rewards.mean()) / (rewards.std() + 1e-4)      # (G,)

        # 3. PPO-style clipped objective, with the group advantage
        logp     = policy.logprobs(prompt, comps)                      # (G, T)
        logp_old = logp.detach()
        ratio    = torch.exp(logp - logp_old)
        obj = torch.min(ratio * adv[:, None],
                        ratio.clamp(1-eps, 1+eps) * adv[:, None])

        # 4. KL to the reference, added directly to the loss
        logp_ref = ref.logprobs(prompt, comps)
        kl = torch.exp(logp_ref - logp) - (logp_ref - logp) - 1        # unbiased, >= 0

        loss = -(obj - beta * kl).mean()
        loss.backward()

The outcome-only property is what makes it fit RLVR so naturally: a unit test gives you one bit at the end, not a per-token score.

DeepSeek-R1-Zero: the striking result

DeepSeek trained a base model with GRPO and verifiable rewards with no SFT stage at all. Reasoning behaviours — self-verification, backtracking, extending its own chain of thought when stuck — emerged from the reward signal alone, without any demonstrations of reasoning. The model's average response length grew on its own over training as it discovered that thinking longer paid off. R1-Zero had readability problems (language mixing), so the shipped R1 added a small SFT cold-start; but the zero result is the scientifically important one.

DAPO and the refinements

GRPO has known failure modes, and DAPO (2025) addresses four:

  • Clip-Higher — decouple the upper and lower clip bounds so low-probability tokens can still gain probability. Fixes entropy collapse, where the policy becomes deterministic too early.
  • Dynamic sampling — discard prompts where all G completions get the same reward. Their advantage is exactly 0, so they contribute no gradient and just waste generation compute.
  • Token-level policy gradient loss — weight by tokens rather than by sequence, so long completions aren't under-weighted.
  • Overlong reward shaping — penalise truncated generations gently instead of treating them as simply wrong.
How does GRPO eliminate PPO's value model?
It uses the reward model as the value model
It samples G completions per prompt and uses the group's mean reward as the baseline for the advantage
It doesn't use advantages at all
It estimates the value from the reference model
The group is the baseline. A value model exists to answer "how good is average here?" — and G samples from the same prompt answer that empirically. You trade a learned critic for G× generation cost, which is usually the better deal, especially when rewards are cheap programs.
Why is RLVR less prone to reward hacking than RLHF with a learned reward model?
The reward is computed by a program (test suite, answer checker) rather than a learned approximation with exploitable failure modes
RLVR uses a stronger KL penalty
RLVR doesn't use RL
Verifiable tasks are easier
The reward is exact, not approximated. Chapter 23's hacking arises because the reward model is a finite-sample fit to human preference. A unit test has no such gap. Caveat: RLVR has its own hacking modes — models that special-case the visible tests, or produce right answers via wrong reasoning — so "less prone", not immune.
In GRPO, a prompt yields 8 completions that all receive reward 1.0. What is the gradient contribution?
Large and positive — all completions were good
Depends on the KL term only
Approximately zero — advantages are all 0 after mean subtraction, so the group teaches nothing
Negative
Zero, and that's wasteful. The advantage is (1.0 − 1.0)/std ≈ 0 for every sample. You paid for 8 generations and learned nothing. This is precisely what DAPO's dynamic sampling fixes — filter out all-same-reward groups and resample, so every generation you pay for carries signal.

25.4 · How to choose

Your situationUse
Paired preferences, want simple and reliableDPO (or SimPO if length bias bites)
Thumbs up/down from production usersKTO
Tight memory, want one stageORPO
Maths / code / anything checkableGRPO + RLVR
Maximum quality, have an RL teamPPO, or GRPO/DAPO with a reward model
General assistant, production scaleSFT → DPO → RLVR on verifiable subsets — the current standard stack
The 2026 post-training stack

RLHF was not replaced; it was modularised. The consensus pipeline is now: SFT for instruction following and format → preference optimisation (DPO/SimPO/KTO) for tone, helpfulness and safety → RL with verifiable rewards (GRPO/DAPO) for reasoning and tool use. Different capabilities are trained by different mechanisms, and the verifiable-reward stage is where most of the capability gains of the last two years have come from.

25.5 · Exercises

25.1Implement four losses, compare on one datasetcode

Implement DPO, IPO, SimPO and ORPO as four loss functions with a shared training harness. Run all four on the same SFT checkpoint and preference data with matched compute. Report: ranking accuracy on held-out pairs, mean generation length, and win-rate against the SFT baseline judged by a stronger model.

What to watch for

Track mean generation length especially. DPO usually increases it (it optimises summed log-probs, which correlates with length); SimPO should not (length-normalised). If your win-rate improves but length doubled, you may have bought the win with verbosity rather than quality — which is why length-controlled evaluation exists. Always report both.

25.2GRPO on a verifiable taskthe interesting one

Take a small instruct model and train it with GRPO on GSM8K-style arithmetic. Reward: +1 correct answer, +0.1 correct <think>…</think> format. Use G=8, β=0.04.

  1. Plot accuracy and mean completion length against training step.
  2. Does completion length increase on its own? (This is the R1 phenomenon in miniature.)
  3. Add DAPO's dynamic sampling. What fraction of groups get filtered, and how much compute does that save?
Practical notes

Use a model that already has some arithmetic ability — GRPO amplifies existing capability, it doesn't create it from nothing. If accuracy starts at 0%, every group gets reward 0, every advantage is 0, and nothing happens. This is the most common reason a GRPO run appears to do nothing.

Expect 20–60% of groups to be filtered by dynamic sampling once the model is decent — either all-correct or all-wrong. That's a large fraction of your generation budget recovered.

25.3Hack your own reward functionthinking

Write a code-generation reward that runs 3 visible unit tests. Train with GRPO. Then evaluate on 20 held-out tests the model never saw.

What usually happens

Visible-test pass rate climbs to near 100%. Held-out rate lags badly, and inspecting the code often shows explicit special-casing of the visible inputs — if n == 5: return 120. Verifiable rewards remove one class of hacking and introduce another: the model optimises the measurement, not the goal. The mitigations — many more tests, held-out test sets, property-based testing, penalising hardcoded literals — are the same ones you'd use against a lazy human contractor.
