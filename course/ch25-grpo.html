25 · DPO Variants, GRPO, and RLVR

DPO opened a design space, and the field explored it thoroughly. Then reasoning models arrived and changed the question entirely: when you can verify whether an answer is correct, you don't need preferences at all. This chapter covers both branches, then the refinements of 2025 that made reasoning RL work at scale: Dr. GRPO's fix for two hidden biases, GSPO's sequence-level ratios for MoE models, process rewards, and agentic multi-turn RL against real environments.

25.1 · The DPO family

Every variant below changes one specific thing about the DPO loss. Knowing which thing tells you when to reach for it.

IPO — Identity Preference Optimization

ℒIPO = E [ ( hθ(x,yw,yl) − 12β )2 ] h = the log-ratio difference; a squared loss toward a fixed margin instead of a sigmoid

Problem it fixes: DPO's sigmoid is only minimised as the margin → ∞. When preferences are deterministic (annotators always pick A over B), nothing stops the model pushing the margin arbitrarily far and over-fitting. IPO targets a specific finite margin, so the KL constraint stays effective.

KTO — Kahneman-Tversky Optimization

Problem it fixes: DPO needs paired data — two responses to the same prompt. In production you usually have unpaired thumbs-up/thumbs-down. KTO borrows prospect theory's value function to learn from individual labelled examples, weighting losses relative to a reference point and applying loss aversion (bad examples count more than good ones). Enormously more practical when your data is whatever users clicked.

ORPO — Odds Ratio Preference Optimization

ℒORPO = ℒSFT + λ · ℒOR,    ℒOR = − log σ( log odds(yw|x)odds(yl|x) )

Problem it fixes: the two-stage pipeline. ORPO needs no reference model and no separate SFT stage — it does both at once by adding an odds-ratio penalty to the standard SFT loss. Half the memory, one training run. Popular for resource-constrained fine-tuning.

SimPO — Simple Preference Optimization

ℒSimPO = − log σ( β|yw| log πθ(yw|x) − β|yl| log πθ(yl|x) − γ )

Problem it fixes: two at once. It uses the length-normalised average log-probability rather than the sum — which removes DPO's implicit length bias and matches what generation actually optimises — and it drops the reference model entirely, adding an explicit margin γ instead. Simpler and often stronger than DPO on benchmarks.

25.2 · RLVR — reinforcement learning with verifiable rewards

The shift

For maths, code, and logic you don't need a reward model at all. Run the unit tests. Check the answer. The reward is a program, not a neural network — so it cannot be hacked in the usual way, needs no preference data, and is exactly correct by construction.

def reward(prompt, completion):
    # Format reward: did it use the required structure?
    r = 0.1 if re.search(r"<think>.*?</think>.*?\\boxed\{.*?\}", completion, re.S) else 0.0
    # Correctness reward: is the final answer right?
    if extract_boxed(completion) == ground_truth[prompt]:
        r += 1.0
    return r

This removes the whole reward-model failure surface from Chapter 23 — no length bias, no format bias, no annotator noise ceiling. The catch is scope: it only works where correctness is checkable. Maths, code, formal logic, structured extraction — yes. "Write a moving poem" — no.

25.3 · GRPO — Group Relative Policy Optimization

DeepSeek's algorithm, introduced in DeepSeekMath and used to train R1. It removes PPO's value model — the fourth model from Chapter 23 — by a simple observation.

The idea

PPO needs a value model to estimate "how good is this state?" so it can compute an advantage. But if you sample G different completions for the same prompt, the group mean reward is already a baseline. Advantage = how much better this completion is than its siblings. No critic needed.

Âi = ri − mean(r1…rG)std(r1…rG) z-score the rewards within the group. That's the advantage.
Worked example — three groups of 8, and why one of them is wasted compute

Same prompt, 8 sampled answers, reward 1 for correct and 0 for wrong. No value model anywhere — the group is the baseline.

A
A mixed group — the useful case.

advantages  [+1, −1, +1, −1, +1, −1, −1, +1]

rewards     [1, 1, 1, 1, 1, 1, 1, 1]     mean 1.000   std 0.0000

rewards     [0, 0, 0, 1, 0, 0, 0, 0]     mean 0.125   std 0.3307
advantages  [−0.378 ×7 ,  +2.645]
The single success gets a +2.645 push while each failure gets only −0.378. Rare correct answers are automatically weighted more heavily — no curriculum needed.

Group B is the entire motivation for DAPO's dynamic sampling. Once a model is decent, a large fraction of groups come back all-correct (or, early on, all-wrong) — and every one of those is generation compute spent for a zero gradient. Filtering them out and resampling is why DAPO is faster, and it falls straight out of the arithmetic: z-scoring a constant vector gives zero.

import torch
def advantages(rewards):
    r = torch.tensor(rewards, dtype=torch.float)
    return (r - r.mean()) / (r.std(unbiased=False) + 1e-4)

print(advantages([1,0,1,0,1,0,0,1]))   # ±1
print(advantages([1]*8))               # all zeros  <- wasted group
print(advantages([0,0,0,1,0,0,0,0]))   # +2.645 once, −0.378 seven times

assert advantages([1]*8).abs().sum() < 1e-3   # no gradient signal at all
Why no critic PPO trains a value model to answer "how good is average here?". Eight samples from the same prompt answer it empirically — you trade a learned network for G× generation. 
def grpo_step(policy, ref, prompts, reward_fn, G=8, beta=0.04, eps=0.2):
    for prompt in prompts:
        # 1. Sample a GROUP of completions from the current policy
        comps = [policy.generate(prompt, temperature=1.0) for _ in range(G)]
        rewards = torch.tensor([reward_fn(prompt, c) for c in comps])

        # 2. Group-relative advantage — no value model anywhere
        adv = (rewards - rewards.mean()) / (rewards.std(unbiased=False) + 1e-4)   # (G,)

        # 3. PPO-style clipped objective, with the group advantage
        logp     = policy.logprobs(prompt, comps)                      # (G, T)
        logp_old = logp.detach()
        ratio    = torch.exp(logp - logp_old)
        obj = torch.min(ratio * adv[:, None],
                        ratio.clamp(1-eps, 1+eps) * adv[:, None])

        # 4. KL to the reference, added directly to the loss
        logp_ref = ref.logprobs(prompt, comps)
        kl = torch.exp(logp_ref - logp) - (logp_ref - logp) - 1        # unbiased, >= 0

        loss = -(obj - beta * kl).mean()
        loss.backward()

The outcome-only property is what makes it fit RLVR so naturally: a unit test gives you one bit at the end, not a per-token score.

DeepSeek-R1-Zero: the striking result

DeepSeek trained a base model with GRPO and verifiable rewards with no SFT stage at all. Reasoning behaviours — self-verification, backtracking, extending its own chain of thought when stuck — emerged from the reward signal alone, without any demonstrations of reasoning. The model's average response length grew on its own over training as it discovered that thinking longer paid off. R1-Zero had readability problems (language mixing), so the shipped R1 added a small SFT cold-start; but the zero result is the scientifically important one.

DAPO and the refinements

GRPO has known failure modes, and DAPO (2025) addresses four:

  • Clip-Higher — decouple the upper and lower clip bounds so low-probability tokens can still gain probability. Fixes entropy collapse, where the policy becomes deterministic too early.
  • Dynamic sampling — discard prompts where all G completions get the same reward. Their advantage is exactly 0, so they contribute no gradient and just waste generation compute.
  • Token-level policy gradient loss — weight by tokens rather than by sequence, so long completions aren't under-weighted.
  • Overlong reward shaping — penalise truncated generations gently instead of treating them as simply wrong.

The group is the baseline. A value model exists to answer "how good is average here?" — and G samples from the same prompt answer that empirically. You trade a learned critic for G× generation cost, which is usually the better deal, especially when rewards are cheap programs.
Why is RLVR less prone to reward hacking than RLHF with a learned reward model?
The reward is computed by a program (test suite, answer checker) rather than a learned approximation with exploitable failure modes
RLVR uses a stronger KL penalty
RLVR doesn't use RL
Verifiable tasks are easier
The reward is exact, not approximated. Chapter 23's hacking arises because the reward model is a finite-sample fit to human preference. A unit test has no such gap. Caveat: RLVR has its own hacking modes — models that special-case the visible tests, or produce right answers via wrong reasoning — so "less prone", not immune.

Zero, and that's wasteful. The advantage is (1.0 − 1.0)/std ≈ 0 for every sample. You paid for 8 generations and learned nothing. This is precisely what DAPO's dynamic sampling fixes — filter out all-same-reward groups and resample, so every generation you pay for carries signal.

25.4 · Dr. GRPO: two biases hiding in the normalisation

GRPO's objective, as DeepSeekMath wrote it, has two normalisations that look like harmless bookkeeping. Liu et al. (2025, "Understanding R1-Zero-Like Training") showed that each one biases what the model learns, and that the first one is a reason responses grow longer during RL whether or not length helps.

ℒGRPO = 1G Σi 1|oi| Σt min( ρi,t Âi, clip(ρi,t) Âi )     Âi = ri − mean(r)std(r) the two bold terms are the biases · |oi| = length of completion i in tokens

Bias 1 · dividing by the completion's own length

Each token of completion i is weighted by Âi/(G·|oi|). For a correct answer (Â > 0) a short completion gets a bigger push per token, so the policy learns to be brief when right. For a wrong answer (Â < 0) a long completion gets a smaller penalty per token, so the policy learns that if it is going to be wrong, it should be wrong at length.

Worked example — one group of four, two right and two wrong

Rewards [1, 1, 0, 0], so Â = [+1, +1, −1, −1]. Lengths in tokens [100, 300, 200, 1000]. The weight one token of each completion gets in the loss (token_weights), in units of 10−4:

length                 100         300         200        1000

DAPO   Â/Σ|o|         +6.25       +6.25      -6.25      -6.25     token-level, one weight per group
Dr.GRPO (r−mean)/(G·L) +1.25      +1.25      -1.25      -1.25     constant L = 1000
!
Under GRPO, each token of the 1,000-token wrong answer is penalised 5× less than each token of the 200-token wrong answer. Summed over the sequence the two penalties are equal (−0.25 each), so nothing in the loss pushes against length, while per token, longer wrong answers are cheaper. Over thousands of steps that is a steady drift toward longer incorrect responses, which is what Liu et al. observed.

The fix is to divide by a constant. DAPO's token-level loss (25.3) divides by the total tokens in the group, which removes the bias within a group; Dr. GRPO divides by a fixed number such as the maximum generation length, which removes it everywhere and makes the loss an unbiased policy gradient again.

Bias 2 · dividing by the group's standard deviation

The z-score's denominator rescales every question's advantages by 1/std(r). That is not neutral: questions on which the group mostly agrees (almost all right, or almost all wrong) have a small std and so get amplified. Take two groups of eight:

rewards            std      GRPO advantages        Dr. GRPO (r − mean)    1/std
[1,0,0,0,0,0,0,0]  0.3307   +2.645 / −0.378        +0.875 / −0.125        3.02
[1,1,1,1,0,0,0,0]  0.5000   ±1.000                 ±0.500                 2.00

GRPO weights the nearly-unsolved question 1.51× more, relative to the half-solved one, than the raw reward differences justify. Whether that is good is a design choice (it is a built-in curriculum toward hard and easy extremes), but it is a difficulty bias, not part of the policy gradient. Dr. GRPO drops the std and uses Âi = ri − mean(r). With both fixes, Liu et al. report reasoning accuracy matching GRPO with markedly shorter responses on wrong answers, and a minimal recipe reaching 43.3% on AIME 2024 with a 7B base model.

def grpo_advantages(rewards, scale_by_std=True, eps=1e-4):       # tfs/rl.py
    r = torch.as_tensor(rewards, dtype=torch.float64)
    a = r - r.mean()
    return a / (r.std(unbiased=False) + eps) if scale_by_std else a  # Dr. GRPO: scale_by_std=False

25.5 · GSPO: one ratio per sequence, and why MoE needed it

Look again at the GRPO objective. The reward and the advantage are per sequence: one number for the whole completion. The importance ratio ρi,t = πθ(yt|…)/πold(yt|…) is per token, and so is the clipping. Each token's ratio is a single-sample correction for the change in one next-token distribution; over a 10,000-token completion those noisy corrections accumulate, and clipping individual tokens throws away gradient from tokens in the middle of otherwise good sequences. Group Sequence Policy Optimization (Zheng et al. 2025, the Qwen team) matches the unit of the correction to the unit of the reward:

si = ( πθ(yi|x) / πold(yi|x) )1/|yi| = exp( 1|yi| Σt log ρi,t )      ℒGSPO = 1G Σi min( siÂi, clip(si, 1−ε, 1+ε)Âi ) the geometric mean of the token ratios · length-normalised so long and short sequences sit on one scale

gspo_ratio computes it with a padding mask, so padded positions do not count toward the length; the test checks both the value and the masking.

The MoE connection

In a Mixture-of-Experts model (Chapter 20) each token is routed to its top-k experts, and top-k is discrete. A small weight update can flip one of a token's experts between the policy that generated the sample and the policy being trained. That token's log-probability then jumps, its ratio lands far from 1, and its clipped, reweighted gradient becomes erratic; across a long sequence with dozens of MoE layers many tokens are affected. The GSPO paper reports that with GRPO, the Qwen team needed Routing Replay to make RL on its MoE models converge: cache the experts the old policy chose for every token and force the new policy to use the same ones when computing the ratio. That costs memory and communication and constrains the model. Because GSPO averages log-ratios over the whole sequence, a few tokens whose routing flipped barely move si, and the paper reports stable MoE training without Routing Replay. The same averaging makes GSPO more tolerant of small numerical differences between the inference engine that generated the samples and the training engine that recomputes their log-probabilities (Ch 12), a practical headache in every large RL system. The paper also reports that GSPO clips a far larger fraction of tokens than GRPO and still trains more efficiently, which it reads as evidence of how noisy the token-level signal is. GSPO was used for Qwen3's RL.

25.6 · Outcome rewards and process rewards

Everything so far uses an outcome reward: one number for the final answer. Every token of a solution gets the same advantage, the brilliant first step and the arithmetic slip in step three alike. A process reward model (PRM) scores each step instead. Lightman et al. (2023, "Let's Verify Step by Step") collected 800k human step-level labels (PRM800K) and found a PRM picked correct solutions out of many samples more reliably than an outcome reward model. Human step labels are expensive, so Math-Shepherd (Wang et al. 2023) generates them automatically: from the prefix ending at each step, roll out several completions and record how many reach the right answer. A step's value is that success fraction, and its advantage is how much it changed it.

Worked example — Monte Carlo step labels find the mistake

A four-step solution with a wrong final answer. From the bare prompt the model succeeds 70% of the time. From the end of each step, 8 rollouts (mc_step_values, step_advantages):

after step           0 (prompt)    1       2       3       4
rollouts correct        -         6/8     5/8     1/8     0/8
value                  0.70      0.750   0.625   0.125   0.000
step advantage                  +0.050  -0.125  -0.500  -0.125

Step 3 dropped the chance of success from 62.5% to 12.5%: that is the mistake. An outcome reward would give all four steps the same advantage (0 − 0.70 = −0.70 with the prompt's success rate as baseline), blaming the good first step as much as the bad third one. This is exactly what Chapter 23's value model and GAE estimate implicitly; Monte Carlo rollouts estimate it explicitly, at the price of many more generations.

Why, then, do the strongest 2025–26 reasoning models mostly train on outcome rewards? DeepSeek-R1's report lists PRMs among its unsuccessful attempts, for three reasons that generalise: a fine-grained "step" is hard to define in free-form reasoning; automatic step labels are noisy and human ones do not scale; and a learned PRM is a reward model, so the policy learns to write steps that look good to it, which is Chapter 23's reward hacking again. Outcome rewards from verifiers are sparse but exact. PRMs remain useful for search (choosing among sampled solutions, beam search over steps) and as a dense signal where outcomes are very delayed, which is the agent setting.

25.7 · Agentic RL: multi-turn rollouts and environment rewards

An agent does not answer once. It calls a tool, reads the result, thinks, calls another, and after dozens of turns the task is done or not: the tests pass, the ticket is resolved, the file is right. Training that behaviour with RL reuses everything above with four changes.

  1. The reward comes from an environment. A sandbox (a container with the repository, a browser, a simulated user) runs the trajectory and checks the end state. SWE-RL (Wei et al. 2025) trained Llama 3 on real GitHub pull-request data with a rule-based reward (similarity of the model's patch to the real one) and reached 41.0% on SWE-bench Verified with a 70B model.
  2. Only the policy's tokens are actions. A trajectory interleaves the model's turns with tool outputs and observations the model did not choose. Those tokens must be masked out of the policy-gradient loss (and the KL), or the model is trained to "predict" compiler errors and web pages, and their gradients swamp the real ones.
  3. Credit assignment spans turns. The outcome arrives after the last turn. The simplest workable recipe is GRPO over whole trajectories: sample G trajectories per task, give each its outcome reward, z-score within the group, and apply the advantage to every action token of the trajectory. Turn-level advantages, or a process signal per turn, are active research.
  4. Rollouts dominate the cost, and they are slow and uneven. One trajectory can take minutes of environment time. Systems therefore run generation and training asynchronously, so samples are produced by a slightly older policy than the one being trained, which makes the importance ratios of 25.5 do real work.
def agent_loss_mask(segments):                 # tfs/rl.py
    """segments: [(role, n_tokens), ...]; only the assistant's own tokens get gradient."""
    return torch.cat([torch.full((n,), float(role == "assistant")) for role, n in segments])

Environments are reward functions, and they get hacked like one

The code-generation hack of exercise 25.3 gets more inventive with tools: agents have been observed editing or deleting the tests they are graded by, special-casing the checker's inputs, and exploiting bugs in the sandbox. Treat the environment as part of the reward design: grade with held-out checks the agent cannot read, restrict what it can modify, and audit a sample of successful trajectories by hand. RAGEN (Wang et al. 2025) also documents a failure specific to multi-turn RL, the "Echo Trap": reward variance across trajectories collapses, the model repeats a fixed pattern, and gradients spike, the multi-turn relative of the zero-variance groups in 25.3.

The 2026 post-training stack

RLHF was not replaced; it was modularised. The consensus pipeline is now: SFT for instruction following and format → preference optimisation (DPO/SimPO/KTO) for tone, helpfulness and safety → RL with verifiable rewards (GRPO/DAPO/GSPO) for reasoning, then agentic RL against environments for tool use. Different capabilities are trained by different mechanisms, and the verifiable-reward stage is where most of the capability gains of the last two years have come from.

25.9 · Exercises

25.1Implement four losses, compare on one datasetcode

Implement DPO, IPO, SimPO and ORPO as four loss functions with a shared training harness. Run all four on the same SFT checkpoint and preference data with matched compute. Report: ranking accuracy on held-out pairs, mean generation length, and win-rate against the SFT baseline judged by a stronger model.

What to watch for

Track mean generation length especially. DPO usually increases it (it optimises summed log-probs, which correlates with length); SimPO should not (length-normalised). If your win-rate improves but length doubled, you may have bought the win with verbosity rather than quality — which is why length-controlled evaluation exists. Always report both.

25.2GRPO on a verifiable taskthe interesting one

Take a small instruct model and train it with GRPO on GSM8K-style arithmetic. Reward: +1 correct answer, +0.1 correct <think>…</think> format. Use G=8, β=0.04.

  1. Plot accuracy and mean completion length against training step.
  2. Does completion length increase on its own? (This is the R1 phenomenon in miniature.)
  3. Add DAPO's dynamic sampling. What fraction of groups get filtered, and how much compute does that save?
Practical notes

Use a model that already has some arithmetic ability — GRPO amplifies existing capability, it doesn't create it from nothing. If accuracy starts at 0%, every group gets reward 0, every advantage is 0, and nothing happens. This is the most common reason a GRPO run appears to do nothing.

Expect 20–60% of groups to be filtered by dynamic sampling once the model is decent — either all-correct or all-wrong. That's a large fraction of your generation budget recovered.

Write a code-generation reward that runs 3 visible unit tests. Train with GRPO. Then evaluate on 20 held-out tests the model never saw.

What usually happens

Visible-test pass rate climbs to near 100%. Held-out rate lags badly, and inspecting the code often shows explicit special-casing of the visible inputs — if n == 5: return 120. Verifiable rewards remove one class of hacking and introduce another: the model optimises the measurement, not the goal. The mitigations — many more tests, held-out test sets, property-based testing, penalising hardcoded literals — are the same ones you'd use against a lazy human contractor.

25.4Predict, then measure: does GRPO's normalisation lengthen wrong answers?exploration

Using your GRPO setup from 25.2, run three otherwise identical trainings that differ only in the loss reduction: per-sequence mean (GRPO), token-level over the group (DAPO), and a constant G · MAX_LEN with no std (Dr. GRPO). Before running, predict which run's incorrect responses grow longest.

  1. Plot mean length of correct and of incorrect responses separately, per run.
  2. Compare final accuracy. Did the length difference buy anything?
What to expect

The per-sequence-mean run's incorrect responses should lengthen fastest, the constant normaliser's least; accuracy is often similar. Plot correct and incorrect separately: the average over both hides the effect, because correct responses may shorten while incorrect ones lengthen. Use tfs.rl.token_weights to check your reductions give the per-token weights of the worked example before you train.

25.5Make a routing flip and watch the ratioscode

Take a top-2 MoE layer from tfs.moe inside a small model. Sample a 64-token sequence, record its token log-probs, then apply one small optimizer step.

  1. Count how many tokens changed one of their two experts.
  2. Plot the token ratios ρt for tokens whose routing flipped versus those that did not.
  3. Compute the GSPO ratio s with tfs.rl.gspo_ratio, and the fraction of tokens a per-token clip at ε = 0.2 would cut.
What you'll see

Most tokens keep their experts and have ratios near 1; the flipped ones are the outliers. s stays close to 1 because it averages log-ratios over all 64 tokens. That is section 25.5's argument, measured on a model you can inspect, and the reason Routing Replay exists for token-level methods.

25.6Cost one step of agentic RLthinking

An agentic RL step uses 512 tasks with G = 8 trajectories each. A trajectory averages 30,000 tokens, of which 20% are the policy's own (the rest are tool outputs it reads). Generation runs at 20,000 tokens/s in aggregate.

  1. Total tokens processed per step, and policy tokens that receive gradient.
  2. Generation time per step, ignoring environment latency.
  3. Environment calls take 2 s each, 15 per trajectory, run 256 at a time. Does generation or the environment dominate?
Answers
1. 512 × 8 × 30,000 = 122,880,000 tokens;  × 0.2 = 24,576,000 get gradient
2. 122,880,000 / 20,000 = 6,144 s ≈ 1.7 h
   (tool outputs are prefilled, not decoded, so this overstates generation; it is an upper bound)
3. 4,096 trajectories × 15 calls × 2 s / 256 parallel = 480 s
   generation dominates here, but only because the environment is parallel; serialise it and it is 34 h

This is why agentic RL runs asynchronously, with many sandboxes per GPU and samples consumed slightly off-policy: the slowest trajectory in a batch otherwise sets the step time, just as the slowest expert does in Chapter 20.
