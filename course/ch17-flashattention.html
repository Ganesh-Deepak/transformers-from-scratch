17 · FlashAttention and the Online Softmax

FlashAttention computes exactly the same function as the attention you wrote in Chapter 5. There is no approximation and no sparsity, and the outputs are identical up to floating-point rounding. Yet it is 2 to 4× faster and uses 10 to 20× less memory. That sounds impossible until you see that the arithmetic was never the bottleneck.

Builds onCh 05 — the T x T score matrix
Ch 02 — why memory traffic dominates
Leads toCh 18 — serving stacks assume this exists
Ch 22 — it removed the memory wall, not the quadratic
Why this chapterSame maths, same output, 2-4x faster — because the bottleneck was never arithmetic.
The whole chapter in five sentences

Attention was slow because of memory traffic, not arithmetic. The N × N score matrix was written to HBM and read back for nothing. The online softmax keeps a running max and sum, and rescales what it has added up whenever the max grows. So a row can be processed in tiles and the result is exact. FlashAttention passes tiles of Q, K and V through on-chip memory and never builds the full matrix. That cuts HBM traffic about tenfold and memory from O(N²) to O(N). Decode needs a different split. One query has too little parallel work, so Flash-Decoding splits the keys and merges the pieces by their log-sum-exps. FlexAttention turns any mask or score change into such a kernel, and its speed comes from skipping the empty blocks of a sparse mask.

17.1 · The insight: attention is IO-bound, not compute-bound

A GPU has a memory hierarchy, and its numbers are very lopsided:

LevelSize (A100)BandwidthAnalogy
SRAM (on-chip, per SM)~20 MB total~19 TB/syour desk
HBM (the "GPU memory" you buy)40–80 GB1.5–2 TB/sthe filing cabinet

SRAM is roughly 10× faster and 3000× smaller. Standard attention ignores this completely:

S = Q @ K.T          # write an (N, N) matrix to HBM        ← 4 GB at N=32k, fp32
P = softmax(S)       # read (N,N) from HBM, write (N,N) back ← 8 GB of traffic
O = P @ V            # read (N,N) from HBM again             ← 4 GB
The realisation

We build an N×N matrix in slow memory, then read it back twice, only to throw it away. The output is only N×d. Nearly all the time goes into moving a temporary result that nobody wants. Dao et al. asked: can we avoid writing it down at all?

17.2 · The obstacle: softmax needs the whole row

The obvious plan is to process K and V in tiles that fit in SRAM. But softmax has a denominator that depends on the whole row:

softmax(x)i = exi − max(x)Σj exj − max(x) both max(x) and the sum require seeing every element of the row

(The − max(x) matters. Without it, exp(x) overflows to inf for x > 88 in fp32. Every real softmax subtracts the max.)

So how do you compute a softmax over data you see in pieces?

17.3 · The online softmax

You keep a running max and a running sum. When the max changes, you go back and rescale everything you have added up so far. Milakov & Gimelshein (2018) worked this out, and Dao et al. applied it to attention.

Suppose you have processed a prefix with max m and sum ℓ, and a new value x arrives:

mnew = max(m, x)      ℓnew = ℓ · em − mnew + ex − mnew the correction factor em−mnew re-bases the old sum to the new max

Step through it. The bottom line shows the two agree exactly:

Worked example — four numbers, one at a time, exact at the end

Scores [1, 3, 2, 5]. We never hold them all at once. One arrives per step, and we keep only m (the running max) and ℓ (the running sum).

Six decimal places. The gap is float32 rounding, not approximation.

Why this is the whole proof. Every rescale multiplies the running numerator and denominator by the same factor, so their ratio is untouched. That ratio is the softmax weights [0.0152, 0.1125, 0.0414, 0.8310]. Because the result is exact, FlashAttention can be used for training. An approximate attention would add up to a different model, but this is the same function computed in a different order.

import math, torch
xs = [1.0, 3.0, 2.0, 5.0]

m, l = float("-inf"), 0.0
for x in xs:                                   # one value at a time
    m_new = max(m, x)
    corr  = math.exp(m - m_new) if m != float("-inf") else 0.0
    l     = l * corr + math.exp(x - m_new)
    m     = m_new

streaming = m + math.log(l)
one_shot  = torch.tensor(xs).logsumexp(0).item()
assert abs(streaming - one_shot) < 1e-5        # 5.185182 vs 5.185183

The same correction applies to the running output, and that is what makes it useful for attention:

Onew = Oold · emold − mnew + es − mnew · v rescale the running output, then add the new tile's contribution
Why this is exact, not approximate

Every rescale multiplies both the running numerator and the running denominator by the same factor, so their ratio, the actual softmax output, does not change. This is exact algebra, with no approximation. That is why FlashAttention can be used for training, where an approximate attention would add up to a noticeably different model.

17.4 · The algorithm

# FlashAttention, forward pass (simplified, one head)
#   Q: (N, d)   K, V: (N, d)   →   O: (N, d)
#   Tile sizes Br, Bc chosen so that a tile of Q, K, V and the running
#   state all fit in SRAM simultaneously.

for i in range(0, N, Br):                       # OUTER loop over query blocks
    Qi = load(Q[i:i+Br])                        # → SRAM,  (Br, d)
    Oi = zeros(Br, d)                           # running output    (in SRAM)
    mi = full(Br, -inf)                         # running max       (in SRAM)
    li = zeros(Br)                              # running sum       (in SRAM)

    for j in range(0, N, Bc):                   # INNER loop over key blocks
        if causal and j > i + Br - 1: break     # every key in this block is in the future: skip it
        Kj, Vj = load(K[j:j+Bc]), load(V[j:j+Bc])       # → SRAM

        Sij = Qi @ Kj.T / sqrt(d)               # (Br, Bc)  ← ONLY THIS TILE EXISTS
        if causal and j + Bc - 1 > i:           # the block straddles the diagonal, so
            q_pos = arange(i, i+Br)[:, None]    # mask INSIDE the tile: key j' may not
            k_pos = arange(j, j+Bc)[None, :]    # be later than query i'
            Sij = where(k_pos > q_pos, -inf, Sij)

        m_new = maximum(mi, Sij.max(dim=-1))    # (Br,)
        Pij   = exp(Sij - m_new[:, None])       # (Br, Bc)
        corr  = exp(mi - m_new)                 # (Br,)  the rescale factor

        li = corr * li + Pij.sum(dim=-1)        # rescale + accumulate the denominator
        Oi = corr[:, None] * Oi + Pij @ Vj      # rescale + accumulate the numerator
        mi = m_new

    write(O[i:i+Br], Oi / li[:, None])          # normalise ONCE, then → HBM

Notice what never happens: the (N, N) matrix is never allocated. Only a (Br, Bc) tile exists at any moment, and it lives in SRAM.

Causal masking happens at two granularities

Blocks entirely above the diagonal are skipped: never loaded, never computed. That is where the 2× saving of causal attention comes from. Blocks that cross the diagonal are computed, and they still need the ordinary element-wise mask inside the tile. Without it, each query sees up to Bc − 1 future keys. Drop the in-tile mask and the result is wrong only near the diagonal, so the bug passes a test on short sequences with one big tile. tfs/flash.py is this loop in runnable PyTorch, and test_flash_attention_in_tile_mask checks it against naive attention for square, tall and wide tiles and for one tile covering everything.

The backward pass: recomputation

Backprop through attention needs the attention weights P. We did not store them. So FlashAttention recomputes them from Q, K, V during the backward pass. That sounds wasteful but is not: recomputing a tile in SRAM is far cheaper than writing and re-reading N² values from HBM.

This is the same trade as gradient checkpointing, applied inside the kernel: spend FLOPs to save memory traffic, when FLOPs are plentiful and traffic is the limit.

The complexity result

Standard attentionFlashAttention
FLOPsO(N²d)O(N²d) — the same, or slightly more
HBM accessesO(N² + Nd)O(N²d²/M), M = SRAM size
Extra memoryO(N²)O(N)

With d = 64 and about 100 KB of usable SRAM per block (≈ 50k bf16 values), d²/M is around 1/12. So FlashAttention does roughly ten times fewer HBM accesses for the same FLOP count (the exact factor depends on tile sizes and head dimension). And O(N) memory instead of O(N²) is what made 128k-token contexts possible at all.

FlashAttention does the same or slightly more arithmetic than standard attention. Why is it faster?
It uses lower precision
It skips computing some attention weights
HBM traffic limits attention, and FlashAttention cuts reads and writes sharply by keeping tiles in SRAM
It parallelises across more GPUs
Memory traffic, not arithmetic. The GPU's arithmetic units sat idle waiting on HBM. Removing the round trip of the N×N matrix removes the wait. This is the main lesson: on modern accelerators, moving the data is the algorithm. FlashAttention computes exactly the same function, with no approximation and no change of precision.
What does the correction factor exp(m_old − m_new) do?
Moves the earlier running values onto the new maximum, so the running sum and output stay exact
Approximates the softmax to within a small error
Prevents underflow in the value matrix
Normalises the attention weights so they sum to 1
Exact rescaling. Everything added up so far was scaled by e^{−m_old}, and the new max needs e^{−m_new}. Multiplying by e^{m_old−m_new} converts between them exactly. The numerator and denominator get the same factor, so the final ratio is unaffected. That is why it is exact, not approximate.
Why does the backward pass recompute the attention weights instead of storing them?
Storing them would be numerically unstable
Storing an (N,N) matrix would bring back the O(N²) memory and HBM traffic the whole design exists to avoid
The weights are not needed for the gradient
Recomputation is faster in FLOPs
Storing them would undo the whole optimisation. Recomputation costs extra FLOPs but keeps memory at O(N). When IO is the limit, that is a clear win. It is the same reasoning as gradient checkpointing, applied inside a single kernel.

FlashAttention-42026Blackwell (B200) co-design in CuTe-DSL: fully asynchronous pipelines with larger tiles; part of the exponentials computed by a polynomial on the FMA units; softmax rescaling skipped unless the max grows past a threshold; tensor memory and 2-CTA MMA in the backward passup to 1,613 TFLOP/s bf16 on B200 (71% of peak); up to 1.3× cuDNN 9.13 and 2.7× Triton
FlashAttention-4, March 2026

Zadouri, Hoehnerbach, Shah, Liu, Thakkar and Dao (Princeton, Together AI, Meta, Colfax, NVIDIA), MLSys 2026. Two ideas are worth knowing. They show kernel design chasing whatever the hardware made scarce:

  • The exponential became the bottleneck. Blackwell's tensor cores roughly doubled matmul throughput over Hopper, but the special-function unit that computes exp did not keep up. So softmax, not matmul, set the speed. FA4 computes some of the exponentials with a polynomial approximation on the ordinary FMA units, which splits the work between the two kinds of hardware.
  • Rescale only when it matters. The correction factor of §17.3 is exact for any reference max, as long as the numerator and denominator use the same one. FA4 keeps an old max until the true one has grown past a threshold, which skips most rescales. The final division still gives the exact softmax.

The paper's benchmarks are on B200. On Hopper, FlashAttention-3 is the reference implementation, and on Ampere and older it is FlashAttention-2.

17.6 · Using it

# Almost always the right answer — PyTorch picks the best available backend.
import torch.nn.functional as F
out = F.scaled_dot_product_attention(q, k, v, is_causal=True)
#   q, k, v: (B, n_head, T, d_head)

# Inspect / force a backend:
from torch.nn.attention import sdpa_kernel, SDPBackend
with sdpa_kernel(SDPBackend.FLASH_ATTENTION):
    out = F.scaled_dot_product_attention(q, k, v, is_causal=True)
Why you might silently fall back to the slow path
  • The dtype is fp32. The Flash kernels need fp16/bf16. This is the most common cause.
  • You passed an explicit attn_mask. Use is_causal=True instead of building a mask tensor. A mask tensor usually forces the math backend.
  • d_head is not supported. It usually must be ≤ 256 and a multiple of 8.
  • The tensors are not contiguous in the expected layout.

To diagnose it: if memory grows as O(T²) with sequence length, you are not on FlashAttention. Measure torch.cuda.max_memory_allocated() at T=1k, 2k and 4k. With Flash it grows linearly; with the fallback it grows quadratically.

17.7 · Decode: Flash-Decoding and split-KV

FlashAttention splits the work over batch × heads × query blocks. Each GPU thread block owns one tile of queries for one head and walks through all the keys. In prefill there are thousands of query blocks and the GPU is full. In decode there is one query per sequence, so the work items are just batch × heads, and each one walks the whole cache alone.

Worked example — how idle is the GPU during decode attention?

An H100 has 132 SMs. A FlashAttention-style kernel runs (at least) one thread block per work item, so the number to look at is work items per SM.

batch 1,  32 heads:         32 blocks / 132 SMs = 0.24    76% of the SMs have nothing to do
batch 16, 32 heads:        512 blocks / 132 SMs = 3.88    full
batch 1,  32 heads, 8 splits: 256 blocks / 132 SMs = 1.94  full again

The idle case is the one that matters for long context. At batch 1 and 128k tokens, each of those 32 blocks streams 128k keys and values through one SM while 100 SMs wait. See decode_occupancy in tfs/flash.py, asserted in test_split_kv_decode.

Flash-Decoding (Dao, Haziza, Massa and Sizov, 2023) adds a third way to split the work: split the keys. Cut the cache into S chunks. Each chunk is a separate work item that attends the query to its slice only and returns two things: its normalised partial output oi and the log-sum-exp ℓi of its scores. A small second kernel merges them. This is the same idea as split-K in a matmul (split the dimension you sum over, then add the partial results), with the online-softmax correction from §17.3 as the "add".

ℓ = log Σi eℓi      o = Σi eℓi − ℓ · oi each split's output is weighted by its share of the total softmax mass · exact, by the same argument as §17.3
Worked example — §17.3's four scores, split in two

Scores [1, 3, 2, 5] (the same four as §17.3), values [10, 20, 30, 40]. Split A takes the first two keys and split B the last two. Neither sees the other's scores.

A
ℓ_A = log(e¹ + e³)                           = 3.1269
o_A = (e¹·10 + e³·20) / (e¹ + e³)            = 18.808
B
ℓ_B = log(e² + e⁵)                           = 5.0486
o_B = (e²·30 + e⁵·40) / (e² + e⁵)            = 39.5257
=
Merge. 
ℓ   = log(e^3.1269 + e^5.0486)              = 5.18518     (§17.3's logsumexp, again)
w_A = e^(3.1269 − 5.18518) = 0.1277     w_B = 0.8723
o   = 0.1277 × 18.808 + 0.8723 × 39.5257    = 36.881
direct: softmax([1,3,2,5]) · [10,20,30,40]  = 36.881

scores_partial and merge_partials are in tfs/flash.py. test_split_kv_worked_example checks these numbers, and test_split_kv_decode checks a 1,000-key cache split 1, 2, 7, 16 and 1,000 ways against direct attention.

What the split costs. Each split writes one d-dimensional partial output and one scalar per head to HBM, and the merge reads them back. That is S × (d + 1) values per head, against reading T × d keys and T × d values. For S = 8 and T = 32k it is under 0.02% extra traffic. With too many splits, though, each slice is too short to pay back its setup cost, so engines choose S from the batch size, the head count, the SM count and the cache length. Dao et al. reported up to 8× faster decoding for very long sequences. Note what this means for Chapter 13. The split count depends on the batch, so the order of the final sum depends on who else is in the batch. Flash-Decoding is a textbook example of a kernel that is not batch-invariant.

The same structure appears in DeepSeek's FlashMLA (Chapter 16), which applies it to absorbed MLA. It also appears in the decode kernels of vLLM and FlashInfer, which handle the paged cache layout of Chapter 18 as well (keys come from a block table, not one contiguous tensor).

17.8 · Custom attention without custom kernels: FlexAttention

Every attention variant in this course (causal, sliding window, document masking for packed sequences, prefix-LM, ALiBi, logit soft-capping) is FlashAttention with a small change in the inner loop. Either some scores are masked, or every score is modified by a function of its position. Writing a fused kernel for each one is a CUDA project. FlexAttention (Dong et al., 2024, in PyTorch since 2.5) takes the change as two small Python functions and generates the fused kernel for you:

from torch.nn.attention.flex_attention import flex_attention, create_block_mask

# mask_mod: may query q_idx see key kv_idx?          (b = batch, h = head)
def causal(b, h, q_idx, kv_idx):
    return q_idx >= kv_idx

def sliding_window(b, h, q_idx, kv_idx):              # Mistral / Gemma local layers
    return (q_idx >= kv_idx) & (q_idx - kv_idx < 256)

def document(b, h, q_idx, kv_idx):                    # packed sequences: stay in your own document
    return (doc_id[q_idx] == doc_id[kv_idx]) & (q_idx >= kv_idx)

# score_mod: change a score that IS computed
def softcap(score, b, h, q_idx, kv_idx):              # Gemma 2's attention logit soft-capping
    return 50.0 * torch.tanh(score / 50.0)

def alibi(score, b, h, q_idx, kv_idx):                # ALiBi: a per-head linear distance penalty
    return score + slopes[h] * (kv_idx - q_idx)

block_mask = create_block_mask(sliding_window, B=None, H=None, Q_LEN=4096, KV_LEN=4096)
out = flex_attention(q, k, v, score_mod=softcap, block_mask=block_mask)   # q, k, v: (B, H, T, d)

The two hooks do different jobs. A score_mod runs on every score inside the tile, after QKT and before the online softmax. A mask_mod is evaluated ahead of time, per (128 × 128) block, by create_block_mask. That records which blocks are fully masked (skip them, as §17.4 skips blocks above the diagonal), fully visible (no masking work), or partial (apply the test element by element, the in-tile mask). A sparse mask gets its speed from that first group:

Mask at T = 4,096, 128 × 128 blocksblocks skipped
causal48.4%
packed documents of 1,000, 1,500 and 1,596 tokens, causal78.9%
sliding window of 256, causal90.9%

A sliding window of 256 lets the kernel skip 91% of the tiles. It computes 9.1% of them against 51.6% for causal, under a fifth of the work of causal attention at this length, and nobody had to write a kernel. These counts come from block_sparsity in tfs/flash.py (test_flex_style_masks). test_flex_attention_matches_sdpa runs the real flex_attention with the sliding-window mask and checks it against scaled_dot_product_attention with the same mask written out in full. Generated kernels are fast, but not always as fast as a hand-written FlashAttention for plain causal attention. Their value is getting close for the variants nobody has written by hand.

Why is plain FlashAttention slow for decode at batch 1 and long context?
It materialises the score matrix during decode
It splits work over batch × heads × query blocks; with one query there are only 32 work items for 132 SMs, each streaming the whole cache alone
The online softmax is inexact for a single query
Decode is compute-bound
Not enough parallel work. Occupancy is 0.24 at batch 1 with 32 heads. Splitting the keys multiplies the work items by S without changing the result.
What must each Flash-Decoding split return so the partial results can be merged exactly?
Its maximum score only
Its unnormalised scores
Its output, and nothing else
Its normalised partial output and the log-sum-exp of its scores
Output plus log-sum-exp. The LSE says how much of the softmax weight that split holds, and eℓi − ℓ is exactly its weight in the final average. (The max and the sum together carry the same information.)
In FlexAttention, why is a sliding window written as a mask_mod and not as a score_mod that returns −∞ outside the window?
A mask_mod is turned into a block mask ahead of time, so fully masked tiles are never computed; a score_mod only runs inside tiles that are computed anyway
score_mod cannot return −∞
mask_mod is applied after the softmax
There is no difference in speed
Skipping is the speedup. Both give the same numbers. Only the block mask lets the kernel skip 91% of the tiles at T = 4,096 with a 256 window.

17.9 · What it does not solve

  • FLOPs are still O(N²). FlashAttention removes the memory wall, not the quadratic cost. At 1M tokens you still need real sparsity (Chapter 22).
  • The KV cache is untouched. Flash speeds up computing attention; it does not shrink what you store. That is the job of GQA/MLA (Chapter 16). The two work together and are always used together.
  • Decode needs its own way of splitting work. With a single query row there is no large intermediate to avoid, and too little parallel work. The split-KV method of §17.7 fixes the second problem, not the first. Decode attention stays bandwidth-bound, limited by the cache bytes it must read.

17.10 · Exercises

17.1Implement the online softmaxessential

Write online_softmax_sum(xs, chunk_size). It should process xs in chunks, keeping a running max and sum. Assert it matches torch.logsumexp to 1e-6 for 1000 random vectors, including hard ones with values spanning ±100.

Solution
def online_softmax_sum(xs, chunk=4):
    m, l = float('-inf'), 0.0
    for i in range(0, len(xs), chunk):
        blk = xs[i:i+chunk]
        m_new = max(m, blk.max().item())
        l = l * math.exp(m - m_new) + torch.exp(blk - m_new).sum().item()
        m = m_new
    return m + math.log(l)          # = logsumexp(xs)

x = torch.randn(1000) * 50
assert abs(online_softmax_sum(x) - torch.logsumexp(x, 0).item()) < 1e-6

Try it without the max tracking (just add up exp(x).sum()) and watch it return inf. That failure is why the running max is required.

17.2Write FlashAttention in PyTorchhard

Implement the tiled algorithm from §17.4 in pure PyTorch (no CUDA). It will be slower than the naive version, because of Python loops and no SRAM control, but it must be numerically identical.

def flash_attention(Q, K, V, Br=32, Bc=32, causal=True):
    N, d = Q.shape
    O = torch.zeros(N, d)
    for i in range(0, N, Br):
        Qi = Q[i:i+Br]
        Oi = torch.zeros(Qi.shape[0], d)
        mi = torch.full((Qi.shape[0],), float('-inf'))
        li = torch.zeros(Qi.shape[0])
        for j in range(0, N, Bc):
            if causal and j > i + Br - 1:
                break                                  # whole block is masked
            Kj, Vj = K[j:j+Bc], V[j:j+Bc]
            Sij = Qi @ Kj.T / d**0.5
            if causal:
                qi = torch.arange(i, i+Qi.shape[0])[:, None]
                kj = torch.arange(j, j+Kj.shape[0])[None, :]
                Sij = Sij.masked_fill(kj > qi, float('-inf'))
            m_new = torch.maximum(mi, Sij.max(dim=-1).values)
            corr  = torch.exp(mi - m_new)
            Pij   = torch.exp(Sij - m_new[:, None])
            li = corr * li + Pij.sum(dim=-1)
            Oi = corr[:, None] * Oi + Pij @ Vj
            mi = m_new
        O[i:i+Br] = Oi / li[:, None]
    return O

assert torch.allclose(flash_attention(Q,K,V), naive_attention(Q,K,V), atol=1e-5)

Watch for the fully masked block. If every entry of a tile is -inf, m_new is -inf and you get nan. The break above avoids it. Real kernels skip those blocks too, which is why causal attention is roughly 2× faster than bidirectional instead of the same speed.

Answer
target: ≥ 264 work items
batch 1:  32 × S ≥ 264  ->  S = 9        batch 4:  128 × S ≥ 264  ->  S = 3        batch 32: S = 1
merge traffic, batch 1, S = 9: 32 heads × 9 × (128 + 1) values  ≈ 37k values
cache read: 2 × 8 heads × 128 × 131,072 tokens                   ≈ 268M values   -> 0.014%

In traffic terms the split is free. Its cost is the second, tiny kernel launch and the reduction order that depends on the batch (Chapter 13 §13.7). Real kernels group the 4 query heads that share a KV head into one work item. That changes the counts but not the conclusion.

17.6Document masking with FlexAttentioncode

Pack three sequences of lengths 700, 900 and 448 into one 2,048-token row. Build a document mask_mod, run flex_attention, and check that each document's output equals running it alone. Then print the block mask's sparsity, but predict it first.

What you should see

Expect identical outputs per document. That is the point of the mask: packing without documents leaking into each other (Chapter 11). Expect a sparsity well above the ~48% of causal, because every block that pairs two different documents is skipped. Without the mask, packed training quietly lets each document attend to the one before it.
