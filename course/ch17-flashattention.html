17 · FlashAttention and the Online Softmax

FlashAttention computes exactly the same function as the attention you wrote in Chapter 5 — no approximation, no sparsity, identical outputs up to floating-point rounding. It is 2–4× faster and uses 10–20× less memory. That combination sounds impossible until you realise the bottleneck was never the arithmetic.

17.1 · The insight: attention is IO-bound, not compute-bound

A GPU has a memory hierarchy, and the numbers are wildly asymmetric:

LevelSize (A100)BandwidthAnalogy
SRAM (on-chip, per SM)~20 MB total~19 TB/syour desk
HBM (the "GPU memory" you buy)40–80 GB1.5–2 TB/sthe filing cabinet

SRAM is roughly 10× faster and 3000× smaller. Standard attention ignores this completely:

S = Q @ K.T          # write an (N, N) matrix to HBM        ← 4 GB at N=32k, fp32
P = softmax(S)       # read (N,N) from HBM, write (N,N) back ← 8 GB of traffic
O = P @ V            # read (N,N) from HBM again             ← 4 GB
The realisation

We materialise an N×N matrix in slow memory, then read it back twice, only to throw it away. The output is only N×d. Nearly all the time is spent moving a temporary result that nobody wants. Dao et al.'s question was: can we never write it down at all?

17.2 · The obstacle: softmax needs the whole row

The obvious plan is to process K and V in tiles that fit in SRAM. But softmax has a global denominator:

softmax(x)i = exi − max(x)Σj exj − max(x) both max(x) and the sum require seeing every element of the row

(The − max(x) is not cosmetic. Without it, exp(x) overflows to inf for x > 88 in fp32. Every real softmax subtracts the max.)

So how do you compute a softmax over data you're seeing in pieces?

17.3 · The online softmax

You maintain a running max and a running sum, and when the max changes you retroactively rescale everything you've accumulated so far. Milakov & Gimelshein (2018) worked this out; Dao et al. applied it to attention.

Suppose you've processed a prefix with max m and sum ℓ, and a new value x arrives:

mnew = max(m, x)      ℓnew = ℓ · em − mnew + ex − mnew the correction factor em−mnew re-bases the old sum to the new max

Step through it. The bottom line proves the two agree exactly:

Worked example — four numbers, one at a time, exact at the end

Scores [1, 3, 2, 5]. We never hold them all at once — one arrives per step, and we keep only m (running max) and ℓ (running sum).

t0
x = 1. Nothing seen yet, so m: −∞ → 1.0. 
rescale = 0        (nothing banked yet)
ℓ = 0×0 + e^(1−1) = 1.000000
t1
x = 3 — a new maximum. Everything banked so far was measured against m = 1 and must be re-based: 
m: 1.0 → 3.0
rescale = e^(1−3) = 0.135335      ← shrink the old sum
ℓ = 1.000000 × 0.135335 + e^(3−3) = 1.135335
t2
x = 2 — below the max, so nothing needs re-basing: 
m stays 3.0
rescale = e^(3−3) = 1.000000      ← a no-op
ℓ = 1.135335 × 1.0 + e^(2−3) = 1.503215
t3
x = 5 — new maximum again: 
m: 3.0 → 5.0
rescale = e^(3−5) = 0.135335
ℓ = 1.503215 × 0.135335 + e^(5−5) = 1.203438
=
Against computing it all at once: 
streaming:  m + ln(ℓ) = 5 + ln(1.203438) = 5.185182
one-shot:   logsumexp([1,3,2,5])         = 5.185183
Six decimal places. The gap is float32 rounding, not approximation.

Why this is the whole theorem. Every rescale multiplies the accumulated numerator and denominator by the same factor, so their ratio — the actual softmax weights [0.0152, 0.1125, 0.0414, 0.8310] — is untouched. That exactness is what lets FlashAttention be used for training: an approximate attention would compound into a different model, but this is the same function computed in a different order.

import math, torch
xs = [1.0, 3.0, 2.0, 5.0]

m, l = float("-inf"), 0.0
for x in xs:                                   # one value at a time
    m_new = max(m, x)
    corr  = math.exp(m - m_new) if m != float("-inf") else 0.0
    l     = l * corr + math.exp(x - m_new)
    m     = m_new

streaming = m + math.log(l)
one_shot  = torch.tensor(xs).logsumexp(0).item()
assert abs(streaming - one_shot) < 1e-5        # 5.185182 vs 5.185183

The same correction applies to the accumulated output, which is what makes it useful for attention:

Onew = Oold · emold − mnew + es − mnew · v rescale the running output, then add the new tile's contribution
Why this is exact, not approximate

Every rescale multiplies both the accumulated numerator and the accumulated denominator by the same factor, so their ratio — the actual softmax output — is unchanged. It's algebra, not an approximation. That's why FlashAttention can be used for training, where a lossy attention approximation would compound into a materially different model.

17.4 · The algorithm

# FlashAttention, forward pass (simplified, one head)
#   Q: (N, d)   K, V: (N, d)   →   O: (N, d)
#   Tile sizes Br, Bc chosen so that a tile of Q, K, V and the running
#   state all fit in SRAM simultaneously.

for i in range(0, N, Br):                       # OUTER loop over query blocks
    Qi = load(Q[i:i+Br])                        # → SRAM,  (Br, d)
    Oi = zeros(Br, d)                           # running output    (in SRAM)
    mi = full(Br, -inf)                         # running max       (in SRAM)
    li = zeros(Br)                              # running sum       (in SRAM)

    for j in range(0, N, Bc):                   # INNER loop over key blocks
        Kj, Vj = load(K[j:j+Bc]), load(V[j:j+Bc])       # → SRAM

        Sij = Qi @ Kj.T / sqrt(d)               # (Br, Bc)  ← ONLY THIS TILE EXISTS
        if causal and j > i: continue           # skip fully-masked blocks entirely

        m_new = maximum(mi, Sij.max(dim=-1))    # (Br,)
        Pij   = exp(Sij - m_new[:, None])       # (Br, Bc)
        corr  = exp(mi - m_new)                 # (Br,)  the rescale factor

        li = corr * li + Pij.sum(dim=-1)        # rescale + accumulate the denominator
        Oi = corr[:, None] * Oi + Pij @ Vj      # rescale + accumulate the numerator
        mi = m_new

    write(O[i:i+Br], Oi / li[:, None])          # normalise ONCE, then → HBM

Notice what never happens: the (N, N) matrix is never allocated. Only a (Br, Bc) tile exists at any moment, and it lives in SRAM.

The backward pass: recomputation

Backprop through attention needs the attention weights P. We didn't store them. So FlashAttention recomputes them from Q, K, V during the backward pass — which sounds wasteful but isn't, because recomputing a tile in SRAM is far cheaper than having written and re-read N² values from HBM.

This is the same trade as gradient checkpointing, applied at the kernel level: spend FLOPs to save memory traffic, in a regime where FLOPs are abundant and traffic is the constraint.

The complexity result

Standard attentionFlashAttention
FLOPsO(N²d)O(N²d) — the same, or slightly more
HBM accessesO(N² + Nd)O(N²d²/M), M = SRAM size
Extra memoryO(N²)O(N)

With d = 64 and M ≈ 100 KB of usable SRAM per block, d²/M is around 1/25 — so FlashAttention does roughly 25× fewer HBM accesses at the same FLOP count. And O(N) memory instead of O(N²) is what made 128k-token contexts possible at all.

FlashAttention does the same or slightly more arithmetic than standard attention. Why is it faster?
It uses lower precision
It skips computing some attention weights
Attention is bottlenecked by HBM traffic, and FlashAttention drastically reduces reads/writes by keeping tiles in SRAM
It parallelises across more GPUs
Memory traffic, not arithmetic. The GPU's arithmetic units were idle waiting on HBM. Removing the round-trip of the N×N matrix removes the stall. This is the central lesson: on modern accelerators, the data movement is the algorithm. FlashAttention computes exactly the same function — no approximation, no precision change.
What does the correction factor exp(m_old − m_new) do?
Re-bases previously accumulated values to the new maximum, keeping the running sum and output exact
Approximates the softmax to within a small error
Prevents underflow in the value matrix
Normalises the attention weights to sum to 1
Exact re-basing. Everything accumulated so far was scaled by e^{−m_old}; the new max requires e^{−m_new}. Multiplying by e^{m_old−m_new} converts between them exactly. Since numerator and denominator get the same factor, the final ratio is unaffected — hence exact, not approximate.
Why does the backward pass recompute the attention weights instead of storing them?
Storing them would be numerically unstable
Storing an (N,N) matrix would reintroduce the O(N²) memory and HBM traffic the whole design exists to avoid
The weights aren't needed for the gradient
Recomputation is faster in FLOPs
It would undo the entire optimisation. Recomputation costs extra FLOPs but keeps memory at O(N). In an IO-bound regime that's a clear win — the same reasoning as gradient checkpointing, applied inside a single kernel.

FlashAttention-4, March 2026

Released by Tri Dao and collaborators (Princeton, Together AI, Meta, NVIDIA, Colfax). Two details worth knowing:

  • The exponential became the bottleneck. On Blackwell, matmul throughput grew so much that the special function unit computing exp couldn't keep up. FA4 approximates the exponential with a polynomial evaluated on the general-purpose FMA units, moving that work onto hardware Blackwell has in abundance. That's a striking example of how kernel design chases whatever the hardware made scarce.
  • FlexAttention integration. You can now write attention variants — ALiBi, sliding window, document masking, soft-capping — as plain Python score_mod functions and have them JIT-compiled into FA4 kernels, reportedly 1.2–3.2× faster than the previous Triton backend. Custom attention no longer requires writing CUDA.

FA4 requires Hopper or Blackwell. On older GPUs you're on FA2.

17.6 · Using it

# Almost always the right answer — PyTorch picks the best available backend.
import torch.nn.functional as F
out = F.scaled_dot_product_attention(q, k, v, is_causal=True)
#   q, k, v: (B, n_head, T, d_head)

# Inspect / force a backend:
from torch.nn.attention import sdpa_kernel, SDPBackend
with sdpa_kernel(SDPBackend.FLASH_ATTENTION):
    out = F.scaled_dot_product_attention(q, k, v, is_causal=True)
Why you might silently fall back to the slow path
  • dtype is fp32. The Flash kernels need fp16/bf16. This is the most common cause.
  • You passed an explicit attn_mask. Use is_causal=True instead of building a mask tensor — a materialised mask usually forces the math backend.
  • d_head is unsupported (must typically be ≤ 256 and a multiple of 8).
  • Tensors aren't contiguous in the expected layout.

Diagnose it: if memory scales as O(T²) with sequence length, you are not on FlashAttention. Measure torch.cuda.max_memory_allocated() at T=1k, 2k, 4k — Flash grows linearly, the fallback quadratically.

17.7 · What it does not solve

  • FLOPs are still O(N²). FlashAttention removes the memory wall, not the quadratic. At 1M tokens you still need genuine sparsity (Chapter 22).
  • The KV cache is untouched. Flash speeds up computing attention; it doesn't shrink what you store. That's GQA/MLA's job (Chapter 16). The two are complementary and always used together.
  • Decode gets much less benefit. With a single query row there's no large intermediate to avoid. Decode-optimised variants (FlashDecoding, and DeepSeek's FlashMLA) split the key dimension across SMs instead — a different parallelisation for a different regime.

17.8 · Exercises

17.1Implement the online softmaxessential

Write online_softmax_sum(xs, chunk_size) that processes xs in chunks, maintaining running max and sum. Assert it matches torch.logsumexp to 1e-6 for 1000 random vectors, including adversarial ones with values spanning ±100.

Solution
def online_softmax_sum(xs, chunk=4):
    m, l = float('-inf'), 0.0
    for i in range(0, len(xs), chunk):
        blk = xs[i:i+chunk]
        m_new = max(m, blk.max().item())
        l = l * math.exp(m - m_new) + torch.exp(blk - m_new).sum().item()
        m = m_new
    return m + math.log(l)          # = logsumexp(xs)

x = torch.randn(1000) * 50
assert abs(online_softmax_sum(x) - torch.logsumexp(x, 0).item()) < 1e-6

Try it without the max tracking (just accumulate exp(x).sum()) and watch it return inf. That failure is why the running max isn't optional.

17.2Write FlashAttention in PyTorchhard

Implement the tiled algorithm from §17.4 in pure PyTorch (no CUDA). It will be slower than the naive version — Python loops, no SRAM control — but it must be numerically identical.

def flash_attention(Q, K, V, Br=32, Bc=32, causal=True):
    N, d = Q.shape
    O = torch.zeros(N, d)
    for i in range(0, N, Br):
        Qi = Q[i:i+Br]
        Oi = torch.zeros(Qi.shape[0], d)
        mi = torch.full((Qi.shape[0],), float('-inf'))
        li = torch.zeros(Qi.shape[0])
        for j in range(0, N, Bc):
            if causal and j > i + Br - 1:
                break                                  # whole block is masked
            Kj, Vj = K[j:j+Bc], V[j:j+Bc]
            Sij = Qi @ Kj.T / d**0.5
            if causal:
                qi = torch.arange(i, i+Qi.shape[0])[:, None]
                kj = torch.arange(j, j+Kj.shape[0])[None, :]
                Sij = Sij.masked_fill(kj > qi, float('-inf'))
            m_new = torch.maximum(mi, Sij.max(dim=-1).values)
            corr  = torch.exp(mi - m_new)
            Pij   = torch.exp(Sij - m_new[:, None])
            li = corr * li + Pij.sum(dim=-1)
            Oi = corr[:, None] * Oi + Pij @ Vj
            mi = m_new
        O[i:i+Br] = Oi / li[:, None]
    return O

assert torch.allclose(flash_attention(Q,K,V), naive_attention(Q,K,V), atol=1e-5)

Watch for the fully-masked-block case: if every entry of a tile is -inf, m_new is -inf and you get nan. The break above avoids it. Real kernels skip those blocks too — which is why causal attention is roughly 2× faster than bidirectional, not the same speed.

For T ∈ {512, 1024, 2048, 4096, 8192}, measure peak memory and wall time for (a) your naive attention and (b) F.scaled_dot_product_attention. Plot both on log-log axes and fit the slopes.

Expected

Naive: memory slope ≈ 2 (quadratic). Flash: slope ≈ 1 (linear). The naive version will OOM somewhere around T=8k–16k on a consumer GPU while Flash keeps going. The slope is the proof — if your "Flash" line has slope 2, you fell back to the math backend; check the dtype (§17.6).
